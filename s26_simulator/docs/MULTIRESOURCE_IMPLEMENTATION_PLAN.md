## 3. 자원과 처리 단계의 실행 의미

### 3.1 추론 슬롯과 공유 CPU를 구분

각 요청은 추론 자원 슬롯과 CPU 전/후처리 수요를 가진다. GPU/NPU 추론 중에도 admission·반환·저장 단계가 CPU를 사용할 수 있다. CPU 추론 슬롯이 비었다는 이유로 공유 CPU 비용을 0으로 만들지 않는다.

- route 슬롯은 dispatch에서 실제 AVAILABLE까지 유지하는 보수적인 현 계약으로 시작한다. 추론 종료만으로 슬롯을 반납하지 않는다. 측정 근거 없이 해제 시점을 앞당기지 않는다.
- GAP→ADMISSION→INFER→RETURN_GAP→POST/AVAILABLE 상태를 유지한다. 일반은 계약에 맞는 readback 완료, 긴급은 output_ready가 응답이다. 응답 후에도 남은 후처리/점유가 진행된다.
- CPU 전/후처리를 직렬 서버로 둘지 유한 용량 수요로 둘지는 기존 로그의 실제 겹침·앱 코드로 정한다. 근거가 없으면 공유 직렬 서버를 명시적 중앙 가정으로 두고 다른 가정도 민감도에 남긴다.
- 기존 measured phase wall time에는 OS 대기가 섞일 수 있다. 그 전체를 새 서버의 순수 service demand로 사용하고 별도 queue delay를 또 더하면 이중 계상이다. 분해 가능 여부를 확인하고, 불가능하면 해당 가정/상한임을 표시한다.
- 같은 시각의 이벤트는 기존 완료·AVAILABLE 처리→도착/enqueue 반영→정책 호출 순으로 명시해 고정한다. 같은 시각 요청의 ordinal/id 동점을 보존한다. 새 슬롯이 차거나 실행 가능 요청이 없을 때까지 재결정한다.

### 3.2 실행 중인 작업은 유지

CPU/GPU/NPU마다 추론 진행률을 별도로 추적한다. 병행 요청이 시작/끝나거나 AP가 변하면 이후 처리 속도가 바뀌고 남은 진행량에만 적용한다. 선점·이미 수행한 작업 되돌리기·예상 반납으로 실제 마스크 해제0. 같은 자원에 두 추론을 겹쳐 넣지 않는다.

## 4. 병행·열·에너지 모형

### 4.1 기존 실측에서 가져올 것

원 단독 처리시간/전체 단계 벡터, 측정 AP와 속도 관계, 확인된 분류 GPU/NPU+탐지 CPU 간섭, 전/후처리·실제 겹침·API 전력·AP 시계열을 우선 사용한다. 같은 모델/프로필/입력/AP 영역의 비교를 우선하고 서로 다른 조건의 차이를 병행 인과 계수라고 단정하지 않는다. 8,636 원 벡터와1,216 전이 view는 원 표본 수에서 중복 계수하지 않는다.

### 4.2 미측정 조합은 세 가지 가정으로 분리

추론 간섭과 공유 단계·전력/열의 동시 변화는 함께 다룬다. 임의로 모든 자원이 독립 최고 속도를 내게 하거나 기존 단일 `peer=1`을 triple에도 그대로 넣지 않는다.

- **낙관 가정:** 확인된 간섭은 유지하고 미측정 조합의 추가 간섭은 없다고 둔다. 이상적인 상한 참고이며 예상 실기기 성능이 아니다.
- **중앙 전이:** 기존 조건을 맞춘 병행/단독 비율과 불확실성에서 전이 규칙을 정한다. pair 구분/peer 수·CPU 공유 단계가 드러나도록 적용한다. 어느 관측을 어느 새 조합으로 전이했는지 기록한다.
- **보수 가정:** 관측 비율의 불리한 범위와 추가 peer 누적 가정을 사용한다. “모든 실제 상황을 포함하는 보장 상한”으로 부르지 않는다.

중앙/보수의 수치는 구현자가 결과를 보고 고르지 않는다. 자료 목록 단계에서 산출 식·사용 세션·분위수/불리한 누적 규칙을 정하고 DEV 이전에 봉인한다. 비교 가능한 원 비율이 없으면 식별되지 않은 계수라는 사실과 별도 시나리오 가정을 명시한다. 낙관/중앙/보수는 단순히 공통 plant의 속도만 곱하는 세 모델로 만들지 않는다.

### 4.3 다중 활동의 비용 계상

- 공통 idle/resident 기저는 세 자원에 각각 더하지 않고 세션 전체에서 한 번 계상한다. 3개 runtime 상주 가정과 생성/warmup 포함 여부를 전군 동일하게 고정한다. 미식별 전환 비용을0이라고 확정하지 않는다.
- route 활동·CPU 공유 단계·owner 수·pair 종류·동시 수를 별도 기록한다. 기존 `owner_overlap=max(0,n-1)`에3owner 값을 넣는 것만으로 검증된 열/전력이라고 주장하지 않는다.
- 기존 AP/Gamma-history 식의 검증 영역과 새 triple 외삽을 구분한다. 독립 활동 합/상호작용 전이 가정이 전력 양수·냉각/잔열·활동 없는 극한에서 맞는지 검사한다. 수치가 깨지면 clamp로 유리하게 숨기지 않고 실패/외삽을 기록한다.
- 관측된 온도와 앞으로의 예상 온도를 분리하고, policy에는 지연 전달된 AP만 제공한다. 모형의 실제 AP/잠재 처리 표본/미래 도착·응답은 숨긴다.
- 기존 원기반 모형의 R21 오차(API-J MAE37.53J/AP0.612℃)와 미채택 단계 보완을 함께 유지한다. 새 병행 성능을 실측 검증했다고 주장하지 않는다.

## 5. 정책 비교의 두 단계를 분리

### A. 같은 공통 배정기에서 순서만 비교 · 주평가

세 정책은 같은 슬롯·마스크·공개정보·명목 처리시간·미래 비용 모형을 사용한다.

- FIFO: 현재 실행 가능한 ready 중 arrival→ordinal→id. unavailable head를 건너뛰는 조건을 전군 계약에 명시한다. strict head blocking FIFO와 혼동하지 않는다.
- EDF: 같은 집합 중 절대기한→FIFO 동점.
- 롤링+ATC: 현재 ATC 수식/기존 k를 유지하고 매 도착·반납·센서 사건에서 재계산한다. 임의의 미래 작업/샘플을 주지 않는다.
- 요청을 고른 뒤 자원 선택은 **동일한 공통 배정 함수**로 수행한다. 원 ready 전체를 서로 다른 방식으로 몰래 재정렬하지 않는다. 같은 원자적 사건에서 여러 슬롯을 채울 때의 순서와 재계산을 동일하게 처리한다.
- 공통 배정은 예상 납기 손해→전체 완료 손해를 먼저 줄이고, 동률에서 에너지/열 후보를 비교한다. 기존 J+열 가중합과 “열 악화 금지/에너지 제한” 후보는 DEV의 별도 비교로만 선정한다. 평균/peak 열의 기준 경로는 같은 공개 상태의 고정 참조 rollout이며 실제 미래 기준정책 결과를 읽지 않는다. 기준·허용오차·infeasible 시 fallback을 봉인한다.

공통 배정 후보는 우선 **2개로 제한**한다. `COMMON_WEIGHTED`는 기존 정규화 J+열 가중합, `COMMON_NO_THERMAL_HARM`은 같은 납기 위험 등급에서 고정 참조 rollout보다 평균/peak 열이 악화되지 않는 후보 중 J가 작은 것을 고른다. 참조 rollout은 공개 ready 집합을 최단 명목 응답 경로의 결정적 list schedule로 배치한다. 후보와 참조의 horizon·모형·현재 상태는 같다. 수치 동률 허용오차는 P0에서 봉인하고 실제 열 절감 기준과 구분한다. 제약 적격 후보가 없으면 납기 위험→예상 열 손해→J 순의 결정적 fallback을 사용하고 제약 미충족을 로그에 남긴다. 예측 제약은 실제 열 보장이 아니다.

DEV에서 동일 배정 후보를 FIFO/EDF/ATC에 모두 적용한다. 예상이 아닌 실현된 납기 손해·완료·열 악화·J를 집계해 공통 배정기 **하나**만 고르고, 정책별로 따로 유리한 배정기를 고르지 않는다. 선정 우선순위·정규화·동점 규칙은 DEV 실행 전에 파일로 고정한다. 후보를 추가할 때는 환경 예산도 사전에 바꾼다.

### B. 우리 정책의 순서·자원 공동 탐색 · 선택적 후속

주평가를 마친 뒤 필요하면 현재 ready 큐의 순서·자원 조합을 함께 탐색하는 롤링+ATC 후보를 별도로 만든다. 제한된 horizon/beam/계산 cap·불확실성·정책 계산 비용을 등록한다. 이 결과와 단순 순서 비교를 섞어 “ATC 점수만의 효과”라고 부르지 않는다. 아래 가안 예산에는 B와 RL은 포함하지 않는다.

## 6. 부하와 입력 제안

128건 총량은 유지하고 **같은 예정시각에 B=4/8/16/32건**을 도착시킨다. 균등 몰림 실험은 활동 도착 창16초, 첫도착35초, 묶음 수128/B, 묶음 간격16/(128/B)초로 고정한다. 기존 40ms 간격 도착과 다른 새 부하다. 실제 enqueue는 등록된 실측 jitter를 공통 적용하고 예정 동시/실제 큐 진입 차이를 보고한다. 결과에 맞춰 간격을 바꾸지 않는다.

- **C_ONLY:** 분류 긴급128건, 일반0. 세 자원 분산 자체를 확인하는 대조다. 동일 작업/기한이면 EDF와 ATC가 같을 수 있으며 그 자체가 실패가 아니다. 일반 분모0은 NA, 성공률100%로 채우지 않는다.
- **MIX:** 기존 분류 긴급96+탐지 일반32(U96/N32). 새 미측정 긴급탐지/일반분류 응답 계약을 추가하지 않는다. 각 묶음의 분류:탐지는3:1, 선두 task 배치는 사전 균형 순환으로 고정한다. 동일 예정시각의 ordinal만으로 한 정책이 항상 유리해지지 않도록 개발/평가에서 독립적으로 균형화한다.
- 초기 이력3개는 현재 실측 기반 초기 상태/과거 활동을 그대로 사용하고, 측정 범위 밖 고온은 별도 외삽 실험으로만 둔다.
- 새 정책평가 stream4개는 원벡터를 요청×route 단위로 결합한다. 정책/동시 상한/모형 간 같은 underlying draw를 쓰되 같은 미래 표본을 policy에는 주지 않는다. 과거 STATE draw 재사용0.
- **동시 상한1/2/3**을 같은 새 슬롯 엔진에서 대조한다. 여기의2는 임의 두 개의 서로 다른 슬롯을 쓸 수 있는 상한으로, 기존 CG_DC/CN_DC만 허용하던 legacy2와 다르다. legacy exact 검증은 별도로 수행한다.

강한 몰림에서 CPU 탐지의 고정 처리 용량 때문에 모든 정책이 납기를 못 지킬 수 있다. 자원별 요구 작업량과 납기 창의 완화 하한을 함께 계산해 “정책이 나쁨”과 “현재 모형/허용 경로에서 달성 불가”를 분리한다. 명목 하한만으로 실제 불가능을 확정하지 않는다. 실패 조건도 평가 표에서 빼지 않는다.

## 7. 개발·동결·환경 수 가안

아래는 **제안 예산**이며 아직 예약/실행하지 않았다. 실제 모든 원장/다른 A24 예약과 실행 시간·저장량 추산 뒤 계약 파일로 확정한다.

| 단계 | 구성 | 새 정책 환경 수 가안 |
|---|---|---:|
| P0 | 배정후보2×정책3×부하2×동시상한3×dt2 | 72 |
| DEV | 배정후보2×몰림4×부하2×초기2×모형2×draw1×정책3×동시상한3 | 576 |
| 새 평가 | 몰림4×부하2×초기3×모형3×draw4×정책3×동시상한3 | 2592 |
| 합계 | P0+DEV+평가 | **3240 / cap가안3328** |

P0 두 dt는 기존.005와.0025초 제안이며 동일 입력의 더 촘촘한 적분이다. on-time/완료 계수가 같고 J 차이<0.2J·평균AP 차이<0.01℃를 우선 제안한다. 경계 사건 시험은 이를 더 엄격하게 검증한다. CPU/공유 서버를 추가한 식의 dt 민감성이 크면 주평가 전에 설계를 수정·재등록하고 실패를 보존한다.

DEV는 중앙/보수 가정, 등록한 초기2개, 새 단일 DEV draw에서 공통 배정/계산 cap을 정한다. 초기 이력은 평가에서도 공유될 수 있어 독립 실기기 검증이 아니며, DEV와 평가의 요청 순번/잠재 draw stream은 분리한다. 평가의 낙관 가정을 DEV 최적화 대상으로 쓰지 않는다. 모든 평가 결과를 열기 전에 소스·모형·선정·평가 입력의 SHA와 시각을 봉인한다. 후보 수가 늘면 DEV 예산 산술도 사전에 늘려 등록하며, 576건 밖의 숨은 탐색0이다.

인계 당시 총예약121206에cap3328을 추가할 수 있다고 가정하면124534/137712, 미예약13178이 된다. **이 계산은 실제 새 예약이 아니다.** 최신 원장이 달라지면 다시 산정한다. cap 잔88은 소비된 실패 identity 재시뮬레이션용이 아니다. B단계/RL·모형 fit·후보 전망 호출·감사 재적분 cap은 별도다. 정책환경 cap만으로 무제한 내부 탐색을 허용하지 않는다. 예상 런타임·raw bytes·관련 볼륨8GiB 여유를 START 전에 검증한다.

저장량도 선행 gate다. 기존300raw의1.568GiB를 단순 비례하면3240건 raw만 약16.94GiB이며 새 후보/공유 단계 trace는 더 커질 수 있다. 문서 작성 때 C 여유27.29GiB/D20.69GiB는 읽기 스냅샷이지 완주 보장이 아니다. 감사·prepared·포장·재다운로드 복사까지 보수 추산하고8GiB를 남길 수 없으면 생산을 시작하지 않는다. 기존 원자료를 삭제/재압축/이동하거나 seed·조건을 조용히 줄이지 않는다. 필요하면 새 세대의 원시 포맷에만 내구 lossless 압축을 사전등록하고 uncompressed payload SHA·정확 복구·감사 동등성을 먼저 시험하거나, 사용 가능한 저장 경로를 별도로 정한다.

## 8. 시험과 감사 통과 조건

1. **순수 계약:** 같은 슬롯 이중 점유0, owner<=cap, 동시에 허용한 조합만 dispatch, 실제 AVAILABLE 전 재사용0, 응답/반납 분리, 일반 readback·0단계·같은시각·120/150/180 경계·deadlock 시험. 총 요청과 모든 terminal 상태 전량 계수.
2. **진행량:** 중간 peer 시작/종료·열 변화에서 이미 수행한 work가 보존되고, 이벤트 나누기/합치기 결과가 수치 허용오차 안에서 같아야 한다.
3. **legacy 일치:** 옛 마스크/서버 의미/비용식의 명시적 LEGACY 모드는 저장된 기존 trace 입력으로 재생해 같은 결과가 나와야 한다. 기존 정책 환경을 재시뮬레이션하지 말고 순수 상태 전이와 저장 활동 재생으로 검증한다. 새로운 공유 모델을 켜면 달라지는 부분은 새 가정의 효과로 분리한다.
4. **상태 공개:** 미래 도착/실제 잔여 work/잠재 route 표본/미래센서 유출0, 공개 입력 digest·후보/마스크/점수/예상 완료·선택 이유 전량 저장. 비교군과 동일한 정보/forecast 계산 cap.
5. **비용 일치:** 독립 언어 구현으로 실제 저장 phase 활동→전력/AP/총J/peak/잔열 재적분. 원 전력·열 식의 수치 대조와 새 간섭/공유 단계 모형을 각각 시험한다. arithmetic PASS는 실기기 정확도 PASS가 아니다.
6. **인과 분리:** 동시 상한1/2/3, 순서 정책, 배정 모형/가정의 효과를 분리한다. 상한3이 상한1보다 개선됐다고 ATC 고유 효과라 부르지 않는다.
7. **운영:** raw→prepared→row→terminal, canonical 전역 START 합산, ownheavy1/global Python leaves2·공동 잠금·관련 볼륨8GiB. 실제 살아 있는 worker의 중복·소스 변경0. 미저장/FAIL identity의 대체seed/새label 재수집0. 기존 원V2 EP814/FINAL·CAUSAL·NODGPU gate·다른 WIP/자동화 PAUSED 보존.

## 9. 결과와 화면의 완료 조건

전체 정책/동시상한/부하/초기이력/모형 가정별로 전128납기·긴급/일반 서비스70/80/90/95/100%·전량완료·P95·지연량/미완료·J0~180·AP35~180/peak/180잔열·실제 queue/route/동시 수·공유 단계 대기·WAIT를 보인다. 순서가 다르면 그 최초 공개 상태와 선택 이유를 남기고, 같으면 같은 이유도 확인한다.

- 납기·전량완료를 지킨 같은 입력쌍에서만 에너지/열 절감을 공동개선으로 판정한다. 더 많은 일을 끝내느라 J가 증가한 경우와 일찍 포기해서 J가 감소한 경우를 분리한다.
- 중앙만 유리하고 보수에서 뒤집히면 조건부/불확실이다. 미측정 조합의 낙관 결과를 실기기 절감으로 발표하지 않는다. 합성 draw4개를 독립 휴대폰 표본 수로 세지 않는다.
- 화면은 CPU/GPU/NPU 3lane 타임라인+대기열+슬롯 반납+공유 CPU 단계/간섭+온도/누적J·납기손해를 한 시각에 연결한다. policy 필터는 같은 입력 조건을 고정한다. 관측/전이/가정 배지를 달고 원자료와 연결한다.
- 새 HTML/모바일/좁은 화면을 실제 브라우저에서 검증하고 원 V4 화면을 덮어쓰지 않는다. 결과/소스/packet/원장/실패/감사/준비 명령·SHA·인계 문서를 같은 GitHub 실험 폴더에 올린다.

완료는 “세 자원에 나눠 실행됨”만이 아니라 계약/수치/전수 감사·부하별 손해 판독·화면/문서·재다운로드 SHA가 끝난 상태다. 정책이 우수하지 않으면 그 사실을 보고하고, 같은 평가로 재선정하지 않는다.
