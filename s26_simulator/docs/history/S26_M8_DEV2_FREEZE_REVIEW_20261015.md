# S26 M8 DEV2·정정3판·CONFIRM 동결 수신 판독

새 DEV 블록2는 **19세션·3,048요청 완료**, 요청·순서·지원 점유·응답 경계·정상 readback 416건의 파일 SHA 검산 PASS다. 관측된 v5 게이트의 계산과 계측 창도 재생 검산했다. CONFIRM 동결 파일은 아래 기록 정정과 인계가 남아 있어 전체 확인 실험 완료로 인정하지 않는다.

B2 ZIP에는 과거 B1·P0·스모크도 들어 있다. `stage=dev, block_no=2`와 원시 identity로 새 19세션만 구분했다. 이전 자료를 새 측정으로 중복 계수하지 않았다. B1 당시 host 가용 20세션/3,300요청, EDD a1 회수 후 3,428요청, 대표19군/3,048요청은 서로 다른 분모로 보존한다.

정정3판은 과학·소비 882셀을 보존했다. common20·firstpre20·host app-start21·device entry20의 81/84대상, 온도162셀의 정확한 시각·HAL 경로/SHA·표본·방법이 일치했다. RECENT의 common을 30초 늦은 로그 발행시각으로 잡던 문제도 수정됐다. 첫 요청 전20표본은 모두 미래가 아니고 실제 간격0.100~2.220초다.

회수 EDD a1의 common/device entry는 이미 있는 원자료를 연결하면 누락4온도셀을 복원할 수 있다. firstpre2셀은 이전 표본이15.852초 떨어져 담당자의10초와 별도 CAUSAL_REFERENCE_V1의6초 둘 다 밖이므로 null을 유지한다. 두 허용 gap 규칙은 별도 이름으로 기록해야 한다. 첨부14 PASS는 담당자의 시험 증거이며, 이쪽에서는 소스·시험을 정적으로 대조했고 첨부 프로그램은 실행하지 않았다.

M128의 긴급 기한은0.8초, 일반 기한은2초이며 아래는 응답 경계 기준이다.

| EDD CG 직렬 | 39 | 6 | 45 | 128 |

EDD는 긴급 정시26건을 늘리는 동시에 일반6건을 줄였다. 병행은 실행→AVAILABLE 겹침 CG5.495722222초/CN4.869294722초와 함께 큐 누적 감소를 관측했다. WAIT의 실제 누적은 각각2422.344571/3226.490431/12024.191210ms이며 명목량과 구분한다. 전량 완료와 전량 정시 응답은 별개다.

여유 있는 L64는 두 방식 모두64/64정시였고 PAIR의 실제 겹침은0이다. RECENT 여섯 군도 모두252/252정시다. 따라서 모든 조건에서 병행 효과가 나타난다거나 성공률만으로 열 이력이 무효라고 결론내릴 수 없다. B1과 B2는 서로 다른 게이트·시간대·초기 상태의 DEV 반복이며, 두 블록을 동일한 운영조건의 독립 CONFIRM이나 에너지·열 절감으로 승격하지 않는다. 전체19군·긴급/일반 P95·실제 WAIT·겹침·B1 대비 변화는 B2_EFFECTS_V2에 보존했다.

## 3. 게이트와 CONFIRM 파일의 정정 항목

- B2 최종 START19건의 v5 구현 게이트를 원시 HAL로 재계산했고 강제 START는0, 첫 안정창 Tref26.8℃도 일치했다. B2-11에는 AP 결측7/52행이 있으나 유효45표본·구현된 판정 기준은 통과했고 유효 AP 표본 내부 최대 간격도2.312초다. HAL 행 간격과 유효 AP 표본 사이 공백을 구분한 상세 수치를 GATE_FREEZE_AUDIT에 보존한다. 결측0이라는 등록에 없는 기준을 소급 추가하지 않았다.
- common_boundary.start_ns 기준 앱/HAL 계측 창과 필요한 경계 양측 표본·gap을 직접 대조했다. 창이 존재한다는 결과는 전류 단위·전력계 교정·J 절감까지 입증하는 결과가 아니다.
- DEV PRESTART_REJECT는 B1 16＋B2 7＝**23건**이다. 동결 파일의18건을 정정해야 한다. GATE_UNDECIDABLE_POLL은6＋50＝56회로 별도다. 폴링·사전거절·앱 START를 한 분모로 더하지 않는다.
- B1-03의 rc5 폴더 충돌은 앱 START가 아니며, 다른 세션에서 붙은 host_start를 제거하거나 잘못 연결됐음을 표시해야 한다. 실제 rc0 시도의 시각·identity와 분리한다.
- M128_ORDER의 대표 `validated_now=a2`와 a1 manifest SHA가 섞여 있다. 대표 a2의 manifest SHA와 회수 a1의 SHA를 시도별로 구분한다. a1 정시34/128과 a2 정시46/128을 서로 바꾸지 않는다.
- 19군의 `2/2`는 도구의 유효 판정이다. B1 강제 START5·v2와 B2 v5의 게이트 차이를 지우는 동일조건 반복 표시는 아니다.
- 5블록×19군＝95개 예정 session ID, 도착 계약 참조, 순서 RNG·UUID 식과 수신 세션과의 비중복은 확인했다. 현재 파일에는 새 CONFIRM의 완결된 per-session manifest·실행 원자료·약속한 새 드라이버 소스/시험 묶음이 없다. 파일만으로 현재 휴대전화의 실행 상태도 판단하지 않는다.

`summary.wait.interventions`는 B1/B2 모두 WAIT 구간 수16/12/12와 같다. 이 값을 사람 개입이나 강제 게이트 START로 해석하지 않는다. 요청 감사 초안에서0을 잘못 기대한3개 flag는 초안으로 보존하고, 잘못된 감사 조건을 고친 B2_REQUEST_AUDIT_V2를 현재 판정으로 사용한다. 게이트 감사 초기의 결측0 가정도 별도 오류 이력으로 남겼다. 실측 원본은 바꾸지 않았다.

## 4. 우리가 넘겨야 할 자료와 실제 모형 보완 범위

담당자가 `missing_from_partner`로 남긴 분석 수치 기준·CI/다중비교·예측·ATC/PPO를 완료로 채우지 않았다. 이쪽에는 동결된 S26 M8 DEV1 시간모형 GEN001이 있다. 그러나 이번95개 새 확인 입력에 대한 실측 전 예측 파일과 에너지/AP 모형, 최종 ATC/PPO 실행 묶음은 아직 없다. 기존 개발 재생을 새 확인 예측으로 바꾸어 부르지 않는다.

이번에는 원 GEN001·pool·선정·source를 바꾸지 않고 B2의3,048요청을 기존21개 단계 참조벡터와 비교한 FROZEN_STAGE_DIAGNOSTIC을 추가했다. 이것은 관측 뒤 수행한 단계 잔차 진단이며 큐 전체의 새 예측·시뮬레이션·fit은0이다. 실제 도착/입장 지연과 AVAILABLE 뒤 다음 배정까지의 공백은 식별 가능한 다음 개선 경로다. 이를 임의 물리계수·에너지/열 효과로 바꾸지 않는다. 독립 검토 수치와 구체적 개선 경로는 FROZEN_STAGE_REVIEW를 따른다.

향후 CONFIRM 연결에서는 새 드라이버/정본·정확한 입력 manifest·기기/응답/게이트 계약을 먼저 SHA로 연결하고, 예측이 존재하는 출력만 결과 열람 전에 봉인해야 한다. 분석 기준이 없는 출력은 누락으로 기록한다. 요청 수를 독립 반복 수로 쓰지 않고 블록/세션 단위 불확실성을 보고하며, 열/전류 단위가 미식별이면 null을 유지한다. 새 모형 구현·적합·평가는 별도 등록과 새 출력 계보에서 수행한다.

## 5. 이어갈 작업과 보존

S26 수신 검산 뒤 SCHEDULER-VISUAL-20261015를 이어간다. 저장된 A24/S26 실측과 모형의 요청→큐→CPU/GPU→응답→반납 재생, 두 정책의 동기 비교, 단계/기한/WAIT/겹침과 근거를 보여 준다. 화면에 없는 새 계측·NN·J/AP 결과를 만들지 않는다. B2 감사 결과는 별도 원자료 계보로 보존한다.

원 V2의 미저장 EP814·CAUSAL/NODGPU 생산 gate는 그대로이며 프로젝트 전체 완료가 아니다. 예약 자동 확인은 사용자 중지 지시에 따라 PAUSED다. 이번에 새 측정·환경·학습·추론·optimizer·외부 송신·자동화 재개는0이다.
