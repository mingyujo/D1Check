# S26 담당자 추가 요청 — 현재 자료로 남는 부분만

카카오톡에 복사할 요청문이다. 외부 전송은 하지 않았다. 이전에 이미 받은 원자료·센서 이름·APK 해시·모델/스레드 설정·준비 이력은 다시 요청하지 않는다.

---

받은 자료로 더 보완했습니다. 같은 미래창의 정책 에너지 차이 오차는31.73→22.88J, 방향 일치는8쌍 중3→5쌍으로 개선됐습니다. 첫 요청 직전까지의 관측을 쓰면 초기 문제가 큰 세션의 AP 오차도3.15→.91℃로 줄었습니다. 아직 아래 부분은 현재 자료만으로 해결되지 않아 추가로 부탁드립니다.

**1. 에너지 기준과 보고량 갱신·해상도**

전류·전압·charge_counter·읽기시각 원자료는 이미 있습니다. 직접 대조했더니 동일5~115초에서도 R4C8쌍의 차이 방향이 전류 적분과 charge_counter 사이에서3/8만 같았습니다. 둘은 같은 gauge이므로 charge_counter가 정답이라는 뜻은 아닙니다.

독립 전력/전하 기준과 대조한 자료가 이미 있다면 측정방법·시간구간·단위·오차를 부탁드립니다. 없다면 현재 API/드라이버의 갱신주기·해상도·필터/보정 근거가 있는지 먼저 확인 부탁드립니다. 가능한 범위에서 무부하→연속부하→쉼을 같은 시계로 읽어 값의 갱신과 반복 변동을 확인하는 짧은 진단이 필요합니다. 기존 표본 재전송이나 단위 확인만으로 대신하지는 않겠습니다.

**2. 같은 APK에서 전량 완료한 정책 대응 확인**

R3/R4C/SS의 APK 해시가3종이고 SS는120초에 CPU 정책6~8개, GPU·NPU 정책1개가 남습니다. 기존 J120은 조건부prefix 분석에 쓰되 같은 완료량의 절감으로 해석하지 않았습니다.

현재 한 APK와 모델·입력·CPU1·라이브러리·설정을 고정하고, 두 도착형태(낮은 혼합/밀집·버스트)에서 CPU/GPU/NPU 기존 규칙을 같은 요청수·완료량으로 대응 측정하고 싶습니다. 요청 도착을 충분히 일찍 끝내120초에 모두 실제 AVAILABLE이 되게 해주세요. 미완료는 삭제하지 않고 무효 이유와 함께 남겨주세요. 시작열·SOC·화면·충전·준비 조건을 맞추고 실행 순서를 균형 배치하면 좋겠습니다.

권장 최소안은 **2부하×3규칙×(개발1블록+모형 동결 뒤 새 확인1블록)=12세션**입니다. 초기 확인 규모이며 반복 변동을 충분히 추정하는 규모는 아닙니다. 가능한 계획과 유효 조건·개발/확인 구분을 측정 전에 고정하면 됩니다. 기존 납기·실패 기록은 유지하고, PPO APK를 새로 만들 필요는 없습니다.

**3. 강한 초기 잔류열의 소규모 확인**

요청 직전에 온도를 다시 읽으면 큰 오차는 줄지만, 시간0에서 강한 준비 잔류열을 예측하는 문제는 남습니다. HAL 이름·추출코드·읽기 후 시각은 이미 확인했습니다.

같은 APK에서 안정된 시작과 표준 워밍업 직후 시작 각각, 요청 없이180초 냉각을 기록하는 **개발1회+새 확인1회씩, 총4회**가 있으면 좋겠습니다. 실내온도·직전 부하·기존 전력/HAL 표본과 관측가능한 센서의 실제 갱신·지연 정보를 함께 부탁드립니다. 갱신시각을 읽을 수 없으면 미확인으로 남기겠습니다. 정책에 냉각대기를 넣자는 요청이 아니라 초기화 모형 확인용입니다.

**이미 있다면 문서 한 가지**

APK 해시591cae…(R3), b97a97…(R4C/S), c2e789…(SS)는 확보했습니다. 각각을 만든 source commit·변경사항 연결표가 이미 있으면 위치만 부탁드립니다. 전처리·logger·worker/큐·샘플러 변경 여부를 확인하려는 목적입니다. 해시 자체와 모델/CPU 설정·준비 이력은 다시 보내주시지 않아도 됩니다.

---

새 자료의 개발 부분에서 식·계수·초기화 규칙을 고정한 뒤 별도 확인 자료로 정책 ΔJ와 온도를 평가한다. 같은 gauge 교차검사와 독립 기준을 구분하고, 안 맞는 자료를 빼거나 사후 분할해 정확도를 주장하지 않는다. 이번120초 범위에는 장시간 CPU감속/NPU제어·새NPU지원·미지원 병행/3건 동시 실행을 추가로 요청하지 않는다.
