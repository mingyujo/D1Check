비용 모형을 더 보완했습니다. R4C 에너지 중앙 오차는14.70→6.96→6.21%, 최대는82.56→94.60→15.63%가 됐습니다. 다만 기존 R4C8쌍에서 CPU 대비 GPU/NPU의 실제 에너지 차이 방향을 새 모형이3/8만 맞혀, 정책별 에너지 우위를 말할 정도로는 아직 부족합니다. R4C 원자료는 이미 받아 직접 대응 검사를 했으니 다시 보낼 필요는 없습니다.

우선 기존 요청의 초기화/무부하 진단을 부탁드립니다. R4C0의 초기 전력 문제는 보완했지만, AP는 초기31.5→요청 전27.4℃의 냉각을 여전히 못 맞춥니다. 38.66초에 예측36.43℃/실측27.4℃입니다. 런타임 준비·워밍업·직전 부하부터 첫 요청까지의 전력/열과 가능하면 실제 HAL 센서 이름·종류·원표본/읽기 시각·주변온도를 확인하고 싶습니다. 원HAL CSV는 이미 있습니다. 온도 CSV로 가공되기 전의 매핑/표본이 있다면 그것만 부탁드립니다.

CPU 점유가 커질수록 유효 비용이 달라지는 대리식은 도움이 됐지만 실제 클럭/제어/전처리 때문인지는 미확인입니다. 각 요청의 기존 단계 시각과 연결할 CPU/GPU/NPU 주파수·활동/열제어 로그가 이미 있으면 부탁드립니다. 없는 항목은 결측으로 남기겠습니다. R3와SS 사이의 APK/모델/스레드/워밍업/전처리 설정 대응표도 도움이 됩니다.

새 측정은 단일 정책 총J 정확도뿐 아니라 **동일 요청열에서 두 정책의 J 차이**도 확인해야 합니다. 우선 현재 지원하는 CPU/GPU/NPU 규칙의 대응 반복을 사용하면 됩니다. 같은 모델·입력·완료량·도착·납기, 시작 온도/SOC/화면/충전 조건을 맞추고, 순서를 균형 배치해 원자료·실패/무효·준비 이력을 보존해 주세요. 식/초기화/계수/설정은 개발에서 고정한 뒤 별도 새 확인 자료로 차이와 반복 변동을 보겠습니다.

향후 ATC/PPO 배정표를 직접 재생할 실행기 기능이 이미 있다면, 요청별 경로/순서 지정 가능 여부와 입력 형식만 알려 주세요. 아직 없다면 이번 자료 요청 때문에 PPO APK를 새로 만들 필요는 없습니다. 기존6지원 상태의 고점유·연속/버스트 측정과 초기화 진단을 먼저 진행하면 됩니다. 지원하지 않는 조합/3건/NPU 탐지는 추가하지 않습니다.
