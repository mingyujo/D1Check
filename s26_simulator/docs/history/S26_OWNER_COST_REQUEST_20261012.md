# S26 비용 오차 보강 요청 — 카카오톡 전달용

아래는 요청문 초안이다. 외부 전송은 하지 않았다. 현재 제공한 자료를 다시 달라는 요청과 새 측정을 구분한다.

---

S26 자료로 CPU/GPU/NPU 통합 시뮬레이터를 만들고, 에너지·열 모형을 보완해 봤습니다. 혼합 요청 R4C의 에너지 중앙 오차는14.70%→6.96%, AP MAE는1.26→.94℃로 줄었습니다. 그런데 상태분리 확인6의 에너지 오차는1.75%→8.03%로 커져 새 모형은 채택하지 않았습니다. 기존 M5 null/GPU열0/8/지속 미확인 판정도 그대로 유지했습니다.

특히 R4C index0(세션 `4add7ebd-7f7a-5216-af5a-3f1498caa11e`)은 사전 평균 전력2.89W인데, 요청이 없는 첫35초에는.62W였습니다. AP도31.5→27.4℃로 내려갑니다. 준비 중 전력과 잔류열을 초기값으로 고정하면 이 세션을 설명할 수 없습니다.

우선 다음 자료가 **이미 있으면 원본부터** 부탁드립니다.

1. **세션 설정·준비 이력:** R3/R4C/SS별 APK SHA·소스커밋·모델/정밀도/CPU스레드·요청 입력·런타임 초기화/워밍업 수/시각·직전 부하·화면/밝기/충전/SOC·기기/장소/주변온도. 원 progress/requests/HAL은 받았으니 재전송할 필요는 없습니다. 설정 차이가 있으면 대응표만 주세요.
2. **활동 계측:** 같은 요청 세션과 시각을 연결할 수 있는 CPU 주파수/활동, GPU/NPU 주파수·제어·열상태 로그 또는 Perfetto가 있으면 부탁드립니다. 없거나 권한상 읽을 수 없는 항목은 없다고 표시해 주세요. 이미 있는 dispatch/host_inference_start/return/AVAILABLE 시각은 유지해 주세요. 새 trace를 사용하면 trace-off/on 계측 영향도 별도 확인해 주세요.
3. **전류/센서 근거:** 기존 µA 해석의 독립 단위 대조나 센서 검증 결과가 있으면 원본·명령·판정 부탁드립니다. 전류/전압 원표본과 timestamp는 이미 있습니다. charge_counter로만 대조할 경우 단위·해상도·충전 여부·오차도 함께 주세요.

새 측정이 필요하면 다음 순서로 부탁드립니다. 먼저 계획/가능 항목을 공유하고, 계산 전에 개발/확인 구분과 유효 조건을 고정했으면 합니다.

4. **초기화 진단 우선:** 무부하 안정 상태와 런타임 준비/워밍업 직후 상태에서, 요청 없이 전력·AP/SKIN·가능한 클럭을180초 기록해 주세요. 가능하면 각 상태2회(총4회), 직전 활동과 주변온도도 기록해 주세요. 평균전력만 전달하지 말고 원표본을 남겨 주세요. 불안정한 시도도 제외하지 말고 무효 이유와 같이 보존해 주세요. 정책에 임의 냉각 대기를 추가하자는 요청은 아니고 모형 초기 조건을 확인하려는 진단입니다.
5. **고점유·간격 분리 개발/확인:** 현재6상태 C_CPU/D_CPU/C_GPU/C_NPU/D_CPU+C_GPU/D_CPU+C_NPU를 유지한 측정이 필요합니다. 권장18세션은 상태별 개발2+새확인1입니다. 개발1은 연속 실행, 개발2는 같은 작업 종류·완료량을 버스트/휴지로 나누고, 확인은 모델 동결 뒤 별도 시점의 새 패턴으로 찍어 주세요. 120초 요청/에너지와180초 열관측을 사용하고 전량 완료·실제AVAILABLE를 기록해 주세요. 시작 온도/설정은 같은 허용범위로 맞춰 패턴과 초기열을 동시에 바꾸지 않았으면 합니다.

병행 상태는 실제 동시 점유가50% 이상인5초창이 상태별 최소6개 확보되도록 진단 구간을 넣어 주세요. 현재 M5의 두 병행 상태는 이 창이0개여서 상호작용을 분리하지 못했습니다. GPU/NPU 탐지·미지원 분류 병행·3건 동시는 추가하지 않습니다. 연속/버스트에서 동일 완료량과 병행 노출을 동시에 확보할 수 있는 요청 수·간격은 짧은 준비 확인 후 사전 등록에 고정하면 됩니다.

확인6은 원자료·분할 ID·원장/실패/무효 목록까지 별도 전달 부탁드립니다. 위18세션은 초기 모형 확인을 위한 최소안이고 상태별 확인이1회라 반복 변동을 충분히 추정할 수는 없습니다. 여유가 있으면 상태별 확인2회로 총24세션이 좋습니다. 먼저4번 진단 결과를 보고5번 계획을 고정해도 됩니다. 개발에서 식·계수·초기화 규칙을 동결하고 확인으로 수정하지 않겠습니다. 지금 목표는120초이므로10분 CPU감속/NPU제어는 후순위입니다.

## 수신 후 사용할 방식

- 1~3번은 이미 있는 원계측과 설정의 보충이며, 표준 current_sample/HAL을 새로 요청하는 것이 아니다. 주파수/활동은 가능 항목만 받고 미지원 항목은 결측으로 보존한다.
- 4번은 사전 Ppre를 안정 바탕 전력으로 볼 수 있는지, 준비 후 열의 빠른/느린 초기 상태를 구분할 수 있는지 확인한다. 기존 R4C 이상 행을 삭제해 정확도를 높이지 않는다.
- 5번 권장18세션은 새 설계안이다. 기존 M5 사전 등록을 덮어쓰거나5W 상한을 결과 후 바꾸지 않는다. 필요 노출/시간/품질/환경을 측정 전에 합의하고 실제 가능한 범위로 동결한다.
- 계수의 물리 식별/새 확인 오차와, 실제 정책 쌍의 에너지·열 차이 검증은 별개다. 향후 동일 요청열에서 규칙/학습 정책의 대응 실측도 필요하며, 현재 요청에는 아직 없는 PPO 앱 실행을 포함하지 않는다.
- 자료가 추가되면 새 개발 계약에서 모델을 고르고 새 확인을 한 번 평가한다. 이전 확인 결과에 맞춘 무한 후보 탐색을 하지 않는다.
