# S26 결과는 우리 주제와 맞는가 — 판정

작성: 2026-09-15, 영훈. 근거: `S26_formal_strict/exports-v2` 80런 + 런 2개의 `merged/events.jsonl`
대조 문서: 재설계안 v1.4 §1.5·§12, 합류제안메모 0909, 레포정리_및_목적함수 0911, 현황재확인_및_RL적용정리 0911,
시뮬레이터_설계초안 0912 §3, `D1CHECK_STAGE_GATE_PLAN.md`(레포본), MEASUREMENT_DEFINITION §6·§8

## 0. 한 문단 판정

**끌고 갈 수 있다. 단, 지금 데이터는 "재료"이지 "결과"가 아니다.**
S26 80런은 시뮬레이터가 요구하는 기기 프로파일의 **지연·열 칸을 완전히 채우고**, 우리 문서들이
"미검증"으로 남겨둔 **에너지 단위를 추가 측정 없이 확정할 수 있는 신호까지 담고 있다**. 여기에
A24와 정반대인 자원 순위(GPU 우세)가 실측되어 "기기별 정책"이라는 서사의 두 번째 근거가 생겼다.
그러나 우리 주제의 생사를 가르는 관문 세 개(KS-D 품질 티어, KS-B 부하 임계, KS-C 현행 대비)는
**하나도 판정되지 않았고**, 이 측정으로는 판정할 수 없다. 특히 재설계안이 "유일한 AI 고유성"이라고
못 박은 **품질 티어 축은 여전히 실체가 없다.** 다음 3주의 우선순위는 시뮬레이터가 아니라 KS-D다.

## 1. 우리가 정의한 문제 (문서에서 확인한 그대로)

> 여러 앱이 서로 다른 긴급도로 비동기적으로 던지는 AI 추론 요청을, **하루 안에 소진되는 배터리(비재생)**와
> **쓰면 줄고 쉬면 회복되는 발열 여유(회복형)** 아래서, **어떤 요청을 지금 승인 / 유예 / 거절하고,
> 어느 자원(CPU/GPU/NPU)에서, 어떤 품질(FP32/FP16/INT8)로** 실행할지 결정하는 **승인통제·스케줄링 정책**을
> 설계하고, 반응형 규칙(NPU Manager 근사) 대비 그 가치를 정량화한다. — 재설계안 §12.1, 합류제안메모 §2.3

| 구성요소 | 정의 | 출처 |
|---|---|---|
| 결정변수 | x∈{승인,유예,거절} × r∈{CPU,GPU,(NPU)} × q∈{FP32,(FP16),INT8} | 0911 §3.2 |
| 목적함수 | min Σ wᵢ·max(0, Cᵢ−dᵢ) + c_rej·거절수 + c_q·ΣΔQᵢ | 0911 §3.2 |
| 하드 제약 | T_skin ≤ T_max, ΣE ≤ B(배터리 예산), q ≥ q_min, 순차 실행, 지원 조합 | 0911 §3.2 |
| AI 고유성 | **품질 티어 축이 유일** — 빼도 문제가 성립하면 일반 스케줄링 | 재설계안 §1.5 반박 A |
| 핵심 지표 | 갭 폐쇄율 = (휴리스틱−정책)/(휴리스틱−MILP) | 재설계안 §3 |
| 관문 | KS-D(티어 에너지 또는 발열률 ≥20%) → KS-B(λ≤2에 개선여지 ≥20%) → KS-C(p95 ≥20% 또는 스로틀링 ≥30% 지연) | 합류제안메모 §6 |
| S26의 배정된 역할 | **NPU 포함 최종 자원 비교기 + CPU/GPU 기준선 같은 프로토콜로 재측정** | STAGE_GATE(레포본) §8 |

세 층 구조(0911 레포정리 §2.1): **층 1 측정 → 층 2 룩업표·RC 열모형·시뮬레이터 → 층 3 정책**.
S26 측정은 층 1이다. 층 1의 성공 기준은 "층 2가 필요한 칸을 채웠는가"다.

## 3. 주제에 직접 닿는 발견 5가지

### 3.1 자원 순위가 기기마다 뒤집힌다 — 두 번째 실측 근거

| 기기 | CPU (4스레드) | GPU strict | 빠른 자원 |
|---|---|---|---|
| A24 (MT6789, 조민규) | 41.3 ms | 131.6 ms | **CPU** 3.2× |
| S26 (Exynos 2600) | 4.37 ms | 3.64 ms | **GPU** 1.2× |

같은 모델·같은 프로토콜·같은 fp32 strict인데 정답이 뒤집힌다. 합류제안메모 §5가 S22 수동 측정으로
주장했던 "고정 규칙은 불가능하고 기기별 프로파일링 위의 적응 정책이 필요하다"를 **정식 80런 프로토콜로
두 기기에서 확인**한 것이다. 재설계안 §4.1.5의 "열 특성이 다른 2대 이식성"도 이걸로 성립한다.

### 3.2 S26에서는 GPU가 지연·열·에너지 세 축 모두 우세하다 — 자원 결정은 전환비용 때문에만 비자명

| 축 | CPU (duty 100) | GPU (duty 100) | 비 |
|---|---|---|---|
| 지연 median | 4.37 ms | 3.64 ms | GPU 0.83× |
| AP 상승 | +14.1 ℃ | +11.7 ℃ | GPU 0.83× |
| 처리량 | 13,942회/60 s | 16,376회/60 s | GPU 1.17× |
| AP 상승 / 추론 | 1.01 m℃ | 0.71 m℃ | GPU 0.71× |
| 순 에너지 / 추론 (예비, §3.5) | ≈36 mJ (t01 d50) | ≈22 mJ | GPU ≈0.6× |

**정직하게 말해야 할 함의**: FP32만 있고 전환비용을 무시하면 S26에서 자원 선택은 "항상 GPU"로 자명하다.
결정을 비자명하게 만드는 것은 **초기화 비용**이다 — CPU 31 ms vs GPU 273 ms(interpreter 238 + delegate 35).
추론 1회가 4 ms이니 GPU 콜드 스타트는 추론 약 65회 분량이다. 산발적 단일 요청은 CPU가 8배 빠르고,
버스트는 GPU가 이긴다. 이것이 재설계안 §12.4의 **순서의존 준비시간**이며, 시뮬레이터 `switch_cost_s`가
placeholder(1.0 s)가 아니라 **실측 0.27 s**로 들어가야 정책 비교가 의미를 가진다.
S22·Flip3 수동 관측(0.5~1.5 s)보다 짧으므로 기기 상수로 취급해야 한다.

### 3.3 열 제약이 60초 안에서는 한 번도 걸리지 않았다 — 재설계안이 경고한 플래그십 위험이 실현됨

- 37,613 표본 전부 `thermal_status = 0`. SKIN 최고 **36.9 ℃**, LIGHT(38.0)까지 1.1 ℃ 남음
- 재설계안 §4.1.5: "최신 플래그십은 방열이 좋아 10분 AI 부하로도 MODERATE에 못 닿을 수 있다 → KS-B 실패 위험"

그러나 이것이 "열 제약이 없다"는 뜻은 아니다.

| 센서 | 가열 τ | 60초 시점 정상상태 도달률 | 뜻 |
|---|---|---|---|
| AP | 4~20 s | ≈100 % | 빠른 노드, 즉시 포화 |
| SKIN | 17~48 s | 70~97 % | 느린 노드, 거의 도달 |
| BAT | **≫ 60 s** (피팅 상한 도달) | **미도달** | 가장 느린 노드, 계속 오르는 중 |

60초 부하는 SKIN 정상상태를 거의 보여줬지만 BAT는 아직 오르는 중이었다. 분 단위 지속 부하(또는 λ 스윕에서의
누적)에서 SKIN이 38→40→42 ℃에 닿는지는 **별도 측정이 필요**하다. KS-B 설계에 직접 반영해야 할 사실:
**S26에서 스케줄링이 열 때문에 필요해지는 구간은 "요청이 몰리는 몇 분"이지 "요청 하나"가 아니다.**
이건 우리 문제 정의(다중 앱, 비동기 도착)와 정확히 맞는 방향이지만, 측정으로 아직 증명되지 않았다.

### 3.4 CPU는 duty ≥ 75에서 스스로 제한한다 — OS status 없이도 "회복형 자원"이 성능으로 드러남

| duty | CPU 지연 | CPU AP ΔT_ss | GPU 지연 | GPU AP ΔT_ss |
|---|---|---|---|---|
| 25 | 3.90 | +6.2 | 3.67 | +3.4 |
| 50 | 3.91 | +11.7 | 3.66 | +6.6 |
| 75 | 4.09 | +13.8 | 3.64 | +8.9 |
| 100 | 4.37 | +14.8 | 3.64 | +11.9 |

CPU는 75→100에서 열이 **포화**(+13.8→+14.8)하면서 지연이 **악화**(+12 %)한다 — 전력이 더 못 오르고
클럭이 내려가는 SoC 내부 DVFS의 전형이다. GPU는 열·지연 모두 선형이다. 즉 `thermal_status`가 0이어도
**부하 이력이 지연에 영향을 준다.** 시뮬레이터의 L을 상수 룩업이 아니라 최근 부하율의 함수로 둬야 하고,
이 비선형이 바로 "쉬면 회복되는 자원"을 데이터로 보여주는 증거다.

### 3.5 에너지 단위를 기존 데이터로 확정할 수 있다 — 단계 2가 추가 측정 없이 끝난다

우리 문서 셋이 전부 "단계 2(전류 단위 검증) 전엔 배터리 예산 제약 활성화 불가"라고 적었다.
그런데 80런 각각의 `merged/events.jsonl`에 1 Hz `current_raw`·`charge_counter_raw`가 통째로 있다.
런 2개에서 조민규가 제안한 절차(전류 적분 vs charge counter 감소량)를 그대로 돌렸다.

| 런 | 구간 | 길이 | ∫I dt (µA 가정) | charge_counter Δ | 비율 |
|---|---|---|---|---|---|
| cpu-t01-d050-r005 | 전체 | 554 s | 43,985 µAh | 47,025 µAh | **0.935** |
| gpu-d100-r001 | 전체 | 578 s | 44,706 µAh | 47,025 µAh | **0.951** |

- **S26의 `current_now`는 µA다** (부하 시 −1.4~−2.6 A; S22와 같은 계열, A24·Flip3의 mA와 다름)
- 전 구간 비율이 두 런에서 0.94~0.95로 일치 → ~~±10 % 기준 안. 5 % 언더카운트는 일관적이라 보정계수로 흡수 가능~~
  → **[2026-09-26 사후 증거 감사 — 철회]** ±10 % 는 사전에 등록된 기준이 아니었고, 두 런의 일치로 "일관적 편향"을 말할 수 없다.
  허용오차는 `docs\MEASUREMENT_DEFINITION.md` §10(사후 등록, 3분법)로 대체. 원문은 기록으로 남긴다
- 단, charge_counter는 **4,275 µAh 단위로 양자화**되어 있어(모든 Δ가 그 배수) 60초 구간만 보면 비율이 0.5~2.6으로 튄다. 판정은 런 전체 또는 80런 합산으로 해야 한다
- 예비 원가표: CPU 1스레드 d50 부하 5.32 W / 유휴 0.70 W → **≈36 mJ/추론**; GPU d100 부하 6.55 W / 유휴 0.45 W → **≈22 mJ/추론**. Flip3 CPU4 88 mJ와 같은 자릿수

이건 두 런 결과이고 조민규 계획서의 "한 번의 일치만으로 절대 정확도를 보장하지 않는다"가 맞다.
그러나 **80런을 합산하면 자체 검증이 끝난다.** 이 계산 하나가 목적함수의 하드 제약 하나(ΣE ≤ B)를
placeholder에서 measured로 바꾼다.

## 4. 판정표 — 주제를 끌고 갈 수 있는가

| 질문 | 답 | 근거 |
|---|---|---|
| S26에 배정된 역할을 했는가 | **절반** | CPU/GPU 기준선 같은 프로토콜 재측정 ✅ · NPU ❌ (NNAPI 막힘, ENN·LiteRT Next 미검증) |
| 층 2(시뮬레이터) 재료로 충분한가 | **예, FP32 한정** | 지연·열 measured, 에너지·전환비용 기존 데이터에서 추출 가능 |
| "기기별 정책 필요" 서사를 뒷받침하나 | **예, 강하게** | A24 CPU 3.2× vs S26 GPU 1.2× 역전 |
| "두 제약(배터리·열)" 서사를 뒷받침하나 | **배터리 예, 열은 조건부** | 에너지 단위 확정 가능 / 열은 60 s에선 미발동, 분 단위 지속 부하 필요 |
| AI 고유성(품질 티어)을 검증했나 | **아니오** | INT8·FP16 0건. 재설계안 §1.5의 "이게 빠지면 일반 스케줄링" 그대로 |
| 관문 KS-D / KS-B / KS-C | **0 / 3** | 이 측정으로는 어느 것도 판정 불가 |
| 자원 축이 S26에서 살아 있나 | **전환비용이 있어야만** | GPU 3축 우세 → 초기화 273 ms가 유일한 트레이드오프 |

**결론**: 이 데이터는 우리 문제의 **층 1을 완성하고 층 2를 시작하게 해 준다.** 주제 자체를 흔드는
결과는 없다 — 오히려 3.1·3.4·3.5는 서사를 강화한다. 그러나 주제의 **성립 여부**는 여전히 KS-D에
걸려 있고, S26 측정은 그 질문에 한 글자도 답하지 않았다. 지금 시뮬레이터·RL로 넘어가면 합류제안메모
§6이 경고한 "관문 없이 몇 주를 쓰는" 함정에 그대로 빠진다.
