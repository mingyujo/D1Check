# D1Check 프로젝트 방향 근거 검토

2026-09-25 / `DIRECTION-REVIEW-01`. 검토 기준은 `feature/arrival-scheduling-20260923`, `c8b4e30cf09f4e645553762fd13e73a3d27db357`이다. 시작 작업 트리는 clean이었다. 코드·실측 원본·설정·정책을 변경하지 않았고 추가 실측, ADB, 테스트 재실행, PC 재생·배치도 수행하지 않았다. 기존 분석을 재사용했다.

## 우선 권고: B, 서비스 제약 아래 적용 조건을 밝히는 문제로 제한적 재정의

**현재 P의 개선 개발은 보류하고, 단순 정책을 우선할 조건과 서비스 상충의 경계를 설명하는 연구로 정리하는 것이 가장 타당하다.** 이 문서는 권고이며 목표 변경의 채택 기록이 아니다. S26/NPU 협업 결정도 취소하거나 P를 구제할 필수 범위로 확대하지 않는다.

핵심 이유는 세 가지다.

1. 현재 구현한 P의 추가 이득은 확보하지 못했다. δ 분석에서 P의 단독 최선 구간은 없으며, 모든 조건에서 CPU 긴급우선의 긴급 P95가 P 이하이다. 이 부정적 결과를 무시하고 새 계수·유리한 조건을 찾을 이유가 부족하다.
2. 그렇다고 전체 프로젝트가 실패한 것은 아니다. 두 모델의 실제 요청 실행, 비동시 도착·응답/자원 해제 계측, 독립 평가의 FAIL 보존, 단순·동적 정책 비교와 정확한 제약 경계 분석은 직접 구현·검증한 자산이다. 다만 그 자체가 새로운 알고리즘이나 현실 예측 정확성의 입증은 아니다.
3. 가장 큰 공백은 더 복잡한 정책이 아니라 **구체적 서비스가 해결해야 할 문제와 검증 범위**다. 선행 연구가 이미 이종 배정·경합·앱 수준 적응을 다루고, D1Check에는 실제 도착 로그·필수 서비스 요구와 강한 정적 B2의 실기기 비교가 부족하다. 이 상태에서 A를 계속하면 구현·측정 부담이 큰 반면 기여가 불확실하다. C로 즉시 전환하기에는 현재 결과를 좁게 정리할 여지가 남아 있다.

δ는 지금 확정하지 않는다. 서비스 요구 근거가 없으므로 **허용폭 전체의 민감도 결과**를 유지한다. “CPU만 쓰면 모든 실제 서비스에 충분하다” 또는 “간섭 인지는 쓸모없다”는 결론도 내리지 않는다.

**B2 선정 범위:** 개발 low/queue/burst, seed101~103에서 모든 요청 완료, 각 시나리오의 일반 평균응답이 CPU 긴급우선 이하, 일반 기한 내 완료율이 CPU 긴급우선 이상인 후보만 적격으로 했다. 이후 긴급 위반율 평균→긴급 P95 평균→일반 평균응답→makespan→후보 ID 순으로 선택했다. explore에서는 분류GPU/탐지CPU 병행, strict에서는 양쪽CPU 직렬을 평가 전에 고정했고, 평가 조건별로 다시 선정하지 않았다. 이는 PC 개발용 선정 규칙이며 합의된 서비스 요구나 모든 가능한 정적 정책 중 실기기 최선의 증명은 아니다. 최신 δ 분석의 후보 B2도 이 고정값 그대로다.

**중요한 미구현 차이:** PC `choose()`는 deadline을 정렬에 사용하지만 후보 점수에서 예상 위반 수·일반 서비스 제약을 계산하지 않는다. `simulate()`의 다음 이벤트 목록도 도착/판단완료/단계완료 중심이며 PLAN의 별도 deadline·aging 경계 wake-up을 구현하지 않는다. aging은 다음 판단 호출 때 반영된다. 이는 PLAN 대응의 공백이며, 기존 trace의 손실 전부를 이 차이로 돌릴 근거는 없다. 이번 검토에서 동작을 변경하거나 새 결함 수정으로 기존 결과를 재생성하지 않는다.

### 계수1.5의 출처와 고정 시점

`d1_arrival_explore_batch.defaults()`가 `interference=1.5`와 `predicted_interference=1.5`를 지정한다. [개발 전 계약](results/arrival_explore_20260925/contract_before_development.json)은 이를 **fixed assumed pair factor, no search/tuning**으로 명시하고, [평가 전 동결](results/arrival_explore_20260925/freeze_before_evaluation.json)에도 같은 값이 남아 있다. `run()`은 계약→개발B2선정→동결→평가 순서다. 따라서 **개발 실행 전에 정한 탐색 가정**이며 개발 최적화로 선정한 계수도 실측 보정값도 아니다. 1.5라는 숫자의 실증적 근거는 없다.

`scenarios()`는 `queue_interference_1.0/2.0`에서 **실현값만** 바꾼다. 예측값을1.5로 유지하는 불일치는 기본 설정 누락이 아니라 명시적 민감도 설계다. 이를 자동으로 버그라고 하거나 예측값을 실현값에 맞춰 결과를 개선하지 않는다. 기본1.5 조건도 측정된 현실을 뜻하지 않는다.

### 무엇이 더해지고 무엇이 가정되는가

- [CAL-03 변환 `derive`](../tools/d1_cal03_connection.py)는 개발요청마다 dispatch→응답·dispatch→lane해제 전체 구간을 먼저 구한 뒤 중앙값을 낸다. 구간 중앙값의 합을 전체 중앙값으로 사용하지 않는다. priority별 응답 끝점도 보존한다.
- P 점수는 `예상 lane잔여 + 단독 dispatch→응답 + (k−1)×S→O + (k−1)×상대 lane잔여`다. 추가항은 상대가EXECUTING이고 병행 후보일 때 적용한다. 상대 잔여는 점유 전체의 잔여로, S→O만의 실제 잔여가 아니다. UNKNOWN_OVERRUN이면 임의0으로 만들지 않고 해당 비용 판단을 보류한다.
- 엔진 실현은 단독 개발의 **다섯 구간을 함께 보존한 벡터**를 seed/request/backend로 선택한다. 요청4개를 재사용하는 방식이며 새 모집단 분포 fit이 아니다. 정책에는 실제 벡터·미래 도착·미래 완료를 주지 않는다.
- 두 lane의 S→O가 실제로 겹치는 동안에만 각 lane의 진행률을1/k로 바꾸고, overlap이 끝나면 원래 속도로 돌아간다. 반면 P 점수는 정적인 전체 서비스/상대 잔여 penalty다. 따라서 k가 같아도 정확한 잔여 overlap 예측이 아니며, 준비·저장 등이 포함된 상대 잔여 때문에 과대평가할 수 있다. 이는 의도된 휴리스틱 근사의 한계이지 확인된 현실의 간섭효과가 아니다.
- S→O는 실행 시작→output_ready 전체이며 GPU kernel 시간이 아니다. 가정 감속을 이 전체 구간에 적용한다. 준비(D→S)/저장/worker release/lane callback은 별도 벡터이며 부하2배 조건은 준비·마지막 callback만 늘린다. 판단·기록·dispatch는각0.1ms(고비용조건각1ms)의공통가정이다. 실제통합계측값을현재P의비용으로대입하지않았다.
- 응답은 urgent O, normal persist에서 끝나고 lane은실제L전까지점유한다. 큐 대기는도착과이벤트실행에서생성하므로end-to-end응답을다시서비스시간으로넣지않는다. P 점수penalty도엔진에별도고정지연으로중복청구하지않는다.

대표 증거는 [기존 결정 사례](results/arrival_service_review_20260925/decision_cases.json)의queue/seed201, t=200ms다. GPU 단독응답295.764ms에추가332.692ms를합한628.456ms가 CPU점수582.435ms보다커서P는기다린다. 같은상태B3는GPU를선택한다. 기존대표에서B2와P는긴급6건모두GPU지만대기평균은0.300/266.420ms다. 따라서 손실을 “GPU가 느려서” 하나로 설명할 수 없다. 같은상태에서다른선택의실현결과는자동으로알수없으며기존trace밖의반사실적이득은계산하지않는다.

## 3. 실제 문제와 기존 시스템이 이미 해결하는 부분

[SCOPE 근거](SCOPE_02_EVIDENCE.md)는 일반 사진 태그·색인 중 선택 사진의 객체탐지를 대표 후보로 제시한다. 일반 결과는 나중에 저장해도 되지만 선택 결과는 사용자가 기다린다는 구분은 타당한 **과업 가설**이다. 비선점 단독 실행에서 실행 중 한 건을 끝낼 때까지 기다려야 하고, 병행하면 CPU 전후처리·메모리 등이 경합할 수 있다는 제약도 구체적이다. 그러나 같은 앱에서 두 작업이 얼마나 겹치고 얼마나 불편한지, background 작업을 얼마나 늦춰도 되는지에 관한 실제 로그·채택 근거·사용 요구는 없다. 기능이 가능하다는 것과 적응형 정책이 필요하다는 것은 다르다.

이번에는 선행조사를 새로 확장하지 않고 다음 1차 자료만 재확인했다(2026-09-25 조회).

## 6. 단 하나의 최소 후속 검증과 종료 기준

**제안: PLAN에 이미 있는 사진 정리 흐름 한 가지를 대상으로 실제 사용자/업무 담당자 한 명과 최대 30분의 과업 근거 검토 한 번.** 기존 화면·시연 설명과, 가능하면 이미 있는 사용 기록을 사용한다. 새로운 모델 실행이나 실측은 필요하지 않다. 이번 검토에서는 사람에게 연락하거나 이 후속 검증을 수행하지 않았다.

확인할 질문은 하나다: **배경 분류·색인과 대화형 객체탐지가 같은 앱에서 겹쳐야 하는 실제 과업이 있고, 단순 직렬/우선순위 처리만으로 남는 구체적인 불편이 있는가?** P의 장점이나 정책 이름을 먼저 제시하지 않는다. 이전 과업·기존 기록, 두 결과의 쓰임과 완료 기대, 배경 작업의 중단·연기로 충분한지, 손해가 생기는 이유를 한 장에 사실·보고·가정으로 나눈다. 정밀한 deadline이나 δ 선택을 요구하지 않는다.

- **근거 확보:** 담당자·구체적 과업·겹침 이유·단순 처리로 남는 불편이 같은 기록에 연결되면 B의 실무 질문을 유지할 근거로 삼는다. 한 명의 응답으로 수요의 빈도·보편성·적응 정책의 필요성을 입증했다고 하지 않는다. 현재 민감도를 그 요구에 연결할 수 있는 범위만 정리한 뒤 이 검증을 종료한다. P 개발이나 새 실측은 자동 재개하지 않는다.
- **근거 불충분/반례:** 일반 작업을 중단·연기해도 문제가 없거나, 두 task가 같은 과업에 필요하지 않거나, 실제 경험 없이 가상 선호만 나오면 응용 동기를 확인하지 못했다고 판정한다. 다른 유리한 시나리오·사용자를 연속 탐색하지 않고 추가 정책 개발을 종료한다. 기존 성과를 한정된 기술 검증·부정적 결과로 보존하고 C 전환을 권고한다. 이는 개발 투자에 대한 종료 기준이며, 단일 면담 실패가 시장 전체의 수요 부재를 증명하는 것은 아니다.
- **접근 불가:** 담당자·기존 기록을 확보하지 못하면 미확인으로 남기고 새 개발을 보류한다. 예산·기기·모델을 자동으로 늘리지 않는다.

이 최소 검증은 현실 문제의 존재에 관한 것이다. 시뮬레이터의 예측 정확성이나 정책 성능을 입증하려면 위 공백표의 별도 구현·독립 실측이 여전히 필요하다. 이번에는 그 후속 실험들을 연속 계획하거나 예산을 정하지 않는다.
