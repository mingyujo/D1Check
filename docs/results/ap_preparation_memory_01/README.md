# 준비 이력을 포함한 AP 후보: PC 구현·사후 평가

2026-10-02 · [화면](index.html) · [사전 구조/추정 계약](contract.json) · [결과](final/summary.json) · [검증](verification.json) · [통합 시뮬레이터](../simulator_workbench_01/index.html)

**부분 개선을 구현했지만 후기 재상승은 해결하지 못했다.** 기존 preload 후보보다 이미 본 네 평가 세션의 평균·최고온도 오차가 줄었다. 그러나 개발 세션의 최대오차는 증가했고 후기 상승 크기는 재현하지 못했다. 이번 후보는 `ap-preparation-memory-v1`이라는 별도 사후 진단용이다. 기본 모형·strict 지원·정책 비용·`experiment_ready=false`는 유지한다. 기존 계수·원본·소비 계획은 수정하지 않았다. 새 실측·APK·기기 계획·claim은 없다.

## 선택한 최소 변경과 자료 역할

직전 기각 후보는 새로운 부하의 지연만 표현하고 준비에서 남은 상태를 0으로 시작했다. 이번에는 상태 하나 H를 더한 구조 하나를 적합 전에 고정했다.

```text
u = 기존 상태별 AP 기울기 − 기존 resident_idle 기울기
dT/dt = β(E − T) + u + H
dH/dt = (γu − H) / τ
```

β=0.045932520308001434/s와 모든 상태 기울기는 기존 동결값이다. 준비 뒤 부하 전 AP만으로 각 세션의 E와 H 초기값을 추정한다. E는 유효 기준이며 주변 온도가 아니다. H는 부호가 있는 반응항(°C/s)이며 내부 온도·저장 열의 측정값이 아니다. 실제 lane 일정이 주어진 조건부 예측이고 미래 관측 AP·전류를 예측 입력으로 사용하지 않는다.

기존 유휴 개발 **1세션만** 부하 이후 목표값으로 τ·γ를 적합했다. τ=5…180초(5초 간격)와 γ≥0 최소제곱 절차를 고정하고, 다른 구조나 평가 결과에 맞춘 재적합은 하지 않았다. 나머지 네 세션은 계수 적합에서 제외했다. 다만 모두 이미 결과를 본 자료이므로 **사후 평가이며 새 독립 확인은 0세션**이다. 자료가 5세션이라는 사실과 AP 표본 수는 구분한다.

부하 전 표본은 기존 ≥55초·≥15개·공백≤10초 기준, 각 조회의 전체 시간 괄호가 첫 dispatch 전인 조건을 사용했다. 실제 63.545–65.360초/23–26개다. 첫 표본을 기준으로 E·H를 추정한 뒤, 마지막 부하 전 AP(공통창 +32.220…34.787초)를 T로 관측 초기화하고 H는 식으로 전파한다. 이 초기값은 세션 공통창 시작 AP와 다르다. 평가창도 공통창 전체가 아니라 **첫 부하 이후의 기존 AP 표본(+35.395…37.822초부터 +177.822…179.475초)**이다. 각 정확한 창·표본 수는 [scores.csv](final/scores.csv)에 있다. 중간 AP를 다시 입력하지 않는다.

## 결과와 개선의 실체

비교 대상은 원래 절대 AP식이 아니라 **기존 preload 유효 유휴 기준 후보**다. 원래 동결 모형과 이전 지연4초 후보를 덮어쓰지 않는다. [경로/잔차](final/paths.csv), [구간별 오차](final/phase_scores.csv), [비교 그림](final/comparison.png)을 함께 제공한다.

추정값은 **τ=30초, γ=0**이다. 제약 없는 γ는 −0.340912여서 비음수 경계에 놓였다. 이는 새로운 부하의 지연 가열 항이 식별됐다는 증거가 아니다. 모든 H 초기값도 음수다. 물리적 잔열을 찾았다고 부르지 않는다.

[산술 분해](final/decomposition.csv)는 동일 계수에서 초기 T 변경→E 변경→초기 H→부하 H 순서로 경로 차이를 분해한다. 합계가 실제 후보−기존 경로와 일치함을 검증했다. 후기(≥150초) 평균 변화 중 E 변경은 **+0.539…+0.757°C**, 초기 H는 **−0.005…−0.008°C**, 마지막 표본 초기화는 +0.0004…+0.0013°C, 부하 H는 0이다. 따라서 평균/최고 개선은 주로 **준비 반응과 유휴 기준을 분리해서 추정한 E**에서 왔다. 이는 산술적 설명이며 숨은 물리 기제의 인과 증명은 아니다.

고정 후기150–175초 관측 변화는 CG_DC +0.108°C, 한 묶음 +0.200°C, 두 반묶음 +0.100°C다. 새 후보는 각각 +0.000293/−0.000046/−0.009219°C로 거의 평탄하거나 냉각한다. **작은 후기 재상승과 초기 최고 발생시각 문제는 남았다.** 계수 고정 후 무부하 해는 두 지수함수의 합이므로 임의의 반복 상승·하강을 표현하는 모형도 아니다. 한 점의 최고오차 개선을 경로 전체 해결로 해석하지 않는다.

## 식별과 지원 한계

두 초기계수의 수치 rank는 모두 충족했고 정규화 조건수는 5.728–6.001이었다. 이것은 물리적 유일성을 입증하지 않는다. [전체 τ profile](final/fit_profile.csv)에서 최저 RMSE+0.05°C 이내는 15–40초다. 이 값은 민감도 범위이며 신뢰구간이나 정확도 합격선이 아니다. 각 부하 전 AP에 독립 ±0.05°C 변동을 가정한 결정론적 민감도는 미래 경로 최대 0.204–0.213°C다. 센서 인증 오차 또는 모든 오차의 상한이 아니다.

지원은 A24의 해당 resident·CPU/GPU 상태와 **실제 일정 및 충분한 부하 전 AP가 있는 다섯 보관 사례의 진단**에 한정한다. 747/3d8 APK 프로토콜을 CSV에 구분했다. 원래 동결 시작 AP 범위 밖의 자료이며 strict 확대가 아니다. 즉시 시작하는 queue/ABBA 일정에는 필요한 준비 기록이 없으므로 자동 적용하지 않는다. 새로운 일정의 처리시간·전력·J, 최고온도 보장·열 피드백 정책 순위를 제공하지 않는다. S26·BAT·SOC로 확대하지 않는다.

## 온도→처리시간: 기존 기록에서 확인한 범위

완료된 COLLECT05 개발3+확인 DC_DG1의 **4세션·3,174요청**을 재사용했다. 중단된 다음 세션은 제외하되 과거 실패와 미확인 호출을 지우지 않는다. 각 요청 시작 전에 조회가 끝난 마지막 AP(10초 이내)와 연결했고 누락은 0이었다. 요청의 invocation 시작/끝으로 실제 추론 겹침을 계산했으며 worker/lane 해제까지의 지연은 별도 필드로 남겼다.

세션×원래 블록×task/backend×실제 겹침 유무로 나눈 23개 층에서 AP 범위는 32.5–39.4°C였다. AP·경과시간·겹침 비율(변동할 때)의 기술적 회귀를 계산했다. 조건을 나눠도 AP와 시간의 상관은 최대 |r|=0.886이며, AP–처리시간 조정 연관의 부호는 **양수13/음수10**으로 일관되지 않았다. 탐지 GPU의 연관은 −16.540…+35.747ms/°C였다. [층별 결과](final/temperature_service.csv)는 인과 계수나 스로틀 곡선이 아니다. 모든 연결 표본의 thermal status0도 하드웨어 스로틀 부재 증명이 아니다.

따라서 AP 하나로 결정되는 보편 처리시간 함수를 넣지 않았다. 반대로 온도 영향이 없다고 결론 내리지도 않는다. 이전 부하·시간 순서·클럭/자원 경합을 분리할 통제가 부족하다. 세션 내 3,174요청을 독립 실측 반복으로 취급하지 않는다.

## 완료 범위와 다음 행동 하나

PC에서 준비 반응을 포함한 별도 후보·초기화·연속 전파·평가·분해·지원 차단을 완료했다. 기존 시뮬레이터의 일정/서비스 비교와 보관된 실측 대조는 그대로 사용할 수 있다. 이번 후보는 **사후 조건부 AP 분석 도구**로만 사용하며 임의 도착 에너지/열 정책 비용에는 넣지 않는다. 현 연구의 제한된 결과 본문 완료에는 추가 실측이 필수가 아니다.

**다음 행동은 이 후보의 고정된 초기화·계수에 대한 독립 AP 확인 여부를 결정하는 것 하나다.** 확인이 필요해도 같은 짧은 B2를 반복하지 않는다. 준비 이력이 다른데 초기 AP만 비슷한 경우, ≥55초 부하 전 관측과 등록된 짧은 CG_DC 부하·후기 유휴를 함께 기록해야 E/H 분리가 다른 실행에도 유효한지 판독할 수 있다. 새 기록은 적합에 쓰지 않고 현재 오차·최고·방향 기준으로 보고한다. 이것도 후기 기제의 완전 식별이나 스로틀 검증을 보장하지 않는다. 범용 열 피드백 주장을 하려면 별도의 시간/이력 통제 근거가 필요하다. 이번에는 새 실측 계획·예산·claim을 생성하지 않았으며 반복 수나 정밀도를 근거 없이 정하지 않았다.

## 재현

저장소 루트, Python + NumPy + Matplotlib. 작은 숫자 파생물만으로 재현되며 기기·Android SDK·원본 모델 바이너리가 필요 없다. 출력은 존재하지 않는 경로여야 한다.

```powershell
python -B -m tools.d1_ap_memory_analysis --output output/ap_preparation_memory_check
python -B -m unittest tools.test_d1_ap_preparation_memory tools.test_d1_simulator -v
```

원본으로 파생 입력을 다시 만들 때만 외부 기록이 필요하다.

```powershell
python -B -m tools.d1_ap_memory_analysis --prepare-inputs output/ap_memory_inputs.json --raw-root 'C:/Users/LG/Documents/D1Check_Arrival_Extension'
```

정확한 파일 38개와 해시는 `inputs.json.source_sha256`에 있다. 내부 `docs/` 경로는 저장소 기준, 나머지는 raw-root 기준이다. `energy_ap_idle_response_run_v1`, `energy_ap_cgdc_transfer_run_v2`, `energy_ap_bundle_confirm_run_v2`, `energy_ap_state_run_v5`의 이미 회수한 AP·journal·validated 자료를 사용한다. 원래 freeze 두 파일의 byte 해시 불변도 별도로 검사했다. 현재 Windows 줄끝 환경의 byte SHA이며 줄끝을 바꾼 checkout을 동일 증거로 취급하지 않는다.

실제 CLI의 외부 새 출력과 공유 final의 13개 산출물을 대조했다. 수치10검사 및 기존 시뮬레이터12검사의 **서로 다른 22검사**를 통과했다. 컴파일·가짜 기기 테스트로 실기기 안정성을 주장하는 작업이 아니며 이번 기기 명령·추론·설치·빌드0이다.
