# 기한과 에너지 제약을 가진 공동 롤링 호라이즌

현재 도착한 요청 몇 건의 **순서·CPU/GPU·대기를 함께 계획하고 첫 선택만 실행**하는 산업공학 스케줄러다. 이전 단건 대기/미래 가정과 원 CP-SAT 결과를 보존하고, 계획 전체를 원 열·에너지 모형으로 평가하는 별도 후보를 검증한다. 실제 개선을 전제하지 않는다.

## 결과와 선정

## 계획과 실제 실행의 차이

확인에서 대기0은1,755번 계획·3,393창후보/3,085전체계획 평가, 예측상 선택24번이었다. 실제 resource wait21회·대기0·동시쌍commit0회, 전체 원장은 Band와18/24동일했다.

대기 포함은1,942번 계획·10,282창후보/5,350전체계획 평가, 예측상 선택687번이었다. 실제 추가유휴239회·resource wait27회·동시쌍commit19회, 전체 원장은Band와3/24동일했다. **예측상 선택 횟수는 실제 Band와 다른 첫 행동 횟수가 아니며**, 내부 후속 계획의 이득이 선택돼도 첫 배정이 Band와 같을 수 있다. 계획 전체를 그대로 실행하지 않고 새 사건에서 다시 판단하는 효과도 포함한다.

대기 제거가 열 개선을 만들지 못하고 대기 포함이 조건부 AP를 낮춘 결과로, 이 입력에서는 **실행 시점 분산**이 주요 차이였다. 공동 자원 배정/순서의 보편적 개선은 미입증이다. 평균 창 선별8에 의해 다른 계획이 제외되므로 정확한 전체 최적해나 강화학습보다 좋은 알고리즘이라고 주장하지 않는다.

현재 큐의 완주 계획을 비교해도 아직 도착하지 않은 요청은 모른다. 그 뒤 새 요청이 오고 자원·열 상태가 바뀌면 계획을 다시 세워 예측과 실제 차이가 생긴다. 현재 열모형에는 열에 따른 처리시간/주파수 회복 결합도 없다. 미래 요청을 몰래 넣거나 모형 오차를 없애기 위해 기한/계수를 바꾸지 않았다.

## 현재 권고

롤링 호라이즌의 창·자원·기한·J/AP 목적이 연결된 연구 구현으로 보존한다. **현재 Band 기준을 유지**하고, 낮은 부하/큐의 열 감소와 지속 부하의AP/P95 증가를 함께 발표한다. 실제 운용에서 부하를 알아내는 조건 없이 결과를 보고 workload family별로 좋은 정책만 골라 최종 정책이라고 부르지 않는다.

후속을 검토한다면 평균 창 선별이 제외하는 계획의 영향, 관측 가능한 부하 변화에 따른 계획 안정성, 그리고 실제 제어비용을 먼저 별도 개발 자료에서 확인해야 한다. 새로운 부하 선택 규칙/창 크기/모형/기한을 이번 확인 뒤 조정하지 않았다. 본학습을 추가하기 전에 강한 기준 대비 열/J 성적을 검증한다. 현재 정책을 새로 학습했다고 표기하지 않는다.

## 결과 전 설계 계약

작업 ID `IE-ROLLING-JOINT-01`. A24의 기존 지원 조합인 분류CPU/GPU·탐지CPU, 검증된 분류GPU+탐지CPU 병행만 사용한다. 원 입력·요청 의미·완료량·기한·응답 경계/5단계 lane 해제·초기 측정 preload·W/AP 계수·0…120초 J·35…180초1초 AP grid를 유지한다. 현재 다른 AP 개발 후보는 기존 Arrival 전이/시간상수 식별이 미완료여서 기본에 적용하지 않는다.

계획 창은 EDD 상위4요청이며, CPU 전용 요청 중 최소 응답여유 요청이 창 밖에 있으면 마지막 슬롯을 교체한다. **같은 과업 내부 EDD 순서는 유지**하고 두 과업 간 순서·분류 backend·일반 요청의 최대1개 유휴 구간을 공동 비교한다. 같은 과업도 임의로 재정렬하는 전체 문제나 전역 최적해가 아니다.

| 판단 항목 | 실제 구현 |
|---|---|
| 납기·여유시간 | EDD 후보4, `due−예상응답`의 CPU 전용 요청 포함 |

추가 냉각 credit은 실제 dispatch 사이 누적0.25초이고 첫 대기는 남은 credit 이내다. 계획 내부의 냉각은 양 lane이 비고 현재 가상 대기큐에 긴급 요청이 없을 때만 허용한다. 자원이 점유 중인 것을 응답이나 worker release만으로 비웠다고 처리하지 않는다. 선점·주파수·전력 제한·NPU는 추가하지 않는다.

평가 비용을 제한하려고 최대72개 유한 창 계획을 **평균 문맥/창 내 비용**으로 먼저 정렬한다. 순서는 긴급 실패→일반 실패→J→AP→P95다. 같은 첫 선택의 계획은 최대2개, 상위8계획만 **전체 현재 도착큐+Band suffix**로 원3문맥 평가한다. 창 내 비용은 계산용 선별치이며 전체 J/기한/완료 성적으로 보고하지 않는다.8개 선별 때문에 모든 가능한 스케줄을 최적화했다는 주장은 하지 않는다.

최종 실제 선택은3문맥 모두에서 원 Band 예측 대비 전체 현재 요청의 긴급/일반 실패·긴급 P95·J·공통 최고 AP가 악화하지 않고120초 내 lane 종료가 가능한 계획이어야 한다. 미래 AP 또는 J 차이가 엄격히 줄어야 원 Band에서 벗어난다. 예측 필터는 아직 도착하지 않은 요청의 실제 기한/온도 보장이 아니다. 실제 알려진 도착만 쓰며 이전의 가상 미래 가정을 넣지 않는다.

공유 파일만으로 설정·선정·원 소스 해시·완료량을 다시 확인하는 명령은 `python -B -X utf8 -m tools.d1_rolling_joint_check`다. 기능 검증도 원시 실행 원장 없이 수행할 수 있다.

아래 `prepare/run`은 이번 배치에 실제 사용한 명령 기록이다. 이 실행기는 이전 작업의 로컬 등록·소비 기록과 이번 원장을 필요로 하고 누적 예산·원래 시작 시각을 계승한다. GitHub 파일만 받은 새 폴더에서 본 배치를 자동 재실행하는 명령이 아니며, 완료 폴더에서 다시 `run`하여 완료 기록을 덮어쓰지 않는다. 새 배치가 필요하면 기존 결과를 보존하는 별도 실행 ID와 남은 예산을 먼저 정해야 한다.

```powershell
$env:MKL_THREADING_LAYER='SEQUENTIAL'
python -B -X utf8 -m unittest tools.test_d1_rolling_joint_thermal
output/ie_scheduler_v2_deps/Scripts/python.exe -B -X utf8 -m tools.d1_rolling_joint_study prepare
output/ie_scheduler_v2_deps/Scripts/python.exe -B -X utf8 -m tools.d1_rolling_joint_study run
python -B -X utf8 -m tools.d1_rolling_joint_report
python -B -X utf8 -m tools.d1_rolling_joint_check
```

기존 고립 venv의OR-Tools9.15.6755로 원 CP-SAT을 평가하며 전역 설치/변경을 하지 않는다. 큰 원장/모델/키/APK는 공유물에서 제외하고 설정·seed·정책·hash·CSV·그림·오프라인 화면을 저장한다.
