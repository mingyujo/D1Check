## 어떤 실험인가

- A24, EfficientNet-Lite0 분류 CPU/GPU와 EfficientDet-Lite0 탐지 CPU의 실제 앱 요청 흐름이다. 탐지 GPU는 공통 준비용 runtime이며 본요청 후보가 아니다. NPU·선점·주파수 제어는 추가하지 않았다.
- C252는 분류252건, M128은 CCCDCCCD 요청8건씩16번 몰림, L64는 C/D 교대64건이다. M128의 몰림 사이 간격은 2.032194초이며 요청을 2초마다 한 건씩 보내는 조건이 아니다. 기한 C2.2초/D5초·입력·요청 은행은 같은 부하 묶음 안에서 같다.
- FIFO 직렬 기준, EDD 절대 기한순, 허용 CPU/GPU 병행, 몰림당 최초200ms 대기를 고정 비교했다. 기존 시스템 전체나 학습 정책을 직접 실행한 비교가 아니다.
- 요청 시작은 공통 origin+35초부터, dispatch 종료120초, AP 비교35~180초, 기록210초다. 실제 worker 반환과 완료 응답은 서로 다른 경계다. 각 APP은 네 runtime×2회=8회 공통 준비 추론을 수행했다. 본요청1,144+워밍업64=실제 추론1,208회다.
- 첫 GPU 실제 host는177파일, 후속7군은 원177파일을 그대로 둔179파일이다. 준비 전 냉각만 별도 수정했고 APK·MAIN gate는 그대로다. 군별 실제 source SHA를 기록했으며 모든 군이 동일 전체 host에서 실행됐다고 소급하지 않는다. [동결과 수정 경계](../../../team/a24-measurement-revision02-20261015/dev_window01_continuation_20261015/README.md).

## 해석할 수 있는 차이와 없는 차이

혼합 병행의 통로 동시 점유는14.222초, 앱 inference 호출 구간의 겹침은2.542초였다. 두 값은 서로 다르며 GPU 내부 커널·CPU 연산의 실제 동시 실행 시간을 직접 계측한 값이 아니다. 저부하 병행 군은 실제 겹침0초였다. 따라서 저부하 AP 차이를 병행 효과로 해석하지 않는다.

혼합 대기는 실제16회·합계3.272초를 추가했으며 서비스가 악화됐다. AP 평균 차이 -0.0064℃/최고 -0.1℃만 보고 유리하다고 판정할 수 없다. EDD는 긴급 지연을 줄였지만 일반 기한 준수도 떨어져 단독 우위가 아니다. 혼합 병행은 기한 준수에 유리하지만 최고 AP가 직렬보다0.4℃ 높아 열 감소 후보라고 말할 수 없다.

분류 CPU는 GPU보다 빠르지만 MAIN 직전 AP도 CPU25.9/GPU26.3℃로0.4℃ 차이가 있었다. AP 평균 차이를 자원 선택의 인과적 절감으로 쓰지 않는다. [시작 상태 그림](07_시작상태와_보고온도.png)을 함께 봐야 한다. 모든 온도는 HAL AP 읽기값이며 실제 표면온도·센서 정확도·물리적 갱신 나이가 검증된 값이 아니다. 임의의 AP 한계도 만들지 않았다.

에너지 J는 [전류·전하량 불일치 조사](../energy_readout_audit/README.md)에 따라 미판정이다. 현재 값으로 실제 배터리 절감률을 계산하지 않는다. 한 블록이므로 paired_intervals.csv의 구간은 비어 있으며 독립 반복의 불확실성을 평가하지 못한다. 그림의 군을 잇는 선은 시간 경로나 군 사이 인과관계가 아니라 조건별 값의 표시다.
