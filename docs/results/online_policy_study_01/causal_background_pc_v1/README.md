## 2. 구현한 후보와 정보 경계

`T_candidate = T_frozen + delta`, `delta' = -beta*delta + gamma*r`, `delta(35초)=0`, `gamma≥0`이다. r은 **이미 기록된** 최근10초 기기 전력에서 그 구간의 실제 task 상태 증가분과 부하 전 배경 W를 뺀 잔차다. gamma 단위는 °C/(W·s)이고 전류 raw=mA 해석에 조건부다. r을 외부 앱 전력이나 주변 온도로 해석하지 않는다.

센서 midpoint와 기록 가능 시각을 구분했다. 원본 event `mono_ns`가 발행시각 d 이하인 표본만 사용한다. 마지막 가용 표본의 midpoint에서 정확히10초 이전까지 기존 사다리꼴 적분을 사용하므로 d 직후 표본으로 창 끝을 보간하지 않는다. 샘플 공백2.5초는 기존 적분 기준, 마지막 기록 신선도3초는 사전에 명시한 PC 판독 조건이다. 결측/미지원/음의 추정 배경은 해당 출력을 null로 두고 0으로 채우지 않는다. 실제 앱에 이 입력을 전달하는 경로를 구현·검증한 것은 아니다.

|출력|입력과 경계|해석|
|---|---|---|
|실제 일정 조건부 AP 경로|실제 lane 일정, 기존 부하 전 AP 초기화, 각 시점 전에 얻은 r 갱신|모형 비용 진단. 예정 도착 종단간 예측 아님|

|원래120초 예측|원래 동결 결과 보존|새 rolling 구간 MAE를 전체120초 사전 예측 오차로 바꾸지 않음|

앱이 직접 numeric AP를 읽는다고 가정하지 않았다. 부하 시작 이후 AP는 예측 입력이 아니라 평가 표적이다. Perfetto 자료는 기존 원본에 없고 이번에도 수집하지 않았다. 전력 반영만으로 AP 외란을 모두 예측할 수 있다는 가정을 검증한 결과이지, 새 온라인 정책이나 새 폐루프 일정 생성기 구현 결과가 아니다. forecast의 미래 일정은 원래 PC 결과 그대로이며 현재 큐를 매번 재시뮬레이션하지 않는다.
