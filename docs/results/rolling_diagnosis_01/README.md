# 공동 롤링 계획의 실패 원인·후보 선별 손실 진단

작업 ID `IE-ROLLING-DIAGNOSIS-01`. 사용자 진행 승인에 따라 기존 결과를 보존하고 **지속 부하의 첫 선택과 후속 계획 차이, 평균 선별8개에서 놓친 계획**을 구분한다. 개선을 전제하지 않으며 이번 단계는 새 온라인 정책이나 독립 성능 확인이 아니다.

## 확인한 원인

**선별8개를 먼저 바꿀 근거는 개발 진단에서 나오지 않았다. 대신 후속 계획의 AP 이득이 실제 첫 선택에 남지 않는 반례를 확인했다.** 24회 원행동 재생에서 원장·전이·판단이 모두 정확히 같았고, 선택된 계획1,149개의 원예측값도 복원했다.

| 원자료·정책 | 선택 계획 | 첫 선택 제약 위반 | 큰 창 점검 | 놓친 더 좋은 계획 |
|---|---:|---:|---:|---:|
| 개발 대기0 | 18 | 0 | 0 | 0 |
| 개발0.25초 | 527 | 12 | 24 | 0 |
| 과거 확인 대기0 | 24 | 3 | 0 | 0 |
| 과거 확인0.25초 | 580 | 16 | 24 | 1 |

큰 창은 각 실행의 최초4개만 점검했다. 창이 작았던 대기0에 큰 창 표본0이라는 사실을 전체 선별 손실0으로 해석하지 않는다. 개발의24개 창 밖에서 손실이 없다는 증명도 아니다. 과거 확인의 손실1개는 사후 진단이며, 이를 보고 새 후보의 선별 규칙을 조정하지 않았다.

개발 첫 반례는 seed813010101·평균·61.150702255초의 자원 대기다. 전체 후속 계획의 예상 최고AP는31.406875°C로 Band31.418199°C보다 낮았다. 하지만 첫 자원 대기 뒤 Band로 이어가면31.418490°C로 오히려 높아졌다. 후속 냉각/순서를 실제로 보장하지 않으면서 그 이득을 첫 선택에 전용한 것이다. 다른 실행시간 두 문맥도 같은 위반을 보였다. 숫자는 원 모형의 진단값이며 실제 물리적 온도 차이를 입증하지 않는다.

## 전체 실행에서 악화가 생기는 경로

개발 첫 seed·평균에서 최초 배정 차이는 일반 요청13이었다. Band40.466510042초 → 후보40.645265852초로178.756ms 늦어졌고, 다음 실제 도착도40.645265852초였다. 이후 전체 일정은 분류GPU가12건 늘고 실제 병행이4.236875초 증가했다. 에너지는0.691480J 줄었지만 최고AP는0.089894°C·긴급P95는222.844227ms 증가했다. 이는 결과를 알고 계산한 경로 설명이며 미래 도착을 정책 입력에 넣은 실험이 아니다.

같은 원계수로 점유 상태의 J 기여와 후보 최고 시각의 AP 기여를 분해했다. 위 사례의 J 차이는 분류CPU−1.158687·분류GPU−0.273763·탐지CPU−3.020578·병행+3.761548J의 합이다. 후보 최고89초에서 AP 기여 합은+0.214855°C이며, Band 자체 최고와89초값의 차이−0.124961°C를 더하면 최고값 차이+0.089894°C가 된다. **최고온도 차이는 상태별 기여 합에 시각 정렬 보정까지 포함해야 한다.** 합산 오차1e−8 이내를 확인했으며 이 수치 허용은 분석 회계 검사로만 사용하고 정책/SLA 기준을 완화하지 않는다.

따라서 이득이 보장되지 않는 첫 선택을 막는 검사를 [별도 한 후보](../rolling_prefix_01/README.md)에 추가했다. 위 문제가 지속 부하 악화의 전부라고 단정하지 않으며, 실제 새 도착·재계획으로 생기는 전체 일정 변화는 별도로 평가한다.

## 결과 전 고정한 진단 범위

- 이전 개발·확인의 지속 부하 각6조건 × 대기0/0.25초 두 원정책 =24회 원엔진 재생이다. 원결과의 행동을 그대로 반환하는 진단 실행이며, 원장·전이·판단 전체가 정확히 같아야 인정한다. 이미 소비한 확인은 사후 원인 분석에만 사용한다.
- 각 원실행에서 후보가8개를 넘는 최초4개 계획 시점을 구조 규칙으로 선택한다. 평균 문맥에서 유효한 모든 유한 후보(최대72개)를 현재 전체 큐와 원3문맥으로 평가한다. 원8개 선택과 전체 유한 후보의 최선 점수를 비교한다. 전체 연속시간·미래 요청·전역 최적해는 아니다.
- 선택된 원계획은 전부 점검한다. 전체 후속 계획의 비용/서비스와 실제 첫 단건·동시쌍·대기/자원반환 대기 뒤 Band suffix의 예측을 비교한다. 원3문맥·모든 현재 도착 요청·5단계 lane 점유를 보존한다. 이후 실제 도착은 사후 설명에만 쓰고 예측 입력에 넣지 않는다.
- 이전6,296환경/641학습을 계승한다. 기대24회·이번32회 상한(실패 포함), 등록 후30분·마지막5분 저장이다. 새학습·기기·ADB·NPU·계수적합0이며 기본/strict/experiment_ready=false를 유지한다.
- 원인에 근거한 수정은 별도 소스·입력·예산 계약으로 진행한다. 개발 자료에서만 선택하고, 새 확인 seed815030101/102의 사용 이력을 검사한다. 이번 진단에서 새 확인을 실행하거나 사후 후보를 성능 정책으로 채택하지 않는다.
