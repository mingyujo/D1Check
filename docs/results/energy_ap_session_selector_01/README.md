# 에너지·AP 세션 선택 후보 — 2026-10-05

**구현한 후보는 `ENERGY_AP_SESSION_SELECTOR_PC_V1`이다.** 기한을 지키는 두 고정 실행 방식 중, 명시한 AP 제약을 만족하면서 공통창 에너지가 최소인 방식을 한 번 선택한다. 기존 시간 중심 P를 에너지 최적화 정책으로 바꿔 부르지 않는다. 실기기 정책 우월성이나 새로운 요청별 온라인 스케줄러를 완성한 것은 아니다.

## 정책 정의와 비교 대상

알려진 등록 작업 묶음(192요청·400ms·분류 긴급/탐지 일반 교대)에 대해 부하 전35초까지의 AP 이력·배경 전력을 입력받는다. 이후 실제 AP·전류·완료시각은 사용하지 않는다. 기기·모델·resident·부하를 바꾸지 않으며 모형을 재적합하지 않는다.

1. 기존 CPU 긴급우선 직렬과 B2 분류GPU＋탐지CPU 병행 두 전체 일정을 기존 엔진으로 예측한다.
2. 전체192요청의 긴급1.5초/일반6초 기한, 마지막 lane 해제120초 이내, 예측 AP 상한을 검사한다. 출력준비와 저장완료·worker release·lane 해제를 구분한다.
3. 가능한 방식 중 **공통0–120초 전체 기기 에너지 최소**를 고른다. 동률은 낮은 예측 AP, 그다음 정책 ID 순서다. 불가능하면 null이며 기한/열 조건을 완화하거나 임의 fallback하지 않는다.

AP 조건은 **common35–180초의 1초격자 예측 최고값**이다. 연속 최고온도·안전 보장이 아니며 에너지120초 창과 다르다. 준비 이전이나180초 이후까지의 전체 사용 에너지를 뜻하지 않는다. 시작 AP만을 주변 온도로 가정하지 않는다. AP는 BAT 온도가 아니고 J는 잔량·사용시간이 아니다.

연구용 AP 상한은 **미설정(null)** 으로 유지한다. 현재 계약에 검증된 안전 상한이나 정책 허용 온도가 없으므로 결과를 보고 임의 상한을 채택하지 않았다. 화면/CLI에서 명시적으로 값을 넣으면 참고 규칙의 동작만 확인한다. 정확한 선택 분기점을 계산했지만 권고 온도로 삼지 않는다.

| 정책 | 이번 처리 | 이유 |
|---|---|---|
| CPU_URGENT_ONLINE_V1 | 동일 입력·초기값으로 계산 | 최신 동결 모형의 등록 실행 문맥 |

## 대표 PC 결과

결과를 계산하기 전에 contract.json에 두 행동·목적·창·기한·상한 미설정·동률·미지원 처리를 고정했다. 기존 이미 관측한 초기조건index0 하나에서 두 일정만 계산했다. 새로운 독립 평가나 최적 입력 탐색이 아니다.

| 모형상 결과 | CPU 직렬 | 고정 병행 |
|---|---:|---:|
| 기한 충족 | 192/192 | 192/192 |
| 공통120초 J | 185.389926 | 183.299134 |
| 35–180초 격자 최고 AP °C | 31.716671 | 32.444091 |
| 긴급 P95 ms | 377.955 | 286.608 |

동일 초기조건의 모형상 병행−CPU는 **−2.090792J / +0.727421°C**다. AP 값은 이번1초격자 정의이며 기존 실제 host 표본 시각에서 계산한 최고값과 혼동하지 않는다. 작은 수치 차이를 실기기 유의미한 우열로 사용하지 않는다.

- AP 상한이 약31.716671°C 미만: 모형상 만족 행동 없음.
- 약31.716671°C 이상32.444091°C 미만: CPU만 가능.
- 약32.444091°C 이상: 둘 다 가능하며 J 목적은 병행을 고름.

경계의 정확한 소수는 summary.json을 따른다. 이는 수식의 분기점이며 센서 정밀도나 권장 열 한도가 아니다. **에너지 목적과 열 제약이 실제로 선택을 바꾼다는 구현 근거**지만 후보가 좋은 정적 정책보다 더 낫다는 증거는 아니다. 한 동일 입력·초기조건에서는 결국 두 고정 방식 중 하나와 같으므로 둘 모두를 엄격히 능가할 수도 없다.

## 지원·정확도·실행의 경계

- 부하 전 결정하는 세션 단위 선택이다. 미래 **예정** 도착을 알고 있다. 미래 **실현** 처리시간/AP는 알지 않는다. 임의로 새로 들어오는 요청에 적용하는 온라인 정책이 아니다.
- 기존 `energy-ap-policy-selection` 차단과 strict/default는 수정하지 않았다. 함수는 `model_only_action`만 반환하고 `deployable_action/policy_winner/accuracy_pass=null`, `dispatch_enabled=false`, `experiment_ready=false`다. 새 후보에서 작은 수치 차이를 근거로 이 차단을 우회하지 않는다.
- 과거8세션에서 관측 정책 차이의 부호가 달랐다는 사실과 미래 배경 변동의 검증된 한도 부재를 유지한다. 사후 최대 오차를 새 실행의 보편적 오차 한도로 넣지 않는다.
- A24 온도→처리시간 법칙, 추가 대기·임의 배정·상태 전환, 의사결정 실제 계산시간은 검증되지 않았다. 새 계수·가열·AP 평행이동·S26 전용 계수는 추가하지 않았다.
- 다음 필요한 결정은 **서비스 조건과 별개로 허용할 열 부담을 무엇으로 정의할지 정하는 것**이다. AP 상한의 실제 사용 근거가 없는 동안은 분기·상충만 보고하고 기기 제어를 실행하지 않는다. 같은 실측 반복이나 전체 감사가 다음 단계는 아니다.
