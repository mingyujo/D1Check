# 강화학습 외 요청별 스케줄링 대안 비교

2026-10-05 SCHEDULER-ALTERNATIVES-PC-01. 사용자 요청에 따른 PC 구현·평가이며 기기 작업은 포함하지 않는다. 기존 PPO 결과는 사후 개발 지식으로 사용하고, 새로운60001–60004 개발 / 70001–70008 최종 도착seed를 분리한다. 기존 물리모형·초기조건·서비스문맥·입력생성규칙·기한·120초J/35–180초AP 경계는 유지한다.

## 결론과 권고

**현재 PC 기준 스케줄러는 EFT를 유지한다. 이번에 에너지·열·서비스를 동시에 개선하는 새 우승 정책은 찾지 못했다.** 개발에서 선정된LLF_EFT는 새로운96시험조건 전부에서 EFT와 요청별 배정·시각까지 같았다. 이름만 새 정책으로 바꾸지 않는다. 예약보존backfill은 작은 서비스/J 이득과 열 손해의 선택지로 남기되 자동 적용하지 않는다. 두MPC와PPO도기본정책으로승격하지않는다.

이 결론은 정책 구현/비교 도구를 완성할 수 없다는 뜻이 아니다. **제한된 모형에서 요청별 실행·여러 정책 비교·기한 및 비용 판독은 동작하며 재현 가능하다.** 그러나 “우리 스케줄러가 기한을 지키면서 실제 발열·배터리 소비를 줄였다”는 원래 우월성 주장은 아직 입증되지 않았다. 그 목표의 완료를 문서/PC 테스트 완료로 대신하지 않는다.

### 실패를 알고리즘 이름 탓으로 돌리지 않는 판독

[저장일정 비교](run_v1/mechanism_summary.json): LLF와EFT가96/96에서정확히같았고 두MPC도96/96에서서로같았다. 현재상태와후보집합에서두MPC의목적순서를바꿔도다른행동이선택되지않았다. 이는모든MPC가동일하거나쓸모없다는뜻이아니다.

MPC는각결정의이미도착한큐에대한3문맥가드를지켰지만, 아직도착하지않은작업과반복유예의누적결과는그가드에없다. 대표low/70001/mean의탐지요청은45.848초부터250ms 유예를반복해47.848초에실행됐고 응답2,619.471ms로6초기한안에남았다. 이후일정과겹침이달라지면서전체열은기준보다증가했다. 저장기록의국소→전체차이를확인한것이며 개별원인의효과를분리한인과실험은아니다. 유한180초AP적분은그뒤잔열을비교하지않는다는한계도남는다. 최종결과를본뒤유예제거/가중치수정/추가학습을하지않았다.

### 프로젝트 완성을 막는 구체적 원인

1. **queue/burst의요구자체가현재지원모형에서과부하다.** 탐지작업은CPU만지원한다. 분류와응답후점유를제거한낙관적필요조건에서도queue24/24·burst24/24시험조건의CPU기한창수요가초과했다. 최대초과1.163750초/0.471868초. 어떤스케줄러도이모형과입력그대로모든기한을충족할수없다. 실제폰전체의물리적불가능성을인증한것은아니다. [시간창·요청수·필요량](run_v1/capacity_bounds.csv).
2. **처리가능부하에서도줄일수있는J가작다.** 기한·순서를낙관적으로제거한J하한과EFT의평균차이는low0.259481J,queue0.094134J,burst0.070425J,sustained2.348519J다. 그크기만큼절감할수있다는뜻이아니라 이비용식에서의개선여지상한이다. 기존독립관측오차(−5.541~+8.210J/120초)와동일한의미의통계구간은아니지만, 이작은모형상이득을실제절감으로확정할근거가부족함을보인다.
3. **지원행동이좁다.** 현재동결서비스/증분전력은분류CPU/GPU·탐지CPU·CG_DC만연결된다. 과거고정CC_DG자료에탐지GPU가존재하므로“전혀측정하지않았다”는말은틀리다. 그러나그480초별도프로토콜의계수와요청경계를현재120초모형의빈칸에그대로넣을수는없다. [기존범위](../simulator_workbench_01/README.md), [원자료와전이한계](../../ENERGY_AP_POLICY_MEASUREMENT_AUDIT_20260929.md). DVFS·품질변경·추론생략·전원OFF도현재동일작업근거가없다.

### 완성 경로 하나

**EFT를기준경로로유지하고, 현재부하의용량조건과모형상상충을보이는시뮬레이터를연구본체로사용한다.** low/sustained에서본시험EFT기한은각576/576·4608/4608이며, queue/burst는과부하에서의지각/우선순위연구로분리한다. 이는기존입력을몰래완주입력으로바꾸거나실제기기지원범위를확대하는것이아니다.

원래목표인추가에너지·열개선까지이어가려면, 같은3개cell에알고리즘을계속바꾸기보다 **탐지GPU의기존자료로CPU병목을푸는배정경로를현재모형에연결할수있는지**를다음한작업으로한정한다. 필요한것은exact모델/입력/품질,요청5단계와lane해제,동일resident/계측에서의detGPU·CC_DG·DC_DG비용과전환근거다. 기존자료를먼저재사용하고, 없는필드만부족으로남긴다. 새계수전용/상상한감속/같은B2재실측을기본해법으로삼지않는다. 이확장을이번에구현·검증완료했다고주장하지않으며 새실측/APK/기기계획은만들지않았다.

## 판독과 선택

[고정 계약](contract.json). 4입력×3문맥×4개발seed×8정책384계산 후, 서비스악화조건수→열(최고/면적)악화조건수→J악화조건수→평균J→평균AP면적 순서로 후속후보 하나를 선택한다. 선택은통과나채택이 아니다. 모든후보/코드해시를동결한뒤 최종8seed×4×3×11정책1056계산. 기준CPU/고정split/EFT와 기존PPO3정책을 함께 비교한다. 새학습/결과후튜닝/유리한조건만선택 없음. 본PC배치상한3600초,최대1440계산. 중단되면부분결과를보존하며무한반복하지않는다.

최종에서는 전체/등급별 기한·미완료·조건별P95·J·AP최고/부담을 각각 보고하고, 정확도 허용폭이나 안전온도를 사후 만들지 않는다. J/AP부담의 평균만으로 조건별 손해를 가리지 않는다. policy/trace는모형상계산이며센서샘플/독립기기세션이 아니다. 기존PPO의시험입력을다시미관측시험으로 부르지 않는다.

### 개선 여지의 계산

기한·도착·순서와 겹침의 실현 가능성을 풀고, 전체 작업이120초안에끝나는 경우의 J 낙관하한을 계산한다. 분류GPU 개수0..N별 단독 비용에서 CG+DC 겹침 할인(W)을 가능한최대겹침에 곱해 뺀 최소값이다. 이것은 실행 가능한oracle정책이나 열하한이 아니다. 기준J−하한은 현 비용식에서의 개선 여지 **상한**이며, 달성 가능한 절감 보장이 아니다. 결과가 원모형확인오차보다작은지를 같이읽되 과거오차를미래오차상한으로 취급하지않는다.

### 연구·구현 근거와 미선택 대안

[Receding horizon control 원 저자 설명](https://stanford.edu/~boyd/papers/code_gen_rhc.html)의 반복 예측·첫 제어 원리와 [backfilling 원 연구](https://www.cs.cmu.edu/afs/cs.cmu.edu/Web/People/ekrevat/docs/KrevatMEngThesis.pdf)의 예약보존 아이디어를 적용한 프로젝트 구현이다. 기존논문의보장/속도/산업배포실적을승계하지않는다. 여러문맥의동일첫행동은 [multi-forecast MPC](https://stanford.edu/~boyd/papers/ip_mf_mpc.html)와 원리가관련되나 해당최적화해법의재현은 아니다.

전체미래도착을보는MILP/CP-SAT는 현재실행가능한온라인정책과정보가달라 주정책으로고르지않았다. 작은오프라인최적화는 향후참조용이지온라인우월성증거가 아니다. DVFS/화질티어/추론생략/전원OFF/배치추론은현재동일작업·실측프로필에없어이번에비용을가정하지않는다. S26열→처리율/NPU계수를A24에섞지않는다. 새로운물리계수추정이나실측은필요없고수행하지않는다.

## 계산비용·지원 범위

호스트 callback별 wall time 총합/P95/최대를 직접 기록한다. 이것은 Windows PC 시간이며 폰 실행시간/에너지로 변환하지 않는다. 시뮬레이션은 기존의 추가스케줄러연산비용0 가정을 유지하므로 특히MPC의작은예측이득은그비용을무시한값이다. 미래도착·미래완료·실현문맥은 콜백에 들어가지않는다. 검증된3개 task×backend와CG_DC병행만 사용하며 미지원조합비용을0으로 채우지않는다.

완료범위는 제한모형에서여러방법을구현·평가하고 후속방법/무이득을판정하는것이다. 실제배터리수명/SOC/BAT/기기절감·정책우월성·strict지원승격과구분한다. experiment_ready=false.

상태: 등록된 PC 비교를 완료했고, 실행중 계약/소스 변경 및 결과 후 후보 재조정은 없었다.

## 사후 진단 — 입력의 CPU 필수 수요

대안 개발에서 LLF가 EFT와 같고 MPC의 국소 가드가 미래 도착을 보호하지 못한 것을 본 뒤, 별도원인분해로 `tools/d1_scheduler_capacity.py`를 추가했다. 정책/학습/평가선정에사용하거나시험입력을제거하지않는다. 각 탐지 도착a_i부터탐지기한d_j까지 포함된 CPU필수요청의 `prepare+execution+persist` 합이 창길이를넘으면, 분류와응답후lane점유를모두제거해도 불가능한것이다. 같은탐지상대기한6초의모든연속부분열을검사한다. 통과는충분조건이나실기기확인이아니며, 실패는현재고정서비스모형에서의필요조건위반이다. 기록은 `run_v1/capacity_bounds.csv`에 보존한다.
