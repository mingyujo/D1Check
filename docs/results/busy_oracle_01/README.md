# 실행 중 작업·대기열이 있는 조건부 4요청 비교

작업 ID: `IE-BUSY-ORACLE-01`. 사용자의 “알아서 진행” 승인으로 진행하는 PC 진단이다. 기존 실험·모형·체크포인트·기본 정책을 보존한다.

## 결과와 판단

**새 정책 채택은 없다.** 실행 중 작업과 대기열을 넣어도, 선언한 유한 공간에서 서비스·J/AP 조건을 함께 지키며 J와 최고 AP를 모두 줄이는 일정은 0개였다. 다만 **J 동률로 열만 분산하는 여지**는 확인했다. 이득·지연·행동 범위·모형 오차를 함께 보면 현재 RL 학습량을 바로 늘릴 근거는 부족하다.

각 조건은 고정 이력 11건과 선택된 대기 4건, 총15건이다. 원24건 중 다른9건은 제외했다. 같은 유지 요청을 모든 정책이 처리하므로 조건부 비교 안에서는 작업량이 같지만, 원래 전체 도착열의 완료량·우위로 해석하지 않는다. 4조건은 독립 도착 seed 2개에서 파생된 **이미 본** 자료이며 신뢰구간·독립 확인을 주장하지 않는다.

이4개 최소 AP 일정은 **모두 현재 RL의0.25초 냉각 credit 밖**에 있다. 다른 열 개선 일정까지 전부 불가능하다고 증명한 것은 아니다. 선택된 최소 AP 일정에는 일반 평균 비악화도 없다. 다른 열 개선 일정 전체의 일반 평균 비악화 존재 여부를 인증한 것으로 확대하지 않는다.

고정 prefix의 에너지/병행을 보존하고 앞으로의 시간·기한·AP를 완화한 별도 **낙관적 J 하한**도 계산했다. Band와의 차이는 약0.000000412~0.000000414J이며 ns 반올림을 안전하게 포괄한 여유가 대부분이다. 이 작은 조건부 문제의 **현재 모형에서는** 단순히 더 학습해 큰 J 감소를 찾을 공간이 사실상 없다는 근거다. 전체192요청·실기기·다른 모형의 최적성은 아니다. 현재 모형은 실행시간을 과업/backend/측정 문맥으로 고정하고 열에 따른 주파수·속도 회복은 연결하지 않는다. 긴 대기로 현실의 throttling을 피하는 효과를 여기서 자동 입증할 수 없다.

mean 최소 J/AP는 같은 일정이었다. 그 일정을 같은 mean prefix로 short/long 비용에서 재생하고 **같은 유지 요청·prefix·문맥의 Band**와 비교했다. 4역할 재생은 서로 다른2문맥의 같은 일정 중복이며 독립 반복4회가 아니다. 모두15/15·절대 기한 실패0이지만, short에서는 긴급 P95 +15.446742ms/J +0.000215492로 비악화 실패, long에서는 서비스·J/AP 비악화다. 평균 시각에 맞춘 고정 대기가 짧은 실제 실행에서도 응답을 악화시킬 수 있다. 이 결과는 처리시간 문맥 교차이며 열 오차→처리시간 결합 강건성은 미지원이다.

AP는 실측 기반 **모형 채널**이며 최고 표면온도가 아니다. 다른 확인 프로토콜의 J MAE 약3.913J/AP MAE0.260°C와 같은 차원으로 작은 효과임을 설명할 수 있지만, 그 오차를 이번 조건의 보편 허용폭/유의성 한계로 전용하지 않는다. AP의 안전 한도·초과 시간은 근거가 없어 `null`을 유지한다. 원 에너지0…120초는 유휴·대기 비용을 포함하지만 host 판단의 폰 에너지/실제 제어 비용은 측정되지 않았다.

PC 판단 시간 합계(4조건)는 Band0.00737s·리스트0.82244s·CP-SAT8.03588s다. CP-SAT 최초 판단 최대3.868s에는 지연 import 등 준비 비용도 포함된다. solver의0.25초 제한은 전체 callback의 시간 제한이 아니며, 이 시간을 폰의 지연이나 J로 환산하지 않는다. 계산 비용을 반영한 실제 배포 SLA는 미판정이다.

- 새 실측은 이 작업에서 실행하지 않았다. 별도 진행 중 계수 식별 작업은 보존하며 그 결과를 원 모형에 자동 적용하지 않는다. GPU 단독 전력·잔열/회복과 처리시간의 관계·폰 판단 비용이 확보되지 않으면 해당 물리적 효과 판정은 보류한다.

## 결과 전 고정 계약

- 기존 완료된 48개 Band 평가 원장의 도착/dispatch/lane 해제 경계를 시간순으로 조사한다. 같은 시각 dispatch **직전**, 실행 중 작업이 있고 분류·탐지가 각각 2건 이상 대기하는 첫 시점을 선택한다. 각 과업에서 EDD 상위 2건을 고른다. 정책 비용이나 승패는 선택에 사용하지 않는다. 구조 조사에서 4조건이 적격이고 44조건은 해당 대기열이 없어 제외된다. 원 평가 자료를 이미 소비했으므로 독립 확인 자료가 아니다.
- 그 시점 전에 dispatch한 **모든** 요청과 선택된 4요청을 유지한다. 다른 대기·미래 요청은 명시적으로 제외한 조건부 작은 문제다. 전 정책의 요청 집합은 같지만 전체 원 trace 처리량·최종 정책 우열을 판정하는 실험은 아니다.
- 고정 prefix의 실제 시작시각을 원 엔진에서 재생한다. 초기 실측 preload부터 공통 120초 기기 전체 J, 35…180초 1초 간격 AP 모형을 계산하고 snapshot에서 열 이력을 초기화하지 않는다. 실행 중 작업은 중단하지 않으며 5단계 lane 해제까지 점유한다.
- 하위 정책은 원 Band/Triton 적용 규칙, EDD+ECT, 응답 여유시간 ECT, CPU 전용 요청 보호, 열·에너지 리스트, Rolling Horizon CP-SAT/AP 필터의 7개다. 온라인 정책에는 현재 도착 큐·공개 lane·과거 이력만 전달한다.
- 오프라인 참고는 선택된 4요청의 순서·CPU/GPU·시작시각을 전수 확인한다. snapshot + 100ms × 0…30에 해당 요청의 Band/Triton 시작시각을 더한 유한 공간이다. 미래 실현 문맥을 아는 참고이며 연속시간·온라인 전역 최적해가 아니다. 현재 RL의 냉각 credit 0.25초와 3초 탐색대기는 구분한다.
- 양쪽 조건부 기준 대비 전량 완료·긴급/일반 기한 실패·긴급 P95·J·최고 AP 비악화 뒤 엄격한 J/AP 공동감소를 센다. 일반 평균 비악화는 추가 진단이다. 안전 온도 한계를 새로 만들지 않는다.
- 추가 환경 최대80회, 본학습0회, 등록 후 최대1시간·마지막5분 저장. 기존 누적5,255환경/641학습을 계승한다. 최대54회 예상과 오류 여유26회이며 실패도 차감한다. 기기/ADB/NPU0, 원계수/strict/experiment_ready=false 유지.
- mean 최적 일정을 short/long 문맥에서 고정 재생하고 **같은 prefix·요청·문맥의 Band**와 비교한다. 실제 lane 가용성은 다시 확인한다. 열 오차를 처리속도로 바꾸는 미측정 계수는 넣지 않는다.
- 대표는 기존 source index6(812020001/burst/mean)으로 고정한다. 전체 적격·제외 목록과 전수 인증을 함께 보존한다.

## 재현

연결부 오류 수정: 첫 Triton 환경에서 `release identity`가 발생했다. Band가 이미 배정한 CPU 분류 작업을 Triton의 고정 GPU 분류/CPU 탐지 인스턴스로 오인한 원인이다. prefix 작업은 Triton이 새로 배정한 작업의 해제 기록에서 제외하고, 새 인스턴스 배정은 **실제 lane/호환성 guard** 통과까지 dispatch를 보류한다. AP 이력은 실제 전체 점유로 갱신한다. 따라서 여기의 Triton은 외부 실행 이력을 인계받는 제한적 tail 적용이며 원제품 전체 실행이 아니다. 실패 환경도 차감하고 source 개정·재시도·원 등록 clock을 보존한다. SLA/지원/계수/탐색영역은 변경하지 않는다.

```powershell
$env:MKL_THREADING_LAYER='SEQUENTIAL'
python -B -X utf8 -m unittest tools.test_d1_busy_schedule_oracle
output/ie_scheduler_v2_deps/Scripts/python.exe -B -X utf8 -m tools.d1_busy_oracle_study prepare
output/ie_scheduler_v2_deps/Scripts/python.exe -B -X utf8 -m tools.d1_busy_oracle_study run
python -B -X utf8 -m tools.d1_busy_oracle_report
python -B -X utf8 -m tools.d1_busy_oracle_check
python -B -X utf8 -m tools.d1_busy_oracle_reproduce
```

등록·실행 clock과 receipt는 원 실행을 보존한다. 종료된 실행의 시간 제한을 초기화해 재학습하지 않는다. 작은 공유 결과와 원본 대용량 실행물은 구분한다.

원본 환경 결과는 저장소에서 제외된 로컬 출력에 보존된다. 공유 번들의 입력·원장·조건별 인증·source hash는 재검토 가능하다. 새 실행은 같은 명령을 아무 출력 경로에 덮어쓰는 대신 별도 ID·예산·clock을 등록해야 한다.

`check`는 표준 라이브러리만 쓰는 공유물 검증이고, `reproduce`는 NumPy와 공유 입력·모형으로 같은 유한 전수 공간을 다시 계산한다. 환경·학습·기기 실행0이며 원본 output이 없는 clone에서도 인증 수치를 재현한다. `prepare/run/report`는 기존 PC 원본·로컬 실행 기록이 있는 작업 공간에서 원 실행을 확인하는 명령이다. 원 엔진의 새 정책 비교를 시작하는 명령과 순수 인증 재계산을 구분한다.
