# 조건을 바꾸며 찾는 에너지·AP 스케줄링

후속 [지도학습 선택기](../supervised_selector_01/README.md)는 아래 선언형 조건표와 별도다. 이전 요청 이력으로 자동 선택하지만 정상 부하분포 가정과 미학습 조합의 실패가 남으며 기존 결과를 대체하지 않는다.

## 완료 결과와 사용할 방식

**고정 병행 대비 에너지·최고 AP·AP 면적을 함께 줄이는 조건을 찾았다. 그러나 EFT 대비 모든 지표를 동시에 개선하는 만능 정책을 찾은 것은 아니다.** 단일 우승 정책 대신 서비스 적격 조건에서 **에너지 우선/최고 AP 우선**을 명시적으로 선택하는 PC 인터페이스를 구현했다. [`choose(selection, envelope, mode)`](../../../tools/d1_scheduler_condition_selector.py)는 사전에 알려진 입력 사양과 목적을 받으며 미등록/개발 부적격 조건을 거절한다. 미래 도착 목록을 보고 온라인 정책을 선택하는 기능이 아니고, 부하 분류를 자동 학습한 것도 아니다.

- [전체 27조건 지도](run_v2/index.html), [목적별 선택기의 새 seed 확인](selector_v3/index.html), [모든 기준별 차이 CSV](run_v2/condition_support.csv), [기한 적격 비용 절충선](run_v2/feasible_frontiers.csv).
- 본 탐색3,240회/526.967초: 개발1,296→기존 EFT 공동비악화 선택 규칙 동결→확인1,944. 이 규칙은 27조건 모두 EFT를 유지했다. 이를 확인한 뒤 목적별 선택기를 **사후 설계**했다. 새 선택기에는 개발81001/81002 자료만 사용했다.
- 목적별 선택기는 개발에서 전체 기한을 만족한 후보 중 에너지 우선은 평균J→최고AP, 열 우선은 평균최고AP→AP면적→J로 고른다. 임의 가중치·온도 안전 상한은 만들지 않는다. 10/27조건은 개발 적격 정책이 없어 선택 불가다.
- [수정 선택기 동결](selector_v3/freeze_before_confirmation.json) 후 새 seed112001–112003 및 3처리 문맥을 사용했다. 중복 정책 재생을 공유해 **738회/57.237초**, 선택된17조건×9문맥에서 **각 모드 7,344/7,344요청 기한 충족**. 고정 병행 대비 J·최고AP·AP면적이 9문맥 전부 낮은 조건: 에너지 모드10/17, 열 모드9/17. 다른 조건과 실패를 삭제하지 않았다. EFT 대비 공동 개선0이다.
- 이전 selector_v2는747회 계산을 보존했다. 개발의7.27e-9J 반올림 차이가 JIT 정책 선택을 좌우하는 결함을 발견해 순위 계산만1e-6해상도로 동률 처리했다. 이는 실기기 오차 허용폭이 아니다. 해당 수정 후 결과에 맞춘 매개변수 변경 없이 별도 새 seed를 사용했다. 최초selector_v1은 상대/절대 경로 처리 오류로 계산0회이며 기록을 보존했다.
- 실제 PC 계산 총 **4,773회 = 본3,240 + 첫 CSV 실패 전48 + 수치 보정 전747 + 최종738**. 과거 전체 배치/PPO재학습/기기 실행은0. 현재 본/최종 확인 **3,978 ledger·190,944 요청**을 독립 재집계했다. J 차이 최대2.8422e-14J, 원동결 파일 해시 불변, 테스트32건 통과.

### 대표 조건: 평균0.45초·분류75%·4요청 군집

새 확인3seed×3처리 문맥 평균 차이이다. 모든 방식432/432요청 기한 충족. P95는 문맥별 P95의 평균이며 pooled P95가 아니다. 원시 온도 단위는 AP이고 BAT/피부 온도가 아니다.

| 선택 방식 | 고정 병행 대비 J/120초 | 최고 AP 차이 | AP면적 차이 °C·s | 긴급P95 차이 | 일반 평균응답 차이 |
|---|---:|---:|---:|---:|---:|
| 에너지 우선 → PAIR_COALESCE | −0.970805 | −0.082048°C | −3.400566 | −290.427ms | −92.392ms |
| 열 우선 → TOKEN_CPU | −0.392547 | −0.520191°C | −15.289700 | −180.839ms | +905.141ms |

강한 EFT 기준으로 바꾸면 에너지 모드는 **−0.342211J / 최고AP+0.305141°C / 긴급P95+167.173ms**, 열 모드는 **+0.236047J / 최고AP−0.133001°C / 긴급P95+276.762ms**다. 이 차이가 에너지와 열 사이의 실제 모형상 상충이다. 두 모드 중 하나가 항상 더 좋다고 쓰지 않는다. 고정병행은 D1의 연구 기준이며 상용 Android/OS 스케줄러의 동일 구현이 아니다.

17조건 중 고정병행 대비 공동 절감이 확인된 조건의 평균 차이 범위는 에너지 모드 **−1.7133~−0.2100J / −0.4210~−0.0207°C**, 열 모드 **−1.7133~−0.1540J / −0.5202~−0.0457°C**이다. 이 범위는 유효 조건을 명시한 기술 요약이며 모든27조건 평균이 아니다. 전체 조건 CSV와 기한 미적격 분모를 같이 제공한다.

### 효과가 없는 경우·종료 판단

- 빠른0.15초 도착은 이번 모든 작업비율/군집 조건에서 개발 적격 정책이 없다. 첫 확인243입력 중54개는 탐지CPU의 낙관적인 필수 작업량만으로도 기한창을 넘는다. 필수 수요 검사를 통과했다는 것만으로 스케줄 가능성을 보장하지 않는다.
- 1.2초·분류75%·군집1처럼 CPU가 충분히 비어 있는 조건에서는 EFT/CPU가 같아 추가 제어의 이득이 없고, 불필요한 대기는 응답만 늦출 수 있다.
- 0.45초·분류50%·군집4에서 token/JIT 평탄화는 첫 확인의 기한을 놓쳤다. 에너지나 AP가 낮아도 적격 정책으로 채택하지 않는다.
- [330초까지의 냉각 꼬리 확인](run_v2/tail_sensitivity.csv)은 사후 경계 점검이다. 대표 조건의35–180초 AP면적을330초까지 늘려도 수치가 같았다. 단, 면적은 유효 기준 위 양의 부분만 집계하므로 이것이 실제 물리적 총열량/완전 평형 증명은 아니다. 120초 에너지는 작업을 끝낸 같은 창을 유지했다.
- 현재 가능한 결과는 **조건·목적별 PC 비용 절충과 후보 선택**이다. 새로운 입력의 독립 실기기 예측 정확도·실제 절감·미지원 상태·정책 우월성을 완료 처리하지 않는다. 특히 약0.1~1.7J와0.02~0.52°C의 모형 차이를 기기에서 구분할 수 있는지는 별도다. 기존 한 세션의 오차를 보편 오차 한도로 사용하지 않는다.
- 권고: 효과를 찾은 이 대표 조건에서 두 모드와 EFT/고정병행의 차이를 검증 대상으로 특정한다. 이번 작업에서는 추가 기기 계획·실측을 만들지 않았다. 다시 전체 자료 감사나 알고리즘 무한 탐색으로 돌리지 않는다.

## 연구 질문과 사전 고정

사용자 지시에 따라 기존 네 입력의 순위 비교에서 **어떤 부하에서 어떤 방식이 유효한가**로 PC 탐색 범위를 확장했다. 기존 [비RL 비교](../scheduler_alternatives_01/README.md)는 보존하며, 물리 모형을 재적합하거나 미측정 자원의 비용을 추가하지 않는다. 기준 정책 하나에 대한 실패로 다른 부하에서도 불가능하다고 단정하지 않는다.

- 입력: 48요청, 분류 비중 25/50/75%, 평균 예정 간격 0.15/0.45/1.2초, 군집 크기 1/4/8의 **전체 27조합**. 군집 내 간격 30ms, 군집 사이 간격은 전체 평균 간격이 같도록 구성하며 ±5% jitter를 사전 부여한다. 각 정책에 동일한 도착·작업·기한을 준다. 완료를 보고 도착을 늦추지 않는다.
- 분류 긴급 1.5초·탐지 일반 6초 기한은 그대로다. 2초의 최대 추가 대기와 보수적 현재 큐 여유를 사용하는 후보를 평가한다. 기한 내 응답 지연을 무조건 실패로 보지 않으며 P95 손해를 같이 보고한다. 기한 숫자를 결과에 맞춰 완화하지 않는다.
- 개발 seed 81001/81002, 별도 확인 seed 91001/91002/91003. 처리시간은 기존 개발 평균·짧은·긴 문맥 3개. 8정책 × 27조건 × 5seed × 3문맥 = 3,240 계산. 새 seed 확인은 독립 **실기기** 검증이 아니다.
- 에너지 0–120초, AP 35–180초, 동일 초기 입력0·resident 구성·작업 분모. 미래 도착·실현 처리시간·미래 AP를 정책에 제공하지 않는다. 조건별 부하 사양을 미리 아는 세션 선택기와 요청별 온라인 결정을 구분한다.
- 조건별 선택 규칙은 개발에서만 정한다. 모든 개발 문맥에서 전 요청 기한 충족, EFT 대비 J·최고 AP·AP 면적 비악화이며 적어도 한 항목 개선한 후보 중 평균 J→AP 면적 순으로 선택, 없으면 EFT 유지. 확인에서 규칙을 수정하지 않는다.
- 모든 정책을 CPU·고정 split·EFT 각각에 비교한다. 낮은 기준만 골라 보편적 우월성을 주장하지 않는다. 1e-8 비교값은 부동소수 판정용으로, 실기기 정확도·효과 합격선이 아니다.

| 구현 ID | 원리와 이번 적용 | 필수 한계 |
|---|---|---|
| TOKEN_EFT_V1 | 네트워크 token bucket처럼 추정 lane 작업량을 0.65초 용량/초당0.65초 보충으로 조절하고 EFT 배정 | DVFS·실제 전력 제어 아님; 현재 큐 기한이 급하면 토큰을 빌려 서비스 우선 |

| JIT_CPU_V1 | 실시간 latest-start 원리를 적용해 현재 큐의 긴 처리시간 문맥 여유 90% 범위에서 CPU 작업을 유예 | 미래 요청을 모르는 제한적 휴리스틱, 전역 기한 보장 아님 |

기존 CPU_REFERENCE/SPLIT_REFERENCE/EFT_REFERENCE와 슈퍼컴퓨터 예약 보존 방식의 RESERVED_BACKFILL_V1을 재사용한다. 이전 MPC·PPO 전체 배치를 다시 돌리지 않는다. 새로운 정책의 source와 실행 입력은 [사전 등록](run_v2/preregistered.json)에 고정한다.

원리 근거: [IETF RFC3290 §5 및 Appendix A: shaping/token bucket](https://www.rfc-editor.org/rfc/rfc3290), [CMU Krevat: backfill 예약](https://www.cs.cmu.edu/~ekrevat/docs/KrevatMEngThesis.pdf), [Boyd 외: 열 제약 processor control](https://www.web.stanford.edu/~boyd/papers/proc_control_temp.html). 마지막 연구의 주파수/전압 제어는 현재 자료가 지원하지 않아 구현하지 않는다. 이식한 것은 제어 원리이며 원 논문 알고리즘 전체·현업 Android 정책의 재현은 아니다.

## 실행·검증 경계

- 최초 run_v1은 48개 개발 계산 뒤 서로 다른 계측 열의 CSV 저장 오류로 중단했다. 해당 ledger를 보존했다. 합집합 열 저장으로 수정하고 회귀 검사를 추가했다. 모형·정책·입력·선택 규칙을 성능 결과에 맞춰 변경하지 않았다. run_v2는 새 출력 폴더에서 시작한다.
- 실행 중 원 코드·동결 파일 해시를 대조하며 결과별 예정 도착, 분모, lane 해제, 단계 순서를 검사한다. 전체 과정은 PC 전용이며 ADB/APK/실측/기기 계획/claim0이다.
- 현재 요청별 처리시간을 새 혼합 입력에 적용하는 것은 전이 가정이다. strict 지원이 자동 확대되지 않는다. AP→처리시간, 스로틀, 전원 차단, 다른 기기 계수를 새로 만들지 않는다.
- 모델 AP는 BAT/피부/안전 온도가 아니다. raw=mA 해석 조건과 절대 J 정확도 미인증을 유지한다. 제어기 실행 비용은 기존과 같이0 가정이며 작은 J 차이를 실제 절감으로 확정하지 않는다.
- AP 면적은 유효 유휴 기준 위의 **35–180초 한정** °C·s이며 물리적인 총발열량이 아니다. 작업 지연으로 창 밖에 옮겨진 열을 제거된 열로 해석하지 않는다. 최고 AP·응답·완료 시각과 같이 읽는다.
