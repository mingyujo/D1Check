# 정책 예측 연결 — 원래 목표는 진행 중

등록된 실제 일정의 AP 재생은 하위 작업 완료이며 연구 전체 완료가 아니다. 사용자는 자원 배정·시작 시점 결정으로 응답·완료 요구를 지키면서 기기 전체 J와 AP 부담을 줄일 수 있는 조건을 밝히는 원래 목표를 재확인했다. 과거 ‘팀 공유로 마무리’ 권고는 이 목표의 종료 기준으로 사용하지 않는다.

## 이번에 구현한 연결

`tools.d1_policy_prediction_bridge`는 기존 도착 엔진과 CAL03 시간 자료, 원래 8상태 W식, 변경 없는 M0를 연결한다. queue201 24요청에 CPU_URGENT/B2/B3와 단일 200ms 시작 대기 B2를 계산했다. 200ms는 기존 입력 간격 하나를 사용한 **대기 연결 검사**이며 열 이득을 얻도록 튜닝한 값도, 다음 실측 권고 입력도 아니다. 전체 배치·새 적합은 없다.

- 사전 PC 계약은 `contract.json`, 결과는 [pc01/index.html](pc01/index.html), 수치는 `pc01/summary.csv`다. 계산 가능한 것과 지원/독립 검증/정책 차이 판정을 분리한다.
- 준비 AP는 등록 확인의 공통+35초 **전** 관측만 사용한다. 이후 AP/전류와 실제 실행 일정은 전달하지 않는다. 예정 도착은 공통+35초부터이며 대기는 dispatch만 지연하고 도착·마감·전체24 분모를 바꾸지 않는다.
- 일정은 과거 calibration 벡터와 seed201·기존 간섭1.5 가정에서 새로 생성한다. 계측 기반 시간 입력이지만 병행 간섭과 온라인 실행은 독립 검증되지 않았다.
- AP는 +35..180초 계산, J는 전체0..120초와 예측 생성 이후35..120초를 각각 표시한다. 전반35초는 이미 지난 유휴 구간이므로 전체120초를 세션 전 완전 사전 예측이라고 하지 않는다. 전력에 idle을 lane마다 다시 더하지 않는다.
- 없는 상태 계수는 해당 출력을 null 처리하고, 미완료 lane이 있으면 공통창 비용을 제공하지 않는다. 코드가 값을 반환해도 짧은 전환/대기/새 배정의 strict 검증을 통과했다는 뜻이 아니다.
- 같은 준비 이력을 반사실적 정책에 주는 계산이다. 화면은 새 실측–예측 확인 그림이 아니며 J/AP 우열·정확도 PASS를 부여하지 않는다. 열→처리시간 연결을 새로 가정하지 않는다.

```powershell
python -B -m tools.d1_policy_prediction_bridge --output output/policy_bridge_fresh
python -B -m unittest tools.test_d1_policy_prediction_bridge -v
```

공유 파일과 Python/NumPy만 필요하다. 기존 모형·기기 실행기·APK를 수정하지 않았다. `contract.json`의 W는 원래 freeze SHA `35ed6987b1fc09789284018f8502107eaf4e3125373651a01e3a08d427034c54`에서 그대로 추출했다. M0/원래 분석 코드의 등록 byte hash를 검증한다.

## 원래 목표의 완료 기준

| 필수 연결 | 현재 상태 | 완료 판독 |
|---|---|---|
| 예정 도착＋자원/대기 결정→일정·응답→J/AP | PC 연결 구현, 외삽 진단 가능 | 미래 실제 완료시각/AP/전류 없이 계산, 모든 요청·공통창 분모 보존, 정보 누설/회계 검사 통과 |
| 짧은 정책 일정의 기기 전체 전력 | 원래 W식 오차·유휴 변동 남음 | **기존 개발6의 전력과 이미 확보한 CPU/B2 기록을 사용해** 배경과 작업 증분을 구분할 수 있는지 판정하고, 필요 계수만 별도 개발본에서 식별. 기존 후보/동결본은 보존. 수치 rank만으로 실용 식별을 주장하지 않음 |
| 예정 일정의 독립 확인 | 이전 결과는 실제 일정에 조건부·기록 재생 | 모형/정책/입력/초기정보를 사전 동결한 뒤, 실제 일정·응답·공통창 J/AP의 오차를 같은 기록으로 판독. 일정 오차와 비용 모형 오차를 따로 산출 |
| 정책 판단 | 새 정책의 비용 우열 미판정 | 서비스 guard·전체 분모를 먼저 검사하고 정책 차이와 예측 오차·세션 차이를 함께 비교. 개선/상충/구분 불가를 보고하며 차이가 작으면 우월성을 주장하지 않음 |

단순 정책이 충분하거나 대기 이득이 서비스 손실보다 작다는 결과도 원래 연구 결과다. 모든 온도·기기·부하의 물리 모형 완전 식별, RL, OS 열 보호 제거를 완료 요건에 추가하지 않는다. 반대로 위 독립 정책 평가 전에 ‘제한 도구 완성’으로 연구를 종료하지 않는다. 정확도 허용폭/유의성/실측 반복수를 결과에 맞춰 만들지 않는다.

**다음 실제 작업:** 이미 있는 개발6의 전류·전압·무부하 C와 CPU/B2 자료로 정책 비용 식별을 진행한다. 이전 단순 가산 후보를 다시 채택하거나 같은 AP 진단을 반복하지 않는다. 식별되지 않는 경우에만 해당 자원/부하 이력과 동결 후 정책 확인을 묶은 한 실행 설계를 확정한다. 이번에는 새 실행 계획·claim·ADB 호출이 없다.

이번 PC6검사는 실제 engine admission·도착/마감 보존, whole-device 적분, 미래 관측 배제, 출력별 미지원/null, 미완료 차단, 네 사례 실제 entry/export를 통과했다. 최초 테스트의 ‘대기하면 urgent P95 악화’ 가정과 ‘정확히200ms 지연’ 가정은 잘못됐다. 실제로 GPU urgent가 대기 해제 시 우선 dispatch되며 기존 scheduler overhead300us가 추가될 수 있다. 구현을 결과에 맞추지 않고 테스트를 올바른 dispatch 하한·기존 overhead·분모 계약으로 수정했다. 실제 결과는 원문 CSV에 보존한다.
