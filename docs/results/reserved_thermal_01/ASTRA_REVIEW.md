# 기한 예약과 열 분산 규칙 구현 검토

2026-10-08 KST · RESERVED-THERMAL-01 · 단계2 성능 실행 전 검토

**판정은 REVISE_BEFORE_RUN이다. 현재 구현을 그대로 성능 배치에 넣지 않는다.** 최초 완료 예약과 누적 에너지 식은 보수적인 1차 가설로 유지한다. Sol이 아래 일정 보존·장부·등록·검증을 보완하고 pilot 실행기까지 준비한 뒤, Astra가 변경 코드와 해시를 확인한다. 그 다음 Sol이 기존 48조건 pilot을 실행한다. RL 진행 판정은 pilot 결과를 본 뒤 별도로 한다.

이는 정책 우수성의 부정이나 확인이 아니다. 현재 21개 검증 기록은 기본 경계 확인에 유용하지만, 후속 일정 유지와 최종 에너지 제약까지 입증하지 않는다. 이번 검토는 코드 읽기, 저장된 fixture 재계산, 환경을 시작하지 않는 직접 일정 투영으로 수행했다. 추가 환경·학습·기기 실행은 모두 0이다.

## 수정이 필요한 부분

### 저장된 후속 일정의 시각이 유지되지 않는다

**P1 — 계획의 핵심 차이가 아직 완전히 구현되지 않았다.** `d1_reserved_thermal.py`의 `_retained_sequence`는 첫 작업의 지연만 남기고 이후 작업의 지연을 0으로 만든다. 상속한 `d1_pareto_beam.py`의 `finish_plan`은 이후 작업을 가능한 이른 시각에 다시 배치한다. 저장된 배정·순서는 일부 보존하지만, 열 분산을 위해 둔 시간 간격을 보존하는 경로가 아니다.

직접 투영 반례에서 첫 탐지 작업은 35.100000초부터 35.721737초까지, 두 번째는 35.971737초부터 시작하도록 저장했다. 재구성 결과 두 번째가 35.721737초에 시작하여 **0.25초 간격이 사라졌다**. 이는 지원된 탐지 CPU 비용을 사용한 인공적인 일정 보존 검사이며, 현 성능 배치에서 같은 간격을 선택했다는 증거는 아니다.

수정 계약:

- 새 adapter 안에 저장 일정 전용 재구성 경로를 둔다. 기존 엔진과 기존 beam 구현은 바꾸지 않는다.
- 미실행 요청마다 backend·기존 순서·절대 `not_before_i = saved_start_i`를 보존한다. 현재 시각과 실제 사용 중 lane을 반영한 배치는 `start_i >= max(now, not_before_i)`를 만족해야 한다. 충돌 때문에 늦어진 경우에도 원래 완료 cap 검사를 다시 수행한다.
- 같은 현재 상태에서 입력 변화가 없으면 저장 일정의 아직 유효한 시각·비용을 재현해야 한다. 이미 지난 시각이나 관측 overrun 때문에 불가능하면 이유를 기록한다. 조용히 ASAP 일정으로 바꾼 뒤 ‘저장 일정 유지’라고 부르지 않는다.
- 저장 일정은 후보 하나다. 새 탐색 후보가 더 나아 선택되는 것은 허용한다. 예약 cap과 에너지 장부는 새 후보 선택으로 갱신하지 않는다.
- 기존 WAIT 0.25초/도착 후 2초 제한과 aging 규칙을 확대하지 않는다. 재판단을 위한 짧은 wake-up과 저장된 목표 시작시각을 분리하고, 매 callback에서 목표시각을 뒤로 밀지 않는다. 제한 밖이면 이유를 남기고 다른 후보 또는 서비스 우선 fallback을 사용한다.

### 예산 초과와 예약 파손의 원인이 충분히 구분되지 않는다

**P1 — 현재 행만으로 누적 제약의 성공 여부를 평가할 수 없다.** `no_admitted_calendar`는 탐색 후보가 없다는 뜻인데 모두 예약 파손으로 합산한다. 에너지 제약만 실패하면 `ids=[]`가 되어 원인을 잃는다. 실제 응답 cap 초과, 예측 overrun, 제한 탐색에서 적격 후보를 못 찾은 경우도 서로 다른 사건이다.

저장된 `00011_overrun` fixture에서 공통창 총에너지는 134.64616630884416 J, 마지막 예산은 134.64519010369543 J였다. 차이 **+0.00097620514873 J**는 기존 수치 epsilon보다 크지만 최종 행에 예산·차이·충족 여부가 없다. 이 작은 수치는 모형 내부 장부 검증용이며 실기기 에너지 차이의 의미를 주장하지 않는다. 기존 장부의 실패를 숨겼다는 뜻도 아니다. 원 기록에는 fallback이 남아 있다.

수정 계약:

- `reservation_predicted_violation`, `reservation_observed_violation`, `observed_overrun`, `energy_budget_rejection`, `search_exhausted_no_admitted`, `completion_window_unavailable`를 구분한다. 후보 탈락·callback fallback·요청별 실제 cap 위반을 별도 분모로 집계한다. 원래 서비스 기한 위반과 내부 cap 위반도 분리한다.
- 최종 행에 `final_budget_j`, `final_common_window_j`, `final_budget_margin_j = B_final - J_0_120`, `final_budget_satisfied`, 비용 계산 가능 여부를 저장한다. 미완료면 부분작업 에너지임을 표시하고 서비스 적격으로 승격하지 않는다.
- 큐가 비어 결정 callback이 끝나도 관측·최종 감사에서 남은 비용과 위반을 확인한다. 에너지 빚을 0으로 지우거나 실제 사용 J로 예산을 다시 맞추지 않는다.
- overrun 동안 새 도착을 즉시 예측할 수 없으면 최초 관측시각과 `reservation_pending`을 남긴다. 실제 cap 발행시각과 구분하고 이미 발행한 cap은 유지한다. 정보가 없을 때 임의 잔여 비용을 넣지 않는다.

### 수정 버전 등록과 실행 허가를 구분해야 한다

**P1 — 설계 변경을 정상적으로 인계할 경로가 아직 없다.** `prepare`는 새 소스 revision을 만들지만 `check`는 최초 campaign의 `design`과 현재 `specification()`이 완전히 같아야 한다. 승인된 설계 보완도 현재 방식으로는 등록 후 실패한다. 또한 pilot 본체를 구현하면 실행기 SHA가 바뀌므로 현재 코드 해시로 미래 실행기를 검토했다고 할 수 없다.

수정 계약:

- 최초 campaign·등록 1/2/3·실패·소비 장부는 그대로 보존한다. 예산과 실행 ID를 재생성하지 않는다.
- 승인된 설계 개정은 이전 설계 SHA와 본 검토 SHA를 참조하는 불변 revision으로 추가한다. `check`는 유효 설계 revision과 현재 코드 명세를 대조하며, 임의 변경·옛 revision 회귀·예산 변경을 거부해야 한다. 최초 설계는 이력으로 남긴다.
- Sol이 이번 수정과 pilot 실행기 구현을 모두 끝낸 뒤 source binding을 만든다. Astra의 짧은 재검토에서 그 최종 해시에 `PROCEED_PILOT`을 발행하기 전에는 성능 시작을 허용하지 않는다. 이번 `astra_review.json`의 `REVISE_BEFORE_RUN`은 실행 허가가 아니다.
- 검토 gate 테스트는 임시 경로/명시적 mock으로 파일 없음·수정 필요·해시 불일치·일치 허가를 검증한다. 실제 작업 폴더에 검토 파일이 영원히 없다는 현재 테스트 가정은 제거한다.
- 432행 재사용은 13개 공통 의존 파일만으로 판정하지 않는다. 원 Band/Triton adapter·설정·입력·모형·결과 파일의 기존 manifest와 새 조건의 대응을 확인하고 행별 출처를 보존한다. 일치하지 않으면 조용히 재사용하거나 재실행 범위를 늘리지 말고 차이를 보고한다.

## 핵심식 판정

### 완료 예약은 보수적인 1차 가설로 유지한다

요청 i를 처음 정상 예측할 수 있는 시점에, 도착한 현재 큐 전체의 long-context EFT 완료 계획으로 다음을 한 번 발행한다.

`cap_i = min(D_i, C_i_EFT_long_at_issue)`

`D_i`는 원래 절대 응답/저장 기한이다. 긴급은 output-ready, 일반은 persisted이며 실제 lane 반환과 다르다. 후보 전체의 long-context 완료시각이 발행된 cap을 넘으면 탈락한다. 발행 이후 재판단·새 도착·fallback·예산 회복으로 cap을 늦추지 않는다. 예측 불가 기간의 pending과 이후 발행을 명시한다.

**사실:** 일반 작업에도 원래 기한보다 엄격한 cap을 적용한다. 저장된 mixed 사례의 일반 요청은 원래 기한 41.05초인데 cap은 약 35.785368초였다. 새 도착 뒤 실제 저장 완료가 cap을 넘었지만 원래 기한은 지켰다.

**추론:** 열 분산의 선택 여지가 작고 fallback이 많아질 가능성이 있다. 그러나 아직 48조건에서 후보 다양성을 확인하지 않았으므로 이번 검토에서 일반 cap을 원 기한까지 느슨하게 하거나 새 여유 비율을 만들지 않는다. 먼저 동일 식으로 후보 수·탈락 사유·WAIT·배정 변경을 측정한다. 선택 가능한 대안이 부족하면 단계3에서 별도 수정 정책 여부를 결정하며, 결과를 본 뒤 같은 정책의 cap을 바꾸지 않는다.

long-context는 총 lane 시간으로 고른 개발 스트레스 문맥이다. WCET나 각 응답 단계의 보장 상한이 아니며, 위 식이 실제 긴급 P95 또는 전체 기한 비악화를 보장하지 않는다. 최종 실현 결과를 각각 비교해야 한다.

### 에너지 식은 경로에 의존하는 누적 제약으로 유지한다

`O_t`는 공개된 실행 이력으로 누적한 공통창 모형 J, `V_EFT(x_t,Q)`는 같은 현재 상태에서 큐 Q를 EFT로 완료하고 120초까지 계산한 남은 J다. 실행 중 작업은 양쪽에 똑같이 포함하고, 이미 응답한 작업도 실제 lane 사용이 끝날 때까지 비용에서 빼지 않는다.

첫 발행:

`B = O_t + V_EFT(x_t,Q)`

아직 credit을 발행하지 않은 새 요청 집합 A를 정상 예측할 수 있을 때 한 번:

`B_new = B_old + V_EFT(x_t,Q_old ∪ A) - V_EFT(x_t,Q_old)`

후보 허용:

`O_t + V_candidate(x_t,Q) <= B + 1e-9`

새 ID가 없는 callback에서는 B를 갱신하지 않는다. 음수 credit을 0으로 자르지 않는다. 음수는 병행·재배치에 따른 모형상의 차이일 수 있다. 비용을 계산할 수 없으면 null/비적격으로 처리하고 0이나 실제 소비로 대체하지 않는다. 1e-9는 수치 비교용이며 모형 오차 허용폭이 아니다.

**판정:** 이 식은 과거 소비를 잊지 않는 일관된 장부 규칙으로 사용할 수 있다. 다만 `x_t`가 새 정책의 실제 과거 행동에 따라 바뀌므로 증분들의 합은 처음부터 독립적으로 실행한 EFT/Band의 총 J와 같지 않다. 따라서 B 충족을 ‘Band 대비 J 비증가’로 표시하면 안 된다. 전역 비교는 동일 trace의 완료된 기준정책 행으로 따로 판정한다. fallback·예측 오차가 B를 깨뜨릴 수 있으므로 최종 장부 잔액이 필수다.

향후 다른 예산 방식을 검토하더라도 그림자 EFT 전체 실행이나 다른 비용 계수를 이번 수정에 자동 추가하지 않는다.

### 선택과 탐색 한도

전체 완료 계획을 만든 뒤 cap/J를 검사하고, 탈락한 prefix도 제한 beam의 다음 깊이 후보로 남기는 구조는 유지한다. `누적 최고 AP를 포함한 예상 최고 AP → 전체 J → 긴급 예상 응답 → 정규화 sequence` 순서도 유지한다. 기존 반올림은 수치 동률 처리이며 물리적 동등 판정으로 쓰지 않는다.

64확장·beam8·깊이4는 **상한**이다. 후보가 많으면 64확장을 먼저 써서 깊이4에 도달하지 못한다. 현재 시험은 탈락 prefix의 2단계 연장을 확인한 것이지 유효한 모든 조합의 발견을 보장하지 않는다. pilot에는 실제 최대 깊이, 탐색 한도 도달, 완성 계획 수, 적격 후보 수, 기준/저장/신규 후보의 선택을 기록한다. 판단시간은 PC 비용이며 기기 제어 비용0이라는 기존 모형 가정과 분리한다.

최적화용 AP는 1초 격자와 전이 경계, 기존 최종 비교 AP는 공통 1초 격자를 사용한다. 이를 메타데이터에서 구분하고 비교군의 기존 metric을 바꾸지 않는다. 둘 다 연속시간 표면 온도 최고값의 실측이 아니다.

## Sol 보완의 통과 조건

1. 두 개 이상의 미래 작업 간격을 가진 저장 일정을 재판단해도 유효한 절대 시각이 유지된다. 이른 실제 반환·늦은 반환·새 도착·응답 후 lane 점유 사례를 포함한다. 보존 불가와 새 후보 선택을 구분한다.
2. 새 도착·모형 오차가 없는 고정 일정에서 `O_t + V_remaining`이 callback을 지나며 같은 총 J가 되는지 상태별 적분으로 확인한다. 양/음 credit은 동일 snapshot의 두 완성 계획에서 계산되고 새 ID마다 한 번만 발행된다.
3. fallback 이후 에너지 빚, 빈 큐 뒤 남은 lane 비용, 최종 120초 idle 비용을 보존한다. 원래 기한과 내부 cap 위반을 별도로 확인한다. 미완료를 에너지 성공으로 세지 않는다.
4. 동일 과거의 모든 결정에 대해 첫 미래 suffix 차이 이전까지 의미 있는 선택이 같다. 현재의 첫 결정 하나 비교만으로 끝내지 않는다. 실제 lane 중복·미래 비용·요청 누락·기존 모형 변경 금지는 유지한다.
5. 검토 gate의 네 상태와 수정 등록·재개·예산 불변을 확인한다. 현재 11회 소비와 최초 실패를 보존한다. 기존 21개 PASS는 이전 실행의 증거이며 새 수정본에 자동 전용하지 않는다.
6. 48개 신규 행·432개 재사용 행의 실행/저장/재개 경로를 구현하고, 대표 trace와 비교 입력을 결과 전에 고정한다. 작은 검증은 남은 단계2 예산에서 소비하고, 성능은 최종 소스 검토 전까지 0으로 유지한다.
