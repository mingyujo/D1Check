# 요청 선택을 포함하는 강화학습 규칙

2026-10-06 · REQUEST-PPO-QUEUE-RULES-02 · **설계 완료 / 구현·학습 미실행**

최신 기한 권고: 사용자 후속 요청에 따라 **§8의 과업별 1초/묶음 종료 기준**을 새 주조건으로 삼는다. §7의 처리시간 배수 조건은 민감도이고, 중간값 0.628/4.968초를 실제 과업의 기본 기한으로 정당화하지 않는다. 과거 결과의 기한·판정은 변경하지 않는다.

사용자 요청은 기존 PPO의 선택 범위를 다시 정하는 것이다. 이번 문서는 다음 구현의 규칙이며 실행 가능한 학습 manifest나 새 기기 계획이 아니다. 기존 [PPO 결과](results/request_ppo_01/README.md)와 [방법론 탐색](results/method_followup_01/README.md)을 보존한다. 기존 PPO가 공동 절감에 실패한 원인이 행동 공간이었다고 확정하지 않는다.

## 1. 질문과 변경 범위

질문: 같은 실측 기반 비용식·예정 도착·서비스 조건에서, **도착한 요청 중 다음 실행 요청까지 선택**하면 고정 순서보다 서비스·에너지·AP 상충을 개선할 수 있는가?

방법은 기존 masked PPO-Lagrange를 재사용한다. 알고리즘 교체, 물리 계수 재학습, 탐지 GPU 비용 추가, 스로틀 법칙 추가를 함께 하지 않는다. 기존 기본 정책과 strict 지원, `experiment_ready=false`는 유지한다.

| 항목 | 새 규칙 |
|---|---|
| 관측 | 현재 시각, 도착한 대기 요청, 알려진 기한·나이·작업, 실제 공개 lane 상태, 동결 처리시간 추정, 모형 AP·잔열 상태 |
| 후보 요청 | 기존 aging/우선순위/기한/ordinal/id 정렬의 상위 8개. 정렬은 후보 표현 순서이며 강제 실행 순서는 아님 |
| 행동 | `(slot 0…7, CPU/GPU)` 16슬롯 + `WAIT` 1슬롯 = **출력 17슬롯**. 매 시점 합법 행동만 선택 |
| 자원 | 분류 CPU/GPU, 탐지 CPU. 같은 lane 중복과 미지원 동시 상태는 mask |
| 병행 | 현재 모형에 있는 분류 GPU＋탐지 CPU만. 별도 병행 스위치 없이 두 lane 배정 결과로 발생 |
| 대기 | 기존 최대 250ms 한 단위 유지. 여러 대기 길이 추가는 이번 변경에서 제외 |
| 결정 시점 | 기존 도착·단계/lane 해제·타이머 이벤트. 새 미래 이벤트나 고빈도 장치 조회를 만들지 않음 |
| 실행 | 비선점. 요청 시작 후 완료까지 소유권 유지, 실제 lane_available 전 재사용 금지 |

17개 모두가 동시에 합법인 것은 아니다. 탐지의 GPU 슬롯·빈 후보 슬롯·점유된 lane·미지원 조합은 금지한다. 후보 밖 요청도 전체 대기열 통계와 실패 분모에 포함하고 결과에서 삭제하지 않는다.

## 2. 기한·기아·진행 보장 경계

- 긴급 1.5초, 일반 6초는 **과거 대조 조건**으로 보존한다. 새 기한 설계는 아래 §7의 처리시간 정규화 3조건과 구분한다. output_ready·persist·worker_release·lane_available의 경계는 그대로다.
- 자발적 추월 한계는 요청마다 `A_i=min(2초, max(0, D_i-C_ref_task))`로 정한다. 나이가 A_i 이상이고 합법적으로 즉시 실행 가능한 요청이 있으면, 그중 절대 기한이 가장 빠른 요청을 반드시 후보에 넣고 해당 요청의 합법 backend만 허용한다. 동률은 도착/ordinal/id로 고정한다. 작은 기한에 기존 2초만 적용하면 보호 전에 기한이 끝날 수 있어 수정한 **알고리즘 가드**다. 평균 기반 참조값으로 WCET나 실제 완료를 보장하지 않는다.
- WAIT는 실제 실행 가능한 행동이 있을 때의 자발적 유예로 센다. 현재 큐의 어떤 요청도 위 나이 한계 A_i를 넘도록 유예하지 않으며, 현재 도착 요청 전체의 동결 추정 EFT 연장을 비교해 등급별 예상 기한 실패 수·양의 지각 합계를 늘리는 WAIT는 거절한다. 이미 한계를 넘은 요청이 있으면 WAIT를 허용하지 않는다. 같은 가드를 대조군에도 적용한다.
- 두 lane이 막혔거나 소유권 해제 시각을 추정할 수 없으면 실제 이벤트를 기다린다. 이를 정책이 선택한 WAIT나 잔여시간 0으로 기록하지 않는다.
- guard는 현재 큐와 추정 시간만 본다. 미래 도착·실제 미래 처리시간에 대한 기한 보장은 아니다. 실행 결과의 전체 도착 분모에서 다시 판정한다.
- 기한이 지난 요청을 버려 비용을 낮추지 않는다. episode 상한 이후 남은 요청도 미완료로 남기고 성공 비교에서 제외한다. 창 밖으로 부하를 미뤄 전체 J가 절약된 것처럼 판정하지 않는다.

## 3. 목적과 보상

학습은 **기기 전체 공통창 에너지 최소화 + 서비스·열 제약**이다. J와 °C를 임의의 단일 가중합으로 합쳐 한쪽 악화를 숨기지 않는다.

- 보상: 기존 `-whole_120s_J / 10`. 간격 보상 합이 전체 회계와 일치해야 한다.
- 서비스 비용: 긴급/일반 각각 전체 도착 중 실패·미완료·기한 위반 비율. 목표 0. 과부하에서 달성 불가능할 수 있으며, 기준정책도 실패했다는 이유로 완전 서비스 성공으로 표시하지 않는다.
- 120초까지 모든 요청의 lane 해제가 끝나지 않으면 전체 작업 에너지 비교 부적격이다. 120초까지의 관측/계산 J는 부분 작업의 고정창 비용으로만 남기고 낮은 값으로 checkpoint를 채택하지 않는다. 180초 AP 경로가 없으면 AP는 null이다.
- 열 비용: 같은 초기조건 EFT의 AP 양의 면적과 최고 AP를 각각 기준으로 한다. 면적은 기존 35–180초 유효 유휴 기준 초과량이며 주변온도·안전한도가 아니다. 최고값 제약을 새로 포함해 면적 감소로 최고값 증가를 감추지 않는다.
- 구현 시 value head는 에너지 1개 + 비용 4개(긴급·일반·면적·최고값)다. 기존 면적 `/100`, 최고값 `/1°C`는 수치 스케일이며 정확도/안전 허용폭이 아니다. 승수 초기값·상한·갱신 규칙은 본 학습 전에 기계 판독 계약에 기록한다.
- PPO-Lagrange는 기대 제약을 학습한다. 모든 개별 trace 제약을 보장하지 않는다. 평가에서는 trace별 서비스/J/AP/응답 상충과 실패를 모두 남긴다.

**공동 개선**은 같은 입력에서 전체 작업·기한을 지키고 J·최고 AP·양의 AP면적이 모두 감소한 경우로만 표시한다. 한 지표 동일·나머지 감소는 공동 비악화로 구분한다. float 비교 공차는 수치 처리이며 물리적 유의성이나 정확도 PASS가 아니다. AP 면적 정의에 의존하는 결과와 전체 부호 있는 AP 잔차도 함께 제시한다.

## 4. 미래 정보 차단

관측 AP·잔열은 기존 초기 입력과 지금까지의 **모형 상태**다. 새 실제 센서 관측이나 검증된 열→처리율 모델로 부르지 않는다. 미래 도착 목록·최종 요청 수·scenario/seed·실현 처리시간·미래 전력/AP는 actor 입력에서 제외한다. 관측하지 못한 lane 잔여시간은 동결 추정치 또는 unknown으로 처리한다.

episode 종료 후 학습 보상·평가 계산에는 전체 결과를 사용할 수 있다. 대응 EFT의 사후 전체 비용을 actor 관측에 넣는 것은 금지한다. 테스트 자료로 물리 계수·보상·후보 수·mask를 변경하지 않는다.

## 5. 요청 선택의 효과를 분리하는 비교

두 PPO를 **같은 새 목적·가드·공통 17슬롯/관측 구조·학습량**으로 비교한다.

1. HEAD 대조: 동일 후보 표현을 받되 기존 선두 요청 backend와 WAIT만 허용. 기아 보호 시 강제 후보를 선두로 정규화한다.
2. QUEUE 후보: 상위 8개의 합법 요청/backend와 WAIT를 허용.

기존 PPO 결과는 역사적 결과로 보존한다. 보상·최고 AP 제약이 달라지므로 과거 수치와의 차이를 요청 선택 하나의 효과라고 주장하지 않는다. EFT·고정 CPU·고정 split을 공통 기준으로 보고하고, 같은 후보·가드를 쓰는 비학습 EDF/EFT도 비교한다. CPU/GPU만 가능한 상태 외의 이득은 계산하지 않는다.

학습/검증/최종시험 도착 seed를 분리하고 실제 사용 이력을 검사한다. 이미 확인한 입력 계열에 새 seed를 쓰는 것은 **같은 생성 분포의 보지 않은 trace**이며 새 물리 조건의 독립 확인이 아니다. 기존 네 계열과 mean/short/long 문맥을 유지해 유리한 부하만 골라내지 않는다. 실행량·seed·학습시간 상한·검증 선택 순서·원본 해시는 구현 검증 뒤 학습 전 별도 manifest에서 고정한다. 이번에는 새 학습 실행 예산을 임의로 승인하거나 실행하지 않는다.

검증 선택은 미완료 → 기한 실패 → EFT 대비 열 제약 위반 → J → 응답 순으로 하고 모든 학습 seed 결과를 보고한다. 제약 충족 checkpoint가 없으면 후보 미채택으로 남긴다. 최종시험 결과로 재선정·재학습하지 않는다. 새 정책이 성립하지 않아도 범위 안 상충 또는 EFT와 차이 없음으로 종료한다.

## 7. 후속 기한 설계 — 요구사항과 처리 가능성을 구분

2026-10-06 사용자 후속 요청으로 추가했다. **사용자/제품 SLA는 아직 null**이다. 처리시간을 측정했다고 사용자가 기다릴 수 있는 시간을 알아낸 것은 아니다. 기존 1.5/6초도 제품 요구에서 도출된 것으로 바꾸지 않는다.

### 처리시간에 근거한 연구 조건

예정 도착 r_i, 상대 기한 D_i에 대해 절대 기한은 항상 `d_i=r_i+D_i`다. dispatch가 늦어져도 d_i를 연장하지 않는다. 긴급 응답은 도착→output_ready, 일반 응답은 도착→persist_complete이며 전체 요청 완료에는 lane_available도 확인한다.

`C_ref_task = ceil_1ms(max(동결 개발 CPU 문맥별 평균 응답시간))`으로 고정한다. 정책이 선택한 backend나 시험에서 관측한 시간에 따라 기한을 바꾸지 않는다. CPU는 두 작업에 공통으로 존재하는 고정 참조이며, 느린 자원을 선택해 더 긴 기한을 받는 경로를 막는다. 긴급은 개발 벡터 앞 2구간, 일반은 앞 3구간을 합하고 lane 꼬리를 응답에 섞지 않는다.

| 작업 | 개발 문맥 수 | 반올림 전 참조 | 1ms 올림 참조 |
|---|---:|---:|---:|
| 긴급 분류 CPU | 1 | 156.179931ms | **157ms** |
| 일반 탐지 CPU | 3 | 620.151684ms | **621ms** |

원자료의 요청 P95나 개별 최댓값이 아니라 **문맥 평균들의 최댓값**이다. tail/WCET/기한 보장이 아니고, 현재 동결 서비스 모형과 일치하는 재현 가능한 시간 척도다. 최대 문맥 평균을 택한 것 역시 공학적 설계 선택으로 공개한다. 새 실측·확인 자료를 기한 선정에 넣지 않는다.

상대 기한 `D_i = k_priority × C_ref_task`의 다음 3개 조건을 **모두** 판독한다. 연구용 k는 실측한 허용 대기나 인간 반응 한도가 아니다. 기한을 두 배씩 변화시키는 유한 민감도 설계이며, 일반 요청에 긴급의 두 배 상대 여유를 부여한다. 사후 최선 k를 채택하지 않는다.

| 조건 | 긴급/일반 배수 | 긴급 상대 기한 | 일반 상대 기한 |
|---|---|---:|---:|
| 정규화 1 | 2 / 4 | 0.314초 | 2.484초 |
| 정규화 2 | 4 / 8 | 0.628초 | 4.968초 |
| 정규화 3 | 8 / 16 | 1.256초 | 9.936초 |
| 과거 대조 | 기존 절대값 | 1.500초 | 6.000초 |

현재 기존값을 반올림 전 CPU 참조로 나누면 분류 9.604배, 탐지 9.675배다. 절대 기한은 다르지만 처리시간 대비 여유는 거의 같다. 새 배수는 이 우선순위 의미를 명시적으로 바꾸는 **새 실험 조건**이며 기존 결과에 소급 적용하지 않는다. 3조건은 우선순위 두 배수의 모든 독립 조합을 조사하는 실험은 아니다.

### 부하와 기한을 함께 판정

짧은 기한과 처리 용량을 넘는 도착을 구분한다. 같은 도착·작업·서비스 문맥에서 기한 조건만 바꾼다. 부하를 낮춰 성공시키거나 느린 정책의 기한을 늘리지 않는다.

1. 각 요청의 D가 지원 backend 중 가장 빠른 해당 문맥의 응답시간보다 짧으면, 그 **고정 시간 모형 아래** 단독으로도 기한을 지킬 수 없다. 실기기 불가능 증명은 아니다.
2. 탐지는 현재 CPU 필수다. 어느 구간 [a,b]에 대해 `r_i≥a, d_i≤b`인 탐지들의 고정 문맥상 dispatch→persist 시간 합이 `b-a`보다 크면 해당 모형의 필수 CPU 수요부터 초과한다. 전체 lane 점유/꼬리/분류 수요를 완화한 필요조건이므로 **초과하면 차단 근거, 통과해도 실행 가능 보장은 아님**이다. 독립 코어·GPU가 있다고 탐지 CPU 수요를 두 lane 용량으로 나누지 않는다.
3. EFT의 기한 실패만으로 불가능이라고 판정하지 않는다. 원래 요청 전부의 deadline·응답·J/AP를 남기고, 가능성 미확인/필수 수요 초과/실제 모형 일정 성공을 구분한다. 과부하 자료를 삭제하거나 성공 후보 선택에 쓰지 않는다.
4. 일반 9.936초 조건은 늦게 도착한 요청의 기한이 120초를 넘을 수 있다. 입력 기한을 `min(d_i,120초)`로 자르거나 도착을 앞당기지 않는다. 전체 작업이 120초 안에 lane 해제되지 않으면 기존 J 창으로는 동등 작업의 공동 개선을 판정하지 않는다. 필요하면 `관측창과 요청 수명 불일치`로 남기며 창 연장도 이번 작업에서 자동 수행하지 않는다.

### 실제 서비스와 연결할 때

UI가 눌림을 알리는 시간, AI 결과가 사용 가능한 시간, 배경 저장 완료 시간은 다른 요구다. Google의 [RAIL 설명](https://web.dev/articles/rail)은 웹 입력의 시각적 피드백을 다루므로 그 100ms 값을 D1 추론 완료 기한으로 복사하지 않는다. 페이지는 현재 성능 목표에는 Core Web Vitals를 권한다. Android의 [WorkManager 설명](https://developer.android.com/develop/background-work/background-tasks/persistent)도 지속 작업의 종류·실행을 설명하며 D1의 개별 탐지 6초 SLA를 제공하지 않는다. 2026-10-06 원문 확인. 두 문서는 **요구 경계를 구분하는 근거**이고 위 수치의 출처가 아니다.

제품 시연의 구체적 과업·수용 가능한 결과 지연·실패 처리가 확보되면 그때 절대 SLA를 별도 사전 등록한다. 제품 목표가 기기 성능보다 짧으면 해당 조건 부적합으로 보고, 기기 능력에 맞춰 제품 요구를 조용히 완화하지 않는다. 현재 연구에서는 위 정규화 조건과 원래 절대 기한 조건을 구분해 보고한다. S26은 자체 참조를 써야 하며 기기 정규화 결과를 동일 사용자 경험으로 비교하지 않는다.

## 8. 실제 실행한 두 작업에 연결하는 과업별 기한

사용자 후속 요청: 실행했던 작업의 의미를 근거로 기한을 정한다. **연구 설계 채택이며 기존 실측을 실제 앱 이용 실험으로 재명명하지 않는다.** [기계 판독 명세](results/request_ppo_01/task_deadline_contract_v1.json).

### 확인한 작업과 새 역할 가정

실제로 수행한 것은 EfficientNet-Lite0 분류와 EfficientDet-Lite0 객체탐지·후처리·저장이다. ImageNet 분류/COCO 객체탐지가 본질적으로 긴급/일반인 것은 아니다. 기존 합성 trace에서 분류→긴급, 탐지→일반으로 지정했고 실제 사용자 도착 로그·사용자 허용시간은 확보하지 않았다. `MULTITASK_EXPERIMENT_PROTOCOL` §1·§4·§7, `SCOPE_02_EVIDENCE` §2·§3, `ARRIVAL_ENERGY_SYNTHETIC_RESEARCH`의 task/priority 결합 한계를 유지한다.

새 주질문은 **대화형 분류의 결과 준비를 보호하면서, 유예할 수 있는 탐지 결과 저장을 같은 완료 예산 안에 끝낼 때 J/AP 부담을 줄일 수 있는가**다. 역할은 다음 실행 전에 선언한 가정이다. 실제 카메라 실시간 탐지·야간 사진 색인·분류/탐지 역할 교환까지 검증했다고 하지 않는다.

| 실제 계산 작업 | 새 연구 역할 | 채택할 기한/완료 조건 | 근거의 성격 |
|---|---|---|---|
| EfficientNet-Lite0 분류 | 사용자가 결과를 기다리는 요청의 대리 | 예정 도착→output_ready **1.000초 이내** | 상호작용의 약 1초 응답 지침을 연구 목표로 채택. 이 앱 사용자에게 검증된 SLA는 아님 |
| EfficientDet-Lite0 탐지·결과 저장 | 유예 가능한 백그라운드 작업의 대리 | 개별 5/6초 SLA를 만들지 않음. 등록 묶음의 모든 결과를 **공통 원점+120초까지 저장 완료** | 기존 120초 J 회계창과 동일 작업량 비교에 맞춘 실험 완료 예산. 실제 사진 앱의 120초 요구가 아님 |
| 모든 요청 | 동등 작업량의 J/AP 비교 | 결과 준비/저장 외에도 **전 요청 lane_available≤120초**, 이후 180초까지 AP 관측/계산 | 일을 창 밖으로 보내 소비를 낮추는 해법 차단 |

일반 요청의 절대 기한은 같은 120초이며 상대 기한은 `120초−예정 도착`이다. 첫 요청이 공통35초이면 남은 실행 기간은 **85초**다. 각 요청이 도착한 뒤 새로 120초를 부여하는 것이 아니다. 묶음 종료가 알려진다는 사실은 미래 요청 목록/개수/처리시간을 안다는 뜻이 아니다. late·실패·미완료는 전량 분모에 남기고 작업을 버리거나 자동 연장하지 않는다.

일반 저장 완료가 120초 안이어도 lane 해제가 그 뒤면 개별 저장 목표와 전체 J 적격성을 구분한다. 분류의 1초 절대 기한이 창 밖으로 나가는 입력도 기한을 자르거나 도착을 변경하지 않고 창 불일치로 표시한다.

### 외부 근거가 지지하는 범위

[Nielsen의 응답시간 지침](https://www.nngroup.com/articles/response-times-3-important-limits/)은 약 1초가 상호작용 흐름을 유지하는 경계라고 설명한다. **이는 1초 연구 목표의 설계 근거이며 EfficientNet SLA의 실증 자료가 아니다.** 현재 `output_ready`는 화면 그리기 전의 결과 객체 경계이므로 화면 표시까지 1초라고 주장하지 않는다. 실제 UI에 적용할 경우 화면·입출력 예산을 포함한 별도 end-to-end 검증이 필요하다.

[Apple Photos 사례](https://machinelearning.apple.com/research/recognizing-people-photos)의 주기적·충전 중 야간 클러스터링은 백그라운드 과업에 짧은 요청별 SLA가 필수는 아님을 보여주는 사례다. 우리의 EfficientDet, Android, 비충전 환경과 같은 작업/계약이 아니며 **일반 5초·6초·120초의 근거로 전용하지 않는다.** 이 구분 때문에 일반 과업에는 외부 근거 없는 단일 초값 대신 명시적인 실험 묶음 예산을 사용한다.

### 실측 개발값은 가능성 점검에만 사용

동결 개발 벡터를 재사용했다. CPU 분류 dispatch→output_ready 평균 156.180ms, GPU 분류 문맥 평균 286.608–301.501ms, CPU 탐지 dispatch→persist 평균 618.791–620.152ms다. CPU 탐지의 문맥 평균 중 최대 **lane 점유 622.422ms**와 분류 CPU 응답 156.180ms를 더하면 **778.601ms**다.

이는 이미 실행 중인 탐지 한 건을 기다린 뒤 CPU 분류 한 건을 실행하는 **평균 기반 국소 산술**이 1초 아래라는 점을 보여준다. 큐에 여러 요청이 있거나 실제 꼬리 지연이 큰 경우까지 보장하지 않는다. 1초를 이 합산값에 맞춰 역산한 것이 아니며, 정책/새 확인 결과를 보고 기한을 완화하지 않는다. 분류 CPU 한 문맥과 탐지 세 문맥의 평균을 P95/WCET/분포로 바꾸지 않는다.

### 앞선 규칙과의 관계 및 실행 차단 경계

- §7의 0.314/2.484, 0.628/4.968, 1.256/9.936초는 유한 공학 민감도 자료로 보존한다. **0.628/4.968을 주 과업 기한으로 추천했던 것은 철회**한다. §8은 새 사용자 요청으로 목적을 더 구체화한 규칙이며 결과 개선을 확인한 뒤 바꾼 것이 아니다. 그 사이 새 정책 실행 0회다.
