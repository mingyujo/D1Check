## 질문과 보존

“조작 기반 배경 시작 제한과 요청 우선순위·정적 배정을 비교할 때, 대화형 AI 응답과 같은 배경 작업량의 완료 사이에 어떤 차이가 생기는가?”

기존 일반 서비스 제약 아래 긴급 지연 최소화와 구별되는 후속 개발이다. 기존 주 결합 FAIL, 부분 결과, CAL-03 동결40값·기존20null, 종료 계획, `experiment_ready=false`를 보존한다. 현재 P 수정·새 적응형 후보·강화학습은 제외한다. 특정 사용자 면담은 필수 gate가 아니다. 공개 근거와 합성 시나리오를 구분한다.

이름은 **공개 앱을 참고한 요청 단위 배경 시작 제한**이다. [Ente 고정 commit의 compute controller](https://github.com/ente/ente/blob/a492f9db8e67def81d5f17c687f69b5778ec0df3/mobile/apps/photos/lib/services/machine_learning/compute_controller.dart)의 Android 기본15초와 조작에 따른 타이머 갱신, [run control](https://github.com/ente/ente/blob/a492f9db8e67def81d5f17c687f69b5778ec0df3/mobile/apps/photos/lib/services/machine_learning/ml_run_control.dart)의 시작한 stage 마무리를 참고한다. D1Check의 이미지 요청은 Ente stage와 다르다. Ente 전체 구현·건강 상태/override/재시작 규칙을 재현하거나 Ente 대비 우위를 주장하지 않는다. 합성 조작 사건은 실제 터치·렌더링 부하가 아니며 UI 끊김/표시시간 개선을 뜻하지 않는다.

## PC 시간·입력 계약 (구현 전 고정)

- 새 버전 `arrival-interaction-pc-v1`. 기존 엔진의 기본 호출 경로와 기존 정책 ID/설정은 유지한다. 새 wrapper는 CPU 고정과 정적 배정만 사용하며 현재 P를 호출하지 않는다.
- 요청은 기존 task/priority/예정 도착/deadline/ID 형식이다. 조작은 별도 `{id, at_ns}` 목록이며 요청을 자동 생성하지 않는다. task와 priority는 독립이다. 미래 조작/요청 목록은 엔진만 갖고 정책에는 도착 큐·현재 lane·관측된 gate 상태만 전달한다.
- 모든 시각은 한 가상 monotonic ns 시계다. 시작 상태는 **유휴·타이머 없음**으로 고정한다. foreground 진입 자체가 조작이라는 Ente 초기 상태를 재현하지 않는다. 필요하면 t=0 조작을 입력에 명시한다.
- 마지막 관측 조작 t에서 `blocked_until=t+idle_ns`, 기본 `idle_ns=15_000_000_000`. `now < blocked_until` 동안 새 normal dispatch만 금지하고 정확한 만료 시각에는 허용한다. urgent는 이 gate를 우회하지만 실제 자원 점유·비선점 제약을 우회하지 않는다. 초기화/건강 gate를 우회한다는 의미도 아니다.
- 같은 시각 순서: **CPU→GPU의 단계 완료/실제 lane 해제 → 조작(ID순) → 요청 도착(ordinal/ID순) → 타이머 만료(세대 검사) → 진행 중 판단 완료와 dispatch 재검사 → 새 판단**. 같은 시각 새 조작이 이전 만료보다 우선한다. 0길이 단계는 새 판단 전에 소진한다.
- 조작은 타이머 세대를 증가시킨다. 과거 만료는 무효 이벤트로 기록하고 새 판단을 유발하지 않는다. 유효 만료는 요청 도착·완료가 없어도 재판단을 깨운다.
- 판단 중에도 조작·도착·완료 사건은 처리한다. 선택한 normal은 **실제 dispatch 직전** gate를 다시 검사한다. 금지되면 pending 배정을 취소한다. 요청은 원래 큐·ordinal에 남고 lane을 점유하지 않으며 실현 서비스 벡터도 소비하지 않는다. 그때까지 쓴 판단/기록/dispatch 준비 비용은 반환하지 않는다. 이후 urgent 또는 타이머 사건을 기다린다.
- 이 엔진의 예약은 단일 scheduler의 pending 선택뿐이다. 실제 lane을 RESERVED로 바꾸지 않는다. pending 중 두 번째 판단을 시작하지 않으므로 같은 lane의 이중 예약은 없다. 실행 중 요청은 gate 때문에 취소하거나 선점하지 않는다. O/P/W가 와도 실제 L 전에는 lane을 재사용하지 않는다.
- 선택 없는 판단은 판단+기록 비용을 한 번 소비하고 상태 변화까지 기다린다. 판단 도중 관측한 상태 변화는 유실하지 않는다. stale timer만으로 busy polling하지 않는다. 사건 수·입력 수·가상 horizon은 bounded다.
- gate 처리 자체의 CPU 비용은 이 PC 단계에서 **미측정·0 가정**이다. 정책 판단/기록/dispatch 비용은 기존 명시적 설정을 재사용하며 추가 판단·취소도 기록한다. 가상 비용과 host에서 실제 Python 실행에 걸린 시간을 혼동하지 않는다.
- 새 비교의 제한 on/off 양쪽은 같은 사건 관측·timer wake-up 규칙을 사용하며 dispatch 허용만 다르다. `enabled=False`는 비교용 off와 별개인 전체 기능 비활성 호환 경로로 기존 엔진에 hook 없이 전달한다. 제한 on에서만 scheduler 구현 차이가 붙는 비교를 피한다. 진행 중 판단이 완료/lane 해제/만료를 가로지르면 그 비용을 끝낸 뒤 관측한 변경을 재판단한다.

## 관측 구간·종료·분모

모든 비교에 같은 요청·입력·조작·관측종료 T·drain D를 주고 horizon은 `T+D`다. T는 모든 예정 도착/조작을 포함한다. 계약 입력은 마지막 조작의 타이머 만료가 horizon 이내일 것을 요구한다. 그래도 처리 미완료가 가능하며 drain을 결과에 맞춰 늘리지 않는다. 모든 작업이 먼저 끝나도 공통 관측종료·horizon 설정은 결과에 남긴다.

- urgent 응답: 예정 도착→output_ready. normal 응답/배경 완료: 예정 도착→persist_complete.
- T까지 저장 완료한 배경 건수, horizon까지 완료한 배경 건수와 전체 배경 분모를 각각 보고한다.
- 전체 배경 완료 시각은 모든 배경 요청의 persist가 있을 때만 max(P), 배경 총 소요시간은 max(P)−min(배경 예정 도착)다. 일부 미완료면 둘 다 null이다. 배경 persist가 끝나도 lane 정리가 끝났다는 뜻이 아니다.
- 전체 lane 해제 시각/기존 makespan은 모든 요청의 L이 있을 때만 계산한다. 앱/host cleanup은 이 시뮬레이터가 실행하지 않아 `not_modelled`다.
- 전체 planned/arrived/response-ready/lane-released/unfinished/not-arrived를 보존한다. 실패·거절·만료의 확률모형은 기존처럼 미지원이며 실패 0의 실기기 근거로 삼지 않는다. 완료된 요청의 P95만으로 성공을 판정하지 않는다.

## 공정한 후속 비교 (이번에는 선정·성능 배치 미실행)

두 축은 시작 허용(on/off)과 배정(CPU 고정/개발 선정 정적)이다. 새 wrapper는 두 배정 모두 기존 `B2_PC`의 **같은 urgent/EDF/aging 정렬**을 재사용한다. CPU 고정은 양 task CPU/직렬 설정이며 과거 등급 내FIFO의 `CPU_URGENT`와 같은 이름으로 바꾸지 않는다. 배경 aging도 닫힌 gate를 뚫지 않는다.

정적 후보는 동일한 task별 최대4배정과 합법적인 직렬/병행만 사용한다. 양 시작 규칙에 동일 후보·개발 입력·튜닝 예산을 준다. 두 규칙의 개발 승자가 다르면 그 둘을 양쪽 gate에 교차 적용한다. 후보를 전달받아 교차 구성하는 기능만 준비하며 이번에 B2를 재선정하지 않는다. 평가 조건별 oracle은 금지한다. 미래 실제 처리시간을 입력하는 최적화도 없다.

15초는 출처가 있는 참고값이지 검증된 UX 기준이 아니다. 이번에는 변경 탐색을 하지 않는다. 향후 다른 timeout 후보·선정 예산, 허용 대화형 손실·최소효과·독립 block 수는 별도 동결 항목이다. 요구 근거가 없으면 서비스 상충 전체를 보고하고 성능 PASS를 부여하지 않는다.

동작 fixture는 조작 없음·간헐적 조작·유한 burst 후 유휴를 포함한다. 동일 요청 목록과 배경 총량을 사용하며 조작만으로 AI 요청을 만들지 않는다. 모든 정책에 같은 조작 종료·T·D를 적용한다. 이는 수작업 확인 가능한 기능 예제이며 실측 프로파일·정책 순위·새 독립 평가가 아니다.

## Android 연결과 추가 실측 공백

현재 Android에는 이 gate가 없다. `ArrivalSchedulerActivity`의 dispatch executor/대기열/배정 직전과 실제 lane callback을 연결 지점으로 삼는다. 별도 조작 입력과 generation timer를 같은 dispatch 소유권으로 직렬화하고, worker 제출 직전 normal 허용 여부를 재검사해야 한다. `ArrivalCollectionDev`/기존 timing recorder의 판단·기록·dispatch 및 callback 경계를 재사용한다. GPU 생성·사용·해제 worker 소유권을 바꾸지 않는다. 실제 UI 이벤트 연결은 합성 조작 재생과 별도다.

| 현재 자료 | 지원과 제한 | 새 비교에 필요할 때 확인할 것 |
|---|---|---|
| CAL-03 task×backend×priority8조건 | 각 단독 개발1/확인1세션·상관요청4개, 전체 구간/40값 | 새 역할/큐 순서로의 비용 전이와 재사용, tail 보장 불가 |
| 분류CPU urgent + 탐지GPU normal | 특정 co-run 순서·host API overlap 관측, observed bridge는 정확한 재생만 | 사진 과업의 반대 priority와 다른 overlap/부하를 쓰면 새 조건 확인 |
| 분류GPU + 탐지CPU | 단독 cell은 있으나 이 쌍의 병행 실측 미지원 | 정적 후보에 병행을 넣으려면 동일 입력의 단독 대조·병행·memory/품질/worker 점유 확인 |
| 현재 active CPU fallback/shadow | 단독 판단 경계와 고정 배정 관측 | 새 gate의 실제 timer/dispatch 재검사·취소·추가 판단/기록 비용 |

새 기기 예산은 후보×조작조건×독립paired block×정책 실행 수에 초기화4runtime/warmup 계약·요청수·trace/drain·회수·냉각·cleanup·설치/gate를 합산한다. 현재 paired 변동성으로 새 gate의 표본 수·효과·정밀도를 보장할 수 없다. 종료된 예산을 전용하지 않는다. 신규 실기기·추가 측정은 이번에 실행하지 않는다.

## 재현과 검증 기록

구현 완료: [새 모듈](../tools/d1_arrival_interaction.py), 기존 [엔진의 선택적 hook](../tools/d1_arrival_explore.py), [위험별 테스트](../tools/test_d1_arrival_interaction.py). `simulate()`는 새 `REPLAN_STATIC_PRIORITY_DEV` ID를 보고하고 기존 `B2_PC` 정렬/정적 배정 kernel의 재사용과 B2 미선정을 명시한다. `comparison_matrix()`는 외부 개발 동결 식별자를 가진 최대2승자와 CPU 고정을 양 gate에 교차 구성한다. 해시 문자열 형식을 검사할 뿐 실제 동결 파일의 진위를 검증하거나 정책을 선정하지 않는다. 향후 실행 계획에서 실제 파일/후보·예산 대응을 별도로 검증해야 한다.

관련 PC38건(새23+엔진15), CLI 합성3trace 수작업 일치, 보존 HEAD 기본 경로의 작은3정책 전체 출력 일치를 확인했다. [정확한 명령·시각·소스 hash·기대값 정정 이력](results/replan_pc_01_20260925/README.md)을 따른다. 이 결과는 기능 완료이며 Android 구현·GPU 병행·정책 우월성 검증이 아니다. 완료된 전체960배치·빌드·원자료 감사를 반복하지 않았다. S26 선정·별도 NPU 개발은 유지하며 A24 후속의 필수 조건으로 확대하지 않는다.

다음 작업은 별도 Android 개발 경로에서 동일 조작/timer/dispatch 의미를 구현하고, 필요한 정적 후보의 지원 확인과 paired 예산을 한 묶음으로 준비하는 것이다. 그 뒤 한 번의 개발→설정 동결→평가를 제안하되 현재 미승인인 실기기 실행을 자동 시작하지 않는다. 단순 기준으로 충분하거나 적응형 필요성이 확인되지 않으면 새 P를 추가하지 않고 해당 결론으로 종료한다. 미측정 조합·허용 손실·표본 설계가 해소되지 않으면 실기기 성능 평가 진입을 보류한다.
