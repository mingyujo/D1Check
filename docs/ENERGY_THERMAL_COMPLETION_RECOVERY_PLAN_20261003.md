# 에너지·열 최적화 목표를 유지하는 해결 계획 — 2026-10-03

상태: **DESIGN_PROPOSED_NOT_RUN_READY**. 사용자 요청은 해결 계획 수립이다. 이번 기기 명령/실측/실행계획/claim 0. 이 문서는 실행 승인이나 동결된 Run 계약이 아니다. 기준 HEAD25e153b, 기존 원본/동결/FAIL/strict/experiment_ready=false 보존. 아래 수집 수와 예산은 제안이며 실제 구현·Check 전 확정값으로 쓰지 않는다.

## 1. 해결해야 하는 문제와 끝낼 문제

목표는 **응답·완료 요구를 지키면서 CPU/GPU 배정과 작업 시작 시점을 조절해 기기 전체 J와 AP 부담을 줄일 수 있는 조건을 밝히는 것**이다. 응답 비교만으로 끝내거나 예측 차단 기능을 최종 모형 완성으로 부르지 않는다. SOC/사용시간/BAT온도 인증, 모든 외부 앱의 미래 활동 예측, 모든 기기·모델, RL은 완료 요건이 아니다.

[현재 근거](results/online_policy_study_01/post_idle_pc_v1/README.md): 동일CPU75–120초46.551/82.138J, lane상태/조회량 차이로 설명되지 않는 AP상승. '부하 전 배경이 계속 일정'이라는 가정으로 이 전력·열 변화를 설명하지 못한 것이 현재 모형의 적용 한계다. 실제 외부 활동, 센서/시스템 관측 특성, 숨은 열 이력 중 어느 원인인지는 확정하지 않는다. 이 오차가 발생한 시각은 찾았으므로 같은 원본을 다시 포괄 감사하지 않는다.

모든 미래 외란의 정확한 개방루프 예측을 요구하면 달성 불가능한 목표가 된다. 대신 **예정 도착 기준의 개방루프 오차**, **현재 관측까지 사용하는 온라인 갱신 예측**, **실제 정책의 독립 J/AP 효과**를 각각 평가한다. 온라인 갱신으로 과거 오차를 지우거나 이미 관측한 미래를 예측한 것처럼 표시하지 않는다.

## 2. 먼저 PC에서 구현할 묶음

1. 기존 앱/worker/sampler/소유권/회수 경로에 제한된 시스템 관측을 연결한다. 앱 CPU시간 누적과 기존 event/lane/power/AP를 같은 elapsedRealtime 축으로 기록. Perfetto의 sched/process/frequency 관측으로 benchmark/host계측/기타 시스템 활동을 구분한다. 기존 AP/current 주기와 화면·비충전·thermal gate는 유지한다.
2. trace는 세션 시작 전에 등록된 설정으로 **기기에서 유한 시간 기록**, 종료 후 한 번 회수한다. 실시간 ADB polling 증설·자동 reconnect·다른 앱 종료는 없다. profile 내용은 CPU시간·이름범주·클럭·idle 위주, heap/callstack/화면/사용자 콘텐츠는 수집하지 않는다. PID+생성시각/실행ID와 기존 app monotonic 마커로 결합한다. 해당 A24가 실제로 제공하는 data source와 clock/loss를 시작 단계에서 확인한다.
3. native/GPU/모뎀 전력을 CPU시간만으로 모두 설명했다고 하지 않는다. 전체/자기 UID traffic 카운터는 지원될 때만 보조로 사용하고 byte=J 변환은 하지 않는다. 권한/카운터가 없으면 unsupported, 다른 앱 UID 자료를 읽을 수 있다고 가정하지 않는다. 읽을 수 없는 필수 구분을 profiler 없이 해결했다고 표시하지 않는다.
4. 계측이 실행과 소비를 바꿀 수 있다. 개발·확인에서 동일 관측 설정을 유지하고 tracer 자체 CPU·버퍼손실·파일크기를 기록한다. tracing 비용을 임의로 빼지 않으며, 결과를 계측 없는 제품 APK의 정확도로 자동 전용하지 않는다. tracing 비용이 비교를 흐리거나 데이터 손실/시간정렬이 발생하면 해당 branch는 중단한다.
5. 이미 있는 0본요청 resident control을 이번 96요청 실행 경로의 단일 캠페인에 연결하고, 후보용 사전선택/대기와 예측 발행시각/입력 cutoff를 구현한다. 기존 원인·후속cleanup오류 분리와 소비 차단은 재사용한다. 가짜 adb/trace로 실제 진입·중복/소비 차단·손실·종료·정보누설 검사를 통과시킨다. 필요한 새서명APK는 기존 키/모델/정밀도만 재사용. 기기실행 전 해시·예산·검사를 다시 동결한다.

공식 근거: [Perfetto CPU scheduling](https://perfetto.dev/docs/data-sources/cpu-scheduling), [frequency/idle](https://perfetto.dev/docs/data-sources/cpu-freq), [Android trace 구성](https://perfetto.dev/docs/learning-more/android), [자기 프로세스 CPU시간](https://developer.android.com/reference/android/os/Process#getElapsedCpuTime()), [TrafficStats 지원·접근 제한](https://developer.android.com/reference/android/net/TrafficStats). 기능 설명은 A24 지원·계측비용 검증을 대신하지 않는다. GPU/전력 rail 지원을 전제하지 않는다.

## 4. 모형과 정책을 어떻게 보완할 것인가

기존 계수는 참조M0로 보존한다. 새로운 자료를 본 뒤 여러 후보를 최선이 나올 때까지 시험하지 않는다.

- 전력: 현재 `P=preload평균+상태증가분`을 task 비용과 시간변동 background로 구분한다. 4state 증가항은 개발D2~D5만으로 필요시 별도version에 추정한다. CPU시간/클럭/통신을 각자 J로 변환하는 다수계수는 식별 근거 없이 추가하지 않는다. 관측전력−task예측 잔차를 곧바로 '외부앱전력'이라고 부르지 않는다.
- AP 후보 구조는 사전에 하나로 제한한다. 기존 AP 예측에 `d(delta)/dt = -beta*delta + gamma*r(t)`를 더한다. `delta(시작)=0`, beta/기존 상태가열/준비이력 항은 동결본 그대로, 새 추정값은 gamma≥0 하나다. `r(t)`는 최근 완료된 10초 관측의 `(기기 전체 W - 기존 상태 증가 W)` 평균에서 해당 세션 부하 전 배경 W를 뺀 값이다. 이를 외부 앱의 실측 전력이나 주변 온도라고 부르지 않는다. 전체 기기 W를 다시 task 전력에 더하는 이중 합산도 금지한다.
- gamma는 개발 자료에서만 추정한다. beta·숨은 상태·지연·여러 gain을 동시에 맞추지 않는다. 수치 rank뿐 아니라 신호 변화량, 세션 제외 민감도, 잔차 방향을 공개한다. gamma를 식별할 신호가 없거나 한 세션에만 의존하면 null로 남기고 확인을 시작하지 않는다. D1/D6이 단조 평탄하다는 이유로 평형·주변 온도를 식별했다고 하지 않는다. 이 수식은 해결 보장이 아니라 검증할 최소 후보다.
- **신호 접근을 먼저 고정한다.** 앱은 현재 numeric AP를 직접 읽지 못하며 `ArrivalStartApGate`는 시작 전 host 승인 한 번이다. 따라서 Perfetto와 host AP는 사후 판독용이며 실행 중 정책 입력으로 가정하지 않는다. 실제 정책의 온라인 입력은 기존 앱 sampler의 과거 전류·전압, 이미 발생한 lane/요청 기록, 시작 전에 전달된 AP·준비 초기상태로 한정한다. 이후 AP는 모델 상태로 계속 전파한다. thermal status는 기존 안전 gate일 뿐 numeric AP 대체가 아니다. 초기화에 필요한 부하 전 AP 이력/요약은 최초 부하 전 한 번 전달하는 경로를 PC에서 검증한다. 앱의 전력 표본 신선도·실행 중 읽기 경계가 연결되지 않으면 해당 정책은 아직 실행 불가다.
- 센서 기반 갱신은 기존 sampler snapshot을 사용하고 10초마다 한다. 시각 d에 발행한 예측은 d까지 수신·완료된 표본만 사용하며 다음 10/30초의 r은 마지막 유효값 유지라는 가정을 표시한다. 나중에 회수한 AP로 과거 예측을 재초기화하지 않는다. 미래trace/전류/AP를 넣은 조건부 진단A, 예정 도착만의 개방루프B, 과거 표본으로 미래 구간을 예측하는 온라인C를 따로 저장한다. 초기화·유효표본·cutoff·horizon별 평가는 확인 전에 동결한다.
- 정책 후보는1개: 현재지원CPU/PAR배정과 normal요청의 **마감여유 안 대기**만 허용하는 단순 규칙. urgent는의도적으로기다리게하지않는다. 추가가열/호출/부하축소/미지원병행0. 동결된처리시간·큐·AP예측으로deadline/열제약을먼저검사하고 가능한선택중예측J를최소화한다. 동률/모형상태미확인은 필수 환경 gate가 유지될 때만 사전고정된PAR fallback, 모든deadline분모보존. 필수 환경/센서 gate 실패는 fallback이 아니라 중단이다. 처리시간 추정상 deadline을 넘기는 대기는 허용하지 않으며 실제 deadline 보장을 주장하지 않는다. 배정변경은빈lane에서만하며공통window의idle비용까지포함한다.
- 이 정책은 아직 구현·검증되지 않은 설계다. D자료로 식별된 모형/규칙/한계가 만들어지고 PC 지원검사를 통과해야 확인12로 간다. 후보가 두등록입력에서PAR와실제선택이전부같다면 불필요한12실측을하지않고 '선택여지없음'을기록한다. 대기효과를보이려고사후입력·마감변경을하지않는다.

기존 자료 재사용도 구현의 첫 관문이다. 위 구조·10초창을 고정한 다음 기존 개발 자료로 한 번 식별 가능성을 계산하고, 이미 본 확인 자료는 사후 평가로만 사용한다. 여기서 계수가 안정적으로 식별되고 새 실행 프로토콜에 전용할 근거까지 갖춰지면 개발6을 관성적으로 다시 측정하지 않는다. 새 자료가 필요한 항목만 남겨 캠페인 예산을 줄인 뒤 동결한다. 아래18세션은 최대 제안이며 최소 필요 반복 수라는 증명이 아니다. 과거 확인 자료를 새 독립 확인으로 세지 않는다.

주파수로 성능 변화가 확인되지 않으면 throttle곡선을넣지않는다. online갱신도 갑자기발생할 미래외란을예지하지못한다. 통계적 외란구간과 완전한 세션별 경로예측은 별개다.

새 후보의 실행은 별도 연구용 opt-in 경로다. 기존 `decision_support`의 정책 우월성 차단·strict·기본 모형을 해제해 실행하는 방식으로 만들지 않는다. 후보를 실제 비교하는 승인과, 예측 정확도/정책 우월성이 입증됐다는 판정은 다르다.

사전 accuracy PASS 수치는 현재 근거가 없으므로 만들지 않는다. 대신 PC개발 단계에서 검정할 **최소 정책 차이와 허용 서비스/열 손실의 근거**를 정리하고 확인 전 동결한다. 실용 효과 기준을 연구 요구나 센서 해상도로 정할 수 없으면 '통계적 차이 탐색'만 하며 실용 우월성 합격을 주지 않는다. 에너지와열의유리한지표만사후선택하지않고, 주지표/제약/다중비교처리를동결한다. 6쌍에서 분해능·변동성보다차이가작으면 '이조건에서는구분안됨'이 최종결과다. 모형오차한도와정책차이의불확실성은별도다.

## 6. 규모·시간·현실적인 준비 상태

제안 상한18세션=개발6+확인12. 본요청4×96+12×96=1536, warmup18×8=144, 총명시적추론1680, runtime72, staging18회·126파일. 앱별도적격성호출을추가하면 이수치에포함시키기전에는실행금지. 기존준비품질검사와warmup기록재사용이원칙이다. APK필요시전송/설치각1, 설치본pull각block1로최대2 제안. 재시도·대체·추가세션0.

고정 관측18×210=3780초=63분. 기존코드 budget식 `600+700*n+90*(n-1)`를 **참고 추산**하면 개발5250+동결180+확인9990=15420초(4시간17분)이며 기존원래계획의승인이아니다. 새trace 시작/회수/정리 예산을세션당60초로예약하는 설계목표는1080초, 합16500초(4시간35분). 실제trace지원/회수속도/새코드경로에서이상한을검증하기전에는최종예산으로부르지않는다. ADB기존 명령 예약의 참고 산식은 `(6*3200+200)+(12*3200+200)=58000`; 추가trace 명령상한은 아직미산정이며Run계획을 만들때한번고정한다. 숫자만줄이거나timeout을즉석늘리지않는다.

최근실제7세션37.7분을18세션으로단순비례하면약97분이다. 새trace·회수·동결시간과환경대기를고려한**운영 예상은 약2–3시간**이지만 실측된소요시간이나완주보장이아니다. 배터리/온도gate에따라미시도종료할수있다. 충전중측정/가열/무제한대기없음. 필요하면 처음부터개발·확인block사이에충전·휴식공백을별도기록하고각block시작환경을재확인한다.

PC구현에는 trace parser/clock·callbudget·새정책/onlinecutoff·서명APK/Check가남아있다. 기존소스로당장18세션을실행할수있는상태가아니다. 계획만요청된이번에는 APK빌드/Run/claim을만들지않는다. **다음 행동 하나: 위 한 후보의 기존 자료 식별 검사와 앱 과거 표본 기반 온라인 예측을 PC에서 구현·검증하고, 필요한 관측 확장과 캠페인 예산을 함께 동결한다.** 이과정에서조건을충족못하면설계차이를보고하며사용자주제를응답최적화로조용히바꾸지않는다.
