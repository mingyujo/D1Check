## 목표와 새 규칙

전량 완료·기한 준수·긴급 응답을 유지하면서 **최고 AP 온도 감소를 주목표, 전체 J 비증가를 조건**으로 둔다. AP와 J 모두 감소하면 공동 개선으로 구분한다. 새 연구의 열 우선 목적이며 과거 J 우선 실험을 소급 재판정하지 않는다. AP를 표면 온도나 스로틀링 효과로 부르지 않고, 외부 제품 전체가 아니라 동일 모형의 제한적 요청 adapter와 비교한다.

기존에는 beam/MPC, 3개 처리시간 문맥 검사, 예약 backfill, 제한 WAIT, 85관측·17행동 PPO가 이미 있다. 열 상태·도착 이력을 추가한다는 설명만으로 새 정책이라고 하지 않는다. [49,152 본학습 결과](REQUEST_RULES_RL_AMOUNT_20261007.md)와 [기존 국소 검사/전체 결과 차이](results/method_followup_01/README.md)를 설계 근거로 사용한다.

새 `RESERVED_THERMAL_REQUEST_V1`의 필수 차이는 다음과 같다.

1. **실행 가능한 현재 큐 전체의 후속 일정**을 저장하고 다음 공개 이벤트에서도 이어받는다. 저장 계획과 현재 SHARED_EFT 후속 계획을 후보에 포함한다. Band 원 adapter는 비교군으로 보존한다.
2. 기존 요청의 최후 응답/완료 예약과 소모한 여유를 기록한다. 새 callback의 기준정책을 다시 계산했다는 이유만으로 이전 예약을 늦추지 않는다. 시작시각 전체를 고정해 시간배치 자유도를 없애지 않는다.
3. 도착한 요청만 대상으로 배정·순서·제한 대기를 검토한다. 후보 전체를 완성한 뒤 서비스/비용을 검사하며 중간 단계의 J/AP 증가만으로 완성 가능한 조합을 버리지 않는다.
4. 지금까지의 모형 J·최고 AP·예약 변경을 누적한다. 후보 선택은 AP 최고값 우선, J 비증가 조건이며 미래 전체 기준정책 결과를 현재 예산으로 넣지 않는다.
5. 새 요청 삽입/관측 overrun/탐색 한도로 예약이 깨지면 `reservation_broken`과 원인을 기록한다. 요청을 버리지 않고 서비스 우선 기준정책으로 실행한다. 이미 생긴 손해를 없애거나 복구가 기한 보장이라고 표시하지 않는다.

정확한 예약 생성·유지·파손·복구 및 J 예산 갱신식은 **성능 배치 전에** 코드와 수작업 예제로 고정한다. 원래 deadline을 이름만 바꿔 새 예약이라 하지 않는다. 임의 새 여유 비율·허용 오차가 필요하면 Sol이 성능 결과를 본 뒤 선택하지 않고, 구체 구현안과 함께 Astra 설계 검토로 먼저 인계한다. 이는 남은 설계 경계이며 실행 가능 manifest로 위장하지 않는다.

기본 탐색 크기는 기존 처음 4요청·깊이 4·beam 8·최대 64확장을 재사용하고 전체 현재 큐의 후속 일정을 포함한다. 기존 0.25초 단위 WAIT와 도착 후 2초 유예 제한을 확대하지 않는다. 동점은 AP 최고값→J→긴급 예상 응답→정규화한 요청/행동 ID 순으로 정한다. 수치 동률 허용치는 부동소수점 처리용이지 물리적 개선 허용폭이 아니다.

같은 기저·공통창에서 상태별 총점유시간을 유지하면 모형 J가 같다는 성질을 활용할 수 있다. 그러나 새 도착·겹침 변화·예측 오차가 있으므로 국소 통과가 전체 J 비악화를 보장하지 않는다. 미래 도착 제한이 없는 상황에서 전역 기한 보장을 주장하지 않는다. 응답/저장/worker release와 실제 lane 해제를 분리하고 예측시각만으로 lane을 해제하지 않는다.

## Astra 단계 3

예약 유지와 정보 시점, 완료 요구, 기존 정책 보존, 후보 다양성, J/AP 상충, 판단 비용을 검토한다. 전부 기준정책과 같은 일정이면 RL이 선택할 대상이 있는지 확인한다. 적격 대안의 개선 근거가 없으면 대규모 학습을 자동 시작하지 않는다. 제한 탐색 실패를 개선 불가능의 증명으로 쓰지도 않는다.

판정은 `PROCEED_RULE_ONLY`, `PROCEED_RL`, `REVISE_BEFORE_RUN`, `STOP_NO_EVIDENCE` 중 하나로 기록한다. 기존 오류를 고칠 수 있으면 구체 수정 범위를 Sol에 넘긴다. 기한/완료 요구·물리 계수·평가 범위를 유리하게 바꾸는 수정은 하지 않는다.

## 동일 조건과 최종 판정

분류 output-ready 1.5초, 탐지 persist-complete 6초, 전체 J 0–120초, AP 35–180초를 유지한다. 미완료 J는 부분작업으로 표시하고 AP 전체창 적격성을 분리한다. 임의 AP 안전 임계값은 만들지 않는다.

새 시험은16 trace seed × 기존4부하 × 기존3처리문맥 =192조건이다. low/sustained96조건을 주 서비스 판정으로, queue/burst96조건은 용량 경계와 함께 과부하 진단으로 모두 공개한다. 부하 생성기·요청 수·입력·기한·실현 비용 규칙은 바꾸지 않는다. mean/short/long은 개발 스트레스 문맥이며 신뢰구간/WCET가 아니다.

새 seed 범위는 기존 모든 실행 이력과 충돌 검사 후 입력 생성 전에 등록한다. train/validation/test 의미 서명과 hash를 분리한다. 검증은 low/sustained ×4seed ×3문맥 =24조건이다. 새 합성 seed는 독립 실기기 확인이 아니다.

최초 계획은 pilot10개 + 동결RL3seed=13개/2,496행, RL보류 시10개/1,920행이었다. 실제 단계3에서 내부EFT 대조를 추가하고 원후보 대신R2를 동결해, RL0·11개/2,112행으로 명시적 개정했다. 상세 범위/허가는 RULE_ONLY_REVIEW.md·registration.json을 따른다. Triton 모든 설정, 강한 제한해제/2건허용, Band, EFT를 각각 비교하고 좋은 RL seed만 보고하지 않는다.

각 조건·각 기준별로 전량·기한·긴급P95 비악화를 먼저 확인한다. 그 다음 `ΔAPpeak<0, ΔJ<=0`를 열 개선형, 둘 모두 음수를 공동 개선형으로 표시한다. 단위는 °C/J/ms이며 절대 섭씨의 퍼센트는 쓰지 않는다. 전체 조건 비악화와 일부 조건 개선을 구분하고 평균의 이득으로 개별 기한 실패를 상쇄하지 않는다. 일반 완료시간·AP면적·WAIT/병행·예약 파손·fallback·판단시간도 저장한다.

작은 모형 차이를 실제 기기 성과로 승격하지 않는다. 모형 밖 제어 비용0이라는 기존 가정과 PC callback 시간을 분리한다. 대표 trace는 결과 전에 첫 등록 seed/mean과 정한 부하로 고정한다.
