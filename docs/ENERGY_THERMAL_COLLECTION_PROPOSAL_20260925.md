# 현재 두 모델 에너지·열 결합 수집 후보 — 실행 미승인

> 2026-09-25 후속 준비: 이 단독8세션/3480요청/127분 후보는 **미실행 과거 제안**으로 보존한다. 현재 실행 준비는 [두 병행 조합·실제 직렬 대조 계약](ENERGY_THERMAL_COLLECTION_PREP_02_20260925.md)의 새 예산/namespace를 따른다. 이 후보를 소비하거나 소급 변경하지 않는다.

ENERGY-THERMAL-PC-01의 남은 공백만 다룬다. 과거 종료 계획/registry/예산을 재사용하지 않는다. 이번 작업에 실기기 명령·ADB·설치는 없다. **계약/예산 후보이며 Android telemetry 연결·긴 세션용 별도 timeout 계약·device manifest는 아직 미완료**다. 실행 가능한 기기 CLI가 있다고 표시하지 않는다.

## 질문과 범위

A24 현재 EfficientNet-Lite0 분류와 EfficientDet-Lite0 탐지, exact 입력/hash·CPU thread1·resident4runtime·현재 품질 판정을 유지한다. 분류 normal/탐지 urgent를 대표 역할로 사용한다. 양 priority에 동일 전력계수를 전용한다고 검증하지 않는다. 새 일시정지 구현·NPU·다기기·정책 최적화는 선행조건이 아니다.

최소안은 CPU/GPU의 **4개 단독 경로**다. 양 backend 후보를 비교하는 데 필요하므로4개이며 thread/duty 전체 행렬을 다시 측정하지 않는다. 병행은 이번 최소안에서 계속 unsupported다. 병행 후보를 실제 사용할 때에는 해당 한 조합과 동일 두 작업량의 직렬 혼합 대조를 추가한 별도 수정 예산이 필요하다. 반대 방향 co-run 자료를 전용하지 않는다.

## 한 세션 구조와 관측

새 프로세스 → runtime4생성 → 기존 순서 warmup8 → resident idle120초 → 고정 요청량의 단독 연속 실행 → runtime 유지 idle/냉각180초 → 기록 회수·정상 해제·host cleanup.

기존 logger의 전류/전압/전하량·plugged, thermal parser의 AP/BAT/PA/SKIN/thermal status와 bracket clock, adapter의 요청 시작/추론/output/persist/worker/lane를 연결한다. battery %도 남기지만 요청별 에너지로 환산하지 않는다. 전류 원시값·단위 가설·유효성·원시 센서 덤프를 보존한다. CPU/GPU worker 소유권·memory admission은 유지한다.

약1Hz 표본은 요청별 직접 에너지가 아니라 긴 상태 구간 평균용이다. 호출별 동기 journal은 사용하지 않고 기존 버퍼 기록·overflow/실패를 보존한다. 같은 logger/화면 밝기/interactive/무선 연결/비충전 조건을 모든 세션에 적용하고 실제 값/주변 조건/폰 위치를 기록한다. logger overhead는 전체 기기 에너지에 포함되며 관측 없는 앱의 절대 전력으로 주장하지 않는다. warmup 비용은 별도 구간으로 남기고 유휴에서 제외한다.

120초는 A24 counter 변화 중앙간격 약60초의 두 주기, 180초 냉각은 옛 A24 AP의 관측 식별 시정수 최대 약58초의3배를 참고한 **초기 제안**이다. resident/새 모델에서 같은 상수가 성립한다는 뜻이 아니며 BAT/SKIN 식별이나 완전 냉각은 보장하지 않는다. 초기 신호가 부족하면 추가 반복으로 감추지 않고 미식별로 종료한다.

## 개발→동결→확인과 예산 후보

독립 단위는 새 프로세스의 세션이다. 개발4조건 각1세션, 규칙/계수/지원 범위 동결, 확인4조건 각1세션: **총8세션**. 이는 각 조건 한 번의 확인 가능성을 확보하는 초기 보정 최소안이며 power/tail/반복 안정성을 보장하지 않는다. 요청 수를 독립 표본 수로 세지 않는다.

같은 task는 CPU/GPU에 같은 완료량을 사용한다. CAL-03 개발의 dispatch→lane 중앙값을 오직 시간 예산의 초기 참조로 사용한다. 분류 normal CPU0.177216154s/GPU0.321623346s, 탐지 urgent CPU0.6251414235s/GPU1.148384462s. 가장 빠른 경로도 약120초가 되도록 분류678건·탐지192건을 **후보**로 둔다. 연속 실행 전이·저장 부담으로 실제 시간은 달라질 수 있으므로 처리시간 상한으로 사용하지 않는다.

| 항목 | 제안 값/근거 |
|---|---|
| 세션 | 개발4 + 확인4 = 8 |
| runtime 생성 | 최대32 |
| 진단 요청 | (678×2 + 192×2)×2 = 3,480 |
| warmup | 8×8 = 64 |
| 명시적 추론 | 최대3,544 |
| 설치 | 변경 APK가 필요할 경우 최대1회, 정확히 동일하면 생략 |
| retry/대체/추가 | 모두0 |
| 기준 실행량 시간 추정 | 전체 약22.6분(CAL-03 단독 점추정 기반, 보장 아님) |
| resident 유휴 | 120초×8 = 16분 |
| 냉각 관측 | 180초×8 = 24분 |
| 생성/warmup 예약 | 최대90초×8 = 12분 |

실행 순서는 개발 `분류CPU→탐지GPU→분류GPU→탐지CPU`, 확인은 역순으로 제안한다. 이는1회씩의 초기 보정 순서이며 완전한 순서 효과 균형화/정책 paired 평가가 아니다. 확률 seed로 독립성을 꾸미지 않는다.

중요: 기존 짧은 arrival Activity watchdog/host timeout으로 위 장시간 세션을 실행할 수 없다. **기존 timeout을 조용히 늘리지 않는다.** 별도 수집 경로에 단계별 timeout과 새 전체 예산을 구현·PC 검증하고 manifest를 동결한 후 승인받아야 한다. 과거600초 진단 계약이나 종료된 수집 예산을 재사용하지 않는다. 이번127분은 그러한 후속 실행에 대한 계획 후보이며 현재 실행 가능한 승인 예산이 아니다. 각 세션 상한14분(120+360+180+90+90초), 합계8×14+5+10=127분이다.

## 사전 적격 조건과 중단

- 같은 기기/fingerprint/모델·입력 hash/품질·runtime/thread를 확인한다. 비충전·기존 안전 thermal/memory/배터리 gate를 유지한다. 안전 gate 값을 이번 자료에 맞춰 완화하지 않는다.
- boot/시계/세션 일치, 원시값과 단위 분리, 충전·sentinel·상충 중복 없음. clock bracketing 불확실성과2.5초 넘는 power gap은 별도 기록한다. 주요 구간 coverage95% 미만이면 계수를 산출하지 않는다. 이는 수집 구조 적격성이지 에너지 정확도 허용폭이 아니다.
- counter 감소가 양자화2단계보다 작으면 단위 일관성의 결정 근거로 쓰지 않는다. 충분한 변화가 있어도 counter를 외부 참값으로 승격하지 않는다. μA/mA 해석이 구별되지 않으면 absolute J는 조건부/미확정 유지한다.
- 초기/부하/냉각 온도 곡선의 변화가 baseline 변동 또는 sensor3단계 중 큰 값보다 작으면 해당 센서의 계수를 미식별로 남긴다. 주변온도 미측정이면 equilibrium을 ambient라 부르지 않는다.
- 모든 예정 요청의 시작/종료·품질/실패·미완료를 보존한다. 요청 상한/실행 시간 초과·누락/overflow·환경 이탈·연결 실패이면 전체 중단, 회수/cleanup, 재시도0. 미완료의 makespan/완료량당 절감 성공은 계산하지 않는다.
- 확인 전에 산출 규칙·개발 계수·해시와 지원 범위를 고정한다. 확인 오차는 그대로 보고하고 재보정하지 않는다. 에너지/온도 예측의 실용 허용오차는 아직 서비스 근거가 없어 **미확정**이다. 그 값이 결정되기 전에는 정확도 PASS 없이 초기 확인 오차만 보고할 수 있다.

성공하면 현재4단독 경로의 resident idle·상태별 에너지·AP 등 식별 가능한 열 응답을 초기 보정할 수 있다. 병행·다른 역할·고부하/tail·에너지 절감·정책 우월성 PASS는 남는다. 다음 단계에서 오류가 작다는 이유만으로 독립 정책 평가를 자동 실행하지 않는다.
