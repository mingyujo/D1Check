# 시작 전 CPU 활동을 이용한 기준전력 후보 결과

**시작 전 CPU 활동을 추가했지만 에너지 평균 오차 감소를 확보하지 못했다.** 후보를 실제 구현하고 개발6/이미 본 확인6에서 평가했다. 확인6의 공통120초 평균 절대오차는 기존 δ=0 보완식4.564→5.522J로 악화해 미채택한다. 직전 활동이 이후에도 유지된다는 가정의 반례를 기록으로 확인했다. 새 기기 실행·새 실측 계획·기존 모형 교체는 없다.

## 질문과 고정한 후보

[직전 근거](PREBOUNDARY_EVIDENCE_RESULTS_20261010.md)는 같은 resident C0 조건에서도 pre50 전력과 추가 CPU 활동이 높았다가 이후 함께 감소한 사례를 찾았다. 이번에는 그 사후 연관을 미래 CPU를 쓰지 않는 예측으로 옮길 수 있는지 검사했다. 이전 AP 초기정보 보완 결과는 그대로 보존하고 AP를 재추정하지 않았다.

[분석 계약](results/cpu_prebaseline_01/analysis_contract.json)을 새 pre 정보 추출·추정 전에 기록했다. 구조1개/계수1개/다른 회복시간 블록 제외2회＋최종개발1회, 총3회만 추정했다. 창·목표·계수 제약을 결과를 보고 바꾸지 않았다.

```text
U50 = other CPU core seconds / wall second, [-20,30] 평균
Ulate = 같은 지표, [10,30] 평균
P_new = P50 + b × (Ulate − U50)
```

- b는 개발6의 **부하 전50초** 5초 bin에서 전력/CPU 값을 각 세션 평균으로 중심화하여 비음수 최소제곱으로 추정한다. 세션 가중치는 같다. 전역 intercept·미래 전력 목표·확인 온도·새 물리 계수를 넣지 않는다.
- 실제 전력은 기존 전류·전압 적분을 사용한다. CPU 값은 기존 Perfetto `sched`의 `other` 분류다. 특정 앱·ADB·GPU·무선 활동의 인과적 J 계수를 뜻하지 않는다.
- P50 및 기존4상태 전력 계수는 그대로다. 보정은 고정된35..120초에만 적용하고0..35초는 변경하지 않는다. 범위를 넘어 연장하거나 음수 전력을 clipping하지 않는다.
- 실제 lane 일정이 주어진 **조건부 에너지 계산**이다. 예정 도착부터 일정·응답을 생성하는 종단간 예측이나 온라인 정책 성능 검증이 아니다. 공통0..120초에는 가정한 정보 경계35초 이전의 회계도 포함한다. 순수한 이후 예측35..120초를 따로 보고한다.

최종 b=0.5914086056 W/(core seconds/second), 회복30 제외0.5958887427/회복180 제외0.5841654906이다. 수치적으로 한 계수를 추정할 변동은 있었지만, 인과적 CPU 전력과 미래 활동의 지속성을 식별한 것은 아니다. 개발 세션의 시작 전 전력 잔차 RMSE는0.101895W다.

## 왜 이 후보가 실패했는가: 실제 반례

| 무부하 확인 | U50 | Ulate | 이후35..120초 U | CPU 후보의 보정 | 필요한 사후 유휴 차이 |
|---|---:|---:|---:|---:|---:|
| 회복180 C0 | 0.34358 | 0.45900 | 0.27245 | +0.06826W | −0.03267W |
| 회복30 C0 | 0.39213 | 0.39209 | 0.28209 | −0.000027W | −0.07420W |

이후 U와 ‘필요한 차이’는 **평가·원인 분해용 관측값**이며 후보 입력에는 없다. 회복180은 직전 CPU 증가를 지속된 기준으로 삼아야 한다는 가정과 반대로 이후에 감소했다. 이 사례의120초 절대오차는2.764→8.566J로 악화했다. 회복30은 pre 평균 활동이 거의 같아 후보가 보정하지 못했지만 이후 전력은 낮아졌다. 4.421→4.418J의 극소 감소는 핵심 오차를 해결한 것이 아니다.

추가로 확인6 중4개는 pre CPU 수준 또는 대비값이 개발6의 관측 범위를 벗어났다. 이 조건들도 제외하지 않고 **계산된 외삽 진단**으로 공개한다. 범위 안의2개도 한 개 개선/한 개 악화하여 ‘범위 밖4개를 버리면 채택 가능’이라고 결론 내릴 수 없다. 관측 범위 표시는 새 strict 판정이나 사후 좋은 조건 선택이 아니다.

**해결하지 못한 항은 작업 상태의4계수가 아니라, 준비 중 활동의 어떤 부분이 이후에도 남는지에 대한 기준부하 예측이다.** 실제 CPU와 전력의 동시 변화라는 근거는 있지만, 시작 전 마지막20초만으로 그 지속·소실을 판별하지 못했다. 숨은 원인을 특정 앱·무선·충전·GPU로 확정하지 않는다. 이것은 이 후보의 실패이며 모든 CPU 정보 또는 모든 모형 보완의 불가능성 증명이 아니다.

## 가용성·구현·검증

- 12세션 전부 기존8CPU trace coverage·loss0·BOOTTIME equality·source binding을 검증했다. 전력 pre50을 기존 값과1e−10W 이내로 재현했다. 유효 pre bracket의 마지막 event는35초보다 앞이다. 미래 전류/AP/CPU를 바꿔도 예측이 변하지 않는 경계 시험을 실행했다.
- **trace CSV는 종료 후 생성된 파일**이다. 이번 특성은 사건 시각상 예측 전 정보지만 실제35초에 CSV가 생성·전달된 것은 아니다. 결과는 저장 기록의 오프라인 진단이고, live CPU 특성 추출·전달 API는 미구현이다. 기존 앱이나 RL의 실시간 입력에 연결하지 않았다.
- 새 경계 단위시험7건 통과. 부분집계 가산성1e−9J 이내, 공유 누적곡선1,440점 재생 차이0J. 기존 원자료/trace/CSV120파일의 해시 불변을 확인했다. AP재생·새환경실행·기기/ADB/추론/설치/빌드0이다.
- 이번 새 후보의 RMSE 표시에서 가중치 복원 누락1줄을 발견해 고쳤다. 최초 소스와 frozen 후보/등록/receipt는 보존하고 [source amendment](results/cpu_prebaseline_01/source_amendment.json)에 수정 근거를 남겼다.0.032222는 실제W RMSE가 아니라 가중 잔차 값이었다. 올바른 값0.101895W를 별도 판독에 기록했다. 계수·J 예측·평가값·채택 결론은 바뀌지 않았고 정식 추정3회는 반복하지 않았다. 기존 모형의 처리 결함이나 예측오차 감소로 포장하지 않는다.
- 기초 동결식5682082a…·AP후보aa28410d…·δ=0 후보bf12fd70… byte는 유지했다. AP의 power proxy도 바꾸지 않았다. 나머지23자료는 이번 trace 입력/계약 밖으로 자동 적용하지 않았다.

## 완료 판정과 다음 한 가지

CPU 기준전력 후보의 구현·유한 평가·반례 확인은 완료했다. 평균 에너지 개선은 확보하지 못해 **미채택**이고, 기본 시뮬레이터/RL/strict/experiment_ready=false는 보존한다. 이전 AP 확인6 MAE0.230→0.166°C의 초기정보 개선 근거는 취소하지 않지만 이번 작업이 AP를 더 개선한 것은 아니다. 독립 정확도·작은 정책 차이 판별·실기기 절감은 미완료다. A24 raw=mA와 절대J 미인증을 유지하며 S26 계수는 쓰지 않았다.

다음 PC 질문은 **동일 원자료의 등록회복 전체 전력·CPU 이력에서 지속되는 기준부하와 일시적인 준비 활동을 구분할 수 있는가** 하나다. 50초 직전값 지속 가정과는 다르고, 이미 있는 회복30/180초 구간을 이용할 수 있다. 새 측정이나 성공할 때까지 창·계수를 바꾸는 탐색을 자동 추가하지 않았다. 이를 시작할 때도 개발/이미 본 평가를 분리하고 미래 활동은 평가에만 남겨야 한다.
