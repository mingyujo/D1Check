# ENERGY-OPERATIONAL-PAIR-01의 제한된 PC 연결

2026-09-26. [원래 4세션 결과](ENERGY_OPERATIONAL_PAIR_01_RESULTS_20260926.md)의 원본을 읽기 전용으로 재생하고, **개발 직렬 1·병행 1세션만** 단계별 고정 작업묶음 템플릿에 넣었다. 기존 개발 설정 SHA-256 `1dc5766a…2881`은 그대로 두고 별도 [PC profile](results/energy_operational_sim_01/frozen_profile.json)과 [평가 명세](results/energy_operational_sim_01/evaluation_spec.json)를 저장한 후 확인 직렬 1·병행 1세션의 오차를 산출했다. 이번 연결은 **확인 결과 요약을 이미 본 뒤** 설계했고, 중간 확인 오차를 열람한 상태에서 개발 자료의 미계측 경계와 manifest 식별 검사를 보완했다. 따라서 최종 모형의 확인 오차는 완전한 사전등록 독립 검증이 아닌 탐색적 holdout이다. 확인 오차에 맞춘 계수 재보정·PASS 기준 조정은 하지 않았고 PASS 기준 자체도 없다.

## 지표의 실제 경계

모든 요청의 분모는 세션당 분류 CPU 678·탐지 GPU 192 = 870건이다. 두 block 모두 완료·품질 적격이며 개발 순서는 직렬→병행, 확인 순서는 병행→직렬이다. 시작 AP는 개발 직렬/병행 29.4/29.2°C, 확인 병행/직렬 29.1/29.1°C다. 같은 AP 값이 동일 내부 열 상태를 뜻하지 않는다. 세션별 resident idle 평균전력은 개발 직렬/병행 1.161/1.116W, 확인 병행/직렬 1.146/1.096W였다. 시간 경과·순서·유휴 소비 차이를 병행의 인과효과에서 분리할 독립 반복은 없다.

| 지표 | 시작→종료 | 개발 병행−직렬 | 확인 병행−직렬 | 준비 포함 여부 |
|---|---|---:|---:|---|
| 작업 완료시간 | 부하 시작→각 870건 완료 | −122.456초 | **−126.319초** | resident 준비·baseline 제외 |
| 완료시점까지 기기 전체 에너지* | 부하 시작→각 870건 완료 | −179.801J | **−143.341J** | 준비·완료 후 idle 제외 |
| 공통 관측창 기기 전체 에너지* | 부하 시작→480초, 빠른 arm의 완료 후 resident idle 포함 | −36.255J | **+4.559J** | 준비·냉각 제외 |
| 부하 중 AP 최고온도 | 부하 시작→870건 완료 | +1.2°C | **+1.9°C** | AP 센서만, 시작 온도 별도 |

명목 480초 공통창의 실제 기록 경계는 세션별 480.000~480.082초였다. PC 템플릿은 명목 480초로 고정하므로 그 미세한 경계 차이도 오차에 포함된다.

* A24 raw 전류=mA 해석과 기기 전체 전압×전류 적분에 조건부인 J다. CPU/GPU 직접 에너지가 아니며 절대 정확도는 미인증이다. 준비·baseline·냉각은 [CSV](results/energy_operational_sim_01/comparison.csv)에 **별도 계측 단계**로 보존했다. 초기 runtime/gate 일부, baseline→load 전환 약 1.3~1.5초, 일부 cooling의 전류 커버리지, 최종 host 회수·cleanup은 완전 계측되지 않았다. 미계측 구간을 0으로 채운 `전체 운영 에너지`는 만들지 않는다. 단계별 관측 에너지의 단순 합도 전체 에너지라고 부르지 않는다. AP 경로는 같은 단계의 raw monotonic 시계와 맞추고, host 시간과 직접 빼지 않는다. BAT 온도 모형은 미식별로 유지한다.

## PC 연결과 제한

`tools/d1_energy_operational_sim.py`는 기존 정책·이벤트 엔진 기본 경로를 바꾸지 않는 격리된 **고정 episode 모형**이다. A24 fingerprint, 현재 두 모델·입력 hash, 4-runtime resident, CPU thread 1, `classification_CPU 678 + detection_GPU 192`의 CC_DG, 원래 고정 준비·baseline·부하·완료 후 대기·냉각과 480초 관측창에만 사용한다. 동일 작업량의 직렬 또는 병행을 **미리 지정**해야 한다. 새 도착·선택·GPU kernel 동시성·반대 배정·부분 overlap·다른 duty·고온 반복·BAT 온도는 지원하지 않는다. 기본 CAL-03 시뮬레이터의 병행 허용 범위나 `experiment_ready=false`는 그대로다.

- **원본 재생:** 원시 기록을 기존 validator로 다시 적분해 4개 `validated.json`의 경계·시간·에너지·AP 지표와 일치하는지 검사한다. [결과](results/energy_operational_sim_01/raw_replay.json)는 계측/구현 일치 검사이며 미래 예측 검증이 아니다.
- **제한된 예측:** 개발 세션의 계측된 단계 길이·평균 기기 전력·AP 단계별 관측 경로를 고정한다. AP 경로는 관측 시작값에 평행 이동한 경험적 템플릿이며 물리적 가열 방정식이나 전력→열 계수가 아니다. 확인 단계의 **첫 준비 AP 관측값만** 초기 조건으로 받는다. 미래 완료시간·미래 요청·확인 계측값은 입력하지 않는다. 준비·부하·idle·냉각은 시간상 중복 없이 이어지나 baseline→load 전환 에너지는 `null`로 두고, 냉각 전류 커버리지가 부족한 arm의 전체 냉각 에너지도 `null`로 둔다. 공통창은 부하와 완료 후 idle의 합이다. 따라서 완료시점·공통창 예측은 있지만 전체 운영 에너지의 완결 예측은 없다.
- **탐색 가정:** 다른 작업량·입력·병행 배정·도착 간격·온도 초기조건에서 이 수치를 재사용하는 모드는 구현하지 않았다. 단독전력 합을 병행전력으로 만들지 않는다.

## 해석과 다음 조건

현재 PC 기능은 **이 CC_DG 고정 묶음에서** 작업을 빨리 끝낼 때 완료시점 에너지와 480초 기기 전체 에너지·AP 최고온도가 서로 다르게 움직일 수 있음을 보여준다. 서비스 기준·에너지/온도 가중치가 미정이어도 절대값을 함께 읽을 수 있다. 이 한 block의 순서 교차와 arm당 1세션으로 병행 자체의 인과효과, 에너지 절감 PASS, 반복 안정성, 발열 안전 상한, 운영 전체 에너지, 정책 우월성은 판정할 수 없다. 기존 40 동결값·20 null·FAIL·종료 계획은 유지한다.

다음 필수 단계는 **연구 주장 범위 결정**이다. 고정 CC_DG 기술 비교에 머무르면 새 실측 없이 이 표와 모형의 공통창 방향 실패까지 보고하면 된다. 다른 배정·임의 도착·장시간 운영에 대한 에너지/열 최적화나 서비스 제약 충족을 주장하려면 해당 조건의 독립 계측과 지원 범위를 먼저 별도 계약으로 정해야 한다. 이번 PC 연결만으로 실기기 추가 수집이나 정책 조정을 시작하지 않는다.

재현 명령·입력 경로·작은 산출물은 [결과 README](results/energy_operational_sim_01/README.md)에 있다.
