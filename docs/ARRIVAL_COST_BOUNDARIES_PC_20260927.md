# B2·B3·CPU 긴급우선의 미측정 비용 경계 — 2026-09-27

**결론:** 기존 PC 결과만으로 서비스 지표와 **가정된 전력 아래의 대수적 역전점**은 비교할 수 있다. 그러나 도착 작업의 상태별 기기 전체 전력·AP 반응은 측정되지 않았고, 일반 기한 손실과 긴급 응답의 허용 상충도 확정되지 않았다. **특정 미측정 상태가 에너지·열 후보 판단을 막지만, 그 상태만 측정해도 최종 단일 정책은 선택할 수 없다.** 이번 결과는 새 실측이나 정책 우월성 판정이 아니다.

## 입력과 같은 경계

기존 [정책 선별](ARRIVAL_POLICY_CANDIDATE_SCREEN_20260927.md)의 B2·B3·CPU 긴급우선만 사용한다. low/queue/burst × 기존 평가 seed 201–205 × 실현 간섭 1/1.5/2에서 같은 24요청·동결 CAL-03 벡터·PC 엔진·공통 120초를 맞췄다. [기존 응답 CSV](results/arrival_diagnostic_02/interference_metrics.csv), [기존 사후 전력 회계](results/arrival_diagnostic_02/energy_boundaries.csv), [기존 seed201 상세 trace](results/arrival_visualization_01/timeline.csv)와 [기존 AP 가정 결과](results/arrival_visualization_01/arrival_energy_stress.csv)를 **재집계**했으며 엔진 실행 배치는 다시 돌리지 않았다. B2는 개발에서 고정한 분류 GPU＋탐지 CPU 배정이고 평가 조건별 재선정이 없다. 24건 모두 완료한 PC vector여서 실패·거절의 기기 확률을 평가하지 못한다. 긴급 1.5초·일반 6초는 연구용 요청별 기한이다.

| 상태/비용 | 기존 근거로 확인한 것 | 미측정 또는 지원 경계 |
|---|---|---|
| 단독 CPU/GPU, 준비·callback·저장 | CAL-03 동결 단독 구간이 PC 처리시간 벡터에 반영됨. 저장된 PC timeline에서 각 lane의 단계·점유·해제와 seed201의 CPU/GPU 단독 시간을 읽을 수 있음 | 합성 도착에서의 단독 **기기 전체 전력/AP**과 장시간 부하 변화는 미보정. 준비·callback을 별도 전력 상태로 식별하지 못함 |
| 큐 대기 / resident idle | timeline에서 요청별 도착→dispatch 대기와 두 lane 유휴를 구분함. 공통창에서 대기 전력은 idle 또는 다른 활성 상태에 **한 번** 포함 | 큐 자체의 추가 전력·열 비용은 식별 불가. 0W로 넣지 않음 |
| B2 분류 GPU＋탐지 CPU | seed201/실현1.5의 queue에서 두 lane 점유 2.531초, burst 2.486초; 실제 양쪽 `execute` 단계 겹침은 각각 1.857/1.797초 | 이 **CG_DC** 배정의 도착 상태별 기기 전력·AP 미측정. 과거 고정870건 **CC_DG**(분류 CPU＋탐지 GPU)를 대칭 복사할 수 없음. API 실행 단계 겹침은 GPU kernel 동시 실행 증거가 아님 |
| B3의 혼합 병행 | seed201/실현1.5 queue의 두 lane 점유 약 10.338초 중 **탐지 CPU＋탐지 GPU 8.326초**, CG_DC 1.324초, CC_DG 0.688초. 여러 병행 조합을 실제로 사용함 | 동일 task 두 backend의 동시 실행, 혼합 overlap 각각의 실제 전력·AP·간섭 미보정. 단일 `pair W`는 탐색용 뭉뚱그린 값 |
| CPU 긴급우선 | CPU 단독·전체 직렬; queue/seed201/실현1.5 단독 점유 12.402초, 두 lane 점유 0 | 합성 도착 resident idle/CPU 활성 전력·AP 역시 미보정 |
| AP 열 | 기존 seed201/실현1.5 사후 1차 상태 모형의 **가정** 아래 최고 AP를 다시 비교할 수 있음 | 시작29°C, idle/단독/병행 평형29/34/30·42°C와 τ60초는 이 도착 상태의 확인된 계수 아님. BAT·표면온도·열→실행시간 피드백 없음 |

5 seed의 **idle·단독·두 lane 점유** 평균은 [상태 CSV](results/arrival_cost_boundaries_01/state_durations.csv), seed201의 CPU/GPU 방향·대기는 [상세 CSV](results/arrival_cost_boundaries_01/representative_states.csv)에 있다. queue에서 실현 간섭을 1→1.5→2로 바꾸면 B2의 두 lane 평균 점유는 **1.910→2.534→3.223초**, B3는 **6.831→9.646→12.542초**로 변한다. 이는 PC 모형의 실현 간섭을 바꿔 **일정 자체가 달라진** 결과다. CPU는 병행 0초다. 실현 간섭 1/1.5/2도 검증된 기기 분포가 아니다.

## 정책 쌍의 조건부 경계

첫 정책−둘째 정책, queue/실현 간섭1.5, 동일 seed 5개. 응답은 기존 PC 일정, 에너지는 그 일정을 고정하고 **idle 1W·단독 2W·병행 2W 또는 3W**로 사후 회계했다. J는 기기 전체 에너지의 가정값이며 절대 정확도·가능 전력 범위가 확인되지 않았다. 상대 %는 각각 둘째 정책 에너지 대비 seed별 비율의 평균이다. 괄호의 역전점은 병행 전력만 변경했을 때 seed별 0 교차 범위다.

| 첫째−둘째 | 긴급 P95 평균 Δ | 일반 평균응답 Δ | 기한 위반 Δ (긴급/30, 일반/90) | 2W 에너지 Δ 평균 | 3W 에너지 Δ 평균 | 병행 전력 역전점 |
|---|---:|---:|---:|---:|---:|---:|
| B2−B3 | −627.9ms | +114.4ms | 0, +3 | +0.594J (+0.452%) | −6.518J (−4.623%) | 2.070–2.100W |
| B2−CPU | −169.6ms | −308.3ms | 0, −6 | −0.424J (−0.320%) | +2.110J (+1.595%) | 2.156–2.179W |
| B3−CPU | +458.3ms | −422.6ms | 0, −9 | −1.017J (−0.769%) | +8.628J (+6.522%) | 2.093–2.116W |

모든 시나리오·간섭·seed의 절대 J/상대 %, 응답·위반·미완료와 역전점은 [seed별 경계표](results/arrival_cost_boundaries_01/pair_boundaries.csv), [27행 요약](results/arrival_cost_boundaries_01/boundary_summary.csv)에 있다. low에서 B3와 CPU는 PC 일정·응답·가정 에너지가 동률이고 B2는 긴급 응답이 느리다. queue/burst의 간섭 2.0에서는 B2가 B3보다 긴급·일반 응답 모두 빠르지만, 앞의 1.5 결과는 상충한다. 병행 전력 **2W**를 고정한 채 실현 간섭을 1→2로 바꾸어도 B2−B3 에너지 방향이 queue/burst에서 뒤집힌다. 이는 전력 계수의 변화가 아니라 **점유시간·일정 변화**다.

위 역전점은 `ΔE = Δt_idle P_idle + Δt_single P_single + Δt_pair P_pair = 0`의 대수적 해다. idle/단독 가정을 0.8/1.8→1.2/2.2W로 같이 바꾸면 queue/1.5의 B2−B3 역전점도 **1.870–1.900→2.270–2.300W**로 이동한다. 2–3W나 그 경계가 실기기에서 가능한지 알려 주는 상태별 측정 근거는 없다. 과거 고정870건의 전체 평균 전력은 도착의 idle·단독·CG_DC·동일 task 병행 계수가 아니며 전류 절대 단위도 조건부다. 특히 2W 근처의 <1J 차이를 현재 근거로 의미 있는 배터리 절감이라고 판정할 수 없다.

저장된 **seed201·실현 간섭1.5만**의 AP 최고온도 가정 차이는 병행 평형을 30→42°C로 바꿀 때 queue의 B2−B3가 **+0.522→−0.927°C**, B2−CPU가 **−0.175→+0.257°C**, B3−CPU가 **−0.696→+1.183°C**로 바뀐다. 이는 [대표 AP 표](results/arrival_cost_boundaries_01/representative_ap.csv)의 사후 경로 결과이며 다른 seed·간섭에서의 열 순위를 말하지 않는다. 열은 일정이나 정책 선택에 피드백되지 않는다.

## 판단과 다음 작업

**측정 필요성 분류:** 특정 미측정 상태가 실제 에너지·열 후보 판단을 막는다. 다만 긴급 응답과 일반 기한 손실 사이의 서비스 선호가 미정이므로 **측정만 늘려도 단일 정책은 선택할 수 없다.** 현 단계에서 결정 가능한 것은 조건별 응답 상충, 공통창 전력 역전식, 어떤 상태가 비교를 좌우하는지까지다. B2·B3·CPU 모두 에너지·열을 실제 dispatch 판단에 쓰지 않는다. 이번 에너지/AP는 사후 회계이며 발열·배터리 피드백 정책 성과가 아니다.

**다음 행동 하나:** B2−B3의 queue/burst 공통120초 비교를 바꿀 기기 전체 전력·AP의 **측정 목적**을 별도로 고정한다. 관측 상태는 resident idle·CPU/GPU 단독·B2의 CG_DC·B3의 탐지 CPU＋GPU를 포함한 실제 병행 혼합이며, 출력은 동일 24요청의 완료·lane 해제·상태 점유·공통창 에너지·AP 경로다. 기존 약 1초 전류/2초 AP 갱신으로 B2의 2.5초 병행이나 개별 짧은 요청의 비용을 안정적으로 분리할 수 없으므로 요청별 전력 추정을 목표로 하지 않는다. 상태가 충분히 오래 지속되는지와 독립 block 변동성을 먼저 확인해야 한다. Android active B2/B3와 관측 방법이 준비되지 않았으므로 세션 수·새 예산·실측 승인은 여기서 확정하지 않는다. 이 측정은 서비스 선호 대신 선택해 주지 않으며, 새 정책 개발·P 튜닝도 아니다.
