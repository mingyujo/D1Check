# 합성 도착 조건의 응답·에너지·AP 연구 계약 (PC v1)

2026-09-26, 출발 HEAD `28599175cdaa41b34594c44f17f2ab8873549407`. **사용자 결정:** 실측으로 보정한 모형과 출처를 밝힌 합성 조건에서 발열·배터리·응답을 함께 연구한다. 실제 서비스 SLA 충족, 실사용 배터리 절감, 동적 정책 우월성은 아직 주장하지 않는다. [기존 중간 질문](ENERGY_THERMAL_TO_ORIGINAL_GOAL_PLAN_20260926.md)은 고정870건 CC_DG이고 이번 도착 trace의 요청별 기한으로 대체하지 않는다. 과거 FAIL·부분 결과·동결값·종료 계획은 그대로 둔다.

## 최소 질문과 입력

질문: **같은 합성 도착·작업·품질·공통 관측시간에서 요청 배정/대기 선택이 긴급 응답, 일반 완료, 기기 전체 에너지와 AP 관측 경로에 어떤 상충을 만드는가?** 이 질문의 에너지·AP 부분은 아래의 새 상태 근거가 생기기 전에는 수치 비교하지 않는다.

기존 [`d1_arrival_explore_batch.workload`](../tools/d1_arrival_explore_batch.py)의 `evaluation` 입력 중 아래 세 가지를 정책 결과와 관계없이 선택했다. 세 조건 모두 24요청(긴급 분류6, 일반 탐지18), 기존 합성 기한은 긴급1.5초·일반6초다. 예정 도착부터의 기한이며 실제 사용자의 SLA가 아니다. 평가 trace는 과거 960실행에서도 이미 열람됐으므로 새 정책의 독립 평가 자료가 아니다. [입력 SHA·분모](results/arrival_energy_research_01/scenario_manifest.json).

| 조건 | 출처·생성 규칙 | 필요한 상황 | 실제 서비스와의 차이 |
|---|---|---|---|
| low | 기존 `low`, 1,200ms 간격 | 낮은 부하의 제어비용·idle 비중 | 실제 사용자 간격 분포 아님 |
| queue | 기존 `queue`, 200ms 간격 | 큐와 혼합 우선순위 | 실제 요청률·긴급 비중 미검증 |
| burst | 기존 `burst`, 80ms 간격, 6건마다 1초 추가 | 짧은 밀집 구간의 긴급 도착 | W-burst 계약의 별도 backlog+urgent burst를 그대로 재현한 것은 아님 |

작업/우선순위가 묶여 있어 task 효과와 priority 효과를 분리하지 못한다. 간섭계수1.5, 판단·기록·dispatch 각0.1ms, 부하 전이와 시간 벡터 재사용은 [기존 탐색](ARRIVAL_FOLLOWUP_AND_EXPLORATION_20260925.md)의 가정이다. 재현 가능한 입력이라는 뜻이 현실 도착 분포나 독립 검증이라는 뜻은 아니다. 새로운 deadline·작업량·유리한 workload는 만들지 않았다.

## 공통 지표·회계 경계

모든 정책에 동일한 요청 목록·실현시간 선택 규칙·시각 `0..120초`를 적용한다. 시작은 첫 예정 도착 `0`이며 마지막 도착은 low27.6초, queue4.6초, burst4.84초다. 마지막 도착 후 같은 120초까지 drain을 허용한다. 120초 뒤 응답/해제가 완료되지 않은 요청은 전체 **예정 24건** 분모에 남겨 미완료와 응답 미확인으로 따로 센다. 이를 지연0이나 완료로 처리하지 않는다. 완료 표본의 P95는 nearest-rank이며 해당 분모를 함께 표시한다. 미완료가 있으면 전체 makespan/throughput 성공값을 내지 않는다.

| 지표 | 정확한 경계 | 미확인·주의 |
|---|---|---|
| 긴급 응답 | 예정 도착→`output_ready` | 완료 응답만 P95에 포함; 늦음과 응답 미확인을 별도 기록, 기한 내 비율 분모는 전체 긴급 예정 도착 |
| 일반 응답·완료 | 예정 도착→`persist_complete`; 요청 완료는 실제 `lane_available` 확인 | 일반 평균/P95에는 관측 응답만, 기한 내 비율은 전체 일반 예정 도착. 저장 완료와 lane 해제는 별개 |
| 실패·미완료 | 예정 전체→성공·미완료·미도착·응답 경계 미확인 | 기존 PC 엔진은 실패/거절 확률 미구현이므로 실패율0의 실기기 근거가 아님 |
| 기기 전체 에너지 | 같은 `0..120초`의 `∫V·I dt` 또는 명시적 상태별 평균전력×체류시간 | 이 도착 조건의 유효한 전력 profile 없음. 준비/초기화는 0이 아니라 **창 밖·미계측**, 비교에 넣으려면 모든 정책에 같은 경계로 별도 수집 |
| AP 관측 경로 | 같은 `0..120초`의 AP 센서 시계열·최고·상승폭 | AP는 BAT/표면온도/공식 안전 한도가 아님. 임의 상태 전이의 열 법칙 미식별 |

실행·대기·idle·준비·저장·callback과 두 lane 동시 점유는 서로 배타적인 공통 시간 구간으로 회계한다. `worker_release`는 `lane_available`이 아니다. 기존 [`ledger_segments`](../tools/d1_energy_thermal.py)는 queue 대기 수를 함께 제공하고 새 adapter는 대기 중인 구간을 `|queued`로 분리한다. 전력은 기기 전체에서 **한 번만** 청구하며 CPU/GPU 독립 전력을 합해 병행 전력으로 만들지 않는다. 판단·기록 비용을 실행 전력에 또 더하지 않는다. 별도 준비/냉각은 이 120초 창에 포함되지 않으며 총 운영 비용이라고 부르지 않는다. 초기 AP를 같다고 가정하거나 AP를 평행 이동해 검증된 열 범위를 넓히지 않는다.

## 정책 대응과 다음 수집 경계

[PLAN의 원래 B2/B3/P](PROJECT_PLAN.md#7-반드시-넘어야-할-기준정책)는 각각 강한 정적 배정, 단독 예상완료 기반, 병행 비용·대기를 추가한 동적 규칙이다. 현재 `B2_PC`는 개발에서 선정한 strict CPU/CPU 직렬과 explore 분류GPU+탐지CPU 병행을 구분한다. 후자는 **에너지 미측정**이다. `B3_SOLO_EFT_PC`는 단독 추정 기반, `P_PAIR_COST_PC`는 가정 계수1.5와 상대 lane 피해·대기 추가다. 셋 모두 같은 미래정보 제한을 받지만 현재 축소 PC 구현은 원래 Android 정책 전체가 아니다. FIFO나 고정 분리를 약한 최종 기준으로 대체하지 않고, B2를 이번 결과로 다시 선정하지 않는다. 따라서 이번 버전은 새 성능 순위를 실행하지 않는다.

**새 실측이 반드시 필요한 경우는** 임의 도착의 정책별 에너지/AP 효과나 실측 기반 직렬/병행 최적화를 주장하려는 경우다. 식별 대상은 (1) 동일 A24·모델·입력/resident 환경에서 idle·queue·각 task/backend의 단독·준비/저장 비용과 AP 시간 경로, (2) 이번 정책이 실제 고르는 분류CPU+탐지GPU overlap의 길이별 전력/AP 및 직렬 대조, (3) B2 explore 반대 배정을 포함하려면 분류GPU+탐지CPU의 동일 자료, (4) 새 도착 trace와 정책을 Android에서 active로 재생했을 때의 실제 비용/완료다. (3)은 그 정책을 비교하지 않으면 최소 필수가 아니다. 기존 고정 묶음과 CAL-03의 재분석으로 (1)~(4)를 독립적으로 식별할 수 없다.

최소 후속 계측 계약 후보는 **정책 집합을 먼저 제한**한 뒤 low/queue/burst의 같은 trace·입력/품질·공통 120초와 준비/냉각 분리 관측을 쓰는 것이다. 첫 단계는 CPU 긴급우선과 CC_DG 고정 분리만 대상으로 각 조건의 단독/병행 상태 coverage와 실제 device 전류/전압/AP·상태 전이를 보정한다. 최소 조건 coverage는 `2정책×3조건=6개 조건`; 개발/독립 확인을 한 block씩 분리하면 산술상 **12세션 하한**일 뿐 안정성/효과 검정에 충분한 반복 수가 아니다. 새로운 실기기 active 정책 연결, 기기 계측 샘플링/오차, 조건별 세션 벽시계·충전/냉각 소모를 PC에서 먼저 확인해야 설치/추론/warmup·전체 시간 상한을 정할 수 있다. 실제 120초 창 12개만 **24분 고정 관측 하한**이며 초기화·준비·냉각·회수는 빠져 있다. 이 예산·계측 계약은 **실행 불가 후보**다. 성공 기준은 단위·시계 정합/전력 커버리지, 단계별 AP 갱신 신호, 작업량·품질/완료 분모, 두 arm 모두 동일 경계, 독립 확인 오차를 결과 전에 동결하는 것이다. 실패하면 효과 판정/정책 확장을 중단한다. 보정 표본을 독립 정책 평가로 전용하지 않는다. B3/P나 반대 B2를 비교하려면 사용 상태가 더 생기므로 별도 적격성·예산이 필요하다.

다음 한 묶음은 **Android active 재생·상태 계측의 PC 계약과 샘플링/세션시간 타당성 검증**이다. 그 후에만 위 최소 후보의 실제 예산·동결/중단 규칙을 확정한다. 이번에는 ADB·설치·추론·실측 0, 예산 승인 0, 새 정책 선택/튜닝 0. `experiment_ready=false` 유지.
