# D1Check 프로젝트 수정 실행계획

- 작성일: 2026-09-15
- 개정: 3 — DEFINE-01에서 프로젝트 범위, 사용자 시나리오, 완료 시점, 평가지표와 목적함수 우선순위를 확정했다.
- 문서 상태: 범위·시나리오·지표 계약은 공식 정의다. 절대 마감시간과 아래 실험 규모·성공 수치 기준은 CALIB-01 및 최종 평가 전에 고정한다.
- 수정 근거: A24 80슬롯 보정 분석, diagnostic v2 실기기 진단, S26 80슬롯 export 검토 및 최근 논의.
- 적용 범위: 기존 기준보고서 원문을 덮어쓰지 않고 향후 구현·검증의 기준으로 사용하는 별도 개정안.

## 1. 목표와 현재 판정

**D1Check는 하나의 온디바이스 AI 앱 내부에서 CPU/GPU/NPU 후보 중 실행 자원을 선택하고 긴급·일반 요청 큐를 관리하는 애플리케이션 수준 스케줄러다. Android 운영체제 전체의 스케줄러가 아니다. 목표는 기기별 최적 고정 자원과 단순 우선순위 정책보다 긴급 응답시간을 개선하면서 일반 요청 처리와 열 제약을 유지하는 것이다.**

구현 가능성은 높다. 다만 동적 자원 선택의 추가 효과는 아직 확인되지 않았다. 현재 확보한 것은 측정 기반과 기기별 성능 특성이며, 스케줄러의 우수성이나 실무적 필요성이 입증된 상태는 아니다.

기기별 CPU/GPU 우열 역전은 초기 캘리브레이션의 필요성을 뒷받침한다. 이것만으로 실행 중 자원 전환이 필요하거나 이득이라는 결론을 내리지 않는다. S26 formal의 GPU 우세는 보조 사례로만 유지하며 새 S26 정책 평가는 수행하지 않는다.

A24에서는 CPU가, S26에서는 GPU가 우세하므로 기기별 calibration 필요성을 핵심 연구 근거로 삼는다. 이 근거는 자원 선택의 필요성을 뒷받침하지만 동적 스케줄러가 강한 고정 정책보다 우수하다는 증거는 아니다.

## 3. 현재 증거와 해석 한계

| 증거 | 확인한 내용 | 아직 주장할 수 없는 내용 |
| --- | --- | --- |
| A24 formal 80슬롯 | CPU 중앙 지연 약 41.2 ms, GPU 약 131.6 ms, GPU/CPU 약 3.196. CPU 1/2/4 스레드 차이는 매우 작고 위치 변경 민감도 검사에서도 CPU 우세 방향 유지 | 모든 모델·부하에서 CPU가 우세하다는 일반화. 위치·주변온도 영향 제거 |
| S26 formal 80슬롯 | 원시자료 감사와 지연 재계산 통과. GPU가 pooled CPU보다 duty별 약 1.062~1.201배 빠르고 20개 block-duty 대응 비교 모두 GPU 우세. 모든 GPU run은 31/31 노드 full delegation, fallback 없음 | compatibility-list override 없는 결과로 일반화. 측정 APK와 Git 소스의 완전한 cryptographic binding |
| 기기 간 입력·설정 기록 | 모델, LiteRT 1.4.2, strict profile 설정, 대표 텐서 내용·전처리·라벨 해시 일치 | 두 기기의 전체 실험 계약과 소스가 완전히 동일하다는 주장 |
| 온도 | S26의 20개 block-duty 대응 비교에서 GPU AP 온도 상승이 모두 더 낮게 관측됨 | 동일 완료량에서 더 효율적임, 에너지 절감, 기기 간 AP 센서의 직접 동등성 |
| diagnostic v2 | trace-off/on 실기기 경로 확인. trace에서 sched 및 gpu_frequency 표본 확인 | GPU 내부 실행시간, fence, H2D/D2H 분해, 실제 FP32/FP16 확인 |
| CPU 설정 | CPU1/2/4 조건에서 뚜렷한 속도 이득이 관측되지 않음 | 실제 worker 수 또는 스레드 증가 효과에 대한 인과 결론 |

추가 주의사항:

- 대표 텐서셋은 정확도 preflight 입력이다. 실제 timed load 입력이 대표 이미지라고 가정하지 않는다. 새 요청 실험에서는 사용한 입력 바이트·생성 방식과 정확도 검사 입력을 구분하여 기록한다.
- A24 warm-up 설정은 5, S26 보고서 표기는 20 s이다. 원본 명령과 코드로 값의 단위·적용 위치를 확인하고 새 비교에서는 통일한다.
- S26은 `gpu_compatibility_list_supported=false`, `formal_gpu_compat_list_override=true`였다. compatibility-list override 사실을 모든 비교 결과에 공시한다.
- S26의 tensor container 해시는 A24와 다르다. 기록된 텐서 내용 해시는 같지만 컨테이너 차이를 직접 검증하지는 않았다.
- S26 `dataset_manifest`의 accuracy/pilot 문구는 수정이 필요하다. 원본은 보존하고 수정 설명 또는 새 export로 정정한다.
- A24의 약 22·72번째 장소 이동, 재시도와 실제 duty 차이는 기존 분석의 제한으로 유지한다.
- 실제 FP32/FP16 하드웨어 실행 여부는 unknown이다. GPU 내부 H2D/GPU/D2H 및 fence timing도 확보되지 않았다.
- 에너지 단위가 검증되지 않았으므로 J/mWh와 에너지 절감률을 사용하지 않는다.
- 측정 당시 설치 APK와 Git 소스의 완전한 cryptographic binding이 부족하다.
- S26 재시도 raw run 하나는 failure 기록이 불완전하다.
- 기존 formal 데이터, diagnostic v2 trace-off, trace-on, 새 스케줄러 실험을 서로 구분한다. 프로토콜 변경 자료를 동일 반복으로 합치지 않는다.

## 4. 제어 범위와 문제 정의

### 4.1 앱이 제어할 것

1. 대기 중인 요청의 실행 순서.
2. 다음 요청을 실행할 CPU/GPU/NPU 후보 경로.
3. 일반 요청의 실행 시점과 실행 빈도.
4. 큐 상한, 만료 요청 및 과부하 시 처리 정책.

OS 전체 스케줄링, 다른 앱의 작업 배치, CPU/GPU 주파수 강제 제어는 범위에 포함하지 않는다. 초기 구현에서는 해상도·모델·정확도를 변경하지 않는다.

### 4.2 공식 사용자 시나리오

- 긴급 요청: 사용자가 갤러리에서 사진 한 장을 선택하고 즉시 분류 결과를 요청하는 대화형 이미지 분류 작업.
- 일반 요청: 갤러리의 여러 사진을 백그라운드에서 분류하고 색인하는 일괄 작업. 요청 단위는 개별 이미지이며 결과 저장으로 완료된다.

긴급 요청이 도착했을 때 진행 중인 일반 요청을 처리하는 방식은 후속 설계에서 다음 후보를 비교한다.

1. 현재 일반 이미지 작업을 완료한 뒤 긴급 작업을 실행한다.
2. 현재 이미지는 완료하되 다음 이미지 경계에서 일반 batch를 중단하고 긴급 작업을 실행한다.
3. 다른 가용 자원으로 긴급 작업을 동시에 실행한다.

`Interpreter.run()` 자체를 실행 중간에 강제로 중단할 수 있다고 가정하지 않는다. 동시 실행 후보는 실제 자원 간섭과 메모리·열 비용을 별도로 검증한다.

### 4.3 요청, 완료와 응답의 정의

각 요청은 request_id, 예정 도착시각, 실제 큐 진입시각, 긴급/일반 구분, 절대 마감시각, 입력 식별자를 가진다. 추가로 실행 자원, 시작·완료시각, 상태 및 실패 사유를 기록한다.

- 큐 대기시간 = 실행 시작 − 실제 큐 진입.
- 추론 구간 = 정의된 inference 타이머 구간.
- 긴급 요청 응답시간 = 분류 결과가 사용자에게 제공 가능한 시각 − 실제 큐 진입.
- 일반 요청 완료시간 = 해당 이미지의 분류 결과가 저장된 시각 − 실제 큐 진입.
- 도착 지연 = 실제 큐 진입 − 예정 도착.

순수 `Interpreter.run()` 지연과 사용자 체감 종단간 지연을 구분한다. 종단간 시간에는 실제 이미지 읽기, 전처리, 큐 대기, 추론, 후처리 및 결과 반환·저장 중 해당 요청 완료에 필요한 구간을 포함한다. 느린 정책 때문에 요청 발생기까지 느려지는 오류를 막기 위해 요청은 예정된 시각에 독립적으로 도착시킨다.

### 4.4 지표의 집계 계약

- 주요 지표는 긴급 output-ready 응답시간 P95, 긴급 마감시간 위반율, 일반 기한 내 완료율, 전체 도착 요청 대비 완료율, 전체 처리량, 최고 온도 또는 Android thermal status, CPU와 GPU의 실제 사용 비율, 정확도 검증 통과 여부다.
- 완료 응답 P95는 출력 준비 시각까지 측정된 완료 요청에서 계산하는 **조건부 지표**다. 완료 표본 수와 전체 도착 수를 함께 표시한다. 완료 표본이 없으면 NA이며 0으로 기록하지 않는다.
- 유형별 기한 내 완료율 = 기한 내 출력 준비된 요청 수 / 해당 유형 전체 도착 수. 기한 내 완료하지 못한 모든 요청을 서비스 실패에 포함한다. 늦게 완료·거절·만료·취소·오류·종료 시 미완료를 별도 집계한다.
- P95 향상은 서비스 성공률·일반 요청 제약과 함께 판단한다. 성공 표본의 변화로 생기는 선택 편향을 밝히고, 미완료에 임의의 짧은 응답시간을 대입하지 않는다.
- 예정 도착→출력 준비 시간도 기록하고, 마감시간은 사전에 정한 예정 도착을 기준으로 산출한다. 실제 enqueue가 늦어져 마감시간이 자동 연장되지 않게 한다. 발생기 지연 허용 범위와 세션 처리 기준을 평가 전에 고정한다.
- 종료 후 큐 처리 시간, 만료 정책, 분위수 계산법, 최소 유효 표본 수를 평가 전에 명시한다. 같은 입력 규칙이어도 정책별 큐 상태 차이로 거절 건수는 달라질 수 있다. 이를 오류로 숨기지 않고 결과로 보고한다.

### 4.5 목적함수 우선순위와 제약

다음 사전적 우선순위를 사용한다.

1. 안전·정확도 제약 준수.
2. 긴급 요청 마감시간 위반 최소화.
3. 긴급 요청 P95 최소화.
4. 일반 요청 기한 내 완료율 최대화.
5. 처리량 최대화.
6. 온도와 자원 전환 비용 최소화.

아직 가중치 합으로 하나의 목적함수를 확정하지 않는다. 각 KPI를 별도로 보고하고 필요하면 후속 실험에서 가중치를 결정한다. 일반 요청 최소 서비스, 열 안전, 큐·메모리 상한을 명시적인 제약으로 둔다.

- 과부하: 무조건 모든 요청을 완료할 수 있다고 가정하지 않는다. 거절·만료·취소·오류도 전체 도착 요청을 분모로 집계한다.
- 에너지: 전류·charge-counter 단위 검증 전에는 J/mWh와 에너지 절감률을 제시하지 않는다.

### 4.6 자원과 마감시간 상태

- 1차 구현 자원은 CPU와 GPU다.
- NPU는 capability detection과 실제 실행 검증에 성공한 기기에서만 활성화한다. 미지원 또는 접근 실패 시 CPU/GPU만으로 정상 동작해야 하며 NPU 지원은 프로젝트 성공의 필수조건이 아니다.
- S26에서는 현재 NNAPI가 `nnapi-reference` CPU만 노출했다. 이를 실제 NPU 지원 증거로 사용하지 않는다.
- 긴급·일반 요청의 절대 마감시간 상태는 `calibration_pending`이다. 임의 수치를 공식 기준으로 사용하지 않는다.
- CALIB-01에서 Galaxy A24의 실제 이미지 읽기, 전처리, 큐 대기, 추론, 결과 반환·저장을 포함한 종단간 시간을 소규모로 측정한 뒤 결과 평가 전에 절대 마감시간을 사전 고정한다. S26에는 새 calibration·설치·앱 실행을 하지 않고 기존 formal 80슬롯을 기기별 특성 차이의 보조 사례로만 유지한다.

## 5. 최소 구현

### 5.1 실행 구조

- CPU/GPU 실행 인스턴스를 준비하고 초기화·warm-up 시간을 따로 기록한다. NPU는 capability와 실제 실행 검증을 통과한 기기에서만 후보에 추가한다.
- GPU 인스턴스는 해당 런타임의 스레드·컨텍스트 요구사항을 지키도록 전용 실행 경로에 둔다.
- 기본 비교에서는 한 번에 추론 한 건만 실행한다. 별도 자원 동시 실행 후보는 간섭 검증 후 독립 조건으로 비교한다. 전환 시 인스턴스를 매번 재생성하지 않도록 설계하고 실제 메모리·전환 비용을 측정한다.
- 요청 큐와 실행 경로를 분리하고 동일한 인터페이스로 모든 비교 정책을 실행한다.
- 실행 중인 개별 `Interpreter.run()`은 끝까지 처리한다. 일반 batch 중단 후보는 다음 이미지 경계에서만 적용한다.
- 앱 프로세스 종료나 런타임 오류는 요청 실패로 남긴다. 성공 표본만 집계하지 않는다.

### 5.2 제안 정책의 첫 버전

관측값은 자원별 최근 실행시간과 준비·전환 비용, 큐의 요청 수와 마감시각, 사용 가능한 열 상태다. 큐 대기를 backend 실행시간 학습값에 섞지 않는다. 오래 사용하지 않은 backend 추정치에는 시점과 불확실성을 표시한다.

1. 안전 정지 기준을 우선 적용한다.
2. 긴급 우선 원칙에 일반 요청 최소 서비스 규칙을 결합한다. 일반 요청 실행 중 긴급 요청이 와도 추론을 선점하지 않는다. B1/B2/P의 등급 내 정렬 규칙을 동일하게 고정해 EDF 효과를 자원 선택 효과로 오인하지 않는다.
3. 자원별 예상 완료시각에 실행 준비·전환 비용을 포함한다.
4. 검증된 열·지연 프로파일을 이용해 실행 가능 후보를 고른다. 느린 자원으로 전환했을 때 더 오래 점유하는 비용도 고려한다.
5. 일반 요청은 최소 서비스와 만료 규칙을 지키면서 실행을 지연하거나 허용한다.
6. 잦은 자원 전환을 막기 위해 최소 유지시간 또는 전환 이득 기준을 둔다.

열을 예측하는 모델은 실제 검증이 필요하다. AP ΔT만으로 자원별 발열량을 단정하지 않는다. 열 관측이 불가능한 기기는 관측 가능한 지연·큐 기반 정책으로 구분하여 평가한다.

## 6. 반드시 비교할 기준정책

| ID | 정책 | 역할 |
| --- | --- | --- |
| B0 | 기기별 사전 선택 자원 + FIFO | 큐 순서 개선을 확인하는 기초 기준 |
| B1 | 같은 자원 + 긴급 우선 | 우선순위만으로 얻는 효과 분리 |
| B2 | B1 + 단순 열 임계값에 따른 일반 요청 실행 빈도 제한 | 제안 정책이 넘어야 할 강한 단순 기준 |
| P | 큐·기한·열 상태에 따른 다음 자원과 실행 시점 결정 | 제안 정책 |

B0/B1의 자원은 평가 자료와 분리된 캘리브레이션으로 사전 선택한다. B2는 CPU 고정·GPU 고정 각각에 긴급 우선과 단순 열 대응을 적용해 개발 자료에서 비교하고, 제약을 만족하는 좋은 고정 정책을 선정한다. 짧은 단독 추론의 최속 자원이 지속 부하에서도 최선이라고 가정하지 않는다. 후보별 결과를 남기며 B2/P의 튜닝 예산은 동일하게 둔다. 최종 평가에서는 자원과 파라미터를 고정한다. 이 B2 선정 규칙은 간략한 정책표보다 우선한다.

모든 정책은 동일한 정확도 기준, 안전 정지 기준, 입력, 요청 기록, 큐 상한과 만료 규칙을 사용한다. 정책마다 다르게 거절하여 P95만 낮추는 비교를 금지한다. B2와 P에는 동일한 개발 데이터·튜닝 예산을 배정한다.

### 단계 1. 요청 큐와 측정 검증

- FIFO와 긴급 우선 정책을 먼저 구현한다.
- CPU/GPU 출력 준비 경계, 전환 비용, 큐 순서, 만료·오류 처리를 짧은 실기기 실행으로 확인한다.
- 의미 있는 테스트: 긴급 요청이 일반 요청 뒤에 도착하는 경우, 실행 중 추론은 유지되는 경우, 큐 포화·만료·실패가 지표에서 누락되지 않는 경우.

완료 조건: 요청 ID별 도착→대기→실행→결과를 추적하고 누락·중복 없이 재현 가능.

### 단계 2. 개선 여지 탐색

1. 낮은 부하: 대부분 대기 없이 처리되는 조건.
2. 긴급 요청 집중: 일반 요청이 있는 상태에서 긴급 요청이 일시적으로 몰리는 조건.
3. 지속 부하: 큐와 열 상태가 변할 수 있는 연속 실행 조건.

제안 시작 규모는 **기기당 4정책 × 3조건 × 3반복 = 36세션**이다. 이는 탐색용 규모이며 통계적 충분성을 뜻하지 않는다. 구현 확인은 이보다 짧게 수행하고, 효과가 없는 조건은 추가 반복 전에 원인을 검토한다.

- 도착률은 별도 캘리브레이션 처리능력의 비율로 저·중·고부하를 정한다. 모든 정책에 같은 도착률을 적용한다.
- 3~5분 연속 실행부터 검토하되 열 변화와 표본 수가 부족하면 늘린다. 이 길이로 열 평형을 가정하지 않는다.
- 긴급 비율·burst 크기·마감시각·입력 구성은 개발 세션에서 정하고 최종 평가 전에 고정한다.
- 실제 사용자 도착 로그가 없으면 합성 workload라고 명시한다. 먼저 특정 사용 기능과 요구 응답시간을 정하고, 임의로 유리한 마감시간을 선택하지 않는다.
- 각 반복 묶음에서 동일 요청 기록을 네 정책에 재생하고 정책 실행 순서를 무작위화한다.
- 열 초기조건 범위를 맞추고 미충족 시 냉각하거나 블록을 분리한다. SOC·충전·장소·화면 상태를 기록한다.
- 주평가는 trace-off로 한다. trace-on은 원인 진단에만 사용한다.

완료 조건: B2 대비 P에 반복적으로 나타나는 개선 여지가 있는지 판정. 우선순위 효과만 있으면 자원 선택 기능을 축소. P가 유망하면 동일 P에서 backend만 고정한 비교를 추가해 자원 선택 효과를 pacing 효과와 분리한다. 최초 36세션 전체에 이를 자동 추가하지 않는다.

### 단계 3. 독립 평가

- 새로운 요청 seed·실행 세션을 사용하고 정책 파라미터는 고정한다.
- 탐색 결과의 세션 간 변동을 이용해 반복 수를 결정한다. 개별 추론 수가 많다는 이유로 독립 반복 수가 충분하다고 판단하지 않는다.
- 세션별 P95, 위반율, 완료율을 계산하고 대응 세션 차이와 신뢰구간을 제시한다.
- 독립 스케줄러 평가는 Galaxy A24에서 수행한다. 기존 S26 formal 결과를 A24 스케줄러 평가 표본으로 합치거나 S26 실기기 스케줄러 검증으로 재해석하지 않는다.
- 요청 수가 적은 P95는 불안정하므로 표본 수와 불확실성을 함께 보고한다.
- 정책 비교 중 기기 열 조건이 어긋나거나 외부 중단이 생긴 세션의 처리 기준을 미리 정한다. 원기록과 제외 사유를 보존한다.

### 단계 4. 선택적 확장

필요할 때만 CPU/GPU 동시 실행, 추가 모델 또는 NPU를 하나씩 추가한다. CPU/GPU 단독 실험으로 동시 실행 속도를 합산하지 않는다. 공유 메모리·전력·열 및 실행시간 간섭을 먼저 측정한다.

강화학습은 규칙 정책이 특정 상태에서 반복적으로 실패하고, 학습·검증 데이터를 분리할 수 있으며 정책 비용까지 포함해 개선 가능한 경우에만 검토한다.

## 8. 진행·축소·중단 기준

다음 수치는 대회용 실질 개선 여부를 판단하기 위한 **제안 기준**이다. 사용자 기능의 요구사항과 개발 실험을 바탕으로 최종 평가 전에 고정하며 결과를 본 뒤 완화하지 않는다.

| 판정 | 제안 기준 | 다음 행동 |
| --- | --- | --- |
| 계속 진행 | 사전 지정 핵심 조건에서 B2 대비 긴급 P95 10% 이상 감소, 기한 위반율 악화 없음, 일반 기한 내 완료율 감소 2%p 이내, 열 안전 위반 증가 없음 | 독립 반복 및 보고서 작성 |
| 범위 축소 | B0 대비 개선되지만 B1/B2 대비 자원 선택의 추가 이득이 작음 | 우선순위·실행 빈도 제어 중심으로 재정의 |
| A24 정책 채택 | A24에서 동적 정책보다 고정 정책이 우세하거나 이득이 없음 | A24 직접 검증 결과로 범위를 축소하거나 고정 정책을 채택. S26 스케줄러 결과를 주장하지 않음 |
| 구현 수정 | 전환·관측 비용, 큐 발생기 오류 또는 출력 준비 지연이 이득을 상쇄 | 비용을 줄이거나 측정 계약을 수정한 뒤 재검증 |
| 동적 자원 배정 주장 중단 | 현실적인 부하 전반에서 B2와 비슷하거나 악화, 또는 일반 요청 희생·거절 증가로만 P95 개선 | 자원 전환을 핵심 기여에서 제외 |
| 프로젝트 재검토 | 범위 축소 후에도 실제 문제·강한 기준정책 대비 개선·재현성 모두 부족 | 다른 문제 또는 적용 작업으로 전환 |

표의 수치는 효과 크기 목표다. 최종 우수성 판정에는 사전 지정 신뢰수준·대응 비교 방법과 불확실성을 함께 사용한다. 신뢰구간이 넓으면 판정 불충분으로 남기고, 단순히 점추정치가 기준을 넘었다고 성공으로 선언하지 않는다.

열 안전 임계값은 임의의 공통 AP 온도로 정하지 않는다. 기기별 센서 의미와 이용 가능한 시스템 열 신호를 확인하여 정한다. 임계값·일반 요청 서비스 기준이 정해지기 전에는 제약 충족을 주장하지 않는다.

- 고정 자원 우세 조건과 동적 정책 우세 조건을 모두 포함한 결론.

request_results.csv에는 도착 요청 전체를 남기며 완료·기한 초과·만료·거절·취소·오류를 구분한다. 종료 시 남은 큐를 정해진 시간만큼 처리할지 즉시 종료할지도 사전 고정하고, 남은 요청은 완료율 분모에서 빼지 않는다.

15페이지 보고서는 문제와 사용 상황, 기존 방법, 실측 기반 모델, 정책, 실기기 비교, 한계를 중심으로 구성한다. 측정 시스템 구축 자체와 스케줄러 개선 효과를 구분한다. “기기별 CPU/GPU 선택은 기존에 없다” 또는 “OS가 처리하지 않는다”는 포괄적 주장은 사용하지 않는다.

## 10. 기존 기술과의 관계

이전 조사에서 확인한 공식 자료에 따르면, 기기에서 후보 설정을 평가하고 결과를 캐시하는 접근은 이미 존재한다. 따라서 초기 캘리브레이션만을 독창성으로 내세우지 않는다.

- [LiteRT Acceleration Service](https://ai.google.dev/edge/litert/android/acceleration_service): 기기별 CPU/GPU 설정 평가 및 결과 재사용. 문서상 Beta·Play services 범위의 제약이 있음.
- [LiteRT GPU acceleration](https://developers.google.com/edge/litert/next/gpu): 가속기 지정, 버퍼 관리 및 비동기 실행 기능.
- [Android ADPF](https://developer.android.com/games/optimize/adpf): 전력·열 상태와 앱 workload 조절을 연계하는 API.
- [Android Thermal API](https://developer.android.com/games/optimize/adpf/thermal): 기기별 지원 차이를 고려한 열 관측과 부하 조절.

이 자료는 공개 API의 기능 범위를 설명하며, 상용 앱 전반의 채택률이나 모든 업체의 내부 스케줄러 부재를 입증하지 않는다. 기존 기술을 이용한 강한 기준정책과의 비교 및 관련 연구 조사를 통해 차별성을 검증한다.
