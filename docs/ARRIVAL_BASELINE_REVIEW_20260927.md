# 혼합 요청 연구의 비교 기준선 검토 (2026-09-27)

## 첫 페이지: 결론

**권고 C — 현재의 합성 연구용 기준선을 유지한다.** D1Check의 정책 도입 전 앱에는 두 AI 과업의 도착 큐·CPU/GPU 배정기가 없었다. 기존 `benchmark-runner`는 설정된 자원으로 반복 추론하는 계측 도구였으며, `CPU_FIFO`는 2026-09-23의 격리된 arrival 실험과 함께 추가한 **자체 단순 대리 기준**이다. 따라서 CPU_URGENT·B2·B3도 실사용 앱의 기본 정책이 아니다. 현 질문은 “동일한 두 모델·입력·이벤트/계측 계약에서 단순 순서, 강한 정적 배정, 단독 추정 기반 배정과 조건부 정책의 응답·완료·기기 에너지·AP 상충은 무엇인가”로 제한한다. [합성 연구 채택](DECISIONS.md), [현재 PC 탐색 범위](ARRIVAL_THERMAL_FEEDBACK_PC_20260927.md)는 실제 서비스 SLA, 실사용 배터리 절감, 열 제약 준수를 입증하지 않는다. 기존 불리한 P/온라인 후보 결과와 `experiment_ready=false`는 그대로다.

외부에서 가장 가까운 앱 사례는 Ente Photos의 **사용자 조작·기기 건강에 따른 배경 ML 시작 허용**이다. 이는 CPU/GPU 혼합 요청 배정과 다른 제어축이다. Band는 이종 프로세서의 다중 DNN **연구 프레임워크**이며, MediaPipe Tasks는 과업 실행용 **공식 예제/프레임워크**다. 셋 중 어느 것도 현재 동일 과업·입력·runtime·응답/저장·에너지 경계를 가진 실사용 “기본 정책”으로 확인되지 않았다. 외부 코드를 실행하거나 A24에 포팅하지 않았다. 직접 비교를 추가하면 먼저 동작 대응과 같은 계측 경계를 검증해야 한다.

## 우리가 바꾸는 처리와 실제 이전 상태

- **과업과 근거:** EfficientNet-Lite0 이미지 분류와 EfficientDet-Lite0 객체 탐지는 출력·전후처리·지속시간이 다른 두 과업이다. 사진 자동 태그/색인 중 사용자가 선택한 이미지 탐지를 요청하는 상황은 대표 **시연 후보**일 뿐 실제 혼합 도착 수요가 확인된 서비스가 아니다. 긴급/일반 라벨, low/queue/burst 도착, 연구용 1.5초/6초 기한은 실측 사용자 요구가 아니라 고정 합성 입력이다. [범위 증거](SCOPE_02_EVIDENCE.md), [합성 연구 계약](ARRIVAL_ENERGY_SYNTHETIC_RESEARCH_20260926.md).
- **앱 본체:** [`app/MainActivity.onCreate/startTelemetry`](../app/src/main/java/com/example/d1check/MainActivity.kt)는 계측 UI와 `TelemetryForegroundService` 시작/정지를 제공한다. AI 요청 큐·분류/탐지 배정 호출은 이 경로에 없다. OS가 스레드 실행·주파수/thermal 관리를, 모델 runtime이 실제 연산을 맡는다. 이 범위에서 실사용 기본 AI 스케줄러는 **없음**이며, 별도의 다른 상용 서비스 기본 정책은 **미확인**이다.
- **이전 benchmark 경로:** [`benchmark-runner/MainActivity.startBenchmark`](../benchmark-runner/src/main/java/com/example/d1check/benchmarkrunner/MainActivity.kt)와 [`GpuBenchmarkEngine`](../benchmark-runner/src/main/java/com/example/d1check/benchmarkrunner/GpuBenchmarkEngine.kt)는 선택 자원·warmup·횟수/시간·duty로 반복 추론한다. 사용자의 두 과업 도착 큐나 긴급 순위가 없다. `git show 50fa967^:benchmark-runner/src/modelProbe/AndroidManifest.xml`에는 ArrivalSchedulerActivity가 없고, `50fa967`이 그 Activity와 `ArrivalPolicy`를 추가했다. 변경 전 반복 추론을 “직렬 FIFO 스케줄러”라고 소급 명명하지 않는다.
- **격리된 실험 경로:** [`ArrivalSchedulerActivity.runSession`](../benchmark-runner/src/modelProbe/java/com/example/d1check/benchmarkrunner/ArrivalSchedulerActivity.kt)는 `modelProbe`의 별도 Activity이며 manifest 요청 목록을 예정 시각에 큐로 넣는다. dispatch 1개, CPU/GPU worker 각 1개이고, 실제 worker 완료·기록 뒤 lane을 해제한다. 긴급 응답은 `output_ready`, 일반 응답은 `persist_complete`다. [`ArrivalPolicy.choose`](../benchmark-runner/src/modelProbe/java/com/example/d1check/benchmarkrunner/ArrivalPolicy.kt)는 도착해 대기 중인 ticket만 읽는다. `CPU_FIFO`는 ordinal CPU 직렬, `CPU_URGENT`는 urgent 우선 CPU 직렬, `FIXED_SPLIT`은 urgent CPU/normal GPU, `CONDITIONAL`은 CPU 잔여·앞선 큐 추정과 GPU 단독 추정을 비교한다. **정의됨/manifest로 호출됨/실험에 사용됨**을 구분하며 앱 본체의 기본 동작으로 옮기지 않는다. 기기 계측의 memory/thermal admission은 실험 안전 gate이지 열·배터리 최적화 배정은 아니다. 사용자 조작·배경 상태의 admission은 이 Android arrival 경로에 없다.
- **PC 정책:** [`d1_arrival_explore.choose/simulate`](../tools/d1_arrival_explore.py)의 `B2_PC`는 개발 trace에서 선택해 고정한 task별 정적 배정, `B3_SOLO_EFT_PC`는 단독 예상 완료시간·aging/EDF를 쓰는 축소 구현이다. [개발 선정 기록](ARRIVAL_FOLLOWUP_AND_EXPLORATION_20260925.md)의 explore B2는 **분류 GPU＋탐지 CPU** 병행이며, 이는 실측 CC_DG의 역방향이다. Android `FIXED_SPLIT` 하나가 B2 전체가 아니며 Android `CONDITIONAL`은 B3/P가 아니다. strict의 CPU fallback/전체 직렬화와 explore의 가정 병행을 합쳐 A24 실측 순위로 부르지 않는다. 기존 연구용 P와 별도 `THERMAL_ENERGY_PC_V1`도 상용 기본 정책이 아니다.

## 비교 구성과 주장 한계

1. **동일 엔진 정책 효과(주 비교):** 모델 binary/입력·품질, CPU thread=1, resident 네 runtime, task×backend 적격성, 비선점·실제 lane 해제, 예정 도착/응답/저장/공통 관측창, 누락·미완료 분모를 공통으로 한다. `CPU_FIFO`는 **자체 CPU 단순 대리 anchor**로만 둔다. `CPU_URGENT`로 순서 효과를, 개발 고정 `B2_PC`로 강한 정적 배정을, `B3_SOLO_EFT_PC`로 간단한 동적 배정을 본다. `FIXED_SPLIT`과 Android `CONDITIONAL`은 해당 구현의 별도 제한 비교로 표기한다. PC B3/P/열 후보는 현재 Android active 정책과 혼동하지 않는다. B2를 평가 자료로 재선정하지 않는다. 동일 지원 범위가 아니면 strict/탐색을 나눠 보고한다.
2. **외부 전체 시스템 효과(현시점 주 비교 아님):** Ente·MediaPipe·Band를 원래 구현 그대로 실행하면 모델·입력·runtime/delegate·정밀도·전후처리·queue·저장·계측·기기 환경이 함께 달라진다. 그러한 차이는 스케줄링 효과만으로 환원할 수 없다. 외부 정책만 같은 엔진으로 옮기는 경우 결과 이름은 **정책 재구현**이며 원 구현의 초기 상태, enqueue/worker choice, fallback, 동률·실패·drain 의미 일치 검증이 필요하다. 외부에 없는 긴급/일반 라벨은 연구자가 붙인 수정으로 기록한다. 외부 기본 설정과 합리적 조정 설정을 분리하고, 한쪽에만 추가 GPU/thread/resident를 주지 않는다.

**이 권고로 말할 수 있는 것:** 측정 근거와 공개된 가정 아래 동일 합성 요청에서 자체 단순·강한 정적·축소 동적 정책 간 상충. **말할 수 없는 것:** 실사용 앱의 기존 scheduler보다 우월, Band/Ente 전체보다 빠름, 실제 서비스 SLA/배터리 절감·열 안전 입증. 이미 관측한 P의 불리한 결과, 미측정 B2 역방향 병행 전력·AP, `experiment_ready=false`는 그대로다.

**구현 전 남은 확인 한 가지:** 외부 정책 재구현을 실제 비교군으로 추가하기로 별도 결정한다면, 먼저 Band의 고정 scheduler 하나에 대해 job→request, subgraph→worker, window/예상비용, priority 부재, callback·저장 차이를 대응표로 동결하고 원 코드의 결정 trace와 작은 동등 사례를 대조한다. 이번 검토는 그 adapter나 기기 실험을 시작하지 않는다. 현재 합성 연구의 주 비교에는 이를 선행 필수조건으로 두지 않는다.
