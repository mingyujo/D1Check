# CC_DG 고정 묶음의 에너지·AP·완료시간 선택 가능성

## 연구 결과 본문용 제한 결과 — 2026-09-30 연결

**연구 질문과 범위.** A24에서 동일한 분류 CPU 678건과 탐지 GPU 192건을 4개 runtime이 상주한 상태로 직렬 또는 병행 처리할 때, 완료시간·기기 전체 에너지·AP 최고온도가 같은 방향으로 개선되는지 보았다. 개발과 확인에 각 방식 1세션씩 사용했고, 개발의 순서는 직렬→병행, 확인은 병행→직렬이었다. 모든 요청은 완료됐지만 독립 확인은 방식당 **1세션**이다. 이 작업은 정해진 870건 묶음의 실행 방식 비교이며 개별 요청이 도착할 때마다 결정하는 온라인 배정 정책 실험은 아니다.

**관측 결과.** 병행은 직렬보다 개발에서 122.456초, 확인에서 126.319초 빨리 870건을 마쳤다. 완료시점까지 기기 전체 에너지는 각각 179.801J, 143.341J 낮았고, 부하 중 AP 최고온도는 각각 1.2°C, 1.9°C 높았다. 그러나 **같은 480초 공통창**에서는 병행−직렬 에너지가 개발 **−36.255J**, 확인 **+4.559J**로 방향이 뒤집혔다. 완료가 빠른 방식은 그만큼 긴 resident 유휴 구간을 같은 창 안에서 보냈으므로 완료시점과 공통창 에너지는 다른 질문에 답한다. J는 A24 전류 raw=mA 해석에 의존하는 기기 전체 전압×전류 적분이며 절대 정확도는 인증되지 않았다.

**모형 평가 결과.** 개발 직렬·병행 각 1세션의 단계별 시간·전력·AP 경험 경로를 고정한 제한 PC 템플릿은 확인에서 병행−직렬 완료시간 **−122.456초**와 AP 최고차 **+1.5°C**를 예측해 관측 방향(−126.319초, +1.9°C)을 재현했다. 공통480초 에너지는 **−36.216J**를 예측했으나 확인은 **+4.559J**였다. 방향 오류는 두 arm의 공통창 예측오차 차이 **−40.774J**와 일치한다. 기록 기반 분해에서 가장 큰 산술 항은 부하 단계 평균전력 차이의 arm 간 기여 **−43.448J**였지만, 순서·초기 열 이력·기기 상태·계측 변동 중 어느 것이 원인인지는 식별되지 않는다. 확인 결과를 이미 본 뒤 작성한 템플릿을 사용했으므로 이 오차는 완전히 사전등록된 독립 예측 평가도 아니다. `TRADEOFF`는 상충과 판별 불가를 표시하며 에너지 절감, 열 안전, 정책 우월성의 PASS가 아니다.

**그림 설명.** [직렬·병행 4지표 그림](results/energy_operational_sim_01/tradeoff.png)은 *관측된* 개발·확인의 작업 완료시간, 완료시점까지 에너지, 480초 공통창 에너지, 부하 AP 최고온도를 보여준다. 막대는 모형 예측이 아니다. [모형 예측과 확인의 오차표](results/energy_operational_sim_01/confirmation_evaluation.json) 및 [오차 분해](results/energy_operational_decision_01/energy_error_decomposition.csv)를 함께 제시해야 공통창 순위 실패를 숨기지 않는다. 같은 AP값이 같은 내부 열 상태라는 증거는 없고, 표본·요청 수를 세션 반복 수로 계산하지 않는다.

**적용 경계.** 지금 사용할 수 있는 계산은 동일 A24·모델/입력·resident·870건 CC_DG와 명목480초 창의 회고 비교다. 서비스 기한과 AP 기술 한도가 지정되면 기존 선택 인터페이스에서 그 *모형상* 제약을 탐색할 수 있으나, 현재는 둘 다 미정이다. [2026-09-30 연결 판정](AP_SIMULATION_CLOSURE_PC_20260930.md)에서 저장된 임의 도착 정책 135사례의 실측 기반 전체창 J/AP 지원은 **0개**로 유지됐다. 이 고정 묶음 결과를 B2/B3/CPU_URGENT의 동적 에너지 순위로 전용하지 않는다. 기존 동결 profile·원자료와 `experiment_ready=false`는 그대로다.

## 공통창 에너지 오차의 기록 기반 분해

기존 profile을 재보정하지 않고, 각 arm에서 `예측 공통창−확인 공통창 = 부하 지속시간항 + 부하 평균전력항 + 완료 후 resident idle 지속시간항 + 그 평균전력항 + 계측 경계 잔차`라는 산술 항등식으로 분해했다. 전력항은 **동일 단계의 개발 평균전력과 확인 평균전력의 차이**이지 인과 추정치가 아니다. 부하와 idle은 실제 같은 480초 창의 서로 다른 부분이며, 먼저 끝난 병행 arm의 대기를 제외하지 않았다. [전체 수치 CSV](results/energy_operational_decision_01/energy_error_decomposition.csv), [기계 판독 JSON](results/energy_operational_decision_01/energy_error_decomposition.json).

| 예측−확인 오차 항목, 조건부 J | 병행 | 직렬 | 병행−직렬 오차 기여 |
|---|---:|---:|---:|
| 부하 지속시간 차이 | +1.720 | −5.283 | +7.003 |
| 부하 평균전력 차이 | −13.615 | +29.834 | **−43.448** |
| 완료 후 idle 지속시간 차이 | −1.030 | +3.429 | −4.459 |
| 완료 후 idle 평균전력 차이 | +4.456 | +4.327 | +0.129 |
| 실제 window와 단계 경계 잔차 | −0.0002 | −0.0003 | +0.0002 |
| **공통창 예측−관측** | **−8.468** | **+32.306** | **−40.774** |

따라서 동결 템플릿의 병행−직렬 `−36.216J`와 확인 관측 `+4.559J`의 불일치가 계산상 일치한다. 개발→확인 resident baseline 평균전력은 병행 1.116→1.146W, 직렬 1.161→1.096W였고, 완료 후 idle 전력도 병행 1.172→1.156W, 직렬 1.172→1.143W로 바뀌었다. 이것은 환경·순서·잔열·관측 변동 가능성을 보여줄 뿐 원인을 식별하지 않는다. 기존 단위·경계 버그는 발견되지 않아 동결 profile, 원본 적분, 기존 4세션 판정을 수정하지 않았다. 이번 진단은 이미 본 확인 자료를 다시 기술한 것이며 새 독립 검증이 아니다.

## 별도 PC 선택 계약

입력에는 profile SHA/기기 fingerprint·모델/입력 hash·동일 작업량·CPU thread/resident 수·AP 시작 관측 출처를 고정한다. 유효한 에너지 지표는 **부하 시작부터 명목 480초까지의 조건부 기기 전체 J** 하나다. `max_work_completion_s`는 부하 시작부터 870건 완료까지이며 대화형 개별 요청의 종단 간 응답시간이 아니다. `max_load_ap_peak_c`는 부하 중 AP 최고 관측값에 대한 **사용자 지정 기술 제한**이다. 두 제한 모두 `null`이면 미설정이며 프로젝트 기본값을 만들지 않는다. 완료시점까지 J를 공통창 J와 바꿔 넣거나, 준비·초기화·cleanup까지의 미계측 전체 에너지를 목적함수로 선택하는 입력은 `OUT_OF_SUPPORT`다.

기존 v1 출력은 `MODEL_CANDIDATE`(입력 제약 아래 한 arm만 두 기술 시나리오에서 충족), `TRADEOFF`(둘 다 충족하지만 빠른 병행은 AP가 높고 에너지 순위가 뒤집힘), `INDETERMINATE`(제약 충족이 단일 확인오차 시나리오에서 뒤집히거나 둘 다 미충족), `OUT_OF_SUPPORT` 중 하나였다. 확인 arm당 **1세션의 부호 있는 오차**를 동결값에 적용한 값은 사후 민감도 시나리오일 뿐 신뢰구간·안전 여유·보장 상한이 아니다. v1 [예시 결과](results/energy_operational_decision_01/decision_no_service_limits.json)는 보존한다. 후속 `decision-preview-v2`는 단일 후보를 `RETROSPECTIVE_MODEL_CANDIDATE`로 표기하고 29.1°C의 사후 확인 출처·개발 시작값·AP 평행 이동 가정·배포 불가를 출력에 명시한다. [v2 예시](results/energy_operational_decision_01/decision_no_service_limits_v2.json)도 제한 미설정 상태에서 `TRADEOFF`이며 자동 정책을 고르지 않는다. 두 확인 arm의 첫 준비 AP가 모두 29.1°C였으므로 이 숫자 검사는 **회고적 오차 적용 경계**일 뿐 물리적 지원 온도 범위가 아니다. 새 온라인 관측이나 가상 시작 온도 스윕은 지원하지 않는다. [채택된 중간 질문과 원래 목표 경로](ENERGY_THERMAL_TO_ORIGINAL_GOAL_PLAN_20260926.md).

## 대회 보고서 범위와 다음 결정

주장 가능: 동일 입력·870건 묶음의 직렬/병행 구현 및 4세션 계측, 완료시간·조건부 기기 전체 에너지·AP 최고온도의 **상충**, 원본 적분 재생, 개발 템플릿의 확인 오차와 공통창 에너지 방향 실패, 임계값 미설정 상태에서도 판단 불가를 표현하는 PC 기능. 주장 불가: 병행의 인과적 에너지 절감, 검증된 BAT·표면온도 안전, 서비스 제약 충족, 장시간·다른 작업량·반대 배정·임의 도착에서의 최적화, 기존 P 또는 새 동적 정책의 우월성. 기존 FAIL·부분 결과·동결 40값·20 null·종료 계획과 `experiment_ready=false`는 그대로다.

다음 사용자 결정은 **주장 범위** 하나다. 고정 CC_DG 기술 상충을 보고서의 제한된 결과로 채택한다면 추가 실측 없이 오차와 지원 범위를 함께 보고할 수 있다. 실제 서비스의 에너지·발열 최적화까지 주장하려면 먼저 비교할 서비스 완료기한/AP 기술 제한과 공통 관측창 또는 준비 포함 비용 중 어느 경계를 최종 지표로 쓸지 정해야 한다. 그때 선택을 바꿀 공백에만 독립 반복·미계측 준비/cleanup 에너지·해당 배정/도착 조건의 관측을 계약할 수 있다. 목적이 결정되기 전 새 실측 예산이나 허용 손실을 임의로 정하지 않는다.
