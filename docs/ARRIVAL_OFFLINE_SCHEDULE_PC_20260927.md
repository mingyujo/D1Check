# 작은 합성 도착 사례의 offline 일정 탐색 (ARRIVAL-OFFLINE-SCHEDULE-PC-01)

## 판정

질문 A는 “같은 작은 사례에서 비교 정책보다 **각 요청의 응답과 전체 완료·기한 위반을 악화시키지 않고** 공통 120초 기기 전체 에너지 또는 AP 최고온도를 낮출 일정이 있는가?”이다. 고정한 세 사례의 **제한된 이산 행동 공간을 완전 탐색**했지만 `THERMAL_ENERGY_PC_V1` 대비 A의 개선 일정은 없었다. 다른 세 기준 정책에 대해서는 offline 판단 0.5ms 대 기준 0.1ms 비용 등으로 A에 적격한 일정 자체가 없었다. 이는 임의 도착·연속 시간·다른 profile에서의 개선 불가능성이나 실기기 최적성 증명이 아니다.

질문 B는 요청별 응답 손실을 연구용으로 최대 250 또는 500ms 허용하되 완료·기한 위반을 늘리지 않을 때의 상충이다. `burst/thermal_cap`에서 기존 열·에너지 후보보다 250ms 조건은 **−0.114J / AP 최고 −0.032°C**, 500ms 조건은 **−2.004J / −0.080°C** 일정이 발견됐다. 후자의 최대 요청별 응답 손실은 **498.438ms**이며 AP 30.03°C 연구용 한도 초과 시간은 11.130→7.004초로 줄었지만 여전히 초과한다. `queue/energy_shift`의 500ms 조건은 **−0.127J / −0.0014°C**, 최대 응답 손실 467.266ms다. `low/loose_cpu`에는 500ms까지 에너지 개선이 없다. 이 차이는 미측정 W/AP 가정의 **수치상 탐색 결과**이고 최소 의미 절감 기준·반복 변동성 근거가 없어 실질 효과나 실기기 절감으로 판정하지 않는다.

세 사례 모두 0 미완료·0 기한 위반이었다. 긴급 표본은 사례당 **1개**다. 개별 응답과 일반 1~2개의 응답, 모든 비교 정책의 절대 지표·분모·AP 초과 시간은 [비교 CSV](results/arrival_offline_search_01/run_v1/comparisons.csv), 질문 A/B의 baseline별 최저 발견 일정과 최대 응답 손실은 [허용폭 CSV](results/arrival_offline_search_01/run_v1/witnesses.csv)에 있다. `B2`는 과거 개발에서 고정한 `GPU_CPU_parallel` 배정을 그대로 썼다. 결과를 보고 정책·전력·온도·허용폭을 바꾸지 않았다.

## 고정한 탐색 공간과 재생 계약

[CONFIG.json](results/arrival_offline_search_01/CONFIG.json)을 첫 탐색 전에 고정했다. 기존 24요청 `evaluation` low/queue/burst의 **시간순 첫 2/3요청**을 택했다. 요구·우선순위·1.5/6초 연구 기한·seed301의 backend별 실현 벡터·초기 AP·profile·공통 120초 창은 기존 계약에서 가져왔다. 사례 선택은 기존 24요청 결과를 이미 본 후의 회고적 설계이며, 작은 요청 수가 상태 점유와 공통창 에너지 차이를 바꾼다. 이 사례를 전체 24요청이나 독립 실기기 표본으로 대표시키지 않는다.

기존 이벤트 엔진을 그대로 사용하고 opt-in `decision_provider`만 추가했다. 탐색기의 실행 가능한 행동은 기존 열·에너지 후보의 aging/EDF **큐 선두**를 현재 비어 있는 CPU/GPU에 배정하거나 250ms 대기하는 것이다. 선두의 도착 후 자발적 대기는 최대 500ms로 제한했다. 이는 원래 온라인 후보의 최대 2초보다 좁은 행동 부분집합이다. 타이머는 이산적이지만 실제 도착·판단 종료·응답·persist·worker_release·lane_available과 병행 간섭은 연속 사건으로 처리한다. 전체 요청 순서 재배치·선점·busy lane 조기 해제는 허용하지 않았다. 병행 상태와 에너지/AP 계수는 기존 explore profile의 **미측정 가정**이며 strict 지원·Android 병행 적격성으로 승격하지 않는다.

탐색 시 미래 도착과 backend별 실현 비용을 이용해 분기를 평가한다. 따라서 발견 일정은 **offline oracle** 참고값이다. 기존 온라인 정책의 `choose`에는 이 정보를 전달하지 않았고, 각각 자신의 기존 판단 비용과 frozen 설정으로 같은 축소 trace를 새로 실행했다. Offline 일정 자체에도 열·에너지 후보와 같은 판단 0.5ms, 기록·dispatch 각 0.1ms를 부과했고 탐색 프로그램의 PC 실행시간은 기기 시간에 넣지 않았다. 다른 기준 정책의 판단 0.1ms는 기존 설정 그대로다. 비용 차이 때문에 질문 A의 기준 비교는 offline에 더 엄격하며, 동일 계산비용으로 통일한 가상 비교를 실행했다고 쓰지 않는다.

공통창 에너지는 idle을 포함한 **기기 전체 절대 전력 W**를 상태별로 한 번만 적분한다. AP는 상태별 평형온도와 τ=60초의 가정된 1차 전이이고 에너지→온도 물리 보정식이 아니다. 완료 이전/이후의 idle·잔열과 AP 한도 초과 시간은 기존 회계 경계와 일치한다. 긴급 응답은 output_ready, 일반은 persist_complete, lane 재사용은 lane_available이다. 작업별 미래 실현시간과 미래 도착은 **offline 탐색에만** 쓰인다. 엔진의 성공 전용 실현 벡터에는 확률적 실패·거절 모델이 없어 이 실험의 실패 0은 실기기 실패율 근거가 아니다.

전수 열거는 사례당 1,500~3,000노드와 20초 cap을 미리 지정했다. 실제 68·258·301노드/0.156·0.718·0.797초로 stack을 모두 비워 `complete`다. 검증되지 않은 가지치기는 없고, 비지배 일정은 요청별 응답·완료/위반·공통창 에너지·AP 최고·AP 한도 초과시간을 별도 축으로 계산했다. [비지배 CSV](results/arrival_offline_search_01/run_v1/pareto.csv)는 동등 수치 일정을 한 번만 보존한다. 예산이 소진됐다면 `budget_exhausted`와 미탐색 prefix를 남기며 “개선 불가능”이라고 하지 않는다. `complete`도 **이 사례·격자·500ms 대기·큐 선두·가정 모형 안에서만** 최저값을 증명한다. 10⁻⁶ 수치 비교 tolerance는 의미 있는 효과 기준이 아니다.

## 해석과 다음 행동

질문 A 실패는 현재 제한된 조건에서 응답을 그대로 지키면서 에너지/AP를 더 줄일 여지가 작다는 **모형 내부의 상충**을 시사한다. B의 개선 일정은 `THERMAL_ENERGY_PC_V1`의 한 번 앞 선택이 에너지 최저 일정과 달라질 수 있음을 보여주지만, 대부분 요청 응답 손실을 사용하며 offline 미래 정보도 쓴다. 특히 queue의 열 차이 0.0014°C는 센서 실측 차이로 읽을 수 없고, burst의 AP 한도 역시 달성하지 못했다. “온라인 후보의 규칙만 고치면 실기기에서 절감”이라는 결론은 없다.

다음 행동 하나는 **발견한 B 일정의 첫 배정·대기가 당시 관측 정보만으로 구별 가능한지 기존 trace에서 판정**하는 것이다. 구별 불가하면 offline 격차를 새 온라인 정책의 달성 가능 이득으로 삼지 않는다. 구별 가능하더라도 이 보고서만으로 정책 튜닝·새 실측을 자동 시작하지 않는다. 실제 선택을 바꿀 W/AP 또는 판단 비용의 측정 목적은 그 후에만 좁힌다. 기존 P·동결40값·20 null·FAIL·부분 결과·종료 계획·`experiment_ready=false`는 그대로다.

재현·대시보드·출처 SHA와 테스트 명령은 [결과 안내](results/arrival_offline_search_01/README.md)에 있다. 기존 192회 실행과 72개 확인 짝 비교는 재실행하지 않았다.
