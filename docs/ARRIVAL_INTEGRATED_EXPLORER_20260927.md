# D1Check 통합 PC 탐색 도구 — 2026-09-27

**결론.** 기존 [정책 비교 화면](results/arrival_policy_screen_01/dashboard.html)을 한 진입점으로 확장했다. 동일한 low·queue·burst/seed/실현 간섭에서 긴급·일반 응답과 기한 위반, 사용자 δ 제약, 공통 120초 기기 전체 에너지, AP 최고온도 가정을 함께 조작한다. 서비스 성능은 동결 PC 모형 결과이고 전력·AP는 미측정 가정이다. 어떤 정책도 에너지·열을 실제 배정 판단에 쓰지 않으며, 사후 회계가 열 피드백 최적화나 실기기 절감을 입증하지 않는다.

## 왜 기존 병행 전력 경계가 제한적이었나

기존 비용 경계는 전체 병행 시간을 `pair W` 하나로 곱했다. 그러나 동결 일정에서 B2는 **분류 GPU＋탐지 CPU (CG_DC)**, B3는 CG_DC 외에 **탐지 CPU＋탐지 GPU**, 분류 CPU＋탐지 GPU 등도 사용한다. queue/seed201/실현1.5의 공동 lane 점유는 B2 CG_DC 2.531초, B3 CG_DC 1.324초·탐지 CPU＋GPU 8.326초·CC_DG 0.688초다. 단계의 공동 점유이며 GPU kernel의 동시 실행을 뜻하지 않는다. 실기기에서 계측한 고정 묶음 CC_DG를 반대 배정 CG_DC의 계수로 전용하지 않았다.

새 회계는 시점마다 `idle`, 각 task×backend 단독, 각 task×backend 공동 상태 중 정확히 **하나의 전체 기기 전력**을 적용한다. 큐 대기는 해당 활성 상태 또는 idle에 포함되어 유휴 전력을 더하지 않는다. 기존 각 상태에 1/2/2 W를 공통 적용하면 과거 135일정의 상태 지속시간·에너지와 seed201의 기존 AP 스트레스 결과가 일치한다. 과거 CSV와 화면은 보존했다.

B2−B3 차이는 같은 고정 일정에서 `ΔE = C + Δt(CG_DC)·P(CG_DC) + Δt(탐지 CPU＋GPU)·P(탐지 CPU＋GPU)`다. C는 다른 모든 독립 상태 전력을 현재 입력으로 고정한 항이다. [seed별 계수](results/arrival_policy_screen_01/pair_plane_examples.csv)와 화면의 동률선은 재시뮬레이션 없이 계산한다. queue/실현1.5에서 CG_DC를 가정상 2 W로 둘 때 탐지 CPU＋GPU의 동률값은 seed 5개별 약 2.065–2.092 W다. 이 값도 실제 A24 전력의 범위나 임계값이 아니다. 기존 공통 `pair W` 2.070–2.100 W 경계는 두 상태를 결박했을 때의 별도 가정 결과로 남긴다. low에는 두 공동 상태 시간이 없어서 이 축의 동률선이 없다.

## 사전에 고정한 대표 비교 3개

아래 에너지는 idle 1 W·모든 단독 2 W·모든 병행 2 W, AP는 초기 29°C·idle/단독/병행 평형 29/34/30°C·τ 60초라는 **미계측 스트레스 입력**이다. 5 seed별 공통창 에너지와 최고 AP의 평균이며 모두 예정 24건/seed가 완료됐다. 긴급 P95는 각 seed 긴급 6건의 nearest-rank P95를 평균한 값이다. 전체 분모는 일반 90건이다. [정확한 CSV](results/arrival_policy_screen_01/representative_comparisons.csv)와 [보존 응답 CSV](results/arrival_policy_screen_01/policy_screen.csv)를 같은 조건으로 읽었다.

δ는 일반 위반율이 CPU의 정확한 건수/분모보다 몇 %p까지 증가해도 되는지 입력하는 **연구용 제약**이다. 기본 δ=0은 탐색 시작점일 뿐 서비스 합의 기준이 아니다. 제약 충족 후보와 응답 지표의 비지배 후보만 표시하며, 에너지·AP 가정을 합쳐 임의 종합 1위를 만들지 않는다. seed를 고르면 단일 seed 값을, 전체를 고르면 seed별 지표 평균과 정확한 전체 위반 건수를 표시한다. 정책별 미완료·실패를 0으로 숨기는 기능은 없지만 현재 저장된 성공 PC vector에는 모두 0이다.

## 출처와 재현 범위

[사용 안내·재현 명령](results/arrival_policy_screen_01/README.md)과 [상대 경로 번들](results/arrival_policy_screen_01/repro_bundle/SOURCE_HASHES.json)에 입력·코드 SHA-256을 남겼다. 전체 생성은 `python -X utf8 -m tools.d1_arrival_policy_screen`; 번들만 다른 폴더에 복사한 뒤 `python -X utf8 reproduce.py --bundle . --output .`로 동일 HTML을 재생성한다. 번들은 선택된 동결 PC 일정과 응답만 포함하며 모델·APK·실기기 원자료를 포함하지 않는다. 다른 도착 trace나 정책을 다시 시뮬레이션할 수 있는 완전한 모델 묶음은 아니다.

PC 검증은 `python -X utf8 -m unittest tools.test_d1_arrival_policy_screen -v`로 수행한다. 선택 일정 135개의 응답 결과 대조, 120초 상태 분할, 기존 스트레스 에너지/AP 일치, 독립 병행 전력의 선형 차이, 번들 해시 차단·다른 임시 폴더 재현, Chrome의 로컬 HTML 계산 렌더를 확인한다. 이는 브라우저/PC 기능 검증이며 Android 정책 실행 검증이 아니다.

측정 근거가 있는 것은 CAL-03 개발 요청 구간과 별도 고정 CC_DG 운영 실측이다. 임의 도착의 상태별 전력·AP, B2 CG_DC, B3 탐지 CPU＋GPU 전력·열 계수는 없다. 여기의 W/J/AP 수치는 실측 기반 도착 비교가 아니며 BAT·표면온도·절대 에너지 정확도·동적 열 피드백·정책 우월성 PASS를 주장하지 않는다. 기존 FAIL·동결값·원자료·`experiment_ready=false`는 유지한다.
