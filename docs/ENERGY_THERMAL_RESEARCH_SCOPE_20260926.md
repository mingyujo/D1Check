# 고정 CC_DG 에너지·열 연구 질문과 다음 판정 경계

2026-09-26, 출발 HEAD `1c1b44974f456447209e1438ffa55beba9479db3`. 이 문서는 **후속 연구 질문의 권고**이며 기존 프로젝트 목표나 서비스 기준의 채택 결정은 아니다. 근거는 [운영 4세션 결과](ENERGY_OPERATIONAL_PAIR_01_RESULTS_20260926.md), [개발 모형·확인 오차](ENERGY_OPERATIONAL_SIM_CONNECTION_20260926.md), [제약 탐색](ENERGY_OPERATIONAL_DECISION_PC_20260926.md)과 그 문서가 고정한 JSON·코드다. 새 실측·재보정은 하지 않았다.

## 권고와 주장 범위

**권고 중간 질문:** “A24의 현재 분류 CPU 678건·탐지 GPU 192건을 같은 입력과 품질로 처리할 때, 사전에 정한 부하 시작 기준 완료기한을 만족하는 직렬·병행 중 공통 480초의 조건부 기기 전체 에너지가 더 낮은 방식은 있는가? 그때 AP 온도 경로는 어떻게 다른가?” 두 방식의 실제 구현과 완료·품질 기록이 있으므로 이 질문은 검토할 가치가 있다. 그러나 원래 [PLAN의 질문](PROJECT_PLAN.md#1-한-문장으로-설명하는-프로젝트)은 **겹쳐 도착하는 대화형/일반 요청의 순서·CPU/GPU 배정·병행 결정**이다. 고정 묶음의 사전 직렬/병행 선택은 그중 한 단면이다. 대화형 개별 응답·일반 서비스 보장이나 임의 도착에 대한 동적 최적화는 이 질문으로 대체하지 않는다. 발열·배터리 최적화 목표 역시 유지한다.

기존 혼합 도착 A24 독립 평가는 수행됐지만 P의 주 결합 기준은 FAIL이었다. 그 결과가 고정 묶음의 에너지 질문을 입증하거나, 발열·배터리 최적화 가능성을 기각하는 것은 아니다.

|---|---|---|

| 동결 PC 모형 | 개발 단계 길이·기기 전체 전력·AP 경험 경로; 확인 오차를 **재보정 없이** 계산 | 공통 480초 에너지 비교 방향 재현: 개발 −36.255J, 확인 +4.559J(병행−직렬). 동결 예측은 확인에 −36.216J |

확인 block에서 병행은 작업 완료가 126.319초 빠르고 **각자의 완료시점까지** 조건부 기기 에너지는 143.341J 낮았지만, **공통 480초** 에너지는 4.559J 높고 부하 AP 최고는 1.9°C 높았다. 개발 block의 공통창 방향은 반대였다. 단위는 A24 전류 raw=mA 해석에 조건부이고 절대 에너지 정확도는 미인증이다. 같은 AP 시작값이 같은 내부 열 상태를 보장하지 않으며 세션 순서·유휴전력 차이를 분리하지 못했다. 따라서 에너지 절감, 열 안전, BAT 온도/배터리 수명 개선, 정책 우월성은 입증되지 않았다.

## 29.1°C 적용 조건의 출처

동결 [profile](results/energy_operational_sim_01/frozen_profile.json)의 **개발** 첫 준비 AP는 직렬 29.4°C·병행 29.2°C다. [확인 평가](results/energy_operational_sim_01/confirmation_evaluation.json)의 두 arm은 29.1°C였다. [예시 입력](results/energy_operational_decision_01/query_no_service_limits.json)의 29.1°C는 **확인 결과를 본 뒤** 두 arm의 오차 시나리오를 같은 관측 시작값에 놓으려고 선택한 값이지 개발 모형의 기준점, 사용자 시나리오, 물리적 적용 한도가 아니다. `tools/d1_energy_operational_decision.py`의 동일값 검사는 이 회고적 예시에서만 작동한다. 다른 값이 `OUT_OF_SUPPORT`인 것은 기기에서 그 온도로 실행할 수 없다는 판정이 아니라, 두 arm에 공통인 확인 오차를 적용할 근거가 없다는 뜻이다.

`tools/d1_energy_operational_sim.py:predict`는 개발 단계별 AP 변화량을 입력 AP에 **평행 이동**한다. 전력→열 법칙이나 초기 온도 변화에 따른 동역학을 식별한 것이 아니다. 29.1°C에서도 확인 각 1세션의 기술 오차만 있고 시작 온도 반응은 검증되지 않았다. 직접 `predict`에 다른 숫자를 넣을 수 있다는 사실을 측정하지 않은 온도의 지원으로 해석하지 않는다. 기존 frozen profile·확인 결과·예시 query는 보존한다.

## 다음 검증 계약에서 고정할 기준

| 항목 | 현재 상태 | 다음 판정에 필요한 정의 |
|---|---|---|
| 같은 작업·품질·완료 | 기존 870건·입력 hash·품질 적격성·실제 lane 해제 기록 있음 | 양쪽 모두 같은 870건을 정상 완료해야 하며 실패·미완료·누락을 분모에서 빼지 않음 |
| 완료기한 | **미정**. 이 묶음에 합의된 서비스 SLA 없음; 과거 engineering deadline은 전용 불가 | 부하 시작→870건 완료의 기한과 근거를 새 결과 열람 **전** 지정. 개별 대화형 응답 기한과 구별 |
| 공통 에너지 경계 | **관측 기반 기술 경계**: 부하 시작→명목 480초, 완료 후 resident idle 포함 | 이 중간 질문의 일차 비교량 후보. 준비·초기화·냉각·cleanup을 포함한 전체 운영/배터리 절감으로 부르지 않음 |
| AP 온도 | 부하 AP 경로·최고 관측됨; BAT 모형 미식별 | AP는 보조 관측 지표. 서비스/안전 한도는 **미정**이며 근거 없이 제약으로 확정하지 않음 |
| 최소 의미 절감·변동성 | **미정**. 개발/확인에서 공통창 차이의 부호가 역전했고 arm당 block별 1세션 | 배터리 예산·사용 맥락에서 의미 있는 절감량과 독립 block 변동성 산정 절차를 먼저 정함. 확인 1세션 오차를 신뢰구간/보장 상한으로 사용하지 않음 |

향후 검증은 같은 작업·환경·관측 경계에서 개발 기준/모형을 동결하고, 별도의 독립 block에서 **기한 충족 여부, 공통창 병행−직렬 에너지 차이, AP 경로, 누락/실패**를 함께 보고해야 한다. 절감 판정은 사전 합의한 최소 효과와 변동성 근거를 모두 요구한다. 지금은 그 수치가 없으므로 PASS나 반복 수를 정하지 않는다. 기존 자료는 이미 모형 구성·오차 검토에 사용했으므로 새 후보의 독립 평가로 재명명하지 않는다. 이 판정이 필요해질 때만, 무엇을 선택할지 바꿀 불확실성을 지정해 새 실측 필요성을 판단한다.

**다음 행동 하나:** 이 고정 묶음을 원래 목표의 *중간 기술 질문*으로 사용할지 정하고, 사용한다면 비대면 서비스/배터리 요구 근거로 `부하 시작 기준 기한·공통 480초 경계의 적합성·최소 의미 절감량`을 결과와 독립적으로 한 계약에 동결한다. 채택하면 좁은 조건의 에너지·시간·AP 상충을 엄밀히 검증할 수 있지만, 임의 도착의 적응형 최적화·BAT/수명·전체 운영 에너지 주장은 포기해야 한다. 채택하지 않으면 현재 4세션은 제한된 기술 결과로만 남기고 그 방향의 추가 수집은 시작하지 않는다. `experiment_ready=false`, 기존 FAIL·부분 결과·동결 설정·종료 계획은 그대로다.
