기존96요청의1.713J를 입증할 때까지 반복하는 계획이 아니다. 지속 부하에서의 관측 차이·예측 한계·상충을 끝까지 판독한다. 관측 가능한 변화가 부족하거나 동일 서비스 제약 비교가 성립하지 않으면 그 결과로 종료한다. 정책 절감 성공·정밀 오차 한도·범용 열 모형 완성을 보장하지 않는다.

## 입력 하나와 PC 착수 gate

단일 후보: 분류/탐지 교대 **192요청(96:96), 400ms 예정 도착**, 첫 common35초·마지막111.4초, 공통 에너지창0~120초, 기존 baseline/cooling을 포함한 고정 관측210초. 분류 urgent1.5초·탐지 normal6초는 유지한다. CPU/PAR만 사용한다.

선정 이유: 기존 입력을 더 오래 제출하는 연속 사용을 표현하고, CPU 개발 phase 평균에서 분류+탐지 lane 점유 약0.787초가 두 도착 간격0.8초에 가까워 지속 점유와 기한 충족을 함께 검토할 수 있다. 이것은 평균 기반 배치 가능성의 근거이며 실제 완료 보장이 아니다. 400ms를 선택한 이유는 에너지 오차나 가장 큰 절감을 탐색한 결과가 아니다. 다른 간격·요청 수를 연속 시험해 성공하는 입력을 찾지 않는다.

1. 동결 처리시간으로 두 정책의 모든192요청 기한·공통창 내 lane 해제, 실제 사용하는4상태와 전환을 검사한다. 관측 분산·cold/early 특성이 반영되지 않은 평균 예측의 한계를 표시한다.
2. 예상 CPU/GPU 점유·유휴 비중과 정책별 차이를 공개한다. 에너지 차이가 두 배가 되거나 배경 변동이 없어질 것으로 가정하지 않는다. 새로운 열 이력은 기존 strict 확인이 아니라 **프로토콜/입력 전이 평가**다.
3. 기존과 실질적으로 같은 정보밖에 주지 않거나 한 정책이 기한을 못 지키면, 이 후보의 동등 서비스 최적화 비교는 취소한다. 입력/기한을 즉석 변경해 통과시키지 않는다. 새 가정 전력·스로틀 계수도 금지한다.
4. 기존 에너지·AP 모형은 변경 없이 적용 가능한 식만 별도 진단 출력으로 사용한다. 계수 미지원/수학적 입력 부적격이면 예측null; 관측만으로 모형 검증을 완료했다고 하지 않는다.

현재 구현 제약: `ArrivalPolicyStudy.COUNT=96`과 Python `d1_separated_power_protocol.validate`가96개/350ms 확인 입력을 강제한다. **현재 APK/실행기를 그대로 써서192개를 실행할 수 없다.** 기존 버전 유지＋별도 opt-in192입력 검증, 호출 상한, 정상/실패 종료, 기록/회수, host 소비 집계를 함께 연결해야 한다. 필요한 프로젝트 키 서명 APK만 빌드하며 모델/키를 공유하지 않는다. PC gate 전부터 설치하지 않는다.

## 주 실행과 사전 판독

최대4쌍(8세션). 순서 제안은 CPU/PAR, PAR/CPU, PAR/CPU, CPU/PAR이며 새 자료 전에 manifest와 함께 동결한다. 이미 순서 교차를 했던 과거 비교를 무시하지 않는다. 이번4쌍은 **다른 입력의 독립 관측과 전이 오차를 얻는 제한된 규모**이며 충분한 검정력이나 작은 절감의 입증에 필요한 수라는 주장이 아니다.

- 동일 입력·resident4·warmup8·APK/계측 버전·공통창. 시작 AP/부하 전 전력/배터리/이전 부하·휴식 이력은 각각 보존한다. 시작 AP만 같다고 숨은 열 상태를 같다고 하지 않는다.
- 전체 예정요청 분모, 시작/반환/output_ready/저장/worker_release/lane 해제, deadline 충족과 P95를 함께 보고한다.
- 주 비용은 동일0~120초 전체 기기J. AP는 사전 공통 판독창과 조회 coverage를 동결하고 최고값·절대경로·변화량·MAE/max를 별도 보고한다. 센서 결측을0으로 채우지 않는다.
- 직접 정책 차이와 동결 모형 오차를 구분한다. 비교쌍별 원 수치·평균·범위를 공개하고,4쌍으로 미래 오차 한도·동등성·정밀 정책 순위를 선언하지 않는다. 통계 방법을 추가한다면 새 결과 전 가정과 사용 조건을 고정한다.
- 최소 유효 에너지 절감과 허용 열 증가의 실용 기준이 현재null이므로 **실용 최적 정책 PASS는 만들지 않는다.** 응답 개선만 있으면 에너지·열 최적화 달성으로 쓰지 않는다. 관측된 동시 개선/상충/차이 미확인을 구분한다.

## 실패 수정과 재실행 — 사용자의 추가 요청 반영

**최대2회 추가 세션 시도**, 같은 미확정 원인을 성공할 때까지 반복하지 않는다. 8개 주 실행의 실패 자리를 보완하는 범위이며 새로운 질문·추가 후보·추가 부하를 위한 여유 실행이 아니다. 정상 완료했으나 오차가 크거나 정책 이득이 없는 것은 재시도 사유가 아니다.

|실패 종류|자율 처리|
|---|---|
|원본 판독/표시/CSV 오류|PC에서 수정·회수된 자료 재분석. 기기 재실행하지 않음|
|재현 가능한 host/manifest/소유권/실행 코드 오류|원래 오류/부분 소비 보존→최소 수정→관련 PC 검증→새 해시/ID/출력·한도 동결 후 실패 자리 최대1세션 보완. 전체 캠페인 추가시도2회 한도|
|필수 환경 gate·배터리·충전·thermal·자료 적격성 실패|기준/timeout/설정 완화 없음. 무인 상태에서 사용자 조치가 필요하면 기기 단계 종료|
|연결 소실·대상/소유권 불명확·원인 미확정 lifecycle|자동 reconnect/daemon 재시작/다른 transport 전환·앱 재실행 금지. 계약상 증거/정리만 수행하고 미확인 보존|
|모형 오차·절감 없음·큰 배경 변동|관측 결과로 남김. 계수 재조정·표본 제외·새 조건 실행 금지|

소비된 ID/registry 초기화·종료 계획 재개 금지. 재시도 자료는 원 실패를 지우는 대체품이 아니라 **추가 획득 block**으로 보고하고, 최초8세션이 모두 성공한 것으로 합치지 않는다. 새 APK/계측 동작으로 의미가 바뀌면 기존·새 버전을 분리한다. 동일 프로토콜 비교의 타당성을 유지할 수 없으면 남은 세션 중단하며 전체 재수집을 자동 시작하지 않는다.

기존 block 실행기가 첫 실패에 전체를 종료하면 그 계획은 그대로 종료한다. 다음 새 block에는 아직 미시도인 원래 자리와 승인된 보완 자리만 넣는다. 최초8자리＋추가시도2의 캠페인 원장을 따로 유지해 새 계획 생성으로 소비를 초기화하지 않는다. 실행 계획은 최초 포함 최대3개다. 같은 ID 재개 없이 이 경계가 구현·검증되지 않으면 자동 복구 실행은 하지 않는다.

부모/자식 실행 상태와 실행ID·시작시각·명령 식별이 불명확한 활성 실행 위에서 새 실행하지 않는다. 정상 앱 cleanup·host force-stop·프로세스 부재를 구분하고 단일 담당이 정리한다. 실패한 정리가 최초 오류를 덮지 않는다. 통신 소실/PC 정지/native hang까지 항상 종료를 보장할 수 있다는 주장은 하지 않는다.

현재 코드 식으로 n=8 본 block 예약은 `600+8×700+7×90=6,830초`, ADB `8×3200+200=25,800`이다. 최대3개 계획으로 나누어10세션을 시도할 때 preflight3×600＋세션10×700＋모든 세션 사이 예약9×90을 합하면 **참고 예약9,610초·ADB32,600**이다. block 경계의90초 두 번까지 포함하며 preflight와 겹쳐 시간 절감을 가정하지 않는다. 3시간 기기 단계10,800초에서 남는1,190초는 수정·PC 검사/동결 등의 여유다. 이 합은 기존96경로의 식을 적용한 **상한 설계 목표**이며192경로의 확정 예산이 아니다.

입력변경 후에도210초 관측/700초 세션 예약 안에 처리·환경감시·회수·cleanup이 포함되는지 실제 코드에서 검증한다. 늘어난 요청과 artifact 회수, 재시도 preflight/설치 timeout을 모두 확인한다. 예산이 위 시간·명령·호출 상한 안에 들어오지 않으면 자동 증액하지 않고 기기 단계 취소한다. 작업을 끝내기 위해 마지막 회수/cleanup 시간을 쓰지 않는다. 실제 고정 관측 외 모든 준비 시간이 포함된 예산만 실행 가능 판정에 사용한다.

예산에 별도 적격성 호출을 숨기지 않는다. 현재 warmup 품질 검사 재사용 외 호출이 필요하면 계획을 그대로 실행하지 않는다. AP 조회 신선도/유효성은 유지하고 과거32.5°C 개발 하한을 새로운 안전 기준으로 복원하지 않는다. 현재 battery·비충전·BAT온도·thermal·화면·메모리/품질 gate는 완화하지 않는다. 무인 중 충전 전환·설정 변경·다른 앱 종료·Activity 이탈 명령 없음.

## 잠자는 동안 마무리할 산출물

1. 구현/테스트·지원/전이 범위·모형/입력/APK/분석 해시를 고정한 계획 또는 **실행 불가의 정확한 코드/자료 조건**.
2. 실행했으면 모든 시도·실패·미시도·미확인 소비와 원본 receipt/inventory, 앱/host 종료 기록.
3. 유효자료에 한해 실제/예측 일정·J·AP·누적잔차·직접 정책 차이. 없는 자료를 채운 완성 그림 없음.
4. 시뮬레이터에서 지원된 예측·전이/탐색·미지원·정책 우열 보류를 분리해 연결하고 재현 명령·문서·Git 정리.

**“시뮬레이션 마무리”는 코드·기존 자료·얻은 자료의 판독과 공유물을 일관된 상태로 끝내는 것**이다. 아직 입증하지 못한 열 예측·정책 절감까지 완료라고 표시하라는 뜻으로 해석하지 않는다. 실측 실패 시에도 독립적으로 가능한 PC 산출물은 마무리한다. 후보재적합·다른 입력 선택·추가 캠페인은 이6시간 안의 자동 후속 범위가 아니다.

아침 보고는 완료/중단, 실제 상한 소비, 바뀐 파일과 이유, 확인된 정책 상충/오차, 남은 구체적 한계, 원본·그림·재현·실제 원격HEAD를 포함한다. 네트워크가 유지되면 관련 작은 파일만 정상push한다. APK·키·모델·대용량 원자료·기기식별정보는 제외한다.
