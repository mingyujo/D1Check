# AP 판정·에너지 연결·현재 가능한 비교의 PC 마감

출발 HEAD `c79a44a0b7a59b3ff124b9d3d4bb92e148b5fe9b`, 2026-09-30. **고정 CC_DG 870건 직렬/병행의 회고적 제한 계산은 지금 사용할 수 있다. 동적 low/queue/burst 정책의 실측 기반 전체창 J/AP 비교는 아직 0개다.** 이를 가정 순위나 부분 에너지로 대체하지 않았다. 이번에는 기존 8세션에서 AP 지연 판독과 3세션의 에너지 계산을 수행하고, 기존 선택 인터페이스를 한 번 호출했다. 새 실측·후보 적합·정책 배치는 없다.

## 1. AP 후보의 결론

[이미 동결·확인한 후보](ENERGY_AP_IDLE_RESPONSE_RUN01_20260929.md)는 `dT/dt=β(E−T)+(a_state−a_idle)`다. β와 상태 기울기는 원래 개발3 동결본 그대로, E만 허용된 **부하 전** AP로 계산한다. 확인 MAE 0.418°C는 원래 동결식 외삽 5.461°C보다 작지만 일반 모형 채택을 의미하지 않는다.

유휴에서는 `T(t)=E+(T0−E)exp(−βt)`이므로 고정 E·양의 β 아래 한 방향으로만 움직인다. 상태가 계속 idle인 동안 상승 후 하강하는 **관측 경로**를 이 식 하나로 정확히 표현할 수 없다. 이는 초기값 누락이 아니고, 기존 구현의 온도 연속성도 유지된다. 이번에 β·E·상태 기울기를 다시 맞추거나 평행 이동하지 않았다.

8세션(원래 개발3·DC_DG 확인1·새 프로토콜 CG_DC1·B2 재생1·유휴 개발/확인2)의 실제 lane 점유 합집합을 구했다. 그 뒤 **10초 이상 연속 유휴 19구간**만 판독했다. 10초는 여러 AP 표본을 볼 분석 필터이며 새 지원 경계·센서 갱신 주기·합격 기준이 아니다. 19구간은 19개 독립 세션이 아니다.

| 저온 확인에서 실제 lane-free 구간 | lane 해제 | 첫 확실한 유휴 AP | 최고 첫 표본 | 마지막 AP | 최고 표본−해제 |
|---|---:|---:|---:|---:|---:|
| 첫 묶음 후, 다음 dispatch 전 | 41.326s | 41.601s / 28.9°C | 44.281s / 29.6°C | 60.446s / 28.9°C | 2.955s |
| 마지막 묶음 후 | 72.053s | 73.886s / 28.8°C | 76.516s / 29.7°C | 178.111s / 28.8°C | 4.463s |

두 구간 모두 조회 bracket 전체가 lane 해제 뒤에 있는 표본만 사용했다. 마지막 최고 표본의 조회 시점 범위는 release 후 **4.353–4.573초**다. 이 범위는 Android uptime 기반 조회 bracket이며 **센서 내부 측정시각이나 물리적 열 지연 범위가 아니다**. 이전 낮은 표본부터 높은 값이 처음 보인 조회까지의 범위도 CSV에 별도 보존했다. host monotonic과 Android 시각을 직접 빼지 않았다.

전체 조회 간격 중앙값은 세션별 **2.522–2.680초**, 최대 간격 **3.300–4.365초**였다. 인접 AP값이 반복되고 값 변화가 관측된 시점 사이 중앙 간격은 **10.352–15.053초**다. 양자화·센서 갱신·열 반응 모두 가능한 설명이므로 이를 하드웨어 주기라고 확정하지 않는다. 19구간 중 상승 후 하강은 위 **한 확인 세션의 2구간**에서 확인됐다. 나머지에서 관측되지 않았다는 사실은 지연이나 숨은 열 상태가 없다는 증명이 아니다.

**확정:** 단일상태 후보의 관측 응답 형태 한계가 있다. **미확정:** HAL 값의 갱신 지연, 실제 잔열 전달, 두 효과의 비율. 별도 sensor timestamp나 독립 지연 제약 없이 이 값들만으로 물리적 hidden-state 계수를 유일하게 식별했다고 주장할 수 없다. 새 2상태 모형·지연 계수를 임의로 추가하지 않는다. 기존 후보는 **부하 전 AP＋실제 일정 조건부 진단**으로 보존하고 기본/strict에 채택하지 않는다. 이미 본 확인자료의 후속 분석은 사후 분석이다.

## 2. 에너지와 일정 연결 결과

기존 전체 기기 W를 actual dispatch→lane_available 상태 구간에 한 번만 적용했다. 전류/전압 적분은 기존 midpoint·raw=mA 조건부 환산과 동일한 120초 경계다. 작업 전 대기도 전체창에 남기며 미래 AP/전류를 예측 입력으로 쓰지 않는다. AP 후보는 W를 바꾸지 않는다.

| 실제 일정 조건부 **외삽 진단**, 공통120초 | 관측 J | 동결식 J | 예측−관측 J (%) | 시작~마지막 해제 오차 | 이후 유휴 오차 |
|---|---:|---:|---:|---:|---:|
| 기존 B2 1세션 | 154.696 | 155.758 | +1.062 (+0.686%) | +1.687 | −0.625 |
| 유휴 반응 개발 | 135.618 | 155.708 | +20.090 (+14.814%) | +6.985 | +13.105 |
| 유휴 반응 확인 | 144.565 | 155.870 | +11.305 (+7.820%) | +3.262 | +8.043 |

`시작~마지막 해제`는 순수 실행 시간이 아니다. 유휴 반응 개발의 앞35초 대기, 확인의 앞35초와 두 묶음 사이 대기도 포함한다. CSV에는 정확한 경계가 있다. 에너지 phase 합 및 인접 센서구간의 양/음 오차 합은 전체차와 1e−7J 이내로 일치했다. 이는 산술 보존 검사이며 인과 설명이 아니다.

B2의 양/음 센서구간 잔차는 +13.367/−12.305J로 상쇄됐다. 유휴 개발은 +26.630/−6.540J, 확인은 +21.829/−10.523J다. 유휴 꼬리 오차가 새 두 세션에서 모두 양수인 사실은 기존 W의 조건 전이 오차를 보여준다. 이를 화면·배터리·온도·ADB 하나의 원인으로 귀속하지 않는다. 실제 CG_DC 점유는 각각 1.683/1.678/0.847초로, 이 자료만으로 병행 W를 독립 정밀 식별하지 않는다. 절대 J 정확도 미인증은 유지한다.

따라서 **AP MAE 개선만으로 에너지+열 정책 비교를 완성할 수 없다.** B2의 0.69%를 보편 오차 한도로 쓰지 않고, 서로 다른 시점·부하 이력의 세 총량을 정책 절감 비교로도 쓰지 않는다. 일정·응답은 저장 PC 결과를 그대로 재사용했다. 새 실측의 실제 일정 조건부 비용(A)과 예정 도착으로 일정까지 생성하는 종단간 예측(B)은 계속 분리한다.

## 3. 지금 실행 가능한 완전한 사례와 동적 차단

`d1_energy_operational_decision.decide`에 기존 identity·29.1°C 회고적 시작값·미설정 한도를 전달해 **한 고정 episode 비교**를 재현했다. [기존 870건 계약](ENERGY_OPERATIONAL_DECISION_PC_20260926.md)의 제한 그대로이며, 상태 개발3 모형과 혼동하지 않는다.

| CC_DG 직렬/병행, 같은870건·공통480초 | 개발 템플릿 예측(병행−직렬) | 저장 확인 관측(병행−직렬) |
|---|---:|---:|
| 전체 작업 완료시간 | −122.456s | −126.319s |
| 공통창 기기 에너지 | −36.216J | **+4.559J** |
| 부하 AP 최고 | +1.5°C | +1.9°C |

결과는 기존과 같은 `TRADEOFF`, `model_candidate=null`이다. **고정 묶음에서 빠른 완료와 높은 AP, 에너지 순위 불일치를 기술하는 제한 시뮬레이션은 완료됐다.** 준비부터 cleanup까지 전체 운영 에너지, 임의 시작 AP·부하량, 온라인 정책 비교는 지원하지 않는다. 확인 자료를 이미 본 뒤 설계한 템플릿의 사후 holdout이며 정확도 PASS·정책 우월성은 없다. 원래 동적 연구 목표를 이 결과로 완료 처리하지 않는다.

저장135개 일정의 [기존 차단 CSV](results/arrival_policy_screen_01/measured_support_01/support_status.csv)를 재사용했고 배치를 반복하지 않았다. queue/seed201/실현1.5의 CPU_URGENT/B2/B3 세 대표를 연결했으나 **완전한 동적 J/AP 정책·입력 사례는 여전히 0**이다. 원래 첫 `idle→detection_CPU` 전환은 0.000300초다. 새 B2 자료는 정확히 관측한 CG_DC 일정의 외삽 오차를 추가했을 뿐 다른 일정의 짧은 전환 지원을 해제하지 않는다. B3의 DC_DG 짧은 전환, 다른 초기 이력, 낮은 시작 AP의 전체 모형 전이와 정책 간 차이의 판별력은 미완료다. 존재하는 W로 누락 상태를 채우거나 지원 밖 구간을 버린 순위표는 생성하지 않는다. 열→처리시간 식 부재는 저열 고정시간 탐색을 자동 차단하지 않지만 고온 실제 응답 주장은 계속 제외한다.

**추가 계측은 동적 에너지·열 정책의 독립 비교를 주장할 때 필요하다.** 질문은 B2/B3가 실제 사용하는 짧은 CG_DC/DC_DG→resident 유휴에서 전체120초 비용과 열 반응이 다른 일정에도 재현되는가다. 계수 식별용 반복과 독립 확인은 구분해야 하며, 반복 수·허용오차·기기 예산은 현재 근거로 보장할 수 없다. 이번에는 계획·APK·claim을 만들지 않았다. 같은 B2 진단이나 전체6세션 자동 반복은 권고하지 않는다.

**다음 행동 하나:** 이미 재현 가능한 **고정 CC_DG 직렬/병행의 완료시간–공통창 J–AP 상충과 순위 실패를 연구 결과 본문에 반영한다.** 동적 모형 완성은 위 특정 공백과 분리해 미완료로 남긴다. 새로운 포괄 감사나 모델을 잘 맞을 때까지 바꾸는 단계로 돌아가지 않는다.

## 5. 구현·검증·보존

새 PC 도구 `tools/d1_ap_simulation_closure.py`는 raw→개인정보 없는 상대시간 입력→CSV/그림/기존 decision 호출을 연결한다. 물리 계수·runner·Android·default simulator·strict는 변경하지 않는다. 신규 7건과 관련 기존 후보/선택 12건, strict 도착 회귀1건을 검사한다. 실제 원문 AP 조회 bracket·lane 기록에서 만든 입력으로 정보 손실/결측, phase 적분 합, 후보 온도 연속성, 중복 점유 합집합, 미지원 J/AP의 null을 검증했다. 상세 명령·해시는 [재현 번들](results/ap_simulation_closure_01/README.md)과 검증 요약을 따른다. 이는 기기 안정성이나 정확도 합격 검증이 아니다.

원래 동결 SHA `35ed6987…34c54`, 확인 전 절차 freeze `8507adc1…c7ec5`는 추출 전후 확인했다. 실행 원본·계수·FAIL·종료 계획·미소비 queue24 계획은 수정하지 않는다. 기기 명령/새 추론/설치/APK 빌드0, `experiment_ready=false` 유지. 실제 Git 최종 HEAD는 commit 후 응답에서 별도 보고한다.
