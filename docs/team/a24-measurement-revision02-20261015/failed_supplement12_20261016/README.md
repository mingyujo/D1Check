# 실패·중단 항목의 새 ID 보완 측정 12회

사용자 최신 지시 **“진행하면서 실패했던것도 다시 진행해”**를 보존된 실패·중단 ID 12개에 각 1회 새 시도를 허용하는 범위로 구체화했다. 무제한 재시도가 아니다. 기존 85회 계획·원장·실패 결과·동결 확인40은 그대로 보존하며, 추가12의 별도 원장을 둔다. 합산 회계 상한97(85+12)은 이번 지시를 구체화한 값이며 사용자가 숫자97을 직접 지정했다고 기록하지 않는다.

## 범위와 순서

| 순서 | 보완 항목 | 본요청 수 |
|---|---|---:|
| 1 | 최초 계측: runtime 미상주 유휴 | 0 |
| 2 | 최초 계측: 공통 runtime 상주 유휴 | 0 |
| 3–4 | 최초 계측: 동일 분류32건의 Perfetto OFF/ON | 32씩 |
| 5 | 최초 기능 CPU 시작 거절 | 252 |
| 6 | 최초 개발 CPU 통신·준비 실패 | 252 |
| 7 | 이전 확인 저부하 병행 시작 거절 | 64 |
| 8 | 이전 확인 혼합 EDD의 사용자 중단 | 128 |
| 9–10 | 이전 개정 W1 CPU / W3 GPU 시작 거절 | 252씩 |
| 11 | C9 혼합 EDD 시작 거절 | 128 |
| 12 | R2 새 안정기준 혼합 병행 시작 거절 | 128 |

총12시도·1,520본요청이다. 미상주 유휴는 runtime 준비 추론0, 나머지는 공통 4runtime×2회 준비 추론을 별도 기록한다. 탐지GPU는 공통 준비에만 포함되며 본요청 자원은 기존 분류CPU/GPU·탐지CPU 및 허용 병행으로 유지한다.

이미 같은 실행에서 252건 정상 결과를 회수한 최초 기능GPU는 중복하지 않는다. C3/C4의 APP0 중단 뒤 C5에서 완료된 BASE도 중복하지 않는다. 과거 실패·중단·시작거절과 이후 보완 성공은 각각 보고한다. 새로운 실패가 발생했다고 이12에 무제한으로 항목을 추가하지 않는다.

현재 C10의 원미실행 확인을 우선 유지하고, 그 종료·기록 닫힘·자원 반환·소유권 해제를 확인한 뒤 **아직 시작하지 않은 개정 ORDER1 → 이 보완12** 순서로 단일 기기에서 진행한다. 이미 소비한 R2 PAIR ID를 다시 실행하는 것이 아니다. 새 PAIR는 마지막 보완12에 별도 ID로 있다.

## 비교와 판정 경계

- 별도 계획 `A24-FAILED-SUPPLEMENT12-20261016`, 각 원실패 ID와 새 UUID를 대응한다. 원 계획·슬롯의 상태를 수정하거나 예산을 환급하지 않는다.
- 새 보완은 결과를 본 뒤 진행하는 개발·진단 반복이다. **원래 독립 확인40의 성공 횟수·5반복에 합산하지 않는다.** 이전 버전·초기조건의 자료와 같은 독립 반복이라고 표시하지 않는다.
- 원 처방·작업수·도착시각·상대기한·모델/입력 SHA를 보존하고 요청/실행 ID만 새 namespace로 만든다. Android APK·원179소스·응답/저장 완료·실제 lane 반환·MAIN 온도 조건은 변경하지 않는다.
- 새 보완마다 첫 준비 후 첫 적격 안정60초 이력에서 기준을 고정한다. Perfetto OFF/ON은 OFF에서 고정한 동일 기준과 입력을 공유한다. ±0.5℃·기울기0.1℃/분·최대공백10초·준비 후 최대600초는 그대로다. 결과를 보고 같은 실행의 기준을 다시 고르지 않는다.
- 미상주/상주 유휴는 준비 상태가 달라 각자 첫 안정 기준을 기록하는 **진단**이다. 동일 초기 열 상태의 인과적 에너지 비교라고 주장하지 않는다. 원 유휴 계측의 완전한 재현과 현 APK에서의 재검사를 구분한다.
- 에너지 J는 여전히 미검증이다. 이 보완의 성공으로 전류 단위·센서 정확도·표면온도·실제 절감률 검증이 완료되는 것은 아니다. AP는 HAL 보고값, `experiment_ready=false`다.
- SOC10% 이상·비충전·동일 등록폰/화면·동일 기기 재연결 최대20분을 유지한다. 작업자가 등록한 기술상한은 기기12:40/저장12:45 KST이며 사용자 직접 지정시각이 아니다. 사용자 중지·이동 지시가 우선한다.

## 구현과 PC 검증

별도 등록 validator·controller·실행기를 추가했다. controller는 원 suite와 등록 import·자기파일 경로·설명문만 다르며 실행/대기/MAIN/완료/반환 함수의 AST 동일성을 검증한다. 원179소스·APK는 보존한다.

PC 검증: 보완5검사, 미실행 ORDER 계속2검사, 직렬 후속 큐2검사 통과. 기존 실패 ID 재사용·13번째 APP·미지원 자원·분모 변경·기준 완화·잘못된 parser 증거·활성 owner를 차단한다. 실제12개 manifest의 12개 승인 결합도 PC통과했다. 실제 앱 파서 JVM1검사에서12manifest·48모델 binding·1,520요청을 검산했으며 failure/error/skip0이다. 이는 실기기 보완12의 완료 증거가 아니다. 첫 수작업 요청 합계 테스트의 잘못된 기대값1776을 정확한1520으로 정정한 PC 실패 이력도 남겼다.

소프트웨어/PC 검증 기반 HEAD는5660781+이번 미커밋 새 파일이며, [파일별 SHA](SOURCE_SHA256.json)와 실제 후속 시작 시 runtime context로 버전을 구분한다. 기존 C10 소스·설정·원물은 변경하지 않았다. 새 APK 빌드·설치는 수행하지 않았다.

실제 메타는 `output/A24SUP12/job.json`, 향후 원물은 Documents의 `A24SUP12`, 별도 APP 원장은 `A24SUP12_GLOBAL`이다. 후속 큐는 `output/A24FOLLOW16/queue.json`과 OWNER/LIVE/각 단계 STARTED/STOPPED/QUEUE_STOPPED를 먼저 확인한다. 큐는 기존 C10 종료를 기다리는 동안 기기 명령0이며, 단계마다 같은 폰/APK/화면/SOC/빈 프로세스/미사용 경로를 다시 확인한다. 이미 OWNER가 있는 큐·원물·ID는 중복 실행하지 않는다.

```powershell

python -B -m unittest discover -s tools -p test_d1_a24_supplement.py -v
python -B -m unittest discover -s tools -p test_d1_a24_measurement_followon.py -v

# 아래 실행은 큐가 이미 등록됐으면 재호출 금지
# python -u -B tools/d1_a24_measurement_followon.py output/A24FOLLOW16/queue.json --execute-authorized
```

중지 시 후속 큐의 `STOP_AFTER_CURRENT.json`과 당시 실제 실행 root의 같은 파일로 다음 APP만 차단한다. 이미 실행 중인 작업을 강제 종료하거나 같은 ID의 APP/START를 재전송하지 않는다. 완료/거절/미실행은 실제 원장과 원물로 판단하며 문서의 준비 완료를 실측 완료로 해석하지 않는다.
