S26 스케줄링 시뮬레이터 보완 — 전체 실측 요청 및 우선순위
2026-10-14 / GitHub 전달판 / 기기 실행 전 설계 제안

스케줄링 방식에 따라 에너지·AP온도·납기가 달라지는 조건을 시뮬레이션에서 탐색했습니다. 이를 실제 S26에서 확인하고, 현재 모형에서 빠진 열 이력·전환·유휴 비용을 보완하려고 합니다. 요청을 여러 번 나누지 않도록 필요한 항목 전체를 아래에 모았습니다. P0→P4는 중요도이며, 채택한 대응 대조는 같은 블록 안에 함께 배치해야 합니다.

요청은 ‘차이가 반드시 크게 나와야 한다’는 뜻이 아닙니다. 같은 일을 처리할 때 실제 차이의 방향·크기·변동이 모형과 맞는지 확인하려는 것입니다. 이미 받은 M6의600요청·6경로 시간 자료는 다시 보낼 필요 없습니다. 아래의 새 조건과 빠진 대조만 부탁드립니다.

한 번에 확인해 주실 내용
- 항목별 가능 / 실행기 보완 필요 / 미지원 여부
- 현재 APK·source SHA와 필요한 코드/API 변경
- 지원되는 전력·AP/SKIN·주파수/활동·열상태 계측과 실제 갱신주기
- 예상 소요시간과 날짜별 실행 가능한 블록 수
지금은 전체 요청과 설계안입니다. 미지원 기능을 다른 처방으로 대체하거나 기존 소비된 세션/계획을 재실행하지 말고, 새 실행기·입력·측정 계약을 동결한 새 ID로 진행해 주세요.

우선순위 요약
────────────────────────────────────────
P0 필수 선행: 실행기/계측 확인과 기존 큰 전력 오차의 새 재현 자료
P1 최우선 본 측정: 분류 경로·순서·병행·짧은 대기
P2 우선 보완: 버스트 자체·최근 CPU 부하 이력·긴 대기

P4 새 선택지: 탐지GPU, 필요한 경우 탐지NPU·CPU스레드 설정

P0/P1의 기존 핵심안은87세션입니다. P2는56세션, 기존 전력 오차 재현은 최대16세션을 별도로 제안하여, 세션 수를 정한 부분의 합계는159세션입니다. P3/P4는 기능 확인 후 군과 예산을 고정해야 하므로159에 포함하지 않습니다.159는 전체 목록의 완주 상한이 아닙니다. 이미 같은 조건의 적합한 새 자료가 있으면 출처/SHA를 연결하고 중복 측정하지 않습니다.

────────────────────────────────────────
P0. 실행기·계측과 기존 전력 오차 확인 — 먼저 필요
────────────────────────────────────────
1) 실행기/기능: 같은 request bank의 CPU/GPU/NPU 분류·CPU 탐지 재생, 요청별 backend 고정, arrived-ready FIFO/EDD, 전역직렬, CG_DC 또는 CN_DC의 최대2건 병행, 의도 WAIT와 실제 AVAILABLE 해제를 지원하는지 확인해 주세요. 세션 내 모든 요청·센서 시각은 같은 monotonic 축에 연결해야 합니다.

2) 기존 핵심안의 계측4세션과 기능/용량6세션을 먼저 수행합니다. 이10개는87에 이미 포함되어 있으며 다시 더하지 않습니다.
- 계측4: runtime 미상주 idle / 동일 runtime 상주 idle / C32 GPU의 추가Perfetto off/on. 기본 요청·전력·온도 로그는 off에서도 유지합니다.
- 기능6: C252 CPU/GPU/NPU, M128 BASE/PAIR_G/PAIR_N.
- 내부 전류·전압·전하의 단위·부호·읽기 시작/끝/반환시각·cache/갱신주기와 HAL AP/SKIN 실제 센서를 확인합니다. 같은 gauge의 전류/전하 두 API를 독립된 전력 정답으로 보지 않습니다.
- 기존900ms 계측과 주기적 도착의 위상 문제를 점검합니다. 고빈도 polling을 무조건 적용하지 말고 지원 주기·추가 부하를 DEV에서 확인해 고정해 주세요. 외부 전력계가 있으면 장치·연결·정확도와 원자료를 함께 받고, 없으면 내부 gauge 상대 비교라는 한계를 남깁니다.
- AP180 경계 뒤의 실제 표본이 필요하므로210초까지 기록합니다. idle 각1회와 off/on 각1회는 기능/계측 진단이며 상주 절감이나 계측 동등성의 정밀 검증 완료를 뜻하지 않습니다.

3) 기존 P7/M6의 L-G100 전력 오차 재현: 같은100건 입력 recipe의 L-G와 L-C를 새 ID의 대응쌍으로 반복합니다. 각각 DEV3회+동결 후 새 CONFIRM5회, 최대16세션을 제안합니다. 이는 기존 시간600건 재수집이 아니라 특정 전력 오차의 반복성 확인입니다. 원 APK/상주5runtime·준비 이력과 원 relative deadline/priority/policy·900ms 계측 설정도 manifest대로 유지합니다. P1의 기한이나 새 sampler를 덮어 적용하지 않습니다. 새 APK/계측으로만 가능하면 변경 대응표를 남겨 원 버전의 정확 재현과 새 계약 전이를 구분합니다. 입력 bytes/도착식은 유지하되 새 세션·요청 ID를 사용합니다. 이16개는87과 중복 계산하지 않습니다.

────────────────────────────────────────
P1. 핵심 스케줄링 효과 — 기존87세션 설계 유지
────────────────────────────────────────
공통 C=분류/긴급, D=탐지/일반. 모델·정밀도·전처리·CPU스레드·상주 runtime 목록·워밍업은 모든 arm에서 같습니다. 현재 지원 분류 CPU/GPU/NPU와 탐지CPU만 사용하며 미검증 pair를 추가하지 않습니다.

입력
- L64: C32/D32 교대,35초부터1초 간격. 경합이 거의 없는 대조입니다.
- C252: 분류252건,35초부터333.2ms 등간격. S26 포화 부하라고 부르지 않습니다.
- M128: C96/D32,8건씩16묶음, 묶음마다 CCCDCCCD. 동일 묶음의8건은 동시 도착합니다. 묶음 간격은 공개 명목 평균 AVAILABLE로 8×max(96×s_CGPU,32×s_DCPU)/(128×0.9)를 계산해1µs 올림하며 현 프로필은537.155ms입니다. 실제 이용률 보장은 아닙니다.
- jitter0 고정 recipe입니다. DEV와 CONFIRM은 세션/요청 ID·입력순열·실행순서 seed를 분리하지만, 새로운 도착분포를 검증하는 것은 아닙니다.
- 기한은 예정 도착부터 C0.8초/D2초이며 공학적 조건입니다. 결과에 맞춰 연장하지 않습니다.

블록당11세션
- L64 2군: C_GPU/D_CPU의 FIFO 전역직렬 BASE / 같은 FIFO의 CG_DC 병행 PAIR_G.
- C252 3군: CPU / GPU / NPU. 모두 FIFO·전역직렬·WAIT0.
- M128 6군:
  BASE = C_GPU/D_CPU, FIFO, 전역직렬, WAIT0.
  ORDER = BASE에서 도착한 ready 요청의 선택만 절대납기 EDD로 변경.
  PAIR_G = BASE에서 CG_DC 병행 허용만 변경.
  WAIT200 = BASE와 동일 순서/경로/직렬, 각 묶음 첫 배정 전200ms 의도대기. 최대16회·명목3.2초.
  NPU_SERIAL = BASE의 분류 경로만NPU로 변경.
  PAIR_N = NPU_SERIAL에서 CN_DC 병행 허용만 변경.

FIFO는 arrival/ordinal/id의 head를 유지하고 head 자원이 busy면 뒤 요청을 추월하지 않습니다. EDD 동점은 같은 FIFO입니다. PAIR_G는BASE와, PAIR_N은NPU_SERIAL과 비교합니다. 실제 순서·겹침·WAIT가0이어도 결과를 남깁니다.
WAIT는 ready head가 있고 모든 owner가 실제 AVAILABLE인 경우에만 시작합니다. busy/요청 없음은 의도 WAIT가 아닙니다. 고정 WAIT 타이머 중 새 도착은 enqueue하되 타이머를 재시작/연장/취소하지 않으며, 서비스120초 경계와 기존 안전 중단만 우선합니다. 잘린 dose는 실제 값으로 남깁니다.

세션 수: P0 계측/기능10 + DEV11군×2블록22 + 독립 CONFIRM11군×5블록55 =87.

P2. 탐색에서 찾은 조건의 원인 분리 — 핵심안과 함께 배치
────────────────────────────────────────
P2-A 버스트 자체: 추가21세션
- M128과 같은128건·task/backend·요청별 입력/상대기한·첫/마지막 도착을 유지하고 내부 도착만 균등 분산한 SMOOTH128을 만듭니다. 절대기한은 새 예정 도착+C0.8초/D2초로 다시 계산합니다.
- BASE/ORDER/PAIR_G의3군×DEV2+CONFIRM5블록=21.
- 같은 블록의 M128 BASE/ORDER/PAIR_G와 비교해 ‘묶여 들어와서 생긴 차이’ 및 정책차의 변화를 봅니다. 저부하64와 버스트128의 단순 차이를 버스트 단독 효과로 쓰지 않습니다.

P2-B 최근 CPU 부하/열 이력: 추가21세션
- C252 CPU/GPU/NPU를 각각 ‘CPU60초 준비 부하’ 뒤에도 반복합니다.3군×7블록=21.
- 대응 cold 기준은 같은60초 idle 준비 뒤에 실행하도록 P1 C252의 준비 계약도 함께 고정합니다. 두 준비 모두 종료/마지막 AVAILABLE5초 뒤 첫 본 요청을 시작합니다.
- 공통 안정 AP gate는 준비 시작 전에 적용합니다. 준비 이후 t=0 상태는 관측만 하며, CPU 준비로 변한 온도를 다시 같은 값으로 식혀 처치를 없애지 않습니다.
- 본 첫 요청을35초, t=0을 그35초 전으로 정의합니다. 준비부터 연속 기록하고 준비 작업은 별도 role로 표시합니다. J0~180에 포함된 준비 부분과 본 요청 이후 J35~180을 각각 냅니다.
- 각 이력 안의 CPU/GPU/NPU 차이와 그 차이가 이력에 따라 바뀌는지를 비교합니다. 온도·활동·제어 상태가 함께 달라지므로 ‘열 또는 DVFS 단독 효과’로 확정하지 않습니다.

P2-C 긴 대기와 dose: 추가14세션
- 기존 WAIT200×16은 보존합니다.
- 앞12묶음만 WAIT200, 이후0인 WAIT200x12를 추가합니다:7세션.
- 같은 앞12묶음만 WAIT1000, 이후0인 WAIT1000x12를 추가합니다:7세션. 총12초 상한입니다.
- 두 추가군은 동일 trigger 집합·경로·strict 배정순서를 사용합니다. BASE와 각각 비교하고,200x12와1000x12를 비교해 대기 길이 차이를 봅니다.200x16과1000x12를 대기 길이 한 요소의 차이라고 부르지 않습니다.
- 실제 발생수·대기량·서비스 손해·미완료·잔열을 모두 보고합니다. 냉각을 보고 조절하는 적응형 WAIT 전체의 검증은 아닙니다.

대응 기준과 실행 순서
P2를 채택하면 P1과 같은 DEV2/CONFIRM5블록에 넣어 순서를 함께 무작위 배치합니다. 우선순위가 높다고 P1만 먼저 전부 끝내고 P2를 다른 날 단독으로 붙이지 않습니다. 나중에 별도로 시작하면 당시의 기준군 재측정을 별도 예산에 포함해야 합니다. 채택 모듈과 확인 반복 수는 CONFIRM 결과를 보기 전에 고정합니다.

────────────────────────────────────────
P3. 모형의 남은 비용·물리·상호작용 — 가능 여부와 실행 사양까지 함께 요청
────────────────────────────────────────
아래도 전체 요청 목록에 포함합니다. 다만 현재 APK/API·계측 지원이 확인되지 않아 군/세션 예산이 아직 없으며, 위159세션에 포함하지 않습니다. 항목별 지원 여부를 회신해 주시면 정확한 입력·반복·관측시간을 동결한 같은 요청 계보에서 진행합니다. 임의의 세션 수나 성공을 가정해 실행하지 않습니다.

P3-A 열 회복·성능 변화
- 지원된 C_CPU/C_GPU/C_NPU/D_CPU/CG_DC/CN_DC와 무부하 대조에서 idle30초→고정부하60초→진행 요청 drain→무부하300초 연속 기록을 기본 진단안으로 제안합니다.
- 부하는 실제 AVAILABLE 후 다음 요청을 시작하고 pair는 지원최대2를 유지합니다. 고정시간 부하이므로 완료량/처리율도 기록하며 동일 작업량 에너지 절감으로 해석하지 않습니다.
- 자연 안정 상태와 최근 CPU 준비 상태를 구분해 AP/SKIN, 전력,5단계 시간, 가능한 주파수/활동·thermal_status를 연결합니다.300초 회복만으로 긴 시정수나 steady-state를 완전히 식별했다고 하지 않습니다.
- 외부 가열·강제 클럭·보호 해제 없이 수행합니다. 열상태 API 미지원이나 감속이 관측되지 않은 경우도 그대로 보고합니다. AP만으로 DVFS 원인·임계·전력속도 지수·Wfixed/Wscaled를 확정하지 않습니다.

P3-B backend 전환/첫 호출 비용
- 동일 request별 backend map·CPU/GPU/NPU 총횟수와 입력을 유지한 채, backend별 묶음 실행과 교대 실행을 비교합니다. 모든 runtime은 양쪽에서 같은 목록으로 resident 유지합니다.
- 생성/준비·첫 호출·후속 호출·전환 직전/직후5단계·실제 AVAILABLE와 전체창 J/AP/납기를 기록합니다. 이는 전환 빈도를 포함한 순서/이력 총효과이며 즉시 ‘전환1회당 고정J’로 환산하지 않습니다.
- steady 실행과 runtime 재생성은 별도 대조입니다. 세션 안의 수십 cycle을 수십 독립 세션으로 세지 않습니다.

P3-C 상주·unload/recreate·idle gap
- 같은 초기화/워밍업·선행 작업에서 KEEP과 명시 close→동일 idle gap→recreate→동일 요청을 대응 비교합니다. gap은1/10/60초를 시작안으로 제안합니다.
- recreate는 후속 요청 도착에 의해 시작하도록 고정해 첫 응답 지연과 재준비 에너지를 모두 포함합니다. close/create/워밍업/첫 추론·AVAILABLE·실패/품질과 전체 고정창 J/AP를 받습니다.
- idle steady W 차이와 close+유휴+recreate+후속 작업의 순절감을 따로 계산합니다. 다른 resident runtime·USB/화면/OS 조건은 두 arm에서 같습니다.
- 실제 하드웨어 sleep/wake를 제어·관측하지 못하면 ‘runtime unload/recreate’라고만 부릅니다. 상주 해제만으로 기저 전력을 일정 비율 끌 수 있다고 가정하지 않습니다.

P3-D 부하·작업비율·우선순위·기한 범위
- 밀도: 같은128건·task/input/route/order를 유지하고 간격만 바꾼 낮음/기준/높음 부하. 실제 기기 참조량과 서비스 여유로 수치를 DEV 전에 등록합니다.
- 작업비율/묶음 크기: 같은 총요청수에서 분류/탐지 비율을 바꾸는 비교와, 같은 평균 도착률에서 묶음 크기만 바꾸는 비교를 분리합니다. 한 번에 둘을 바꾸어 단독 원인으로 부르지 않습니다.
- task×priority 및 tight/slack 기한: C긴급/D일반 고정 외에 task와 등급을 교차할 수 있는지 확인합니다. urgent output-ready와 normal persist/readback의 응답 계약이 달라지므로 이를 먼저 구현/고정해야 합니다. 같은 계약이라고 이름만 바꾸지 않습니다.
- 미완료와 납기 손해는 유효 결과로 남깁니다.70/80/90/95/100%는 각 조건의 평가 적격수준이며 그 목표별 제어 정책을 모두 실기기 검증했다는 뜻이 아닙니다.

P3-E 실제 정책 조합
- 순서×경로×병행×WAIT를 조합한 FULL과 동결 ATC/기존규칙/PPO를 같은 공개 관측·동일 입력에서 비교할 수 있는지 확인합니다. 핵심 한 요소 대조만으로 이 조합의 상호작용이나 학습 우위가 검증되지는 않습니다.
- 담당자에게 임의 정책을 새로 만들라는 요청은 아닙니다. 제공될 exact policy/config·CP·SHA와 mask/관측 adapter를 사용하고, 원 실험의 최종 감사·동결 전 가중치를 새 최종 정책으로 쓰지 않습니다.
- 실제 관측에 반응하는 온라인 실행과 사전에 계산된 open-loop 처방 재생은 별개로 표시합니다. 실제 순서/배정/WAIT·입력/마스크·결정 기록을 함께 받습니다.

────────────────────────────────────────
P4. 지원되면 새 실행 선택지를 여는 실측 — 탐지GPU 우선
────────────────────────────────────────
1) 탐지GPU: 현재 exact 모델/정밀도/입력에서 실제 요청을 실행해 delegate 실제 적용·CPU fallback/분할·출력 품질·실패·5단계/응답/AVAILABLE를 먼저 확인합니다. delegate 생성이나 warmup 성공만으로 요청 경로가 검증됐다고 하지 않습니다.
2) 경로 통과 후: 동일 입력의 D_CPU/D_GPU 단독, idle→DG→idle과 같은 상주 상태의 대응 에너지/AP·재현 자료를 수집합니다. 그 다음에만 CC_DG 등 필요한 각 pair를 별도 검증합니다. solo 성공으로 pair를 자동 허용하지 않습니다.
3) 탐지NPU: 가능 여부와 품질/실제 실행을 별도 probe합니다. 미지원이면 미지원으로 남기며 하드웨어 전체 불가능으로 일반화하지 않습니다.
4) CPU thread1/2/4: 실제 API가 지원하면 C_CPU와 D_CPU 각각에서 모델/정밀도/입력·기타 runtime을 고정한 단독 비교부터 합니다. NPU/GPU host thread와 혼동하지 않습니다. 새 설정의 품질/회귀·단독 비용을 확인한 뒤 기존 pair와의 조합 여부를 정합니다.
현재 확인된 최대2건·비선점·실제 AVAILABLE 제약을 유지하며 미검증 병행이나3건 동시 실행을 추가하지 않습니다. P4 역시 기능·품질 admission과 새 예산 고정 전에는 실행 단계가 아닙니다.

────────────────────────────────────────
모든 본 측정의 공통 계약과 반환물
────────────────────────────────────────
- SOC40~80%를 시작안으로 두고 화면/밝기·통신·충전/USB·주변온도·위치/접촉·직전 부하를 기록합니다. 가능하면 동일 방전 조건을 유지합니다. 실제 가능한 Tref±0.5℃/직전60초 기울기 절댓값≤0.1℃/분 기준 또는 날짜별 산출 알고리즘을 DEV에서 고정하며 확인 결과에 맞춰 바꾸지 않습니다. 자연 대기 최대10분 뒤 불충족은 PRESTART_REJECT입니다. 기존 열보호는 유지합니다.
- 일반 본 측정은 t=0 전 최소60초 AP 원기록, 첫 요청35초, 새 dispatch 종료120초, J0~120/0~180, 평균AP35~180, 센서 최소210초입니다. P3 열 회복 같은 진단은 별도 시간 계약을 먼저 고정합니다.
- 긴급 응답은 표시 가능한 결과 객체 완성, 일반 응답은 write/flush/fsync→atomic rename→readback 성공입니다. 주응답은 예정 도착부터이며 enqueue 지연과 AVAILABLE 해제시각은 따로 기록합니다.
- AP35/180 및 J0/120/180 경계의 양쪽 실제 표본과 사전 고정 최대 gap이 필요합니다. 완전창이 없으면null, tail 외삽하지 않습니다. AP를 배터리온도로 대체하지 않습니다.
- session_manifest, 전체 시도 ledger, APK/source/model/input/tensor/prescription SHA, 실제 runtime·thread·delegate/fallback, 예정/실제arrival→dispatch→start→output→persist→release→AVAILABLE, 큐/owner/겹침/WAIT dose와 원 전류/전압/전하/HAL·읽기시각을 반환합니다.
- 실패·거절·관측창 결측·미완료·늦음·아직 기한미도래 pending을 구분합니다. PRESTART_REJECT는 전체 시도 원장과 계획 coverage 분모에 남기며 실제 서비스율과 구분합니다. START된 세션에서는 실패/거절/미완료까지 전체 예정 도착 서비스 분모에 유지합니다. 사전 거절까지 포함하는 보수적 계획기준 지표를 낼 경우 별도 이름/분모를 명시합니다. 나중에 같은 소비 identity를 성공행으로 다시 수집하지 않습니다. 계획 밖 재시도는 자동 추가하지 않습니다.
- 모든 비교에서 ΔJ120/180·평균/최고AP·AP180 잔열·응답 P95·서비스70/80/90/95/100%·전량완료와 실제 개입량을 냅니다. 동일량을 완료하지 못한 세션의 낮은J를 작업 절감으로 부르지 않습니다.
- 개발/새 확인을 분리하고 예측·설정·분석·수치 허용치를 확인 전에 동결합니다. 세션이 독립 반복 단위입니다.5확인 블록은 정밀도 보장이 아니며 부호 반전·작은 효과·불확실성도 보존합니다.
