# A24 스케줄링 차이 실측 계획

2026년 10월 14일 작성. 분류 비중·밀집 도착·병행·순서·대기에서 발견한 모형 내 차이가 실제 A24에서도 나타나는지 확인한다. 현재 상태는 계획 작성 완료이며 기기 실행·APK 빌드·설치·기존 실험 변경은 0이다. 아래 수치는 새 설계 제안이며 기존 소비된 측정 계획의 재실행 지시가 아니다.

## 먼저 할 일

현재 A24 주 online study는 고정96건, 별도 지속 경로는192건 계약이다. CPU 전체 직렬·분류GPU/탐지CPU 직렬·같은 조합 병행 경로는 있으나 아래64/128/252건 입력, 순서 처방과 의도 WAIT를 그대로 지원하지 않는다. 새 opt-in 계약·입력 validator·요청별 경로/순서/WAIT 로그·APK와 host의 회귀 검증이 선행한다. 설치된 APK 상태는 이번 작업에서 조회하지 않았다.

새 기능은 기존 기본 경로와 동결 V2를 바꾸지 않고 별도 버전으로 만든다. 소프트웨어 fixture에서 미도래 요청 금지, FIFO/EDD 실제 순서 차이, 전역직렬, CG_DC 최대2점유, 실제 AVAILABLE 해제, WAIT 타이머·누적량을 확인한 뒤 새 기기 등록을 한다. 기존 PLAN_ONLY와 순서표는 정적 설계이며 이 폴더에 실행 bank로 제공된 것이 아니다. 원 Resident01/02 중지·Resident03 완료·기존192 확인8세션을 재개하거나 재사용하지 않는다.

## 공통 조건과 시간

- 같은 승인 EfficientNet-Lite0 분류·EfficientDet-Lite0 탐지, 정밀도·CPU스레드·전후처리를 유지한다. 모델·APK·실행기·입력 파일과 tensor SHA, 기기 fingerprint를 측정 전에 고정한다. 모델 binary는 이 계획에 넣지 않는다.
- 각 대응 블록 안에서는 요청 ID·입력·도착·납기·작업량이 완전히 같다. 입력은 기존 승인 입력 목록의 슬롯으로 배정하고 실제 파일/tensor SHA를 채운 후 동결한다. 개발2블록과 확인5블록은 ID·입력순열 seed·실행순서 seed를 분리하며 도착 recipe는 같은 jitter0 고정식이다. 새 확인은 독립 기기 반복이며 새 도착분포에 대한 검증은 아니다.
- 모든 arm의 상주 runtime 목록과 워밍업 횟수·순서를 동일하게 고정한다. 기존 앱의 미사용 DG runtime 상주까지 포함하는지 manifest에 적고 조건별로 임의 해제하지 않는다. 탐지GPU 요청은 주계획에서 제외한다.
- SOC40~80%, 동일 화면/밝기·통신·충전 상태를 제안한다. 에너지는 가급적 방전 상태에서 수집한다. 주변온도와 폰 위치/접촉을 기록한다. 시작 AP는 안정 기준 Tref±0.5℃, 직전60초 기울기 절댓값≤0.1℃/분을 제안한다. CONFIRM 전에 Tref 숫자를 고정하거나 날짜별 사전 idle에서 산출할 알고리즘·허용범위·거절 규칙을 동결하며 정책 결과를 보고 그날 값을 수동 변경하지 않는다. 기준 미달은 최대10분 대기 후 PRESTART_REJECT로 남기며 정책 결과를 지우지 않는다. 기존 앱의 열보호·중단 기준을 유지한다.
- runtime 준비·워밍업 후 기준시각 t=0을 기록하고, 첫 본 요청은 t=35초다. 서비스 판정창0~120초, 총소비J0~180초, 평균AP35~180초를 고정한다. 센서는 최소 t=210초까지 기록해180초 경계를 덮는 실제 표본을 확보한다. 준비 이력과 t=0 이전 최소60초의 AP 원기록도 보존해 시작 gate를 검산한다. 아래210초 예산은 t=0 이후이며 이 사전 기록·준비 시간은 추가다.
- 120초에 새 dispatch를 멈추되 이미 시작한 요청은 비선점으로 실제 AVAILABLE까지 기록한다. 미배정 요청은 서비스창 미완료이며 뒤에 다시 수집해 성공으로 바꾸지 않는다. 120초 이후 응답은 별도 drain 기록이다. 도착+납기가120초를 넘는 pending과 이미 늦은 요청을 구분하고, 창 안 성공률 분모는 전체 예정 도착이다.
- 공통 측정 계약의 응답 정의를 유지한다. 긴급 C는 표시 가능한 결과 객체 완성, 일반 D는 write/flush/fsync→atomic rename→readback 성공을 완료시각으로 쓴다. 예정 도착부터 이 시각까지를 주응답으로 계산하며 actual enqueue 지연은 따로 낸다. AVAILABLE은 자원 해제시각이므로 응답 완료와 바꾸어 쓰지 않는다.

## 세 가지 입력

C는 분류·긴급, D는 탐지·일반이다. 주 기한은 도착부터 C2.2초/D5초다. 선언 기한을 결과에 맞춰 바꾸지 않는다. task와 priority가 함께 고정된 제한은 보고하며 모든 우선순위 조합으로 일반화하지 않는다.

| 입력 | 정확한 구성 | 질문 |
| --- | --- | --- |
| L64 | C32/D32, C/D 교대, t=35+i×1.0초, jitter0 | 큐·병행이 거의 없는 음성 대조 |
| C252 | 분류252건, t=35+i×0.3332초, jitter0 | 분류 CPU/GPU 경로에 따른 소비·열·납기 |
| M128 | C96/D32, 8건씩16묶음, 각 묶음 CCCDCCCD, t=35+g×Δ | 혼합 경합에서 순서·병행·대기의 차이 |

M128의 Δ는 공개 명목 평균 AVAILABLE로 `8×max(96×s_CGPU,32×s_DCPU)/(128×0.9)`를 계산해 1µs로 올린다. 현재 고정 프로필 기준 약2.0322초다. 이는 병행 reference의 명목 부하를 맞춘 합성 입력이며 실제 이용률·사용자 클릭 빈도가 아니다. 기존 탐색의 무작위 묶음 구성·위치 jitter와 구분되는 새 통제 recipe다. 정확 Δ·원 프로필 SHA·모든 요청 시각은 CSV에 기록한다.

C252 마지막 도착은118.6332초이고 GPU 평균 기반 마지막 AVAILABLE은 약118.938초다. 120초까지 약1.06초 여유뿐이므로 완주를 보장하지 않는다. 공개 평균은 C_CPU165.216ms/C_GPU304.829ms/D_CPU621.737ms이며 실제 변동·열 감속은 실측 대상이다. M128은 각 묶음을6C2D로 고정하지만 누적 큐와 직렬 arm의 납기 실패는 여전히 가능하다. 이 실패도 결과다.

## 블록당 8세션

| 입력·arm | 처방 | 짝 비교 |
| --- | --- | --- |
| L64 BASE | C_GPU/D_CPU, FIFO, 전역직렬, WAIT0 | L64 PAIR_G의 기준 |
| L64 PAIR_G | 같은 경로·FIFO, CG_DC만 최대2병행 | 저부하에서 실제 겹침이 없으면 zero treatment |
| C252 CPU | 모든 분류CPU, FIFO, 전역직렬, WAIT0 | C252 GPU |
| C252 GPU | 모든 분류GPU, FIFO, 전역직렬, WAIT0 | 분류 route 한 요소만 변경 |
| M128 BASE | C_GPU/D_CPU, FIFO, 전역직렬, WAIT0 | 세 처치의 공통 기준 |
| M128 ORDER | 같은 경로·직렬·WAIT0, 도착한 요청을 절대납기 EDD로 선택 | 순서만 변경 |
| M128 PAIR_G | 같은 경로·FIFO·WAIT0, CG_DC만 최대2병행 | 병행 허용만 변경 |
| M128 WAIT200 | BASE와 같은 dispatch 순서·경로·직렬, 각 묶음 첫 dispatch 전200ms | 의도 대기만 변경 |

FIFO는 arrival/ordinal/id 순서의 head를 유지하며 head 자원이 바쁘면 뒤 요청을 추월하지 않는다. EDD의 동점은 같은 FIFO 순서다. 병행은 같은 FIFO rank와 head 규칙을 유지한 채 전역직렬 gate만 해제한다. 따라서 배정 순서·요청별 backend를 검산할 수 있다. 실제 처리 구현이 이를 보장하지 못하면 순수 병행 효과로 표시하지 않는다.

WAIT200은 해당 묶음 첫 요청이 ready이고 모든 owner가 실제 AVAILABLE로 해제된 뒤 시작한다. 자원 busy나 ready 요청 없음은 WAIT가 아니다. 타이머를 실행하고 실제 시작·끝·경과량과 당시 큐/owner를 기록한다. 최대16회·명목3.2초이며120초 경계에서 잘린 양을 그대로 보고한다. 이 고정 dose 진단을 새 학습 정책의 대기 전략으로 부르지 않는다.

## 순서와 세션 예산

| 단계 | 구성 | 세션 수 |
| --- | --- | ---: |
| I 계측 확인 | runtime 미상주 idle, 동일 runtime 상주 idle, C32 GPU의 추가 Perfetto off/on | 4 |
| F 기능·용량 점검 | C252 CPU/GPU, M128 BASE/PAIR_G | 4 |
| DEV | 전체8군×독립2블록 | 16 |
| FREEZE | 실행기·입력·계측·초기 조건·분석·사전 모형 예측 동결 | 0 |
| CONFIRM | 같은8군×새 독립5블록 | 40 |
| 핵심 계획 합계 | I/F/DEV/CONFIRM | 64 |

I의 idle은 상태·계측 확인용이며 각1회로 상주 전력이나 wake 비용을 식별했다고 주장하지 않는다. Perfetto off에서도 기본 요청/전력/온도 로그는 유지한다. 추가 trace의 읽기 부하를 확인하며 지원하지 않는 카운터는 결측이다. I에서 못 하는 항목은 UNSUPPORTED로 남기고 다른 성공 세션으로 대체하지 않는다.

F·DEV를 보고 형식/계측/용량 결함을 고칠 수 있으나 수정 버전과 실패를 보존하고 CONFIRM 전에 새로 동결한다. 기한·작업량·간격은 유리한 정책 결과를 만들기 위해 조정하지 않는다. 용량 때문에 변경이 필요하면 이유·전체 대조군 공통 변경·새 버전을 기록한다. CONFIRM에 들어간 뒤에는 재선정·반복 추가·유리한 시점 중단을 하지 않는다.

각 블록의 실행 순서는 등록한 난수로 무작위화하고 순서표를 미리 만든다. 블록마다 같은 초기 gate로 되돌아가며 바로 앞 세션의 열이 다음 arm에만 남지 않게 한다. 날짜가 바뀌면 baseline 기준과 환경을 기록하고 같은 블록을 임의로 섞지 않는다. 요청252건을252독립 반복으로 세지 않는다.

세션당210초라 관측 합계224분이다. 세션 사이90초를 단순 예약하면 약5시간19분이며 설치·회수·초기화·온도 gate 대기는 추가다. 실제 수집을 며칠로 나누어도 block 구성을 유지한다. 먼저 I+F+DEV24세션을 받아 점검하고, 그 후 CONFIRM40세션을 진행하는 순서다.

## 열 이력과 추가 dose의 후속 모듈

핵심 계획과 분리해 범위를 선택하고 실행 전에 새 버전을 등록한다. 모두를 기본64세션에 숨겨 포함하지 않는다.

채택할 후속은 확인 전에 범위를 고정하고 같은 DEV/CONFIRM 블록의 기준군과 함께 무작위 배치한다. 나중에 다른 날 추가하면 동시대 기준군 재측정을 별도 예산에 포함한다. 도착식을 바꾸는 SMOOTH에서는 같은 상대기한을 유지하고 새 예정 도착+상대기한으로 절대기한을 다시 계산한다.

1. **최근 CPU 부하:** C252 CPU/GPU를 최근 CPU 부하 상태에서도 DEV2+CONFIRM5블록으로 반복, 추가14세션. 같은 분류CPU를60초 연속 수행하는 준비 구간을 두고 마지막 AVAILABLE5초 후 첫 본 요청을 시작한다. 공통 안정 AP gate는 이 준비 부하 시작 전에 적용하며 t=0 상태는 관측만 한다. 본 시각0은 첫 도착35초 전으로 정의하고 준비부터 연속 기록해 분석창을 덮는다. 준비 요청은 별도 role이며 J0~180에 포함된 부분을 표시한다. 상태 안에서 CPU/GPU를 비교하고, 저온과의 절대 차이를 CPU 기억/DVFS 단독 효과로 해석하지 않는다. 열 상승·감속이 관측되지 않아도 기록한다.
2. **긴 WAIT:** M128의 WAIT1000을 DEV2+CONFIRM5블록에 추가, 추가7세션. 앞12묶음에 각각1초, 이후 WAIT0, 명목 총12초 상한이다. BASE/WAIT200과 같은 요청·순서·경로를 유지한다. 확인 결과가 좋을 때만 사후 추가하지 않는다.
3. **도착 묶음 분리:** M128과 같은128개 입력·순서·첫/마지막 도착 시각으로 도착만 균등 분산한 SMOOTH128을 BASE/ORDER/PAIR_G에서 비교, 추가21세션. burst와 전환·순서 효과를 더 분리하는 후속이며 핵심 계획 전부하 일반화로 미리 계산하지 않는다.

탐지GPU와 CPU스레드1/2/4·runtime unload/reload는 이번 주계획에 포함하지 않는다. 탐지GPU는 과거 A24 실행 근거와 legacy24 경로가 있지만 현재 주96/192 연구 계약의 요청 후보가 아니다. 새 current APK 요청/품질·실제 위임/잔여CPU·5단계/단독J·AP와 CC_DG 별도 admission 이후의 후속이다.

## 필수 산출물과 판정

session_manifest.json, 전체시도 ledger.csv, request/input/prescription SHA, 요청별 actual_arrival/dispatch/start/output/persist/worker_release/AVAILABLE, 상태·실패·거절·미완료, WAIT 시작/끝/이유/큐/owner, 전류·전압·전하 원표본과 단위·읽기 시작/끝/반환시각, HAL 센서 이름/종류/값/표본·읽기시각을 받는다. AP를 배터리 온도로 바꾸지 않는다. 실제 갱신주기·cache age·결측을 기록하고 단순 polling 주기를 새 독립 표본 주기로 해석하지 않는다.

에너지 샘플링은 DEV에서 센서 갱신·지연·위상과 수집 overhead를 확인해 주기·적분법·허용 gap을 동결한다. polling만 무작정 높이지 않는다. 동일 gauge의 전류와 charge_counter는 독립 전력 정답이 아니며 가능하면 검증된 외부 전력계로 대조한다. 충전/USB wakelock 조건은 모든 arm에서 같아야 한다. AP35와180 및 J0・120・180 경계마다 실제 관측 시각이 양쪽을 덮어야 한다. 동결한 최대 gap 안에서만 경계 보간하며 그렇지 못하면 해당 완전창 값은 null이다. tail 외삽으로 채우지 않는다.

서비스는 전체 도착 분모의 긴급/일반70·80·90·95·100%와 전량완료를 각각 보고한다. J120/J180·평균AP35~180·관측최고AP·AP180·P95·backlog·실패/미완료를 함께 낸다. 미완료 세션의 관측 소비를 전량 작업의 절감으로 쓰지 않는다. 적격 공통쌍만의 조건부 비용 효과와 모든쌍 서비스 손해를 병기한다.

주 분석은 각 블록의 처치−기준 ΔJ/Δ평균AP/Δ납기와 실제 route·순서·겹침·WAIT dose다. 동일 완성 모형의 사전 예측을 확인 전에 저장하고 실제 Δ의 방향·크기·반전을 대조한다. 5독립 블록의 대응 구간은 표본이 작으므로 탐색적 불확실성으로 표시한다. 구간이0을 포함하면 방향 미확정이며, 총J 오차만 작고 정책Δ 부호가 틀리면 스케줄링 차이를 검증했다고 하지 않는다. 수치 정확도 PASS 허용치는 계측 확인에서 정해 확인 전에 동결해야 하며, 정하지 못하면 오차·결측·범위만 보고한다.

기존 모형/본학습·FINAL은 그대로 보존한다. 새 기기 자료를 개발에 사용하면 별도 보완 모형으로 동결하고 새 확인 자료에서만 검증한다. 정책 격차를 목표로 물리계수를 정하거나 기존 FINAL을 다시 선정하지 않는다.

## 근거와 이식 상태

기존 탐색34·36과 현재 A24 실행기·공통 측정 계약을 근거로 만든 계획이다. 원래 문서의 데스크톱 로컬경로는 이 전달판에서 제거했다. 이 폴더는 계획이며 실행기·APK·실제 입력 bank가 아직 포함되지 않는다. 노트북 준비와 남은 작업은 [README](README.md)를 따른다.
