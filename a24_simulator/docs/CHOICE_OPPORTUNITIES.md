## V2 개발 후속 등록

V1은 13 START=12 COMPLETE+1 FAIL에서 닫았다. 실패는 `C50_P4_REFERENCE_EDF`의 실행 후 최종 AP 상태 UNKNOWN이며 상세 reason/원 prediction을 먼저 저장하지 못한 실행기 한계를 명시한다. 실패 identity/seed는 재실행하지 않는다. 성공 12개와 실패 원장을 `CLOSED_FRONTIER.json`에 보존했다.

작은 묶음은 두 자원 동시 유휴를 늘렸지만, admission 완료 시각이 수 ms씩 달라 첫 요청을 즉시 배정하면서 복수 ready 요청이 줄었다. V2는 이를 개발 피드백으로 사용한 별도 세대이며 독립 확인이 아니다. 기존 50ms WAIT가 보호 mask에서 허용되고 두 자원이 비었으며 물리 후보 요청이 하나일 때에만 한 번 기다리는 `COALESCED_COST`를 추가한다. 미래 도착 목록을 읽지 않고 보호 mask·시간/열/비용 계수는 유지한다. 실제 배정 48회의 분모에서 WAIT 호출은 제외한다.

V2는 새 seed20269119, C50%·묶음2/4의 대응 입력 4개 × EDF/기존 비용 prior/50ms 모음 비용 prior = 12 START다. V1 미사용15 중12를 이전하여 V1의 잔여는3이다. 원 RL 256 = 기존223 소비+V1 13 소비+V2 12 배분+V1 미배분3+원미배분5다. 전역 예약 증가는0이며 이전 RR 잔여1은 계속 보존한다. 두 정책만의 유리한 조건 선정이 아니라 모든4입력·3정책·미완료/지각을 보고한다.

최종 AP가 UNKNOWN이면 원 prediction과 전체 AP reason을 저장하고 온도 지표를 null로 둔다. 동역학/시계/소비/선택 기회 결과와 AP 미확인을 구분하며 온도0이나 성공값으로 대체하지 않는다. V2 등록·소스 게시 후 실행한다. 원 실행기/실패/기존 완료 검산은 보존한다.

사용자의 2026-10-17 요청인 '1번부터 보완'에 따라 입력의 선택 기회를 별도 개발 조건에서 보완한다. 기준은 `51117e2a`다. 기존 입력·완료 결과·물리 모형·CPU/GPU 각 1슬롯·최대 2요청·AVAILABLE 반환·보호 mask·비용 prior는 보존한다. CPU+CPU 확장은 실측 근거가 없으므로 포함하지 않는다.

## 구현과 검증 계약

- `experiments/choice_opportunities_20261017/design.cjs`가 분류 25/50/75% × 묶음 2/4개, 6개 대응쌍을 만든다. 각 쌍은 기존 파형의 새 seed 입력과 묶음 도착 입력으로 구성된다. 모든 조건은 48요청이다.
- 묶음은 요청당 0.8초 간격에 해당하는 주기로 도착한다. 이는 합성 개발 시나리오이며 실사용 분포나 실제 두 자원 사용률의 측정값이 아니다. 2요청 주기는 1.6초, 4요청 주기는 3.2초다.
- 작업 종류·순서·긴급 비율·상대 납기는 각 쌍에서 동일하다. 도착을 옮긴 만큼 절대 납기를 함께 옮긴다. 결과를 보고 유리한 입력만 선정하지 않는다.
- EDF와 원 보호/비용 prior의 NN 제외 정책 두 개로 각 입력을 평가한다. 같은 쌍·정책 간 잠재 표본 키를 공통으로 사용한다. NN 실행·학습·물리 fit은 0이다.
- EDF는 실제 배정에 보호 mask를 적용하지 않는다. EDF 상태에서 계산한 보호 후 후보 수는 관측용 shadow 진단이다. 비용 prior 정책은 원 mask를 실제 적용한다. 자원 대기 호출과 실제 배정의 분모를 구분한다.
- 주 지표는 실제 배정 직전 복수 요청 후보 비율, 두 물리 자원 동시 유휴 비율이다. WAIT를 복수 요청으로 세지 않는다. 보호 전후 후보 수, 보호 제거·긴급 강제선택을 함께 보존한다.
- 사전 개발 목표는 두 비율이 각각 대응 기준보다 10%p 이상 증가하는 것이다. 모든 대응쌍·정책을 보고하며 납기·미완료·총비용·작업 증분·AP·기저 비중도 함께 보고한다. 선택 기회의 증가는 절감이나 정책 우위의 증명이 아니다.
- 도착 간 회복 여유는 작업창과 기저 비중을 늘릴 수 있다. 새 입력과 이전 입력의 원시 J*를 같은 작업량의 절감으로 해석하지 않는다. 정책 효과는 같은 입력·같은 작업창 안에서만 비교한다.

## 등록·예산

등록은 `OPERATION.json`, 입력은 `INPUTS.json`, 이전은 `BUDGET_TRANSFER.json`이다. 새 6쌍 × 2정책 = 24 START이며 상한 28이다. 닫힌 RL 단계의 기존 256 예약은 223 소비＋28 이전＋5 미배분으로 보존한다. 이번 명시적 새 작업 요청에 따라 별도 세대로 이전하며 글로벌 신규 예약은 0이다. 이전 RR의 잔여 1은 사용하지 않는다. 완료된 부모 출력 namespace에는 재진입하지 않는다.

전역 예약 124838과 실제 START 31712는 부모 인계 시점의 값이다. 현재 다른 PC의 실제 소비를 재확인한 값으로 표시하지 않는다. 신규 단계는 부모의 고정 예약 안에서 이전하므로 전역 예약을 늘리지 않는다. 게시한 이전 영수증을 후속 예산 합산에 포함하고 원 33 잔여를 다시 배분하지 않는다. 자체 Python 1/global 2와 8GiB 보존, 공유 lock, START 선기록·실패 보존·자동 재시도 금지를 적용한다.

먼저 소스·입력·예산 이전을 GitHub에 게시한 뒤 실행한다. 새 모형 예측 24회는 모두 원장에 추가한다. 새 seed와 새 입력이지만 개발용 조건이며 독립 실기기 확인이나 새 RL 확인으로 부르지 않는다. 반복 예약과 GitHub 주기 조회는 OFF다.
