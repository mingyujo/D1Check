# 비용 사전점수와 PPO 잔차를 사용하는 후속 검증40

작업 ID `COST-AWARE-RESIDUAL-PPO-40`. 기존37/38의 작은 절감 결과, 원 실측 모형, 다른 채팅의37-V2 실행을 보존한다. 사용자는 더 큰 스케줄링 효과를 요청했다. 개선의 성공은 사전에 정하지 않고 새 자료에서 판정한다.

## 이번에 바꾼 부분

1. 전체 대기 요청을 ATC로 점수화한다. 종전64개 대기 한도를 사설 복사본에서1024개로 넓히고, 신경망에는 상위6와 실행 가능한 유형별 보충을 합친 최대8후보·49행동만 넘긴다. G2 상태는 기존215특징과 남은 대기 예산1특징을 합친216차원이다. 현재 상태에서 같은 작업/자원의 추정치를 한 판단 안에서 재사용한다. 전체 큐의 미래 실행은 계산하지 않는다.
2. 행동의 명목 에너지를 각 선택 요청의 현재 최저 명목 단독 에너지와 비교한다. `relative_cost=(즉시 행동의 명목 J−선택 요청별 최저 단독 명목 J의 합)/0.1J`이다. 지원되는 GPU/NPU 분류+CPU 탐지의 겹침 이득과 단독 자원 선택의 비용을 표현한다. 원 모형의 계수와 실행 조합은 변경하지 않는다. 새 전력·감속·냉각 비용을 넣지 않는다.
3. `logit=신규 NN 잔차 logit−2×relative_cost`를 사용한다. 신경망은 서비스/열/현재 부하에 따른 보정을 학습한다. 상태·행동의 비용 특징과 정책 출력의 정의가 달라졌으므로 기존 가중치를 새 학습에 넣지 않는다. 기존 PPO38은 별도 고정 대조다.
4. 현재의 무작위 혼합 요청만 반복하지 않고, 짧은 긴급 분류 이후 여러 이미지의 분류·탐지를 처리하는 두 요청군을 추가한다. 단위 작업은 실측 서비스풀의1회 추론이며 처리시간 배율·작업 생략·품질 변경은 없다. 합성 요청 조합이며 실제 앱 사용 분포라고 주장하지 않는다.

G1 12환경의 개발 진단에서 완료까지 J 감소와 최고온도 증가가 함께 나타났다. 이를 보존하고 본학습/주DEV/FINAL0에서 G2를 등록했다. CPU 탐지가 이미 진행 중이고 GPU/NPU에서 일반 분류를 실행할 수 있을 때만250ms 대기를 허용한다. 긴급 요청 대기 중에는 허용하지 않고 총 실제 대기는8초 이하다. 실행 중 작업을 중단하거나 모든 자원을 비우는 냉각 대기는 없다. FIFO/RR/GREEDY는 기존 실행 방식이며, 같은 대기를 사용하는 PACED_COST_RULE 대조도 둔다. A24 36℃·S26 39℃는 해당 규칙의 연구용 관측 AP 기준이며 하드웨어 안전 한계가 아니다. G2 8환경에서 초기NN·보상과 대기/AVAILABLE를 검증했으며 새 native 업데이트는0이다.

## 납기와 평가 구간

긴급 요청은 이전37/38의 연구 조건인 A24 2.2초·S26 0.8초를 유지한다. 다음 요청군의 분류·탐지는 필수 백그라운드 처리로 둔다. 일반 기한은 요청군의 CPU 명목 직렬 작업량×0.75 또는1.10이며120초까지 남은 시간 이내다. CPU 기준은 작업량과 시간 예산을 설명하는 공개 참조이고 정책 입력에는 도착한 요청의 선언 기한만 들어간다. 미래 큐 실행으로 운영 기한을 계산하는 구조가 아니다.

이 기한은 새 합성 백그라운드 시나리오의 계약이다. 원 프로젝트의 strict 기준을 바꿨거나 PASS했다고 표현하지 않는다. 원1.5/6초 기준 관련 `legacy_*` 수치도 보존한다. 일반 기한을 모두 짧은 대화형 응답시간으로 정해90% 이상 실패시키는 조건과, 여러 이미지 처리의 시간 예산을 구분한다. 미완료와 늦은 응답은 전체 도착 분모에 포함한다.

주 지표는 **같은 작업을 마지막 실제 AVAILABLE까지 모두 완료하는 데 든 J**와 AP35~180초 평균이다. 작업 종료 후 비용을 숨기지 않도록 J0~120·J0~180·최고 AP·끝 시각·완료량·긴급/일반 기한 실패도 함께 보고한다. 완료까지 J가 줄었다는 사실을 고정180초의 휴대폰 총소비가 같은 비율로 줄었다는 뜻으로 쓰지 않는다. 작업을 덜 수행한 결과는 같은 작업량 효율 개선에 포함하지 않는다.

## 비교와 학습

FIFO_READY·GREEDY_READY_V17·RR_READY의 원 선택 키와 물리 지원은 유지한다. 최대 큐 확장과 구현 캐시가64개 이내에서 기존 입력/행동/마스크 및 선택과 정확히 같은지 순수 fixture로 검사한다. RR_READY는 비선점 자원순환이다. ATC_PAIR_RULE·명목 상대비용만 사용하는 RELATIVE_COST_RULE·기존 고정 PPO38을 추가한다. 새 PPO가 비용 규칙과 같으면 신경망의 추가 효과는 미확인이라고 쓴다.

기기별 새 시드4003/4011로 각각32경험,8경험씩 native PPO를 업데이트한다.16/32경험 체크포인트를 전체4부하×M0/M1 DEV로 비교한다. DEV 최저점수 모델과 DEV의 조건부 공동 개선 점수 상위2부하를 동결한 후 새로운 도착/환경3반복의 FINAL을 평가한다. 발견과 확인 자료를 분리하고 FINAL로 재선정하지 않는다. 전체 DEV와 모든 FINAL 시드·손해를 보존한다.

G2 학습 비용은 `4×긴급실패율+2×일반실패율+50×미완료율+완료까지J/20J+0.25×증분J180/20J+(평균AP−32℃)/0.5℃+0.5×(최고AP−32℃)/0.5℃`이다. 최고온도를38℃ 초과에만 벌점 주는 G1 식으로는 그 이하의 온도 상충을 학습하지 못해 연속 비용으로 바꿨다. 공학적 정규화와 대리비용이며 실제 금전 손실/하드웨어 안전 한계가 아니다. 고정 구간 지표와 서비스 손해가 별도 채택 판정을 결정한다. 미완료 DEV는 큰 비용으로 부적격 처리한다.

## 근거와 계산 예산

M0는 기존 실측 보정 개발 근사, M1은 기존 전력/수동RC 결합 근사다. 네 프로필을 byte SHA 그대로 복사했다. 결합·전력 분해의 독립 확인과 높은 요청량의 실기기 재현은 미완료다. 특히 큰 요청 묶음은 실측 단일 추론을 반복하는 부하 외삽이며 오차가 그대로 유지된다고 보장하지 않는다.

상한은 신규600환경·새 학습128경험·자체 simulation worker1·BLAS1·2시간·디스크 여유12GiB다. 다른37-V2 worker를 수정하거나 중단하지 않고 공통 소스/프로필도 바꾸지 않는다. 새 fit/APK/기기/GitHub push/외부 메시지0이다. 실제 소비는 이 작업의 receipts/PROGRESS/COMPLETE가 권위이며 예전 프로젝트 누계를0으로 바꾸지 않는다.

실제 PC 처리율을 관측한 뒤 계산 예산 보충을 기록했다. 원2시간 경계에 도달하면 완료한 환경과 체크포인트를 보존해 누적3시간 이내에서 한 번만 이어갈 수 있다. 환경600·디스크12GiB·worker1 상한은 그대로다. 입력/보상/선정/물리계수의 변경은 없고 FINAL 결과에 따른 확장이 아니다. COMPUTE_BUDGET_SUPPLEMENT와 시간 경계의 원 실패를 보존한다.

수치 결과는 `outputs/COST-AWARE-RESIDUAL-PPO-40/RESULTS.md`에 기록한다.10%의 완료구간 J 감소와0.5℃의 평균 AP 감소는 탐색 목표다. 모든 세 비교군/두 모형/새 반복에서 충족하지 않으면 달성 범위를 조건부로 보고한다. 높은 감소율을 얻기 위해 특정 정책에 물리 보너스를 주거나 원 자료/실패/불리한 반복을 삭제하지 않는다.

추가 개발 경로로 실시간 영상의 오래된 미시작 프레임을 버리는 부하 제어도 검토할 수 있다. Android CameraX의 [KEEP_ONLY_LATEST](https://developer.android.com/media/camera/camerax/analyze)는 실제 모바일 처리에서 최신 프레임을 유지하는 근거다. 그러나 이는 필수 요청을 모두 처리하는 본 실험과 다른 서비스 의미다. 이번40에는 작업 폐기/선점을 넣지 않았고 대기는 진행 중 CPU 작업을 보존하는 GPU 배정 조절이다. Android [Thermal API](https://developer.android.com/games/optimize/adpf/thermal)도 고온 시 작업량 조절을 설명하지만 이번 대기 시간/관측 AP 기준의 실측 검증을 뜻하지 않는다.
