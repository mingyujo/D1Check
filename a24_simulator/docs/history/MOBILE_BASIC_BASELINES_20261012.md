# RR·Greedy 포함 최종 모바일 기본군 비교

2026-10-12. 사용자의 추가 요청에 따라 **Greedy를 주 모바일 기본군, RR을 단순 보조군**으로 추가했다. 기존 FIFO·EFT·보완 FIFO_READY＋EFT·EDD/ATC·이전 PPO·현재 ATC＋PPO를 모두 같은 입력에 짝지어 비교했다. 논문을 그대로 재현한 실험이 아니라 D1Check 실행 계약에 맞춘 PC 변형이다.

## 정확한 정책 정의

| 정책 | 요청 순서 | 자원 배정 | 바쁠 때 |
|---|---|---|---|
| 자원 RR_READY | 현재 실행 가능한 가장 오래된 요청 | CPU부터 시작하는 전역CPU/GPU cursor의 현재 지원·legal 경로 순환 | 미지원/busy/금지 병행 경로는 건너뜀; 실제 dispatch에서만 cursor 전진 |
| GREEDY_RESOURCE_FIFO | 각 선호 자원 안에서 FIFO; 실행 가능한 자원별 선두 중 도착순 | 측정 중앙값으로 미리 고정한 선호 경로 | 선호 자원 AVAILABLE까지 기다림; 다른 자원 큐는 진행 가능 |
| FIFO_READY_EFT | 현재 legal 경로가 있는 가장 오래된 요청 | 현재 legal 경로의 최소 점유시간 | 즉시 진전이 없을 때만 자원 대기 |
| 기존 FIFO_EFT | 전역 도착순 선두 | 현재 owner의 AVAILABLE 추정＋단일요청 점유시간으로 EFT 최소 | busy 경로가 이기면 기다림 |

RR은 실행 중 작업을 자르거나 옮기는 시분할 RR이 아니다. D는CPU만 지원하므로 cursor가 D dispatch마다GPU로 이동할 수 있고 CPU/GPU50:50 또는 분류50:50을 보장하지 않는다. 실제 주64조건 배정은 RR 분류CPU48/GPU1680·탐지CPU1728이다. Greedy는 분류/탐지CPU각1728이며 GPU0이다. 지원 외GPU·3건병행·조기AVAILABLE·선점·냉각대기 추가0이다.

Greedy의 선호는 ABBA4 실측5phase **점유시간 중앙값**으로 고정했다: 분류CPU170.043ms(n4), 분류GPU273.996ms(n188), 탐지CPU625.665ms(n192). 따라서 두 모델 모두CPU가 선호 경로다. 실행 후 EMA로 선호를 바꾸거나 결과를 보고GPU로 고쳐 균형을 맞추지 않았다. 분류CPU4표본의 약한 근거는 그대로 한계다. 빠른 선호 경로를 고르는 것이 에너지 최적 배정을 뜻하지 않는다.

## 논문 근거와 변형 범위

COSREL §4.1은 Android10의Pixel2XL에서CPU/GPU RR 배정을 기본군으로 사용했다. 이 단순 자원 배정 원리를 가져오되, 우리는 현재ready 요청/지원 경로만 고르고 최대2건·실제AVAILABLE 계약을 적용한다. 논문의200ms epoch·원모델·학습법·정확RR 구현을 재현하지 않았다. [COSREL 원문](https://par.nsf.gov/servlets/purl/10303786)

Niagara §4.1은 모델의 affinity processor가 idle해지면 배정하는 Greedy를 비교했다. Android10의Snapdragon865/855/750G 엣지SoC/개발보드 평가이므로 휴대폰 실험으로 부르지 않는다. 우리는 선호를 위ABBA 중앙값으로 정의하고 자원별FIFO를 명시했다. 원논문의 서비스DAG·DSP·batch/병행 설정을 추가하지 않았다. [Niagara 원문](https://xumengwei.github.io/files/ICSOC23-Niagara.pdf)

정확한 연구 표현은 **모바일 CPU/GPU 추론의 기본 자원 배정 휴리스틱과 ATC＋PPO 비교**다. RR/Greedy 자체는 여러 분야에서 쓰이므로 산업공학 분야와 모바일 분야 전체의 우위 비교로 해석하지 않는다.

## 비용·응답의 상충과 채택

ATC/CP0는 보완FIFO_READY_EFT보다 P95 평균14.856ms 빠르지만 J는0.161922J 많다. Greedy보다 P95 평균82.389ms 빠르고 J는0.029359J 낮지만 AP 평균은약0.001719°C 높다. 이는 작은 모형 차이이며 실제 발열효과의 통계적 입증이 아니다. 모든조건의 P95/J/AP 비악화를 요구한 원strict는11군 모두FAIL, 새 채택0이다. paired_win_tie_loss.csv에 모든 조건의 손해를 남겼다.

기존 부하8조건에서도 같은 원자료/원기한으로 보완 규칙을 진단했다. FIFO/EFT의 U실패4/5→FIFO_READY_EFT0, 미완료/일반실패0이며 모든과거혼잡 해결을 뜻하지 않는다. **같은 진단에서 RR은 긴급실패0, Greedy는 긴급408건 중185건이 늦었다.** 모든군864건을전부완료했지만, 두모델을CPU에고정해대기하는Greedy는혼잡응답을보장하지못했다. 모델단독최단경로와전체큐의빠른응답은다르다. 낮은공통부하의실패0을혼잡성능으로일반화하지않는다. [전체 진단표](OLD_LOAD_DIAGNOSTIC.md)에 실패를 포함한다. batch n2/n3의 CPU용량 부족과 원873/05 FAIL은 유지한다.

## 실행·감사와 롤링

07은128신규 환경을4프로세스(각32)로 실행했다. 기존06의576행은 재실행하지 않고 source/input/model/reference SHA를 확인해704행으로 합쳤다. 이후 보충등록한 사후진단16환경을 더해 **누적144환경/학습0/실패0**, 각36/40cap·합cap160이다. 원128/704matrix를 수정하지 않았다. 06은원576＋진단8=584/600, 05는2404환경/768학습이다. 이번 세 과제 합계는3132환경/768학습이고 학습은 환경 수에 포함한다. 다른 프로젝트 실행 이력을 초기화하거나 합산하지 않는다. 물리적합·APK·기기·S26·NPU 실행은 세 과제 모두0이다.

17개 순수 검사(05의8＋06의5＋07의4)와 실제학습/재개/동결·전원자료SHA/지원/단계/응답/AVAILABLE/중복dispatch를 검산했다. RR/Greedy는 실제event의 공개prefix만 재구성해 모든 dispatch의 cursor/지원/자원별FIFO를 독립 검산했다. 전체큐 미래rollout/place/J/AP예측이 dispatch에 들어오면 runtime trap으로 실패하게 유지했다. 비차단후속사항:07의사후진단helper는등록된old05 inputSHA를실행때재비교하지않는다. 실제inputSHA는독립검산으로일치해이번결과는유효하다. 향후재개guard를다음등록에서보강하며완료source를소급수정하지않는다.

**롤링은 실제로 들어 있다.** 요청 도착·실제AVAILABLE·자원타이머마다 미시작 요청의 ATC 후보·행동·물리mask·동결PPO 선택을 다시 계산한다. 현재소유자가 응답했다고 자원을 재사용하지 않고 실행 중 작업은 유지한다. 같은시각 사건순서·revision중복방지·CG_DC second-commit guard가 있다. 미래구간을 별도 계획하는 rolling horizon은 없다.

## 권고와 남은 작업

주 모바일 기준은 정적 선호Greedy, 보조는RR·FIFO_READY_EFT, 단순참조는FIFO_FIXED와기존FIFO_EFT로 유지한다. EDD/ATC와 old/future/direct PPO는 효과를 분리하는 연구 대조다. 제안 구조는 ATC 후보＋물리mask＋PPO＋사건별 재판단을 유지하되, 현재선정CP0는ATC 규칙과같고 학습이득 미입증이다.

다음 RL 과제는 별도새개발등록에서만 prior강도·학습길이·행동override와서비스guard를 함께 검토해야 한다. 지금 확인자료로 승리할 때까지 튜닝하지 않는다. 실제 모바일 채택에는 현재모형/4CPU표본·판단비용·기기별성능 확인이 남아 있다. 통상 설계 선택은 이번에 확정했으며 추가로 꼭 필요한 사용자 결정은 없다.

등록/입력/원strict·전체704행/조건별승동패·자원배정·실행원장·source·raw는 이 폴더에 있다. 기준HEAD12d64923의 미커밋작업이며 기존WIP·기본정책·experiment_ready=false를 보존했다. PC 공유호스트 시간은 휴대폰 판단시간이나소비J가 아니다.
