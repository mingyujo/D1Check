## 2. 반영 범위 (조민규 질문 2)

- **CPU 1 스레드 EfficientNet-Lite0 분류 · EfficientDet-Lite0 탐지**: 반영 — 단, **기계적 모형이 아니라 R3 실측 처리시간 분포** (request-runner v2 `591cae72…`, `CpuOptions(numThreads = 1)`, 모델 `6c7ab0a6…` · `40338edf…`). CPU 열은 CPU4 (Interpreter · 4 스레드 · MobileNet) 전력 프로파일 × g_CPU 로 근사 → "CPU 전력" 으로 읽지 않는다.
- **분류 GPU + 탐지 CPU 병행 (B2)**: 반영 — R3 B2 세션의 단계 분포 (간섭 포함) + 두 자원 열 합산. 분류 NPU + 탐지 CPU 도 같다. **R4 (C) 쌍 부호 8/8 · Δ긴급 P95 오차 ≤ 15 ms 6/8 · Δ최고 AP 오차 ≤ 1 ℃ 7/8**.
- 반영 안 됨: 탐지 GPU · NPU (S26 요청 자료 없음 → 거부, 0 으로 채우지 않음) · CPU 조임 · DVFS · 3자원 동시 실측 (R5 ~ R8 은 외삽) · 저장 장치 간섭 · 실내 온도.

## 5. 쓸 수 있는 곳 · 없는 곳

- **쓸 수 있음 (탐색용 꼬리표)**: 짧은 (~ 40 s 부하) 혼합 요청에서 줄 배정 · 대기 · 응답 시각 (긴급 P95 ± 25 ms) · 직렬 ↔ 병행 서비스 차이의 방향 · 열 차이의 **부호**.
- **쓸 수 없음**: 열의 크기 (AP · SKIN 절대값) · 지속 부하 (> 1 ~ 2 분) 의 열과 CPU 처리시간 · 3자원 동시 (외삽) · 에너지 · 100 ms 간격 부하의 실측 범위 밖 결과.
- 규칙 사다리 (`out/ladder.json`) 의 열 비교는 전부 열 "미재현" 모형 위 계산이라 "모형 오차 안 — 우열 미판정" 또는 선별 문턱 아래. 서비스 비교 (긴급 P95) 는 "탐색용".
- 사다리 b200 (3,000요청 · 200 ms 지속) 의 "가드 통과 (전 규칙 3,000 / 3,000)" 는 **실측 R4 (S) 와 반대** (같은 부하에서 CPU 직렬 · GPU 병행은 기한 미충족 있음) → 지속 부하 가드는 이 모형으로 말하지 않는다.

## 7. 연결 (사건 기반 스케줄러)

- 라이브러리: `adapter.ParallelDevice` — `advance(t)` · `state()` (SKIN · AP · GPU/NPU ratio · u · 첫 조임 SKIN 문턱 · 줄 점유 끝) · `estimate(task, resource)` (중앙 단계 × 현재 ratio) · `dispatch(t, id, task, priority, resource, durations=None)` → 단계 시각 6개 · 바쁜 줄에 다시 넣으면 `LaneBusy` · 지원 안 하는 (작업, 자원) 은 `ValueError`. `durations=` 로 **스케줄러 쪽 처리시간을 그대로 넣고 열 · 조임만** 이 모형에서 받을 수 있다.
- 일괄: `adapter run` (규칙 R1 ~ R8) → 요청마다 사건 1줄 JSONL + 마지막 줄 경로 (SKIN · AP 0.5 s).
- 단위 = 초 · ℃ · W · J. 시각 원점 = 세션 원점 (요청 `sched` 와 같은 축).
