## 2. 정책 (A24 `ArrivalPolicyStudy.choose` 이식)

- 공통: 비선점 · 큐에 들어온 요청만 고른다 · 순서 = urgent 먼저 → ordinal → id · pump = 큐 진입 · `lane_available` 때마다 choose 가 null 일 때까지 dispatch.
- **CPU** (`CPU_URGENT_ONLINE_V1`): CPU · GPU lane 이 둘 다 비었을 때만 고른다 → 사실상 CPU lane 하나 직렬 · 모든 요청 `*_CPU`. 두 블록에서 같은 정의 (블록 N 의 NPU lane 은 쓰지 않는다).
- **PAR** (`B2_PARALLEL_ONLINE_V1`, `CG_DC`, 블록 A): 분류 → GPU lane · 탐지 → CPU lane · 두 lane 동시 · 순서상 lane 이 빈 첫 요청.
- **PAR-NPU** (`S26_NPU_PARALLEL_V1`, 블록 N): 분류 → NPU lane (AOT · `classification_NPU`) · 탐지 → CPU lane · 두 lane 동시 · 나머지 (순서 · pump · 비선점) 는 PAR 과 같다.
- 이식 검증 (R1): A24 `ArrivalPolicyStudyTest` 사례를 그대로 통과 + 같은 입력에 같은 선택 순서 · PAR-NPU 는 PAR 사례에서 GPU lane 을 NPU lane 으로만 바꾼 사례가 같은 순서로 통과.

1. 192 요청 전부 성공 (`terminal_status`) · 결과 파일 품질 확인 통과 — 그 세션 **같은 runtime** 의 warmup 2회 각각과 **6 의 허용 범위로** 같음 (분류 top-5 라벨 · index 같고 |Δscore| ≤ 0.001 · 탐지는 6 의 탐지 비교 통과). `classification_NPU` 도 같은 세션 NPU warmup 과 이 범위로 같아야 한다 (자기 출력 일관성 — CPU 기준과의 비교는 §4-N)
2. 시각 순서: scheduled ≤ actual ≤ queue_entry ≤ dispatch ≤ execution_start ≤ output_ready ≤ persist_complete ≤ worker_release ≤ lane_available
3. 모든 `dispatch` · `lane_available` 이 공통창 [35 s, 120 s) 안
4. 정책별 자원 배정이 §2 와 같음 · 그 블록의 상주 runtime 이 모두 생성 · warmup 됨 (§3-1 의 `detection_GPU` 예외만)
5. CPU 세션 겹침 0 · PAR · PAR-NPU 세션 겹침 > 0 (겹침 = 그 정책의 두 lane 이 동시에 바쁜 시간)
6. warmup 품질 (GPU vs S26 CPU 기준 — §3-1 의 1회차 기준 · 2회 각각): 분류 = top-5 라벨 · index 가 같고 |Δscore| ≤ 0.001 · 탐지 = 개수 · 라벨이 같고 |Δscore| ≤ 1e-3 · box 차 ≤ 2 px · CPU warmup 2회차도 1회차와 이 범위로 같음. **이 판정은 그 세션 정책이 쓰는 runtime 에만** 적용한다 — 상주만 하고 쓰지 않는 runtime (예: CPU · PAR 의 `detection_GPU`) 은 결과를 기록하고 불일치면 표시만 한다. **NPU 를 CPU 기준과 비교할 때는 이 허용 범위를 쓰지 않는다** (조민규 62행 — CPU→NPU 에 같은 함수를 부르지 않는다) → §4-N. NPU 자기 출력 일관성은 규칙 1. (S26 CPU 와 A24 PC 참조의 일치는 세션 규칙이 아니라 R2 전 확인 — §11-1)
7. 그 세션 정책이 쓰는 가속 runtime 마다 위임 증거 (러너 PID 줄만 · 구간은 앱이 logcat 에 남기는 runtime 생성 / warmup 시작 · 끝 표시로 자른다):
   - **GPU** = S26 GPU 규칙 v1 (`tools/compiled_model_evidence.py` `gpu-compiled-model-evidence-v1` 의 정규식) — 그 GPU runtime 의 생성 ~ warmup 구간에서 `LITERT_CL` 전체 교체 줄 (x == y > 0) · GPU 환경 생성 줄 · **다른 delegate 교체 줄 0** · 실패 줄 (`FAILURE_RE` · `GPU_FAILURE_RE`) 0
   - **NPU** = 팀 규칙 `npu-dispatch-evidence-v1` 의 조건 (`tools/d1_logger_v4.py` 의 `NPU_DISPATCH_REPLACE_RE` · `NPU_ENN_LOADED_RE` · `NPU_DISPATCH_FAILURE_RE` · AOT 표) — ① `classification_NPU` 생성 ~ warmup 구간에 `DispatchDelegate` 교체 줄 · x == y == 1 (AOT 표의 dispatch 1 · non 0 과 일치) ② ENN 로드 줄 (`SetGenAiPerfConfigFromSoc`) 이 러너 PID 에서 세션 시작 ~ NPU warmup 끝 사이 ≥ 1 (**필요조건일 뿐 단독 증거가 아니다** — CPU 런에도 찍힌다) ③ dispatch 실패 줄 0 — NPU 구간과 공통창 ~ drain 끝
   - 함수 (`evaluate_gpu` · `evaluate_npu`) 는 그대로 부르지 않는다 (CPU runtime 의 XNNPACK 교체 줄이 같은 프로세스에 섞이고, 함수가 러너 PID 를 `D1GPU` / `D1NPU` 태그로 찾는다)
8. plugged 0 · 시작 thermal status ≤ 1
9. 감시 이벤트 0 · 앱 안 멈춤 없음

무효 → 같은 자리 1회 다시 (600 s 쉼 + 게이트) · 또 무효 → 그 블록 멈춤 (보고). 순서는 바꾸지 않는다.
- **시도 번호**: 다시 하는 세션은 같은 sid · request_id 를 쓰고 `attempt` (1 · 2) 를 둔다 · 기기 폴더 `<session_id>/a<attempt>/` · 결과 폴더 · inventory 키 = session_id + attempt · 그 폴더가 이미 있으면 시작하지 않는다 · 판정에는 그 자리의 유효한 시도 하나만 (두 번째가 유효하면 그것).
- **멈춘 블록**: 원인 (연결 · 설치본 · 기기) 을 고친 뒤 이어 할지는 영훈이 정한다 — 멈춘 블록의 KPI (readout) 를 보기 전에 원장에 적고, 이어 하면 남은 index 부터 같은 순서. 이어 하지 않은 세션은 inventory 에 `not_attempted`. 한 블록이 멈춰도 다른 블록은 등록대로 돈다.

### 4-N. NPU 출력 계약 `npu-mixreq-contract-v1` (유효성 규칙 아님 · Q3 판정 조건 · 결과 전 고정)

조민규 규칙 (63행): NPU 변환으로 기준이 실패하면 실패를 보존하고, 결과를 본 뒤 허용치를 늘리지 않으며, 다른 정밀도 계약은 따로 사전 고정한다. 이 계약이 그것이다. **A24 품질 계약 (`d1_probe_compare` — top-5 순서 · |Δscore| ≤ 0.001) 과 별개인 NPU 전용 계약이며, 그것을 대신하거나 완화한 것이 아니다** (조민규 10/8 02:5x 요청).

- 대상: 블록 N 각 세션 warmup 의 `classification_NPU` 출력 (Softmax 1000) vs **같은 세션** `classification_CPU` warmup 출력.
- **통과 = (a) top-1 index 같음 그리고 (b) cosine ≥ 0.99** — 팀 NPU 품질 게이트 `npu-quality-gate-v1` 기준 (argmax 같음 · cosine_min ≥ 0.99) 을 이 이미지에 그대로 적용.
- 지표만 (판정 없음): top-5 순서 일치 · top-5 집합 겹침 (/5) · 최대 · 평균 |Δ| · FP32 허용식 (`|Δ| ≤ 1e-4 + 1e-3·|ref|`) 위반 수 · CPU 와 비트 동일 여부 · NPU top-1 점수.
- 비교: CPU 기준 = 같은 세션 `classification_CPU` warmup 1회차 · NPU warmup 2회 **각각** (하나라도 실패하면 그 세션 계약 실패 · 출력이 없어 계산할 수 없어도 실패).
- 계약 실패: **세션 무효가 아니다** (시간 · 열 자료는 보존) · 기준을 늘리지 않는다 · 블록 N 의 유효 PAR-NPU 세션 (쌍이 안 된 것 포함) 중 하나라도 실패면 **Q3 판정 전부 (서비스 · 응답 · 열) 를 하지 않는다** → "NPU 출력 계약 실패 — 같은 일로 보지 않음 · 기술만" (§6).
- 블록 N 의 CPU 세션: 계산 · 기록만 (그 세션 정책이 NPU 를 쓰지 않는다).
- R1 폰 스모크 (또는 R2 첫 세션 전 스모크) 에서 처음 보게 된다. 결과가 어떻든 블록 N 8세션은 이 설계 그대로 돈다 (줄이거나 미루는 사유는 §11-3 뿐).

## 5. KPI (A24 정의 그대로)

- 응답_i = C_i − scheduled_arrival_i (C = urgent `output_ready` · normal `persist_complete`)
- P95 = nearest-rank `sorted[ceil(0.95 · n) − 1]` — urgent · normal · 전체 · 분모 = 그 등급의 예정 수 (urgent 96 · normal 96 · 전체 192 — A24 `d1_online_policy_model.py` 206 ~ 208행) · 미완료는 +∞ (유효 세션에는 없다 — 조민규 경계표의 "완료 응답 · 완료 0 이면 null" 과 유효 세션에서는 같은 값)
- 기한 충족 수 (urgent ≤ 1.5 s · normal ≤ 6 s) · 완료 수 · 마지막 `lane_available`
- 겹침 초 (그 정책의 두 lane 이 동시에 바쁜 시간 — PAR = `classification_GPU`+`detection_CPU` · PAR-NPU = `classification_NPU`+`detection_CPU`) · 도착 지연 (actual − scheduled) 최대 · P95
- 열 (호스트 HAL): 공통창 시작 SKIN · AP · 공통창 최고 SKIN · 최고 AP · 공통창 끝 SKIN
- 에너지 (**기술만**): 공통창 0 ~ 120 s 기기 에너지 (1 Hz 이상 표본 사다리꼴 · S26 µA 해석) 와 잔량계 눈금 변화 — "S26 J 적격성 미확보 · 기술만"
- 보조 (**기술만 · 판정 없음**): 큐 보조 응답 = C_i − queue_entry_i 의 P95 (조민규 10/8 경계표 `queue 보조 response = C_i − enqueue_ns` — A24 `requests.json` 필드 이름은 `queue_entry_ns`) · lane 서비스 시간 (execution_start → output_ready, backend 별 중앙값 · P95 — 응답 KPI 를 대신하지 않는다)
- A24 대조 계산 (우리 구현과 둘 다로 하고, 다르면 멈추고 보고): (a) 응답 · P95 · 기한 = A24 `tools/d1_online_policy_model.py` 199 ~ 208행의 식을 출처 커밋 · SHA 와 함께 그대로 옮긴 함수 (그 모듈 전체는 A24 전용 모듈 · 산출물 구조에 묶여 있어 그대로 돌릴 수 없다) (b) 에너지 = A24 `tools/d1_energy_thermal.py` 무수정 사본의 `integrate(samples, origin, origin + 120 s, scale_ua=1, max_gap_s=2.5)` (`energy_at` 은 mA (`scale_ua=1000`) 고정이라 쓰지 않는다). 두 블록 모두.

## 6. 판정 — Q1 (블록 A) · Q3 (블록 N)

같은 규칙을 블록마다 따로 쓴다. 병행 정책 X = 블록 A 의 PAR · 블록 N 의 PAR-NPU.

- 쌍 = 같은 블록 · 같은 쌍 번호의 CPU · X (두 세션 모두 유효한 쌍만) · Δ = X − CPU · n = 그 블록의 유효한 쌍 수. **블록을 넘는 쌍은 만들지 않는다.**
- **n < 3 → "쌍 부족 — 기술만"** (아래 판정 안 함).
- **서비스**: 그 블록의 모든 유효 세션이 192/192 기한 충족 → "두 정책 모두 기한 충족" · 아니면 정책별 미충족 수 (판정 이름 "기한 미충족 있음").
- **긴급 응답 (주)**: n 쌍 모두 Δ긴급 P95 < 0 이고 각 |Δ| ≥ 그 쌍 CPU 값의 5 % → **"병행이 긴급 응답을 줄였다 (n쌍 같은 방향)"** · 모두 < 0 이나 일부 |Δ| < 5 % → "같은 방향 · 일부 작음" · 모두 > 0 이고 각 ≥ 5 % → "병행이 긴급 응답을 늘렸다" · 그 밖 → "엇갈림". (5 % = screening 기준 — 오차 한도 · 유의성 아님.)
- **일반 응답 (보조)**: Δ일반 P95 에 같은 규칙.
- **열 (최고 SKIN 주 · 최고 AP 보조)**: n 쌍 모두 |Δ| < 1.0 ℃ → **"열 차이 기준 안 (1.0 ℃)"** · n 쌍 모두 같은 부호이고 각 |Δ| ≥ 1.0 ℃ → "병행이 더 뜨거웠다 / 덜 뜨거웠다 (n쌍)" · 그 밖 → "엇갈림". 쌍 안 시작 SKIN 차를 늘 같이 적는다.
- **에너지**: 판정 없음 (기술만).
- **Q3 순서**: ① 블록 N 의 유효 PAR-NPU 세션 (쌍이 안 된 것 포함) 중 §4-N 계약 실패 (계산 불가 포함) 가 하나라도 있으면 → **"NPU 출력 계약 실패 — 기술만"** (서비스 · 응답 · 열 판정을 모두 하지 않고 쌍별 Δ · 기한 충족 수만 적는다) ② 아니면 n < 3 → "쌍 부족 — 기술만" ③ 아니면 위 규칙 (판정 이름의 "병행" 을 "NPU 병행" 으로).
- **보조 (기술만 · 판정 없음)**: ① PAR vs PAR-NPU — 블록별 정책 범위와 쌍 Δ (PAR − CPU)_A · (PAR-NPU − CPU)_N 를 나란히 · ② 블록 간 CPU 범위 (CPU_A vs CPU_N — 상주 runtime · 시각 · 열 이력 · SOC 차이의 크기). 둘 다 "다른 블록 · 다른 분류 artifact · 정밀도 — 순위 아님".

## 7. 나란히 — Q2 (관측 · 블록 A 만)

- 한 표: 기한 충족 · 긴급 P95 (정책별 범위) · 쌍 Δ긴급 P95 · 일반 P95 · 겹침 초 · 마지막 `lane_available` · 열 (A24 AP · S26 SKIN · AP — 센서 이름 그대로) · J (A24 mA 해석 · S26 µA 해석 — 기술만).
- 블록 N 은 넣지 않는다 (A24 에 없는 정책 · 상주 runtime 이 다르다). 블록 N 은 S26 절의 자기 표로.
- 본문 이름 (조민규 확인 뒤): **"동일 요청 정의의 기기 · 엔진별 이식 평가"** — 기기별 계수 · 표본을 합치지 않는다 · J 비교는 적격성 확인 뒤.
- 문장 틀: 「같은 요청 정의 (192 · 400 ms · 같은 정책 정의 · 같은 KPI 정의) 를 기기 · 엔진별로 이식해 평가했다. A24 는 …, S26 은 … 였다. 두 기기는 엔진 (Interpreter 1.4.2 / CompiledModel 2.2.0) · 센서 · 하드웨어가 달라 우열이나 기기 효과로 읽지 않는다.」

## 8. 반대 해석 (결과 전 목록)

1. 엔진 차이 (Interpreter 1.4.2 vs CompiledModel 2.2.0)

5. 표본기 · 호스트 폴링 부하
6. 밝기 (A24 81 vs S26 0)
7. S26 = 일상 사용 폰 (백그라운드 경합)
8. 센서 이름 · 위치 다름 (A24 AP vs S26 SKIN · AP)
9. 시작 열 상태 · 앞 세션 이력 (거울 순서로 일부만 상쇄)

13. 안전 · 검증 규칙 차이: A24 앱은 BAT > 35.0 ℃ 에서 멈춘다 (S26 = 42.0) · A24 검증기는 호스트 표본의 thermal status 가 전부 0 이어야 한다 (S26 = 시작 ≤ 1 · 비상 3) · A24 는 요청 결과를 고정 기준과 비교한다 (S26 = 같은 세션 warmup 과 비교) · A24 는 앱이 화면을 켜 둔다 (S26 = 호스트 `screen_off_timeout`)
14. 분류 NPU = AOT 변환본 `311e4aac…` (원본 `6c7ab0a6…` 과 다른 artifact) · 실행 정밀도 미확인 (S26 NPU 출력이 FP16 표현값이던 이력 — MobileNet 0925 [D] · EffNet AOT 는 합성 입력에서만 `npu-quality-gate-v1` PASS, cosine_min 0.99985 [D 0928]) → PAR-NPU 의 분류는 CPU · GPU 와 같은 파일 · 정밀도가 아니다

16. 블록 N 은 상주 runtime 5 (NPU 추가) · 블록 A 뒤 다른 시각 · 열 이력 · SOC → 블록 간 비교는 기술만
17. NPU 증거는 "Samsung ENN NPU 경로로 실행" 까지 (앱에서 NPU 코어 직접 증거는 구조상 안 잡힌다 [D 0925])
