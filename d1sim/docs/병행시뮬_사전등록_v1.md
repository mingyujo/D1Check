# S26 자원 병행 시뮬레이터 v3 — 사전 등록 v1 (병행 열 · 서비스 부품 + 확인 기준 2단계 + 규칙 사다리) (2026-10-11 낮 · Cowork 초안 · 코드 · 오차 계산 0)

> **목적**: S26 시뮬레이터를 "조건마다 자원 하나 고정" 에서 **CPU · GPU · NPU 를 동시에 쓰는 자원 병행 시뮬레이터**로 넓힌다. 4쪽 (순서 · 자원 · 시점) 세 결정을 S26 안에서 한 표로 비교하고, 조민규 A24 규칙 (FIFO · 긴급 우선 · 고정 병행 · EFT · EDD) 과 같은 이름의 사다리를 S26 에 세운다.
> **결정 (영훈 10/11)**: "자원 고정이 아닌 자원 병행 시뮬레이터가 필요하다" · "판정 기준을 조금 완화했다가 조여도 된다" → **느슨 (L) · 엄격 (S) 두 단계를 결과 전에 함께 고정**하고 둘 다 보고한다 (§4-0).
> **모형 열 블록은 다시 맞추지 않는다** (v2.2 `e52a922` 그대로). 새로 맞추는 값은 §1 의 g_CPU (와 민감도 κ) 뿐 · 개발 자료 (R3) 에서만.
> 실행 = P1l (`프롬프트_P1l_병행시뮬레이터_1011.md`). 이 문서는 P1l 이 **오차 계산 전에** 레포에 바이트 그대로 커밋한다 → 커밋 SHA · 시각을 원장에. 고치면 `_v2`.
> 표기: [P] 실측 · [P-fit] · [P-시뮬] · [D] · [E] · `미확인` · "P1l 이 정함 (결과 전)" = 코드를 읽은 뒤 P1l 이 정하고 오차 계산 전 커밋에 기록하는 세부.

## 0. 이 등록 전에 본 것 · 범위

- **본 것 (밝힌다)**: R3 (`S26-MIXREQ-02`, 16세션) · R4 (C) (`-02C`, 16세션) · R4 (S) (`-03`, 유효 14 / 시도 18) 의 판정 · 숫자 전부 — 긴급 P95 (CPU 105.7 ~ 132.3 · PAR 74.2 ~ 80.4 ms) · 쌍 Δ · 최고 SKIN 차이 기준 안 · R3 블록 A 최고 AP "엇갈림" (Δ −0.9 ~ −1.3 ℃) · R4 (S) 최고 SKIN 14세션 38.1 ℃ 포화 [D `혼합요청_결과_v2.md` · `작업결과_1010_R4_혼합요청v3.md`]. 단독 자원 모형 오차 (P1j · P1k) 도 봤다.
  → 이 시험은 **"기존 자료 · 예측은 처음"** 이다 (P1k 와 같은 지위). 새로 맞히는지가 아니라 같은 자로 얼마나 틀리는지를 잰다.
- **확인 대상 = 2자원 동시** (탐지 CPU + 분류 GPU · 탐지 CPU + 분류 NPU). **3자원 동시 (CPU + GPU + NPU) 는 확인 자료가 없다 → 외삽**으로만 계산 · 표기.
- 하지 않는 것: v2.2 열 블록 · 제어기 재피팅 · 기존 d1sim · 판정기 코드 수정 · 폰 측정 · 에너지 판정 (J 는 기술만) · A24 계수 사용 (규칙 정의만 가져온다).

## 1. 모형 구조 — v2.2 + 부품 두 개

1. **열 합산 (새)**: 열 노드 (SKIN 2노드 · AP 단계 · BAT) 는 하나를 공유하고, 1 s 마다 자원 r ∈ {CPU, GPU, NPU} 의 바쁨 비율 u_r(t) 로 열 입력을 더한다.
   - P_in(t) = P_idle + κ · Σ_r g_r · (P_r(u_r(t)) − P_idle)
   - **주 모형 M-sup**: κ = 1 (단순 중첩). **민감도 M-κ**: κ 를 R3 에서 1개 피팅. 고르지 않고 둘 다 보고 · 판정 이름은 M-sup 만.
   - P_r(u) = v2.2 전력 모형 (자원별 P0 · α · P_idle). AP 단계의 자원별 G_a 를 동시 실행에서 합치는 식 (바쁨 가중 합 등) = **P1l 이 정함 (결과 전)**.
2. **열 입력 배율 g_r**: g_GPU · g_NPU = v2.2 g_m (EffNet 분류) 그대로. **g_CPU** (탐지 EfficientDet + 분류 CPU · request-runner 스레드 설정 — v2.2 CPU 파라미터는 CPU4 프로파일이라 다를 수 있음) = **R3 에서만 1개 피팅** (닫힌 고리 1 s AP 오차² 런 평균 — P1l 이 정함).
3. **조임**: 자원별 v2.2 제어기 그대로 · 공유 SKIN / AP 로 판정. v2.2 에 CPU 제어기가 없으면 CPU 처리시간 = R3 실측 분포 (조임 없음 가정) 로 두고 그 사실을 원장 · 결과 한계에 쓴다.
4. **서비스 (새)**: 이산 사건 · 줄 (lane) 마다 한 번에 한 작업 · **비선점** · 줄 안 순서 = 정책 규칙. 처리시간 = **R3 실측 경험 분포** (정책 · 자원 · 모델별 — 병행 중 간섭이 이미 담긴 값) × v2.2 조임 배율. 예정 도착 = 실험 ID 의 요청열 (짝수 = 분류 urgent · 홀수 = 탐지 normal · 200 ms) · 응답 = C_i − scheduled_arrival (urgent = output_ready · normal = persist — 조민규 경계표). 저장 · 큐 오버헤드 처리 = P1l 이 정함.
5. 시작 상태: 세션마다 **실제 시작 SKIN / AP / BAT** (확인 자료의 세션 기록) — 열 두 점 규칙을 쓰지 않는다 (P1j 기술 열에서 실제 시작이 더 맞았음 — 결과 전 선언).

## 2. 자료 분할 (결과 전 고정)

| 역할 | 자료 | 쓰임 |
|---|---|---|
| 개발 | R3 16세션 (`-02`) | g_CPU · κ (민감도) · 처리시간 경험 분포 |
| 확인 1 | R4 (C) 16세션 (`-02C`) | 서비스 + 열 (짧은 192요청) |
| 확인 2 | R4 (S) 유효 14세션 (`-03`) | 열 주 (600 s 지속 3,000요청) · 서비스 기술 |

- 무효 세션 (R4 (S) CPU 직렬 index 13 · 14 의 4시도) 은 판정 밖 · 기술만. 블록 N (S) 은 2쌍뿐 → 쌍 판정은 블록 A (S) 4쌍 + (C) 8쌍.

## 3. 지표 (세션 · 쌍마다, M-sup · M-κ 각각)

- 서비스: 긴급 P95 오차 (ms) · 쌍 Δ긴급 P95 (병행 − 직렬) 예측 vs 실측 · 일반 P95 (기술) · 기한 내 완료 수 (기술).
- 열: **AP 최고 오차 (℃)** · AP 10 s 경로 MAE (℃) · SKIN 최고 오차 (38 ℃ 이상 포화 표시) · (S) SKIN 38 ℃ 도달 시각 오차 (s) · **쌍 Δ최고 AP (병행 − 직렬)** 부호 · 크기.
- 실측 열 지표 출처 = 각 판 readout 의 세션 JSON (무변경 · SHA 원장). AP 를 주로 쓰는 이유 = R4 (S) SKIN 포화 (결과 전 선언).

## 4. 판정 — 느슨 (L) · 엄격 (S) 두 단계 (결과 전 고정)

0. **"완화했다가 조인다" 규칙**: L · S 두 기준을 지금 함께 고정하고, 오차를 한 번 계산해 **둘 다 적는다**. 결과를 본 뒤 숫자 · 분모 · 자료 분할을 바꾸지 않는다. **다음 새 자료 (새 폰 세션 · 3자원 실측) 부터는 S 기준만 쓴다.**
1. **열 (확인 1 · 확인 2 각각 판정)**
   - L: AP 최고 |오차| ≤ 2.0 ℃ 인 세션 ≥ 75 % **그리고** AP 경로 MAE 중앙 ≤ 1.5 ℃ **그리고** 쌍 Δ최고 AP 부호 일치 ≥ 3/4 (쌍 수 기준, 내림).
   - S: AP 최고 |오차| ≤ 1.0 ℃ 인 세션 ≥ 85 % **그리고** AP 경로 MAE 중앙 ≤ 1.0 ℃ **그리고** 쌍 부호 전부 일치 **그리고** |예측 Δ − 실측 Δ| ≤ 1.0 ℃ 전부.
2. **서비스 (확인 1)**
   - L: 긴급 P95 |오차| ≤ 25 ms 인 세션 ≥ 12/16 **그리고** 쌍 Δ 부호 8/8.
   - S: ≤ 15 ms 인 세션 ≥ 14/16 **그리고** 쌍 Δ 부호 8/8 **그리고** |예측 Δ − 실측 Δ| ≤ 15 ms 인 쌍 ≥ 6/8.
3. **판정 이름 (부품마다 · M-sup)**: S 통과 → **"병행 [열/서비스] 재현 확인 (기존 자료 · 2자원)"** · L 만 통과 → **"병행 [열/서비스] 탐색용 (오차 ○ 붙임)"** · 둘 다 실패 → **"병행 [열/서비스] 미재현"**. 열은 확인 1 · 2 가 다르면 둘 다 적고 낮은 쪽을 정책 사다리 지위로 쓴다.
4. M-κ 는 같은 표에 나란히 (고르지 않음). κ 피팅값이 1 에서 멀면 (± 0.2 밖) "단순 중첩 가정 의심" 을 기술 (판정 아님).

## 5. 규칙 사다리 (판정 뒤 · 판정 결과와 관계없이 실행 — 지위는 §4 판정 이름을 따른다)

| # | 규칙 | 순서 | 자원 | 비고 |
|---|---|---|---|---|
| R1 | CPU 직렬 FIFO | 도착 순 · 비선점 | 전부 CPU | 순서 효과의 기준 |
| R2 | CPU 직렬 긴급 우선 | 대기 중 urgent 먼저 · 비선점 | 전부 CPU | = R3 기준선 |
| R3 | 고정 병행 GPU | 줄마다 도착 순 | 분류 GPU · 탐지 CPU | = R3 PAR · A24 B2 와 같은 뜻 |
| R4 | 고정 병행 NPU | 줄마다 도착 순 | 분류 NPU · 탐지 CPU | = R3 PAR-NPU |
| R5 | 3자원 EFT | 긴급 우선 | 요청마다 예상 완료가 가장 이른 줄 (지금 조임 배율 반영) | **3자원 동시 = 외삽** |
| R6 | EDD + EFT | 기한 빠른 순 | EFT | 조민규 EDD · EFT 정의를 읽고 맞춤 (P1l 이 정함 — 원문 경로 기록) |
| R7 | 열 인지 EFT | 긴급 우선 | EFT, 단 예측 SKIN 이 자원 첫 조임 문턱 + offset 에 닿을 줄은 제외 (기한을 못 지키면 제외 안 함) | offset {0, −0.5} 는 개발 seed 에서만 고름 |

- 조민규 Band (`BAND_HEFT_WHOLE_REQUEST_ADAPT_V1`) 는 정의가 A24 줄 구조에 묶여 있으면 옮기지 않고 그 사실을 적는다 (가능하면 R8 로 추가 — 결과 전).
- **부하**: (a) 192요청 · 400 / 200 / 100 ms · (b) 3,000요청 · 200 ms 지속. 시작 SKIN 30.5 · AP · BAT = v2.2 열 두 점 규칙 (가상 부하라 실제 시작 없음).
- **seed**: 도착 지터 · 처리시간 표본 = 개발 1 ~ 10 (R7 offset 고르기만) · **확인 61 ~ 65** (S26 정책 비교에서 안 쓴 값 — 한 번만).
- **KPI · 가드 · 선별 (팀 규칙 그대로)**: 가드 = 기한 내 완료 (전체 예정 분모 · 실패 · 만료 삭제 금지) · 긴급 P95 (nearest-rank, 전체 분모) / 주 = 최고 AP · 최고 SKIN (℃) / 보조 = SKIN 38 ℃ 이상 시간 (s) · 처리율. 선별 = ℃ 1.0 · s 60 · P95 max(5 %, 2·CV) — **오차 한도 · 유의성 아님**.
- **판독 (규칙쌍마다)**: 가드 둘 다 지킨 규칙끼리만 열 비교 · "버리거나 창 밖으로 민 일은 절감 아님" · 차이가 §4 의 해당 부품 오차 (확인 MAE) 보다 작으면 "모형 오차 안 — 우열 미판정" 으로 적는다.

## 6. 결과 문장 틀

「S26 자원 병행 시뮬레이터 (v2.2 + 열 합산 · 서비스 부품) 는 기존 병행 실측 (R4 확인 16세션 · 지속 14세션) 을 예측했을 때 열 [판정 이름] (AP 최고 오차 ○ ℃ · 경로 MAE ○ ℃) · 서비스 [판정 이름] (긴급 P95 오차 ○ ms) 였다. 이 모형에서 같은 요청열에 규칙 7개를 적용하자 [가드 결과] · [열 결과 — 오차 안이면 우열 미판정]. 3자원 동시 (R5 ~ R7) 는 확인 자료가 없는 외삽이다.」
- 늘 붙일 것: 기존 자료 (결과 공개 뒤 예측) · g_CPU 를 R3 에서 맞춤 · 2자원만 확인 · SKIN 포화 · 1 세션씩 · 실내 온도 `미확인`.
- 쓰지 않는 것: "검증됨" · "통합 시뮬레이터" · 에너지 판정 · A24 와 숫자 합치기 · "3자원 병행이 낫다" (외삽).

## 7. 반대 해석 (먼저 적는다)

1. 처리시간을 R3 실측 분포로 넣었으므로 R4 (C) 서비스가 맞는 것은 같은 계열 재현일 뿐 (모형의 힘 아님) → 서비스 S 통과도 "기존 자료 재현".
2. 열 합산이 맞아도 SoC 공유 전력 한도 · DVFS 가 동시 실행에서 다르게 작동할 수 있다 (R3 블록 A 병행 최고 AP 가 오히려 낮았음) — κ 가 이를 흡수할 수 있다.
3. g_CPU 가 탐지 모델 차 · 스레드 차 · 제어기 오차를 함께 흡수한다 → "CPU 전력" 으로 읽지 않는다.
4. R4 (S) SKIN 포화 → SKIN 쪽 판정은 약하다 (그래서 AP 주).
5. 3자원 동시 · 100 ms 부하는 실측 범위 밖.
6. 규칙 사다리의 열 차이가 모형 오차보다 작으면 A24 와 같은 "우열 미판정" 이 될 수 있다 — 실패가 아니라 결과다.
